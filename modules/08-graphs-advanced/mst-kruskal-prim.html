MST: Kruskal & Prim

Kruskal sorts edges and unions if they do not form a cycle. Prim grows a tree from a seed, always taking the cheapest edge out. Same MST, different shapes.

Medium 26 min read Prerequisites: Graph Representations, Heaps MST Kruskal Prim DSU P1

Why this exists

You are wiring n houses to each other so that every house can reach every other house along the cables you buy, and you want the cheapest possible total bill. Any connecting set of cables that uses more than n-1 of them contains a loop you could drop without disconnecting anyone, so the cheapest connecting set is always a tree: a minimum spanning tree, the cheapest set of n-1 undirected edges that joins the whole graph. The naive "try every subset of n-1 edges" is hopeless: at n = 10⁵ and m = 2×10⁵ you cannot even list the subsets, let alone score them.

Both algorithms on this page rest on one fact, the cut property. A cut is any way of splitting the houses into two non-empty groups; the property says the cheapest cable that has one end in each group is safe to buy — it belongs to some cheapest tree. Kruskal applies that fact to "the groups I have already wired together": sort every cable from cheap to expensive and buy it if its two ends are still in different groups, which a union-find structure answers in almost constant time. Prim applies the same fact to "inside the tree so far versus outside": always buy the cheapest cable that leaves the tree you have already grown.

Pick Kruskal when you already have an edge list and might stop early, or when queries arrive offline as "add edges in weight order". Pick Prim when the graph is dense — a complete graph of n points in the plane has about n² / 2 edges you do not want to materialise — or when you already hold adjacency lists. In a problem statement the tell is "connect everyone at minimum total cost" sitting next to undirected weighted edges. Close cousins that are still this page: a maximum spanning tree (sort descending), the second-best tree (swap one unused edge), and the min-bottleneck path, whose heaviest edge is the heaviest edge on the unique MST path.

The cut property says the cheapest edge across any split of the vertices belongs to some MST, so you never have to look ahead. Kruskal applies the split "components wired so far"; Prim applies the split "already in the tree versus not yet". Same cheapest tree, two different shapes of code.

Recognise this pattern

Say yes when you see

  • Connect n vertices at minimum total cost
  • Offline queries "how many pairs are connected by edges of weight <= x" (Kruskal + DSU sizes)
  • Min bottleneck path (u, v) = max edge on the unique MST path
  • Dense complete graph (n points in the plane) — Prim without building n^2 edges
  • Maximum spanning tree — negate, or sort descending

Not this pattern when

  • Directed graphs → arborescence / Edmonds, not MST
  • Shortest paths → Dijkstra; MST paths are not shortest paths
  • Steiner tree (must include a subset) → NP-hard, different DP
  • You need a spanning tree of minimum diameter → not MST

Constraint tell: n ≤ 10⁵ and m ≤ 2×10⁵ is Kruskal's window: one sort plus almost-constant union-find. A complete graph on n ≤ 2000 vertices is Prim without a heap, n² scans and no materialised edge list. Individual weights usually fit in an int, but the sum of n-1 of them needs a long. If the statement is directed, this page is the wrong tool.

Core idea and the invariant

Kruskal needs an edge list and a union-find structure. Sort the edges by weight, cheapest first. For each edge (u, v, w) in that order, ask the structure whether u and v already share a representative. If they do, the edge would close a loop and you skip it. If they do not, union them, add w to a long total, and increment a counter of taken edges. Stop when the counter hits n-1: you have a tree. If the list ends with fewer than n-1 taken edges, the graph was disconnected and what you built is a minimum spanning forest.

Prim needs adjacency lists and a heap, and it looks like Dijkstra until you read the key. Set dist[src] = 0 and every other dist to a sentinel, then grow a set S of vertices already in the tree. Repeatedly pop the unused vertex of smallest dist, mark it used, add that dist to the total, and for each unused neighbour v write dist[v] = min(dist[v], w(u, v)) — the weight of the edge into the tree, not a path sum. That single difference is the whole algorithm: Dijkstra settles cheapest routes from a source, Prim settles the cheapest cable that leaves the tree.

Walk the four-house sample in words. Edges in sorted order are 0-1 weight 1, 1-2 weight 2, 0-2 weight 2, 2-3 weight 3, 0-3 weight 4. Kruskal buys 0-1, then 1-2, skips 0-2 because 0 and 2 already share a representative, buys 2-3, and stops at three edges of total 6. Prim starting at 0 first buys the cable of weight 1 to house 1, then the cable of weight 2 to house 2, then the cable of weight 3 to house 3, and reports the same 6. The skipped 0-2 is a tie: another tree of weight 6 exists that uses 0-2 in place of 1-2.

Cut property: for any partition of the vertices into S and V \ S, a lightest edge with one end in each side belongs to some MST. Kruskal's S is one union-find component; Prim's S is the set of vertices already popped into the tree.

In plain words, the cheapest cable that leaves the group you have already wired is always safe to buy, so both algorithms only ever add an edge that some cheapest tree would have added, and they stop when the group is everyone (or when no leaving cable remains).

Prim's key is the edge weight, not a path sum

Copying Dijkstra and writing dist[u] + w builds a shortest-path tree from the seed, which is a different object. The MST question is "what is the cheapest cable that hangs this new house onto the houses I have already wired?", so the heap key is w itself. Test the difference on a triangle with weights 1, 100, 100: both algorithms buy 1 plus 100, never 200.

Structure

Algorithm

  1. Kruskal: sort the edge list by weight. Cheapest first, so the next cable you consider is always a lightest cable across some cut of the groups you have not yet merged, which is exactly the cut property.
  2. Union if the ends are still in different groups. When dsu.union(u, v) returns true, add w to a long total and increment the taken-edge counter; a false return means the cable would close a loop and must be skipped.
  3. Demand n-1 taken edges, or admit a forest. If the list ends with fewer than n-1 successes the graph was disconnected; return a failure, or return the forest if the statement asked for a minimum spanning forest.
  4. Prim: grow a tree from a seed with a heap. The heap key is the weight of the cheapest unused cable into that vertex, not a path sum; skip vertices already popped, add the popped key to the total, and relax unused neighbours with the raw edge weight.
  5. Dense Prim drops the heap for n scans. When every pair of vertices has an implicit edge, it is cheaper to scan the unused dist array n times than to push n² heap entries, which is the complete-graph / points-in-the-plane case.
  6. Keep the total in a long, and keep parallel edges honest. n-1 weights of 10⁵ overflow an int; Kruskal's sort already prefers the cheaper of two parallel cables, and Prim's relax does the same with a min.

Java implementation

JavaMstBrute.java
import java.util.*;
    public class MstBrute {
        static long kruskal(int n, int[][] edges) {
            Arrays.sort(edges, Comparator.comparingInt(e -> e[2]));
            int[] p = new int[n];
            for (int i = 0; i < n; i++) p[i] = i;
            java.util.function.IntUnaryOperator find = new java.util.function.IntUnaryOperator() {
                public int applyAsInt(int x) { return p[x] == x ? x : (p[x] = applyAsInt(p[x])); }
            };
            long ans = 0; int used = 0;
            for (int[] e : edges) {
                int a = find.applyAsInt(e[0]), b = find.applyAsInt(e[1]);
                if (a == b) continue;
                p[a] = b; ans += e[2]; used++;
            }
            return used == n - 1 ? ans : -1;
        }
        public static void main(String[] args) {
            int[][] e = {{0,1,1},{1,2,2},{0,2,2},{2,3,3},{0,3,4}};
            System.out.println(kruskal(4, e));
        }
        // Input : 4 nodes, 5 edges
        // Output: 6
    }
JavaKruskalPrim.java
import java.util.*;
    public class KruskalPrim {
        static class DSU {
            int[] p, r;
            DSU(int n) { p = new int[n]; r = new int[n]; for (int i = 0; i < n; i++) p[i] = i; }
            int find(int x) { return p[x] == x ? x : (p[x] = find(p[x])); }
            boolean union(int a, int b) {
                a = find(a); b = find(b);
                if (a == b) return false;
                if (r[a] < r[b]) { int t = a; a = b; b = t; }
                p[b] = a;
                if (r[a] == r[b]) r[a]++;
                return true;
            }
        }
        static long kruskal(int n, int[][] edges) {
            Arrays.sort(edges, Comparator.comparingInt(e -> e[2]));
            DSU d = new DSU(n);
            long ans = 0; int used = 0;
            for (int[] e : edges) if (d.union(e[0], e[1])) { ans += e[2]; used++; }
            return used == n - 1 ? ans : -1;
        }
        public static void main(String[] args) {
            int[][] e = {{0,1,1},{1,2,2},{0,2,2},{2,3,3},{0,3,4}};
            System.out.println(kruskal(4, e));
        }
        // Input : same
        // Output: 6
    }
JavaPrim.java
import java.util.*;
    public class Prim {
        static long prim(List<int[]>[] g) {
            int n = g.length;
            boolean[] used = new boolean[n];
            long[] dist = new long[n];
            Arrays.fill(dist, Long.MAX_VALUE / 4);
            dist[0] = 0;
            PriorityQueue<long[]> pq = new PriorityQueue<>(Comparator.comparingLong(a -> a[0]));
            pq.add(new long[] {0, 0});
            long ans = 0; int seen = 0;
            while (!pq.isEmpty()) {
                long[] cur = pq.poll();
                int u = (int) cur[1];
                if (used[u]) continue;
                used[u] = true; ans += cur[0]; seen++;
                for (int[] e : g[u]) if (!used[e[0]] && e[1] < dist[e[0]]) {
                    dist[e[0]] = e[1];
                    pq.add(new long[] {e[1], e[0]});
                }
            }
            return seen == n ? ans : -1;
        }
        public static void main(String[] args) {
            List<int[]>[] g = new List[4];
            for (int i = 0; i < 4; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1,1},{1,2,2},{0,2,2},{2,3,3},{0,3,4}};
            for (int[] x : e) { g[x[0]].add(new int[] {x[1], x[2]}); g[x[1]].add(new int[] {x[0], x[2]}); }
            System.out.println(prim(g));
        }
        // Input : same graph
        // Output: 6
    }

Complexity

Time Kruskal O(m log m), Prim O(m log n) Space O(n + m)

Kruskal spends O(m log m) on the sort and then almost-constant time per edge inside union-find, so the sort dominates. At m = 2×10⁵ that is a few million comparisons, comfortable. Prim with a binary heap pushes each edge at most once per improvement and is O(m log n), the same shape as Dijkstra and the same few-million heap operations on a sparse graph.

Dense Prim without a heap scans an unused array of length n once per vertex and is O(n²). At n = 2000 that is 4 million scans and beats a heap that would push about n² entries. Store the running total in a long: n-1 edges of weight 10⁵ already overflow an int.

Edge cases and pitfalls

  • Directed edges
    MST is defined on undirected graphs, so running Kruskal on a tournament of one-way roads produces a set of arcs that does not even mean "connected" in the directed sense, yet the code still returns a number.
    Confirm the statement is undirected. Add both orientations only when you are building Prim's adjacency lists from an undirected edge list, never as a substitute for a directed algorithm.
  • Disconnected graph
    You sum whatever the algorithm bought, call that an MST, and hide the fact that two groups of houses were never joined, which looks correct on a connected sample.
    Count taken edges and require exactly n-1, or return the forest if the statement asked for a minimum spanning forest. Test on two triangles that do not touch.
  • Prim using path-sum keys
    You copied Dijkstra and stored dist[u] + w. The heap then grows a shortest-path tree from the seed, which is a different object and can pick a heavier set of cables than the MST.
    The heap key is the raw edge weight into the tree, w. Test on a triangle 1, 100, 100: both MST algorithms buy 101, never a path of 200.
  • int total
    n-1 edges of weight 10⁵ overflow an int and wrap to a small or negative total that still looks like a plausible bill.
    Accumulate into long ans from the first addition. Test on three edges of weight 10⁵ and check the printed sum is 3×10⁵.
  • Forgetting union-by-rank / path compression
    A chain of unions that always hangs the old root under a new singleton turns each find into an O(n) walk, so Kruskal at m = 2×10⁵ suddenly looks like a quadratic scan.
    Keep both accelerations (rank or size, plus path compression). Path compression alone is already enough at this size; test by unioning i with i+1 in order and timing a find on the last element.

Interview follow-ups

Is the MST unique?

Yes whenever every weight is distinct, because the cut property then names a unique safe edge at every step. When two edges share a weight, more than one cheapest tree can exist, but every MST uses the same multiset of weights: the sorted-edge greedy is forced on every prefix of distinct values, and only the ties may be swapped. The sample on this page has two trees of total 6 that differ on the weight-2 cable.

Is the MST a shortest-path tree?

No. A walk along the MST between two houses can be heavier than a walk that uses a cable the MST rejected. The MST minimises the sum of the cables you buy, not the distance from a chosen source. Prim and Dijkstra share a heap shape and nothing else: Prim's key is the edge into the tree, Dijkstra's key is a path sum from the source.

Min bottleneck path?

Among all walks from u to v, the walk that minimises its heaviest single edge is a walk in the MST (any MST). Build the tree, then read the maximum edge on the unique tree path with binary lifting or heavy-light decomposition. That is why "smallest max-edge" queries on an undirected graph so often start with Kruskal.

Directed analogue?

The directed object is a minimum arborescence rooted at a chosen r: a cheapest set of arcs that reaches every vertex from r. Edmonds' algorithm computes it. Kruskal on a directed graph does not even have a well-defined meaning of "cycle versus connecting", so do not run it. If the statement is undirected, stay on this page.

Recap

  • Cut property: lightest edge across a cut is safe.
  • Kruskal: sort, DSU-union if no cycle.
  • Prim: grow a tree, key = edge weight, not path sum.
  • Need n-1 edges or the graph is disconnected.
  • Min bottleneck path lives on the MST.
