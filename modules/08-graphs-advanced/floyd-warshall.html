Floyd-Warshall

The triple loop for k, for i, for j is "allow vertex k as an intermediate". After k = 0..n-1 every pair is optimal.

Medium 26 min read Prerequisites: Bellman-Ford & Negative Cycles Floyd-Warshall all-pairs APSP P1

Why this exists

You are given a handful of cities and the one-way flight cost between some pairs, and you must answer "what is the cheapest way from every city to every other city?" — the whole square table, not a single source. Running Dijkstra once per city works when every cost is non-negative and the graph is sparse, but with n = 400 cities a dense table already has about 160000 flights, and four hundred heap runs are more code and no faster than one tight triple loop. You also want extras the heap will not give you: a reachability matrix, the smallest bottleneck between every pair, or a flag that some loop of flights refunds money forever.

The algorithm on this page fills an n by n table d by asking one question at a time: "if I am now allowed to use city k as a stopover, does going i → k → j beat the best route I already have from i to j?" That is the single assignment d[i][j] = min(d[i][j], d[i][k] + d[k][j]). The outer loop is k, not i: you must finish every pair's answer using only stopovers from {0, 1, …, k-1} before anyone is allowed to use city k. After k has run from 0 through n-1, every city has been allowed as a stopover and the table is the true all-pairs answer.

The same three loops do more than distances. Replace the min-plus update with a boolean OR and you get transitive closure — a yes/no matrix of who can reach whom. Replace the sum with a max and the outer min stays, and you get the minimax (smallest bottleneck) path between every pair. After the loops, a negative number on the diagonal d[i][i] means a negative cycle touches city i. In a problem statement the tell is n ≤ 400 sitting next to "distance between every pair", "can A reach B after these prerequisites", or "smallest max-edge on a path".

The outer index k is not a source and not a destination: it is the highest-numbered city you are now allowed to use as a stopover. After the k iteration, d[i][j] is the cheapest i-to-j route whose internal cities all lie in {0, 1, …, k}, which is why the loop order is always k, then i, then j.

Core idea and the invariant

Allocate long[n][n], fill every cell with a huge sentinel, then write d[i][i] = 0 so a city reaches itself at cost 0. For each flight u → v of cost w store d[u][v] = min(d[u][v], w), keeping the cheaper of two parallel flights. If the statement is undirected, write both d[u][v] and d[v][u]. That filled table is the answer using no intermediate city, and it is the base of the dynamic program.

Now allow stopovers one city at a time. The outer loop is k from 0 to n-1. For every pair (i, j), if both d[i][k] and d[k][j] are finite, try d[i][j] = min(d[i][j], d[i][k] + d[k][j]). Skipping a half that is still infinite is not a micro-optimisation: adding two sentinels can overflow to a small negative and invent a phantom path. Whenever a relax succeeds and you need the actual route, set nxt[i][j] = nxt[i][k] so a later walk from i follows the first hop toward k.

Walk the four-city sample in words. Flights are 0-1 cost 3, 0-2 cost 8, 1-2 cost 1, 2-3 cost 1, 1-3 cost 7, and we watch row 0. After k = 0 nothing new appears, because using city 0 as a stopover cannot help a route that already starts at 0. After k = 1 the route 0-1-2 beats the direct 8 with 3+1=4, and 0-1-3 writes 10. After k = 2 the route 0-2-3 beats 10 with 4+1=5. City 3 as a stopover adds nothing for this row, and the finished row is [0, 3, 4, 5].

After the outer iteration that has just processed city k, d[i][j] is the cheapest path from i to j whose internal vertices all lie in {0, 1, …, k}, or INF if no such path exists.

In plain words, each outer iteration only asks "may I now use this one extra city as a stopover?", and because every pair has already been optimised for the previous set of stopovers, trying the new city on every pair is enough. A negative d[i][i] at the end means a loop of negative total weight touches city i.

k is a newly allowed stopover, not a source

People coming from Dijkstra hear "for each source" and write i as the outer loop. That updates a pair using a stopover whose own row is not finished yet, so the recurrence is no longer "intermediates from a prefix of cities". Keep k outermost, always. The same skeleton with OR instead of min-plus is transitive closure; with min of max it is the smallest bottleneck.

Structure

Algorithm

  1. Allocate the table and write the base. Fill long[n][n] with a huge sentinel, zero the diagonal so each city reaches itself at cost 0, and write every flight (both ways if the graph is undirected), keeping the cheaper of two parallel flights.
  2. Loop k first: k is the newly allowed stopover. The outer index is the highest-numbered city you may now use in the middle of a route, not a source and not a destination, which is why swapping the loop order silently breaks the recurrence.
  3. Then loop every pair (i, j) and try i → k → j. If both halves of that candidate are finite, write d[i][j] = min(d[i][j], d[i][k] + d[k][j]), because that is exactly "use the new stopover or keep what you already had".
  4. Skip the add when either half is still infinite. Adding two sentinels can overflow to a small negative and invent a phantom path between two cities that cannot reach each other, so the finite-gate is part of correctness, not a speed hack.
  5. Read the finished table, then inspect the diagonal. d[u][v] is the cheapest u-to-v cost, or still infinite if unreachable, and a negative d[i][i] means a negative cycle touches city i.
  6. Recover a route from the nxt table. Whenever a relax through k succeeds, set nxt[i][j] = nxt[i][k], then walk i = nxt[i][j] until you arrive at j to print the actual sequence of cities.

Java implementation

JavaAllPairsDijkstra.java
import java.util.*;
    public class AllPairsDijkstra {
        static long[][] run(int n, int[][] edges) {
            List<int[]>[] g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            for (int[] e : edges) g[e[0]].add(new int[] {e[1], e[2]});
            long[][] d = new long[n][n];
            for (int s = 0; s < n; s++) {
                Arrays.fill(d[s], Long.MAX_VALUE / 4);
                d[s][s] = 0;
                PriorityQueue<long[]> pq = new PriorityQueue<>(Comparator.comparingLong(a -> a[0]));
                pq.add(new long[] {0, s});
                while (!pq.isEmpty()) {
                    long[] cur = pq.poll();
                    int u = (int) cur[1];
                    if (cur[0] != d[s][u]) continue;
                    for (int[] e : g[u])
                        if (d[s][u] + e[1] < d[s][e[0]]) {
                            d[s][e[0]] = d[s][u] + e[1];
                            pq.add(new long[] {d[s][e[0]], e[0]});
                        }
                }
            }
            return d;
        }
        public static void main(String[] args) {
            int[][] e = {{0,1,3},{0,2,8},{1,2,1},{2,3,1},{1,3,7}};
            System.out.println(Arrays.toString(run(4, e)[0]));
        }
        // Input : 4-node graph, row of source 0
        // Output: [0, 3, 4, 5]
    }
JavaFloydWarshall.java
import java.util.Arrays;
    public class FloydWarshall {
        static long[][] floyd(int n, int[][] edges) {
            long INF = Long.MAX_VALUE / 4;
            long[][] d = new long[n][n];
            for (int i = 0; i < n; i++) { Arrays.fill(d[i], INF); d[i][i] = 0; }
            for (int[] e : edges) d[e[0]][e[1]] = Math.min(d[e[0]][e[1]], e[2]);
            for (int k = 0; k < n; k++)
                for (int i = 0; i < n; i++)
                    for (int j = 0; j < n; j++)
                        if (d[i][k] + d[k][j] < d[i][j]) d[i][j] = d[i][k] + d[k][j];
            return d;
        }
        public static void main(String[] args) {
            int[][] e = {{0,1,3},{0,2,8},{1,2,1},{2,3,1},{1,3,7}};
            System.out.println(Arrays.toString(floyd(4, e)[0]));
        }
        // Input : same graph
        // Output: [0, 3, 4, 5]
    }
JavaTransitiveClosure.java
public class TransitiveClosure {
        static boolean[][] reach(int n, int[][] edges) {
            boolean[][] d = new boolean[n][n];
            for (int i = 0; i < n; i++) d[i][i] = true;
            for (int[] e : edges) d[e[0]][e[1]] = true;
            for (int k = 0; k < n; k++)
                for (int i = 0; i < n; i++)
                    if (d[i][k])
                        for (int j = 0; j < n; j++) d[i][j] |= d[k][j];
            return d;
        }
        public static void main(String[] args) {
            boolean[][] r = reach(3, new int[][] {{0,1},{1,2}});
            System.out.println(r[0][2]);
        }
        // Input : 0	o1	o2
        // Output: true
    }

Complexity

Time O(n^3) Space O(n^2)

Three nested loops of length n, each body doing one add and one min, is exactly n³ operations and n² cells of memory. At n = 400 that is 64 million additions, a few tens of milliseconds. At n = 1000 it is a billion additions, which no ordinary judge will accept, so that constraint is telling you to run n Dijkstras or Johnson instead.

The same count holds for the boolean and minimax variants: you still touch every triple (k, i, j) once. Path reconstruction adds an n² next-hop table and a constant amount of work per successful relax, so it does not change the leading term.

Edge cases and pitfalls

  • Loop order i,j,k
    Writing k as the inner loop looks like "try every stopover for this pair" and reads naturally, but you then update a pair using a stopover whose own row is not finished, so the DP is no longer "intermediates from a prefix".
    Keep k as the outer loop, always. To test it, take a three-city path 0-1-2 whose cheapest route needs city 1 as a stopover and confirm the table is wrong if i is outermost.
  • INF + INF overflow
    Two unreachable halves add to a small negative (or wrap an int), so a pair that has no path suddenly looks cheaper than every real route.
    Use the sentinel Long.MAX_VALUE / 4, and also skip the add when either d[i][k] or d[k][j] is still infinite.
  • Forgetting d[i][i] = 0
    A missing zero on the diagonal lets the first pass through k = i write junk into d[i][i], after which a negative-cycle check on that cell is meaningless and other pairs pick up the junk as a stopover.
    Zero every d[i][i] during initialisation, before any edge is written and before the triple loop starts.
  • Directed vs undirected write
    An undirected road written only as d[u][v] makes the return trip look infinite, so a pair that is one hop apart in the other direction is reported unreachable.
    Write both d[u][v] and d[v][u] unless the statement is directed. Test on a single undirected edge and query both orders.
  • Reading d before all k finish
    A table read after only some values of k is "cheapest route using stopovers from a prefix", not the true distance, so a mid-loop query is silently too large.
    Wait until k has run through every city, unless the problem is the reverse-addition variant (CF 295B) that wants the prefix of living vertices.

Interview follow-ups

Why is k the outer loop?

The recurrence is defined on the set of cities you are allowed to use as stopovers. To try city k as a new middle, you need every pair's cheapest route using only {0, …, k-1} already sitting in the table, including the two halves i → k and k → j. Putting k outermost is exactly that dependency. Putting i outermost updates a pair with a stopover that has not finished its own row.

How do you detect a negative cycle?

After the loops, any d[i][i] < 0 means a walk from i back to i of negative total weight, so a negative cycle touches i. A pair (u, v) can then be driven to minus infinity if u can reach such an i and that i can reach v, which you read off the same finished table.

Floyd vs n Dijkstras?

Floyd wins when the graph is dense, when n ≤ 400, or when you want the whole matrix plus extras such as reachability or minimax from the same skeleton. n Dijkstras win on sparse non-negative graphs, especially around n = 2000 and m = 5000, where n³ is a billion and the heap runs are a few million. Johnson replaces the Dijkstras when weights can be negative but there is no negative cycle.

Can Floyd handle negative edges?

Yes, in the same sense Bellman-Ford does: a negative edge is just a number, and the min-plus update does not assume a sign. A negative cycle is not turned into a finite distance; it is reported as a negative diagonal entry, and any pair that can reach that cycle can then be driven without bound. Do not treat those cells as real costs.
