2-SAT

Each clause x ∨ y becomes implications ¬x → y and ¬y → x. Unsatisfiable iff x and ¬x sit in the same SCC.

Hard 26 min read Prerequisites: SCC: Tarjan & Kosaraju 2-SAT implication graph SCC P2

Why this exists

You are seating people, flipping switches, or choosing an orientation of each street, and every rule mentions at most two choices: "at least one of Alice and Bob sits on the left", "these two switches cannot both be on". Trying every assignment is 2n checks; at n = 10⁵ that is not a number you can finish. The same problem with three choices per rule is 3-SAT and is NP-complete. The two-choice version, 2-SAT, is linear, because each rule can be rewritten as two forced arrows and those arrows are a directed graph you already know how to search.

A clause x OR y means two sentences at once: "if x is false then y must be true", and "if y is false then x must be true". Those are directed implications ¬x → y and ¬y → x. Build a graph with two vertices per variable, one for the variable and one for its negation, and add those two arrows for every clause. Implications are transitive: a path a → … → b means "if you set a true you are forced to set b true". Therefore a path from x to ¬x and a path back from ¬x to x is a contradiction — setting x either way forces the opposite. Two vertices that can reach each other sit in the same strongly connected component, so unsatisfiability is exactly "some variable shares an SCC with its negation".

After the SCCs are found, the condensation is a DAG. For every variable you pick the literal whose component is closer to the sinks, which is the side the implications point toward: set x true when scc[x] > scc[¬x]. In a problem statement the tell is a family of pairwise conflicts or "at least one of these two" sitting next to n, m ≤ 10⁵. A rule that names three literals is not this page.

A two-literal clause is two forced arrows, and a forced arrow is transitive, so "x forces not-x and not-x forces x" is mutual reachability. SCC is how you find every such pair in linear time; the sink-side literal of each surviving pair is the assignment.

Recognise this pattern

Say yes when you see

  • Each constraint is a disjunction of at most two literals
  • "At least one of these two is true", "these two conflict"
  • Choose an orientation / a side / a colour with pairwise implications
  • n, m around 1e5 — need linear
  • You can write every rule as (a or b) after introducing x / not-x nodes

Not this pattern when

  • A clause with 3+ literals → NP-complete, not this page
  • XOR-SAT / linear equations over GF(2) → Gaussian elimination
  • You need the number of satisfying assignments modulo p → more than a yes/no SCC

The same Java-stack warning as the SCC page applies: a chain of implications of length 2n overflows the default recursive DFS. A clause with three literals is not 2-SAT and this graph will not save you.

Core idea and the invariant

Fix one encoding and never mix it. The usual packing is neg(i) = 2*i for "variable i is false" and pos(i) = 2*i+1 for "variable i is true", so x ^ 1 flips a literal. The other common packing is i and i+n. For a clause (a OR b) add the two implication edges ¬a → b and ¬b → a. A forced literal a (a unit clause) is the clause (a OR a), which adds the single edge ¬a → a. Forgetting either arrow of a two-literal clause leaves a satisfying assignment that the graph does not force, so both edges are part of correctness.

Run Tarjan or Kosaraju on that directed graph. If any variable i has scc[pos(i)] == scc[neg(i)], the instance is unsatisfiable: i and ¬i can reach each other, so each forces the other. Otherwise assign val[i] = scc[pos(i)] > scc[neg(i)]. Both algorithms number components in reverse topological order of the condensation, so the larger id is the sink side — the side implications point toward, the side you set true. Verify the comparison on the unit clause (x) alone: the edge ¬x → x puts x later, and the assignment must come back true.

Walk two variables and two clauses in words. Clauses are x OR y and ¬x OR y. The four implication edges are ¬x → y, ¬y → x, x → y, and ¬y → ¬x. Every path that starts at ¬y is forced toward y, so y and ¬y do not share a component and y sits on the sink side: y is true. x and ¬x also stay split; the sink-side comparison sets x false. Both clauses become false OR true and true OR true. Adding the two extra clauses x OR ¬y and ¬x OR ¬y would merge y with ¬y and the instance would become unsatisfiable.

If the implication graph contains a path a → … → b, every satisfying assignment that sets a true must set b true. Therefore a path both ways between x and ¬x (they share an SCC) is unsatisfiable.

In plain words, the arrows record forcing, SCC finds every pair of literals that force each other, and the assignment for a surviving pair is "believe the sink-side literal", because that is the direction the remaining arrows still point.

Why the implication graph turns 2-SAT into SCC

A clause is a pair of forced arrows, and a path of arrows is a chain of forcing. If x can reach ¬x and ¬x can reach x, each truth value forces the other: a contradiction. Mutual reachability is the definition of a strongly connected component, so the entire question "does any variable contradict itself?" becomes one SCC run. The condensation DAG then tells you which side of each surviving pair is forced toward the sinks, which is the assignment.

Always add both implication edges

x OR y is two sentences, not one. A single edge ¬x → y does not force anything when y is the false one. Write a helper or(a, b) that inserts both arrows, and encode a unit clause as or(a, a) so you never invent a third code path.

Structure

Algorithm

  1. Allocate 2n vertices and freeze one encoding. The packing neg(i) = 2*i, pos(i) = 2*i+1 lets x ^ 1 flip a literal; the packing i / i+n needs a not() helper. Mixing the two silently swaps half the arrows.
  2. Turn every clause into two implication edges. For (a OR b) add ¬a → b and ¬b → a, because each half of the OR is the sentence "if this side is false, the other side is forced true".
  3. Run SCC on that directed graph. Tarjan or Kosaraju, the same engine as the previous page; the vertices are literals and the streets are forced arrows, not the original variables.
  4. Reject if any variable shares a component with its negation. scc[pos(i)] == scc[neg(i)] means i forces ¬i and ¬i forces i, which is a contradiction no assignment can satisfy.
  5. Otherwise set the sink-side literal true. val[i] = scc[pos(i)] > scc[neg(i)], because both algorithms number components in reverse topological order and the larger id is the side implications still point toward.
  6. Verify the encoding on a unit clause (x) alone. Mapping bugs and a flipped comparison both produce a clean-looking assignment that fails the one-literal instance, so that is the cheapest test you can write.

Java implementation

JavaTwoSatBrute.java
public class TwoSatBrute {
        static boolean sat(int n, int[][] clauses) {
            int lim = 1 << n;
            outer:
            for (int mask = 0; mask < lim; mask++) {
                for (int[] c : clauses) {
                    boolean a = c[0] > 0 ? ((mask >> (c[0] - 1)) & 1) == 1 : ((mask >> (-c[0] - 1)) & 1) == 0;
                    boolean b = c[1] > 0 ? ((mask >> (c[1] - 1)) & 1) == 1 : ((mask >> (-c[1] - 1)) & 1) == 0;
                    if (!a && !b) continue outer;
                }
                return true;
            }
            return false;
        }
        public static void main(String[] args) {
            System.out.println(sat(2, new int[][] {{1, 2}, {-1, 2}}));
            System.out.println(sat(1, new int[][] {{1, 1}, {-1, -1}}));
        }
        // Input : (x∨y)(~x∨y) ; then (x)(~x)
        // Output: true
        //         false
    }
JavaTwoSat.java
import java.util.*;
    public class TwoSat {
        int n;
        List<Integer>[] g;
        int[] tin, low, id;
        boolean[] on, val;
        int timer, cid;
        Deque<Integer> st = new ArrayDeque<>();
        TwoSat(int n) {
            this.n = n;
            g = new List[2 * n];
            for (int i = 0; i < 2 * n; i++) g[i] = new ArrayList<>();
            tin = new int[2 * n]; low = new int[2 * n]; id = new int[2 * n];
            on = new boolean[2 * n]; val = new boolean[n];
            Arrays.fill(tin, -1);
        }
        int pos(int x) { return x << 1 | 1; }
        int neg(int x) { return x << 1; }
        void implies(int a, int b) { g[a].add(b); }
        void or(int x, boolean xv, int y, boolean yv) {
            int a = xv ? pos(x) : neg(x);
            int b = yv ? pos(y) : neg(y);
            implies(a ^ 1, b);
            implies(b ^ 1, a);
        }
        void dfs(int u) {
            tin[u] = low[u] = timer++;
            st.push(u); on[u] = true;
            for (int v : g[u]) {
                if (tin[v] == -1) { dfs(v); low[u] = Math.min(low[u], low[v]); }
                else if (on[v]) low[u] = Math.min(low[u], tin[v]);
            }
            if (low[u] == tin[u]) {
                while (true) {
                    int x = st.pop(); on[x] = false; id[x] = cid;
                    if (x == u) break;
                }
                cid++;
            }
        }
        boolean solve() {
            for (int i = 0; i < 2 * n; i++) if (tin[i] == -1) dfs(i);
            for (int i = 0; i < n; i++) {
                if (id[pos(i)] == id[neg(i)]) return false;
                val[i] = id[pos(i)] > id[neg(i)];
            }
            return true;
        }
        public static void main(String[] args) {
            TwoSat s = new TwoSat(2);
            s.or(0, true, 1, true);
            s.or(0, false, 1, true);
            System.out.println(s.solve() + " " + s.val[0] + " " + s.val[1]);
        }
        // Input : (x∨y) (~x∨y)
        // Output: true false true
    }

public class TwoSatMap {
        static int v(int i, boolean pos, int n) { return pos ? i : i + n; }
        static int not(int x, int n) { return x < n ? x + n : x - n; }
        public static void main(String[] args) {
            int n = 2;
            System.out.println(v(0, true, n) + " " + not(v(0, true, n), n));
        }
        // Input : n=2, literal x0
        // Output: 0 2
    }

Complexity

Time O(n + m) Space O(n + m)

The implication graph has 2n vertices and exactly two directed edges per clause, so 2m edges. One SCC run is O(n + m), and the assignment is a single scan of the n variables comparing two component ids. At n = m = 10⁵ that is a few hundred thousand array operations, a few milliseconds, against a brute 2n that cannot start.

The same Java-stack caveat as the SCC page applies: a chain of 2n implications is a recursion of depth 2n. Counting solutions is not free: only when complementary component-pairs have no extra DAG edges between them is the count a clean power of two; otherwise you need a DAG DP that this linear scan does not perform.

Edge cases and pitfalls

  • Swapping the assignment comparison
    Writing scc[x] < scc[¬x] flips every variable. A sample where both polarities work still passes, so the bug hides until a unit clause or a one-sided force appears.
    Tarjan and Kosaraju ids grow in reverse topological order, so the larger id is the sink side: set that literal true. Verify on the instance that is just the clause (x).
  • Forgetting unit clauses
    A forced x left as a mental note never becomes an edge, so the SCC run does not know x is true and may assign the other way when other clauses allow it.
    Encode a unit clause as (x OR x), which adds the edge ¬x → x. Put that in the same or() helper so there is no third code path.
  • Odd mapping of ~x
    x ^ 1 only flips the right bit when you packed true/false as 2i / 2i+1. Using it on an i / i+n encoding points at a random vertex and the graph is silently wrong.
    Pick one encoding, write a single not() helper, and use it everywhere. Test by printing the two endpoints of a unit-clause edge and reading them by eye.
  • Adding only one implication per clause
    x OR y is two sentences. A single edge ¬x → y does not force anything when y is the false literal, so a satisfying assignment exists that the graph never records.
    Always add both ¬a → b and ¬b → a. The helper or(a, b) should insert the pair and be the only place edges are created.
  • Using undirected edges
    An undirected edge between literals makes each implication run both ways, so two literals that only forced one direction get merged into one SCC and a satisfiable instance is reported unsat.
    The implication graph is directed. Run the directed SCC algorithm from the previous page, never an undirected component search.

Interview follow-ups

Why scc[x] > scc[~x] means x is true?

Implication edges in the condensation go from sources toward sinks: if you believe a source literal you are forced to believe everything it can reach. When ¬x can reach x but not the other way, believing ¬x forces x, so the only consistent choice is x true. Both Tarjan and Kosaraju number components in reverse topological order, so the larger id is later, closer to the sinks, and that is the literal you set true.

Can 2-SAT count solutions?

Sometimes. Each complementary pair of components that is not forced by a path either way is a free bit, and the count is 2k for k such pairs. An extra condensation edge between two pairs destroys that formula, because choosing one pair then forces the other. In that case you need a DAG DP over the condensation, which this linear assignment scan does not do.

How do you force x XOR y?

XOR is "exactly one of the two is true", which is the pair of clauses (x OR y) and (¬x OR ¬y). That is four implication edges: ¬x → y, ¬y → x, x → ¬y, and y → ¬x. Equality is the other pair, (x OR ¬y) and (¬x OR y).

2-SAT vs 2-colouring?

Checking that a graph is bipartite is 2-SAT with one variable per vertex and a clause "adjacent vertices differ" on every edge, i.e. the XOR encoding above. General 2-SAT allows any two-literal clause: forcing two variables equal, forcing a single variable true, or mixing those freely. Same SCC engine, a richer set of arrows, which is why seating and switch problems land here rather than on a 2-colour DFS.
