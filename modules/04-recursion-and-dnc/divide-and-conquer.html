Divide & Conquer

Split the input, solve the halves, and spend linear time combining them — the recipe behind mergesort, inversion counting, majority, and closest pair.

Medium 26 min read Prerequisites: Recursion Fundamentals, Recurrences & Master Theorem divide and conquer mergesort inversions quicksort P0

Why this exists

You are given an array of n numbers and you must sort it, or count how many pairs are out of order, without writing a double loop. Divide and conquer is the reason O(n log n) exists as a default target. Split the array in half, recurse, merge the two sorted runs in linear time. The tree has log n levels and each level touches every element once, so the total is n log n — about 1.7 × 10⁶ operations at n = 10⁵. That accounting is case 2 of the master theorem.

The same split produces inversion counts (a merge that also counts split pairs), majority without Boyer-Moore, and the O(n log n) closest-pair algorithm. Quicksort is the same idea with an uneven, data-dependent split and a free combine — which is why its worst case is quadratic and its expected case is n log n. A reverse-sorted input with the first element as pivot is the picture that kills the naive version.

The skill is the combine. The recursive calls are boilerplate. The interview is: what must each half return so the cross terms can be counted in linear time? For inversions that return is a sorted run plus a count; for closest pair it is a y-sorted strip. If you cannot name the extra payload, you do not yet have a divide-and-conquer solution, only a recursive split.

If the cross-half contribution can be computed in linear time after the halves are sorted, the whole algorithm is O(n log n): log n levels, each touching every element once.

Recognise this pattern

Say yes when you see

  • "Count inversions / reverse pairs / smaller elements to the right"
  • A naive double loop that compares i < j with a[i] ? a[j]
  • Implement mergesort or quicksort
  • Majority element when they want a recursive argument rather than Boyer-Moore
  • Closest pair of points, or any geometric pair that splits on x

Not this pattern when

  • The combine is quadratic and you cannot sort the halves first → T(n) = 2T(n/2) + n² = Θ(n²), no win
  • You need an online answer after each insert → Fenwick or a balanced tree
  • The split is unbalanced and you cannot randomise → worst-case quadratic quicksort
  • n ≤ 40 subset-style counting → meet in the middle

Constraint tell: n ≤ 10⁵ plus a pair-counting condition is the signature for mergesort-with-a-counter: a double loop is 5 × 10⁹ and dies, while n log n fits in a second. Shuffle before a hand-rolled quicksort partition; contests will feed you the adversarial permutation.

Core idea: the combine pays for the split

Mergesort: sort a[lo..mid) and a[mid..hi), then merge into a buffer. Two pointers walk two sorted runs; each step emits the smaller head. Stability comes from preferring the left head on a tie, so equal keys keep the order they had in the input. The buffer is the only extra linear memory; the recursion itself is only O(log n) frames because siblings do not coexist.

Inversions: a pair (i, j) with i < j and a[i] > a[j] is both-left, both-right, or split. The first two come from the recursive calls. A split inversion is counted when the merge takes a head from the right: every unused left element is greater and to the left, so add leftRemaining. On [2, 5, 8] | [1, 3, 9] taking 1 adds 3, taking 3 adds 2, and the five split inversions are the whole answer because each half was already sorted.

Quicksort partitions around a pivot and recurses on both sides; combine is free because the work already happened in the partition. A random pivot makes the expected cost n log n. Majority-by-D&C: the majority of n votes, if it exists, is the majority of at least one half; count the two candidates in a linear pass to decide. Boyer-Moore is faster; this version is the proof you can recite.

After both halves are solved, every pair inside one half is already counted. The combine exists only to handle pairs that cross the midpoint, and it must do that in linear time. In plain words, the recursive calls finish all the local work, and the merge's only job is the pairs that have one foot on each side — leftover left values sitting above a right head — without scanning every pair again.

The recurrence you quote

T(n) = 2T(n/2) + Θ(n) = Θ(n log n). Closest pair is the same class: the strip has a constant number of candidate neighbours per point (the 7-neighbour argument), so the combine stays linear.

mid = lo + (hi - lo) / 2

Left half is [lo, mid), right is [mid, hi), stop when hi - lo ≤ 1. Inclusive bounds plus mid in both calls is the classic infinite-recursion bug.

Boyer-Moore vs D&C majority

Boyer-Moore is O(n) / O(1) and is what you ship. The D&C version is the proof. Know both; do not confuse them.

The three inversion buckets

Algorithm

  1. Write the base case: a run of length 0 or 1 is already sorted and contributes 0 inversions, so the recursion has somewhere to stop.
  2. Split at mid = lo + (hi-lo)/2 with half-open ranges so a two-element run cannot recurse forever on itself.
  3. Recurse on both halves and keep their returned counts; those are the already finished in-left and in-right inversions.
  4. Combine in linear time. For inversions: merge and add mid - i on every right take, because those leftover left values sit above the right head.
  5. Copy the buffer back into a[lo..hi) so the parent merge sees two sorted runs on the next level.
  6. For quicksort: partition, recurse both sides. Shuffle or pick a random pivot so a sorted input cannot become a stick.
  7. For majority: recurse both halves, then count the two candidates in one linear pass over the current range.
  8. Quote T(n) = 2T(n/2) + O(n) and name the combine, because the linear merge is what buys the n log n bound.

Java implementation

The O(n^2) oracle.

JavaInversionsBrute.java
public class InversionsBrute {
    
        static long count(int[] a) {
            long inv = 0;
            for (int i = 0; i < a.length; i++) {
                for (int j = i + 1; j < a.length; j++) {
                    if (a[i] > a[j]) {
                        inv++;
                    }
                }
            }
            return inv;
        }
    
        public static void main(String[] args) {
            System.out.println(count(new int[] {2, 5, 8, 1, 3, 9}));
        }
        // Input : [2, 5, 8, 1, 3, 9]
        // Output: 5
    }

Left leftover on a right-take is the split count. Use long: n = 1e5 can produce ~5e9 inversions.

JavaInversionsMerge.java
public class InversionsMerge {
    
        static long sortCount(int[] a) {
            return go(a, new int[a.length], 0, a.length);
        }
    
        static long go(int[] a, int[] buf, int lo, int hi) {
            if (hi - lo <= 1) {
                return 0;
            }
            int mid = lo + (hi - lo) / 2;
            long inv = go(a, buf, lo, mid) + go(a, buf, mid, hi);
            int i = lo, j = mid, k = lo;
            while (i < mid && j < hi) {
                if (a[j] < a[i]) {
                    buf[k++] = a[j++];
                    inv += mid - i;
                } else {
                    buf[k++] = a[i++];
                }
            }
            while (i < mid) {
                buf[k++] = a[i++];
            }
            while (j < hi) {
                buf[k++] = a[j++];
            }
            System.arraycopy(buf, lo, a, lo, hi - lo);
            return inv;
        }
    
        public static void main(String[] args) {
            System.out.println(sortCount(new int[] {2, 5, 8, 1, 3, 9}));
        }
        // Input : [2, 5, 8, 1, 3, 9]
        // Output: 5
    }

Two other combines: a no-op after partition, and a linear recount of two majority candidates.

JavaDivideConquerTemplate.java
import java.util.Random;
    
    public class DivideConquerTemplate {
    
        static final Random RND = new Random(1);
    
        static void quicksort(int[] a, int lo, int hi) {
            if (hi - lo <= 1) {
                return;
            }
            int p = partition(a, lo, hi);
            quicksort(a, lo, p);
            quicksort(a, p + 1, hi);
        }
    
        static int partition(int[] a, int lo, int hi) {
            int pivotAt = lo + RND.nextInt(hi - lo);
            swap(a, pivotAt, hi - 1);
            int pivot = a[hi - 1];
            int store = lo;
            for (int i = lo; i < hi - 1; i++) {
                if (a[i] < pivot) {
                    swap(a, store++, i);
                }
            }
            swap(a, store, hi - 1);
            return store;
        }
    
        static void swap(int[] a, int i, int j) {
            int t = a[i];
            a[i] = a[j];
            a[j] = t;
        }
    
        static int majority(int[] a, int lo, int hi) {
            if (hi - lo == 1) {
                return a[lo];
            }
            int mid = lo + (hi - lo) / 2;
            int left = majority(a, lo, mid);
            int right = majority(a, mid, hi);
            if (left == right) {
                return left;
            }
            return count(a, lo, hi, left) >= count(a, lo, hi, right) ? left : right;
        }
    
        static int count(int[] a, int lo, int hi, int v) {
            int c = 0;
            for (int i = lo; i < hi; i++) {
                if (a[i] == v) {
                    c++;
                }
            }
            return c;
        }
    
        public static void main(String[] args) {
            int[] a = {2, 5, 8, 1, 3, 9};
            quicksort(a, 0, a.length);
            System.out.println(java.util.Arrays.toString(a));
            System.out.println(majority(new int[] {2, 2, 1, 2, 3}, 0, 5));
        }
        // Input : [2,5,8,1,3,9] and [2,2,1,2,3]
        // Output: [1, 2, 3, 5, 8, 9]
        //         2
    }

Complexity

Time O(n log n) Space O(n) mergesort / O(log n) quicksort expected

Mergesort and inversion count share the same recurrence: two half-size subproblems plus a linear scan of the current range. There are log n levels and each level touches every element once, so the total is n log n — about 1.7 × 10⁶ operations at n = 10⁵.

T(n) = 2T(n/2) + Θ(n) = Θ(n log n)

Quicksort expected: a random pivot produces a uniform split and expected depth O(log n). Worst case: T(n) = T(n-1) + O(n) = O(n²), which is why you shuffle.

D&C majority is O(n log n), strictly worse than Boyer-Moore's single pass. Quote the linear algorithm unless they asked for the recursive proof.

Edge cases and pitfalls

  • Inclusive bounds that recurse forever
    go(lo, mid) and go(mid, hi) with both ends inclusive and mid == lo on a two-element run. The split looks symmetric and the function never reaches a length-1 base case.
    Use half-open [lo, hi) and stop when hi - lo ≤ 1, so a two-element run splits into 1+1.
  • Counting inversions with an int
    n = 1e5 reverse-sorted produces ~5e9 inversions. A signed 32-bit counter wraps to a negative number that still looks like a plausible count.
    long inv from the first line. Same for reverse-pairs, where the product of two ints can overflow too.
  • Adding leftover on a left-take
    You add hi - j when taking from the left, which counts non-inversions: those right leftovers are larger, so they are in order.
    Add leftover-left only when the right head loses the comparison and is emitted into the buffer.
  • Unstable merge
    On a tie, taking the right head. The merge still sorts, so the output looks correct, and interviews then ask for stability.
    if (a[j] < a[i]) take right; on equal, take left so original order is kept.
  • Quicksort without shuffling
    Pivot = first element on a sorted array. The partition produces a stick, so the tree is quadratic and the JVM stack overflows.
    Swap a random index into the pivot slot before every partition, or shuffle the array once.

Interview follow-ups

Why is the closest-pair strip linear, not quadratic?

Points closer than d cannot pack tightly in the strip: each point has only a constant number of neighbours that could beat the current best. Walking the y-sorted strip and looking a few steps ahead is enough. That constant (classically seven) is why the combine stays linear instead of becoming a double loop.

Mergesort or Fenwick for inversions?

Same O(n log n) complexity. Mergesort is self-contained and needs no rank compression. Fenwick on compressed ranks also does online queries after each insert. If the problem is only a one-shot inversion count, write the merge; if later queries arrive, switch to a Fenwick tree.

Is Java's Arrays.sort a mergesort?

Primitives: Dual-Pivot Quicksort, which is not stable and does not expose a merge hook. Objects: TimSort, a stable mergesort cousin. Neither lets you inject an inversion counter, so you write the merge yourself when the problem asks for the pairs rather than a sorted array.

How do I explain majority D&C in thirty seconds?

If a value owns more than half the range, it owns more than half of at least one half — otherwise both halves would be minority and the total could not be a majority. The only two candidates are therefore the majorities of the two halves. Count both on the current range and pick the winner, or report that neither qualifies.

Hint for LC 315 — smaller after self

Mergesort pairs (a[i], i) by value. When the merge takes a right value, it is smaller than every leftover left element and originally sat to its right. Increment those left indices. Same tree as inversions, answers hang off the original indices.

Hint for CF 61E — Enemy is Weak

A triple i < j < k with a[i] > a[j] > a[k] is a length-3 inversion. For each j, multiply (greater to the left) by (smaller to the right). Two Fenwick trees on compressed ranks. Use 64-bit answers.

Recap

  • T(n) = 2T(n/2) + O(n) once the cross terms are linear.
  • Inversions: add leftover-left on every right-take.
  • Use long for any n^2-style counter.
  • Quicksort: randomise the pivot; worst case is n^2.
  • Majority D&C is the proof; Boyer-Moore is the algorithm.
