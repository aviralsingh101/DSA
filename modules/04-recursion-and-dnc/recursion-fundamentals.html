Recursion Fundamentals

A recursive call is a stack frame with a return address, not magic — draw the tree, write the base case first, and treat Java's missing tail-call optimisation as a fact.

Easy 24 min read Prerequisites: Complexity Analysis, Recurrences & Master Theorem recursion call stack base case tail recursion P0

Why this exists

Suppose somebody hands you the top folder of a project and asks how many bytes it holds in total. You cannot write three nested loops for that, because you do not know how deep the folders go — one branch might be two levels deep and another eleven. What you can say is much simpler: the size of a folder is the sum of the files sitting directly inside it, plus the total size of each folder sitting directly inside it. That sentence describes the answer for a big folder purely in terms of the answer for smaller folders, and a function written exactly like that sentence — one that calls itself on each sub-folder — is a recursive function.

The idea is the easy half. The half that trips people up is the machine underneath. When one method calls another, Java sets aside a small block of memory called a stack frame, holding that call's parameters, its local variables, and the address of the instruction to return to when the call finishes. Frames are stacked: the newest one sits on top and has to finish before the one below it can resume. A recursive function therefore pays memory for how deeply it nests, not for how much total work it does. The default HotSpot thread stack is roughly one megabyte and a frame costs tens to a few hundred bytes, so somewhere between a few thousand and about 10⁴ nested calls the program dies with a StackOverflowError.

Cost is the other half. Draw the calls as a tree: the first call is the root, every call it makes is a child, and calls that answer immediately without calling anything are the leaves. Running time is the number of nodes in that recursion tree times the work each node does on its own, while extra memory is the length of the longest root-to-leaf path, because a child always finishes and releases its frame before its sibling is even created. That distinction is worth real money. Naive fib(50), which calls itself twice at every node, builds roughly 2.7×10¹⁰ nodes and runs for minutes, and yet its deepest path is only 50 frames deep.

Two facts are specific to Java and both show up in interviews. First, the JVM never turns a recursive call into a loop, not even when the call is the very last thing the function does — a shape called a tail call that Scheme and Scala do collapse. Writing return fact(n-1, acc*n) still costs one frame per level here, so "make it tail recursive" buys back no stack at all. Second, the constraint line of a problem tells you when plain recursion is simply illegal: a list of length 10⁵, or a graph search over 2×10⁵ nodes that could degenerate into one long path, has to be rewritten with an explicit ArrayDeque before you submit it.

A recursive function is nothing more than a loop over a tree of stack frames: the base case — the input small enough to answer outright, with no further call — is that loop's stopping test, the number of nodes in the tree is your running time, and the longest root-to-leaf path, not the node count, is the memory the JVM must hold all at once.

Recognise this pattern

Say yes when you see

  • The problem on input of size n reduces cleanly to the same problem on a strictly smaller input (or a few of them)
  • The natural description is "do this at the current node, then recurse on the children"
  • You can name a trivial input whose answer is immediate: empty array, n == 0, null node, empty string
  • An interviewer asks you to "think recursively" about a linked list, a tree, or a divide-and-conquer sort
  • You need the shape of the call tree to price the algorithm — branching factor times depth, or a recurrence

Not this pattern when

  • The subproblems overlap and the naive tree is exponential → that is DP; memoise or tabulate, do not just recurse
  • The input is a long path or a linked list of length 10⁵ → an explicit ArrayDeque loop, because the JVM stack will die
  • You are only reducing the argument by one and doing constant work → write the equivalent loop; the recursion adds nothing but frames
  • The recurrence is data-dependent and unbalanced (worst-case quicksort) → analyse expected cost, not a master-theorem split

Constraint tell: The signal is any bound that lets the depth of the recursion grow with the input. The HotSpot default thread stack is roughly 1 MB and one frame costs a few dozen to a few hundred bytes, so you overflow somewhere between a few thousand and about 10⁴ nested calls — long before you run out of time. Treat a linear recursion at n ≥ 10⁴ as illegal in Java unless you have already rewritten it as a loop or an explicit stack. A halving recursion is safe at any bound you will meet, because log₂(10⁹) is only thirty frames.

Core idea: frames, trees, and the base case

When f(n) calls f(n-1), the JVM pushes a frame for f(n), then a frame for f(n-1), and so on, until a call hits the base case — the input small enough to answer with no further call — and returns a value. Each return pops one frame and resumes the caller at the instruction after the recursive call. That last-in-first-out discipline is the call stack, and the chain of resumes is the return path: fact(5) waits to multiply by 5 only after fact(4) comes back. That is why a recursive in-order walk of a BST emits keys in sorted order without you managing a stack yourself.

A recursion tree is the same process drawn in two dimensions: the root is the original call, each edge is a child call, and the leaves are base cases. Time is the number of nodes (each does some work). Extra space is the longest path, because sibling frames do not coexist — a child returns before its sibling is pushed.

Tail recursion is the special case where the recursive call is the last action, so the caller's frame is dead the moment the child starts. Languages with tail-call optimisation reuse the frame and turn the recursion into a jump. Java does not do this. A tail-recursive factorial of n = 10⁵ still explodes. The correct Java rewrite is a while loop that mutates the accumulator.

Write the base case so that every recursive call makes measurable progress toward it (smaller n, a shorter suffix, a child pointer). Then state space as O(depth) and time as "nodes in the tree times work per node". If depth can reach 10⁴, replace the recursion with an ArrayDeque before you talk about anything else.

Java has no tail-call optimisation

This is the most-quoted myth on this page. return fact(n - 1, n * acc) looks tail recursive and is still O(n) frames. The JVM specification does not require TCO, and HotSpot does not implement it. If an interviewer says "can you make it tail recursive?" show the tail form and the loop, and say why only the loop is safe.

Base case first, then one step

The mechanical recipe: (1) name the smallest input and its answer; (2) assume the function already works on every smaller input; (3) write the current answer in terms of those. That is induction, and it is also how you keep a backtracking routine from missing a case or looping forever.

Two trees you must recognise on sight

T(n) = T(n-1) + Θ(1) is a stick: n nodes, depth n. T(n) = T(n-1) + T(n-2) + Θ(1) is the Fibonacci tree: Θ(φⁿ) nodes, depth n. The second is why naive fib(n) dies at n ≈ 40 and why the fix is memoisation (overlap) or a loop (the recurrence is linear), not a "smarter" recursive split.

Algorithm

  1. Name the trivial input and write its answer. Empty, null, n == 0, n == 1 — be explicit about all of them.
  2. State the progress measure. Each call must reduce n, shorten a suffix, or move to a child. If you cannot name it, the function can loop forever.
  3. Assume the function works on every smaller input and write the current answer in terms of those returns.
  4. Draw the tree for a 4-element example. Count nodes (time) and the longest path (space), because those two numbers are the cost you will quote.
  5. Check the JVM stack. If depth can reach thousands, switch to an ArrayDeque or a loop now.
  6. Do not rely on tail recursion to save space in Java. Rewrite tails as while loops that update an accumulator.
  7. If the same nodes repeat, you have overlapping subproblems: add a memo table or go to DP.
  8. Trace one return path by hand so you know what the caller does with the child's result (multiply, min, concat, void side-effect).

Java implementation

The Fibonacci tree is the canonical warning: correct, exponential, and the reason you never recurse on overlapping subproblems without a memo.

JavaRecursionBrute.java
public class RecursionBrute {
    
        static int fib(int n) {
            if (n <= 1) {
                return n;
            }
            return fib(n - 1) + fib(n - 2);
        }
    
        static long fact(int n) {
            if (n <= 1) {
                return 1;
            }
            return n * fact(n - 1);
        }
    
        public static void main(String[] args) {
            System.out.println(fact(5));
            System.out.println(fib(6));
        }
        // Input : fact(5), fib(6)
        // Output: 120
        //         8
    }

The tail-recursive form is shown so you can discuss it, then immediately rewritten as a loop. Only the loop is safe at interview constraints.

JavaRecursionOptimal.java
public class RecursionOptimal {
    
        /** Syntactically tail recursive. Still O(n) stack in Java. */
        static long factTail(int n, long acc) {
            if (n <= 1) {
                return acc;
            }
            return factTail(n - 1, acc * n);
        }
    
        /** The Java version you actually ship. */
        static long factIter(int n) {
            long acc = 1;
            for (int i = 2; i <= n; i++) {
                acc *= i;
            }
            return acc;
        }
    
        static long fibIter(int n) {
            if (n <= 1) {
                return n;
            }
            long a = 0, b = 1;
            for (int i = 2; i <= n; i++) {
                long c = a + b;
                a = b;
                b = c;
            }
            return b;
        }
    
        public static void main(String[] args) {
            System.out.println(factTail(5, 1) + " " + factIter(5));
            System.out.println(fibIter(6));
        }
        // Input : 5 and 6
        // Output: 120 120
        //         8
    }

A depth-guarded template. Use it when the problem is naturally recursive but the input can be a long path. The guard turns a silent overflow into a loud, testable failure.

JavaRecursionTemplate.java
import java.util.ArrayDeque;
    
    public class RecursionTemplate {
    
        static final int DEPTH_LIMIT = 10_000;
    
        static long solve(int n) {
            return go(n, 0);
        }
    
        static long go(int n, int depth) {
            if (depth > DEPTH_LIMIT) {
                throw new IllegalStateException("depth " + depth + "; rewrite as a loop");
            }
            if (n <= 1) {                 // base case
                return 1;
            }
            return n * go(n - 1, depth + 1);
        }
    
        /** Same computation, explicit stack, O(1) JVM frames. */
        static long solveIter(int n) {
            ArrayDeque<Integer> st = new ArrayDeque<>();
            while (n > 1) {
                st.push(n--);
            }
            long acc = 1;
            while (!st.isEmpty()) {
                acc *= st.pop();
            }
            return acc;
        }
    
        public static void main(String[] args) {
            System.out.println(solve(5) + " " + solveIter(5));
        }
        // Input : 5
        // Output: 120 120
    }

Complexity

Time shape-dependent Space O(depth)

Time is the number of nodes in the recursion tree times the non-recursive work at each node. Space is the longest root-to-leaf path, because only that chain of frames is live at once.

T(n) = T(n-1) + Θ(1) ⇒ Θ(n) time, Θ(n) stack

T(n) = T(n/2) + Θ(1) ⇒ Θ(log n) time and stack

T(n) = T(n-1) + T(n-2) + Θ(1) ⇒ Θ(φn) nodes

Java does not recover the stack on a tail call, so the tail-recursive column of any textbook table does not apply. Quote the loop's O(1) auxiliary space instead.

Edge cases and pitfalls

  • Missing or incomplete base case
    if (n == 0) return 1; on a function that is also called with n == 1 in a way that does not terminate, or forgetting the null child on a tree.
    List every trivial input. For trees: null. For arrays: empty and length 1 if the recursive step assumes two sides. For integers: both 0 and 1 when the recurrence mentions n-2.
  • Believing Java will optimise a tail call
    Rewriting return n * fact(n-1) as return fact(n-1, acc*n) and claiming O(1) space, because textbooks call that a tail call and other languages collapse it.
    Say it out loud: HotSpot does not do TCO. Then write the loop. The tail form is useful only as a stepping stone to the loop.
  • Quoting time as the depth
    "Fibonacci is O(n) because the deepest call is fib(0)." Depth is space. Time is the number of calls, which is exponential.
    Draw the tree. Count nodes for time, the longest path for space. They are equal only on a stick.
  • Recursing down a linked list of length 1e5
    An elegant reverse(head.next) that passes the short sample and throws StackOverflowError on the hidden n = 10⁵ list, because the recursive form looks like the textbook definition.
    Interview lists are often short, contest lists are not. If n ≤ 10⁵, use three pointers or an ArrayDeque.
  • Making no progress
    f(n) calling f(n), or a DFS that does not mark visited, or a suffix recursion that passes the same index.
    Every call must change a parameter toward the base case. If the parameter is an index, it must increase (or decrease) on every call.

Interview follow-ups

Why does naive Fibonacci take exponential time if there are only n distinct answers?

Because the tree recomputes fib(k) from scratch at every node that needs it. There are only n distinct values, but Θ(φⁿ) calls. A memo table of size n collapses the DAG back to O(n) work. That collapse of repeated calls into one stored answer is dynamic programming.

Is the space of a balanced binary-tree DFS O(n) or O(log n)?

O(height). On a perfectly balanced tree that is O(log n). On a skewed tree (which is a linked list) it is O(n). Always quote height, then say what the worst-case tree looks like for this input. Interviewers always listen for that distinction.

Can I just raise -Xss and recurse?

In a local experiment, yes. In a judged solution or a production service, no: you do not control the launcher, and a 100 MB stack per thread is not a strategy. Rewrite the recursion as a loop or an explicit ArrayDeque. -Xss is a debugging aid, not a solution.

What should I say when they ask for a tail-recursive version in Java?

Write it, explain that it would be O(1) space in a TCO language, then write the equivalent loop and say that is the version you would actually commit in Java. That answer scores both the concept and the platform knowledge that HotSpot will not collapse the tail call.

Hint for LC 50 — Pow(x, n) without overflowing the exponent

n can be Integer.MIN_VALUE, whose negation does not fit in an int. Widen to long first, then use the halving identity xn = (x2)n/2 with a multiply by x when n is odd. Depth is O(log |n|), which is the rare recursive Java function that is stack-safe at full constraint.

Hint for LC 779 — you do not generate the string

Row n is row n-1 concatenated with its bitwise complement. If k sits in the second half, the answer is 1 minus the answer for k - 2^{n-2} in the previous row. O(n) time, O(n) stack, and you never allocate the 2^{n-1} characters.

Recap

  • A call is a stack frame. Depth is space. Java will not reuse a tail frame.
  • Write the base case first and name the progress measure.
  • Time is nodes; space is the longest path. They coincide only on a stick.
  • Overlapping subproblems mean DP, not a deeper recursion.
  • Linear recursion at n ≥ 10⁴ is a rewrite, not a bigger stack.
