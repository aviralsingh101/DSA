Hashing Patterns

A hash map turns "have I seen the partner of this value?" into expected O(1), which is why two-sum, anagrams, and longest consecutive all look like the same trick.

Easy 22 min read Prerequisites: Complexity Analysis, Prefix Sums hash map hash set frequency prefix P0

Why this exists

You are given 100,000 numbers and asked for two of them that add to a target. The obvious nested loop tries every pair: about 100000 × 100000 / 2 = 5×10⁹ additions, which is an instant time-limit failure. Instead, walk the list once and, for each number x, ask a table "have I already seen target − x?" That question is one hash lookup. A hundred thousand lookups finish in a few milliseconds, provided you store each value (or its index, or its count) as you go. The data structure is the algorithm.

The second skill is choosing the key. For anagrams it is a canonical signature — a spelling of the letter bag that every rearrangement shares, such as the sorted letters or a 26-count. For consecutive sequence it is membership in a set, plus the rule "only start a run from a value whose predecessor is absent", so you do not restart the same run from 2, 3 and 4. For sliding-window uniqueness it is a map of last-seen indices. Wrong keys give wrong collisions, which look like random wrong answers rather than an obvious off-by-one.

Java's HashMap answers each lookup in expected constant time, meaning the average over typical keys is one array hop, and in the worst case a single bucket can degrade to linear if every key collides. In interviews state expected linear. In contests, adversarial tests exist; for integer keys in a small range prefer a plain int[], and for 64-bit keys consider a custom hash. The tell in a real statement is n ≤ 10⁵ plus "pair with given sum", "group anagrams", or "subarray sum equals k".

Store the thing you would have nested-looped for. The key is the partner: target minus x, the anagram signature, the prefix that would complete sum k, or the predecessor that would extend a consecutive run.

Recognise this pattern

Say yes when you see

  • "Two sum / pair with given XOR / pair with given difference" in expected linear time
  • "Group anagrams", "valid anagram", "sort characters by frequency"
  • "Longest consecutive sequence" in O(n) expected
  • "Count subarrays with sum k / XOR k" — prefix + map
  • "Contains nearby duplicate", last-seen index within distance k

Not this pattern when

  • You need ordered keys (floor / ceiling / range) → TreeMap, not HashMap
  • The partner is the next greater element, not an equal-to-target → monotonic stack
  • Keys are 1..n and you may mutate → index as hash
  • You need worst-case O(1) lookups in a contest with anti-hash tests and huge ints → sorted vector + binary search, or a custom splitmix hash

Core idea and the invariant

Two-sum is one pass. For each value x at index i, ask whether map already holds target - x; if it does, those two indices are the answer. Then map.put(x, i). Putting after the lookup is what stops an element being its own partner when the target is 2x. Consecutive sequence dumps everything into a HashSet, then for each x whose predecessor x-1 is missing, walks x, x+1, … until the run breaks. Each number is visited twice at most (once as a membership test, once inside a run), so the whole scan is expected linear.

Prefix-plus-map answers "how many subarrays sum to k". Keep a running sum S, add map.get(S-k) to the answer (that many earlier prefixes would complete sum k with the current prefix), then increment map[S]. The empty prefix 0 must sit in the map with count 1 before the loop, otherwise a subarray that starts at index 0 is never counted. Anagram keys are a sorted char[], or a frozen 26-int signature. Never use the raw string as a key unless you want grouping by identity, not by letter bag.

Walk two-sum on [2, 7, 11, 15] with target 9. The map starts empty. At index 0 the value is 2, the partner 7 is absent, so store 2 → 0. At index 1 the value is 7, the partner 2 is already in the map at index 0, and you return (0, 1) without ever looking at 11 or 15. The same table, seeded with prefix 0, is what counts four subarrays of sum 3 in [1, 2, 1, 2, 1]: every time the running sum hits a value whose complement S-3 was seen, you add that stored count.

After processing prefix a[0..i], the map holds every partner that prefix could complete:

map[v] = how we would answer "have I seen v?" on a[0..i]

In plain words, the table is a notebook of leftovers: each leftover is the value, signature or prefix that a later item would need in order to finish a pair, a group or a subarray. Looking the partner up first, then writing the current item down, is what keeps the notebook honest.

Interview sentence: "I hash the partner, not the whole nested search."

Pick the hash key

Algorithm

  1. Name the partner you would have searched for in a nested loop. That partner — target minus x, a letter-bag signature, a prefix, a predecessor — is the only thing the map needs to store.
  2. Choose the key to match that partner. A value, a canonical signature, a prefix sum, or a membership test: the wrong key collides for the wrong reason and the failure looks random.
  3. Look up first, then insert. Putting the current item into the map before the lookup lets it pair with itself when the target is twice the value.
  4. Seed prefix maps with 0 mapped to count 1. Without that empty prefix, a subarray that starts at index 0 and sums to k is invisible. For longest-subarray, store the earliest index instead of a count.
  5. Start a consecutive run only at x where x-1 is absent. Restarting from every value inside the run revisits the same numbers and turns a linear scan into a quadratic one.
  6. Replace the map with int[] when the range is tiny. Indexing by the key itself removes hashing, boxing and the load-factor constant.
  7. Quote expected O(n) time and O(n) extra space. Interviews want the expected bound; mention the worst-case linear bucket only if they ask about adversarial hashes.

Java implementation

Nested two-sum. Correct, quadratic, the map removes the inner loop.

JavaHashBrute.java
import java.util.Arrays;
    
    public class HashBrute {
        static int[] twoSum(int[] a, int target) {
            int n = a.length;
            for (int i = 0; i < n; i++) {
                for (int j = i + 1; j < n; j++) {
                    if (a[i] + a[j] == target) {
                        return new int[] {i, j};
                    }
                }
            }
            return new int[] {-1, -1};
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(twoSum(new int[] {2, 7, 11, 15}, 9)));
        }
        // Input : [2, 7, 11, 15], target 9
        // Output: [0, 1]
    }

Two-sum, subarray-sum-k, and longest consecutive: three keys, one structure.

JavaHashPatterns.java
import java.util.Arrays;
    import java.util.HashMap;
    import java.util.HashSet;
    import java.util.Map;
    import java.util.Set;
    
    public class HashPatterns {
        static int[] twoSum(int[] a, int target) {
            Map<Integer, Integer> idx = new HashMap<>();
            for (int i = 0; i < a.length; i++) {
                Integer j = idx.get(target - a[i]);
                if (j != null) {
                    return new int[] {j, i};
                }
                idx.put(a[i], i);
            }
            return new int[] {-1, -1};
        }
    
        static int subarraySum(int[] a, int k) {
            Map<Long, Integer> seen = new HashMap<>();
            seen.put(0L, 1);
            long s = 0;
            int count = 0;
            for (int v : a) {
                s += v;
                count += seen.getOrDefault(s - k, 0);
                seen.merge(s, 1, Integer::sum);
            }
            return count;
        }
    
        static int longestConsecutive(int[] a) {
            Set<Integer> set = new HashSet<>();
            for (int v : a) {
                set.add(v);
            }
            int best = 0;
            for (int v : set) {
                if (!set.contains(v - 1)) {
                    int x = v;
                    int len = 1;
                    while (set.contains(x + 1)) {
                        x++;
                        len++;
                    }
                    best = Math.max(best, len);
                }
            }
            return best;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(twoSum(new int[] {2, 7, 11, 15}, 9)));
            System.out.println(subarraySum(new int[] {1, 2, 1, 2, 1}, 3));
            System.out.println(longestConsecutive(new int[] {100, 4, 200, 1, 3, 2}));
        }
        // Input : two-sum [2,7,11,15] t=9; sums [1,2,1,2,1] k=3; consec [100,4,200,1,3,2]
        // Output: [0, 1]
        //         4
        //         4
    }

Canonical keys for anagrams: sorted letters, or a 26-count packed as a string.

JavaAnagramKey.java
import java.util.ArrayList;
    import java.util.Arrays;
    import java.util.HashMap;
    import java.util.List;
    import java.util.Map;
    
    public class AnagramKey {
        static List<List<String>> groupAnagrams(String[] strs) {
            Map<String, List<String>> g = new HashMap<>();
            for (String s : strs) {
                char[] c = s.toCharArray();
                Arrays.sort(c);
                String key = new String(c);
                g.computeIfAbsent(key, k -> new ArrayList<>()).add(s);
            }
            return new ArrayList<>(g.values());
        }
    
        public static void main(String[] args) {
            List<List<String>> g = groupAnagrams(
                new String[] {"eat", "tea", "tan", "ate", "nat", "bat"});
            System.out.println(g);
        }
        // Input : eat tea tan ate nat bat
        // Output: groups [eat,tea,ate], [tan,nat], [bat] (order may vary)
    }

Complexity

Time O(n) expected; O(n L log L) for anagram keys of length L Space O(n) entries in the map / set

Each of n items does a constant number of expected-O(1) map operations: T(n) = Θ(n) expected. At n = 10⁵ that is a few hundred thousand lookups, versus the 5×10⁹ pair checks of the nested loop. Worst case is quadratic if every key collides; interviews want the expected bound.

Consecutive sequence visits each value at most twice (one membership test, one step inside a run). Anagram grouping sorts each string of length L, which is O(n L log L), or O(n L) if you build a 26-count key instead of sorting the letters.

Edge cases and pitfalls

  • Inserting before looking up in two-sum
    When the target is 2x, putting x into the map before the lookup lets the same index pair with itself and returns a pair that the statement forbade.
    Lookup first, then put. For two-sum II on an already-sorted array, drop the map and use two pointers instead.
  • Forgetting to seed prefix 0
    A subarray that starts at index 0 and sums to k never finds a stored prefix, so the count stays zero even though that subarray is legal.
    map.put(0L, 1) before the loop, and use long keys so the running sum cannot wrap.
  • Restarting a consecutive run at every value
    Walking up from 2, 3 and 4 as well as from 1 looks correct on a short sample and becomes quadratic on a single long run of length n.
    Only start a run when !set.contains(v-1), so each number is expanded from its true left end exactly once.
  • Using the string itself as an anagram key
    "eat" and "tea" land in different buckets because the raw strings are different objects, so the group-anagrams map never merges them.
    Sort the letters, or serialise a 26-count with a delimiter, and use that canonical spelling as the key.
  • int overflow on target - x
    When target is Integer.MIN_VALUE and x is 1, the subtraction target - x wraps in 32 bits and looks up the wrong partner.
    Compute long need = (long) target - x, or store keys in a Map<Long, Integer> so the difference cannot wrap.

Interview follow-ups

Why expected O(n) and not worst-case?

Java HashMap is a table with treeified buckets (Java 8+), so a single bucket is O(log n), not O(n), unless you force many distinct keys into pathological hashes. Still say "expected linear" in an interview; in CF, xor a random odd constant into integer keys if you roll your own table.

Two-sum if the array must not be mutated and you need all pairs?

Build a map from value to the list of indices that hold it. After the map is complete, walk keys x that are at most target minus x so each unordered pair is listed once. The time is output-sensitive: if there are p pairs you will spend O(n + p) after the build, not O(1).

Longest consecutive if values do not fit in a HashSet of ints?

They do: at n ≤ 10⁵ a HashSet of n boxed ints is the intended extra memory, Integer cache aside. If the values happen to lie in 1..n, a boolean[] is simpler and removes hashing entirely. The range is not the problem here; n is.

When should the key be a list instead of a string?

A 26-count packed as a string with a delimiter is the easy interview spelling. Arrays.hashCode as a key is wrong because HashMap uses equals: two int[] with the same contents are not equal. Wrap the count in a string, or use a record or a List, so equality is by contents.

Recap

  • Hash the partner, then one pass is enough.
  • Look up, then insert so an item is not its own pair.
  • Seed prefix maps with 0; use long sums.
  • Consecutive runs start where x-1 is missing.
  • Tiny range → int[], not HashMap.
