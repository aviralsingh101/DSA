Hashing Patterns

A hash map turns "have I seen the partner of this value?" into expected O(1), which is why two-sum, anagrams, and longest consecutive all look like the same trick.

Easy 22 min read Prerequisites: Complexity Analysis, Prefix Sums hash map hash set frequency prefix P0

Why this exists

The naive partner search is a nested loop. A map from value to index (or value to count) makes the inner loop a lookup. That is two-sum, group-anagrams (key = sorted letters or a 26-count), and "subarray sum equals k" (key = prefix). The data structure is the algorithm.

The second skill is choosing the key. For anagrams it is a canonical signature. For consecutive sequence it is membership in a set, plus the rule "only start a run from a value whose predecessor is absent". For sliding-window uniqueness it is a map of last-seen indices. Wrong keys give wrong collisions, which look like random WA rather than an obvious off-by-one.

Java's HashMap is expected O(1) and worst-case O(n) if keys collide. In interviews state expected linear. In contests, adversarial tests exist; for integer keys in a small range prefer an array, and for 64-bit keys consider a custom hash.

Store the thing you would have nested-looped for. The key is the partner: target-x, the anagram signature, the prefix that would complete sum k, or the predecessor that would extend a consecutive run.

Recognise this pattern

Say yes when you see

  • "Two sum / pair with given XOR / pair with given difference" in expected linear time
  • "Group anagrams", "valid anagram", "sort characters by frequency"
  • "Longest consecutive sequence" in O(n) expected
  • "Count subarrays with sum k / XOR k" — prefix + map
  • "Contains nearby duplicate", last-seen index within distance k

Not this pattern when

  • You need ordered keys (floor / ceiling / range) → TreeMap, not HashMap
  • The partner is the next greater element, not an equal-to-target → monotonic stack
  • Keys are 1..n and you may mutate → index as hash
  • You need worst-case O(1) lookups in a contest with anti-hash tests and huge ints → sorted vector + binary search, or a custom splitmix hash

Constraint tell: n ≤ 10⁵ with expected O(1) lookups is the hash signature. Integer overflow on target - x needs long keys. Seed prefix maps with (0, 1) for subarray counts. Load factor and boxing cost real constants; an int[] of size R beats a map when R is tiny.

Core idea and the invariant

Two-sum one pass: for each x, if map.containsKey(target - x) return the pair of indices; then map.put(x, i). Putting after the lookup avoids using the same element twice. Consecutive sequence: dump everything into a HashSet, then for each x whose x-1 is missing, walk x, x+1, … until the run breaks. Each number is visited twice at most, so expected linear.

Prefix+map: running sum S, add map[S-k] to the answer, then increment map[S]. The empty prefix 0 must be in the map before the loop. Anagram keys: char[] sorted, or a frozen 26-int signature. Never use the raw string as a key unless you want grouping by identity, not by letter bag.

After processing prefix a[0..i], the map holds every partner that prefix could complete:

map[v] = how we would answer "have I seen v?" on a[0..i]

Interview sentence: "I hash the partner, not the whole nested search."

Algorithm

  1. Name the partner you would have searched for in a nested loop.
  2. Choose the key: value, signature, prefix, or membership.
  3. One pass: look up first, then insert, so an element is not its own partner.
  4. Seed prefix maps with 0. For longest-subarray, store the earliest index.
  5. Consecutive: only expand a run from x where x-1 is absent.
  6. Tiny integer range: replace the map with int[].
  7. State expected O(n) time, O(n) extra space.

Java implementation

Nested two-sum. Correct, quadratic, the map removes the inner loop.

JavaHashBrute.java
import java.util.Arrays;
    
    public class HashBrute {
        static int[] twoSum(int[] a, int target) {
            int n = a.length;
            for (int i = 0; i < n; i++) {
                for (int j = i + 1; j < n; j++) {
                    if (a[i] + a[j] == target) {
                        return new int[] {i, j};
                    }
                }
            }
            return new int[] {-1, -1};
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(twoSum(new int[] {2, 7, 11, 15}, 9)));
        }
        // Input : [2, 7, 11, 15], target 9
        // Output: [0, 1]
    }

Two-sum, subarray-sum-k, and longest consecutive: three keys, one structure.

JavaHashPatterns.java
import java.util.Arrays;
    import java.util.HashMap;
    import java.util.HashSet;
    import java.util.Map;
    import java.util.Set;
    
    public class HashPatterns {
        static int[] twoSum(int[] a, int target) {
            Map<Integer, Integer> idx = new HashMap<>();
            for (int i = 0; i < a.length; i++) {
                Integer j = idx.get(target - a[i]);
                if (j != null) {
                    return new int[] {j, i};
                }
                idx.put(a[i], i);
            }
            return new int[] {-1, -1};
        }
    
        static int subarraySum(int[] a, int k) {
            Map<Long, Integer> seen = new HashMap<>();
            seen.put(0L, 1);
            long s = 0;
            int count = 0;
            for (int v : a) {
                s += v;
                count += seen.getOrDefault(s - k, 0);
                seen.merge(s, 1, Integer::sum);
            }
            return count;
        }
    
        static int longestConsecutive(int[] a) {
            Set<Integer> set = new HashSet<>();
            for (int v : a) {
                set.add(v);
            }
            int best = 0;
            for (int v : set) {
                if (!set.contains(v - 1)) {
                    int x = v;
                    int len = 1;
                    while (set.contains(x + 1)) {
                        x++;
                        len++;
                    }
                    best = Math.max(best, len);
                }
            }
            return best;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(twoSum(new int[] {2, 7, 11, 15}, 9)));
            System.out.println(subarraySum(new int[] {1, 2, 1, 2, 1}, 3));
            System.out.println(longestConsecutive(new int[] {100, 4, 200, 1, 3, 2}));
        }
        // Input : two-sum [2,7,11,15] t=9; sums [1,2,1,2,1] k=3; consec [100,4,200,1,3,2]
        // Output: [0, 1]
        //         4
        //         4
    }

Canonical keys for anagrams: sorted letters, or a 26-count packed as a string.

JavaAnagramKey.java
import java.util.ArrayList;
    import java.util.Arrays;
    import java.util.HashMap;
    import java.util.List;
    import java.util.Map;
    
    public class AnagramKey {
        static List<List<String>> groupAnagrams(String[] strs) {
            Map<String, List<String>> g = new HashMap<>();
            for (String s : strs) {
                char[] c = s.toCharArray();
                Arrays.sort(c);
                String key = new String(c);
                g.computeIfAbsent(key, k -> new ArrayList<>()).add(s);
            }
            return new ArrayList<>(g.values());
        }
    
        public static void main(String[] args) {
            List<List<String>> g = groupAnagrams(
                new String[] {"eat", "tea", "tan", "ate", "nat", "bat"});
            System.out.println(g);
        }
        // Input : eat tea tan ate nat bat
        // Output: groups [eat,tea,ate], [tan,nat], [bat] (order may vary)
    }

Complexity

Time O(n) expected; O(n L log L) for anagram keys of length L Space O(n) entries in the map / set

Each of n items does a constant number of expected-O(1) map operations: T(n) = Θ(n) expected. Worst case is quadratic if every key collides; interviews want the expected bound.

Consecutive sequence visits each value at most twice (membership + walk). Anagram grouping sorts each string: O(n L log L), or O(n L) with a 26-count key.

Edge cases and pitfalls

  • Inserting before looking up in two-sum
    target = 2*x uses the same index twice when you put x first.
    Lookup, then put. For two-sum II (sorted) use two pointers instead.
  • Forgetting to seed prefix 0
    A subarray that starts at index 0 and sums to k is never counted.
    map.put(0L, 1) before the loop. Use long keys for sums.
  • Restarting a consecutive run at every value
    Walking up from 2, 3, and 4 as well as 1 makes the algorithm quadratic.
    Only start if !set.contains(v-1).
  • Using the string itself as an anagram key
    "eat" and "tea" land in different buckets.
    Sort the letters, or serialise a 26-count. Intern the key.
  • int overflow on target - x
    target = Integer.MIN_VALUE, x = 1, the need wraps.
    Use long: long need = (long) target - x; or a Long-keyed map.

Interview follow-ups

Why expected O(n) and not worst-case?

Java HashMap is a table with treeified buckets (Java 8+), so a single bucket is O(log n), not O(n), unless you force many distinct keys into pathological hashes. Still say "expected linear" in an interview; in CF, xor a random odd constant into integer keys if you roll your own table.

Two-sum if the array must not be mutated and you need all pairs?

Map value → list of indices. After building, walk keys x ≤ target-x to avoid listing a pair twice. Complexity is output-sensitive.

Longest consecutive if values do not fit in a HashSet of ints?

They do: n ≤ 1e5, Integer caches aside, HashSet of n boxed ints is fine. If the range is 1..n, a boolean[] is simpler.

When should the key be a list instead of a string?

A 26-count as a string with a delimiter is easy. Arrays.hashCode as a key is wrong because HashMap uses equals: two int[] with the same contents are not equal. Wrap in a string, or use a record/List.

Recap

  • Hash the partner, then one pass is enough.
  • Look up, then insert so an item is not its own pair.
  • Seed prefix maps with 0; use long sums.
  • Consecutive runs start where x-1 is missing.
  • Tiny range → int[], not HashMap.
