Non-Comparison Sorts

When keys live in a small universe, you can sort in linear time by counting, bucketing, or peeling digits — the Ω(n log n) barrier only applies to comparison sorts.

Medium 24 min read Prerequisites: Sorting & Comparators, Constraints → Complexity counting sort radix sort bucket sort P1

Why this exists

You are given 200,000 exam scores, each an integer from 0 to 100, and you must print them in increasing order. Calling the library sort will do roughly 200000 × 18 ≈ 3.6×10⁶ comparisons. You do not need any of those comparisons: walk the list once, increment a 101-slot tally for whatever score you see, then walk those 101 slots and write each score out as many times as you counted it. That is 200,101 writes — about eighteen times fewer operations — because the score itself is already the address of the bucket it belongs in.

That tally-and-emit idea is called counting sort, and it is linear in n plus R, where R is the size of the universe of keys (101 in the exam example). The catch is memory: if the keys were 64-bit ids instead of scores, R would be 2⁶⁴ and you could not allocate the tally. When R is huge but each key still has a fixed number of digits, radix sort — counting sort applied to one digit at a time, least-significant digit first — turns one impossible range into a handful of tiny ones. Four passes of base 256 sort every 32-bit int.

A bucket sort is the same idea with a known distribution: scatter the n values into n buckets, sort each bucket, and concatenate. Maximum-gap is the pigeonhole form, where you prove the largest adjacent gap after sorting cannot sit inside a bucket. In a real statement the tell is values in 0..n, or "sort colours / 0s and 1s", or H-index with citations already clamped to n. Those limits make a comparison sort legal but wasteful: n = 10⁵ and R = n is about 2×10⁵ array writes versus 1.7×10⁶ comparisons.

If the key is already an integer in a small range, do not compare keys: use the key as an array index. Linear time is then a histogram plus a walk that writes each value out as many times as you counted it, or a stable scatter from a prefix of those counts.

Recognise this pattern

Say yes when you see

  • Keys are integers in 0..R with R = O(n) or a tiny constant
  • "Sort colours / 0s, 1s, 2s" — Dutch national flag, a 3-way partition
  • H-index, or any "how many values ≥ x" where x is in 0..n
  • Maximum gap after sorting, when n is large but a comparison sort is still allowed to feel too slow conceptually — bucket / pigeonhole
  • Fixed-width integers (32-bit) and you want guaranteed O(n) with a few passes

Not this pattern when

  • Arbitrary comparable objects with no integer key → comparison sort
  • Range is 10⁹ and you only have n = 10⁵ → sort the n values, or compress then count
  • You need the k-th element, not the full order → quickselect
  • Keys are floats with no distribution promise → comparison sort; buckets can be empty or overloaded

Core idea and the invariant

Start by allocating an array cnt of length R, every slot 0. For each value v in the input, increment cnt[v]. You now hold a histogram: cnt[v] is how many times v appeared. The simplest emit walks v from 0 to R-1 and writes v, cnt[v] times. That is correct but not stable — stable means items that share a key keep their original relative order, which you need when the payload is a pair and this pass is one digit of a radix sort. The stable form turns the counts into starting positions with a prefix sum pos[v] = cnt[0]+…+cnt[v-1], then walks the original array and writes each item to output[pos[key]++].

When R is only 3, you do not need the extra arrays. Dutch national flag — the three-colour in-place partition named after the Dutch flag's red-white-blue bands — keeps three pointers lo, mid, hi. Everything left of lo is 0, everything right of hi is 2, and mid walks the unknown middle. Seeing a 0 swaps with lo and advances both; seeing a 2 swaps with hi and does not advance mid, because the value that just arrived has not been inspected; seeing a 1 just advances mid. Radix LSD is then just the stable counting scatter, once per digit from least significant, so the previous digit's order survives.

Walk [2, 0, 2, 1, 1, 0] through the flag. Start with lo = 0, mid = 0, hi = 5. a[0] is 2, so swap with index 5: the array becomes [0, 0, 2, 1, 1, 2] and hi falls to 4 while mid stays. a[0] is now 0, so swap with lo (a no-op) and both pointers step: lo = 1, mid = 1. The next 0 does the same, leaving lo = 2, mid = 2. Then a[2] is 2, swap with hi = 4 to get [0, 0, 1, 1, 2, 2], and hi becomes 3. Two ones remain; mid walks past them and the loop stops with zeros on the left, twos on the right, and ones in the middle.

After counting, cnt[v] is how many keys equal v, and the prefix pos[v] = cnt[0]+…+cnt[v-1] is the first output index for v:

output[pos[a[i]]++] = a[i]

In plain words, you never compare two keys; you only increment the bucket a key already names, then write that bucket out in order. The prefix of counts is just "how many values smaller than v have I already reserved space for", so each scatter lands in the unique slot that key has earned.

Interview sentence: "I index by the key instead of comparing keys, so the sort is a histogram plus a scatter."

Which linear sort?

Algorithm

  1. Read the range first. If the keys are not integers in a universe you can allocate, counting is the wrong tool and you should fall back to a comparison sort.
  2. When R is 2 or 3, use Dutch national flag. Three pointers partition in one pass and O(1) extra memory, which is why interviews ask "sort colours" this way.
  3. When R is on the order of n, allocate cnt[R]. One tally pass plus one emit or scatter is O(n + R), and that is the whole algorithm.
  4. For a stable scatter, prefix the counts. pos[v] is then the first free output slot for key v, so walking the input writes each item into the unique place it has earned.
  5. Radix LSD applies that stable scatter to one digit at a time. Starting at the least significant digit is what lets the previous digit's order survive into the next pass.
  6. For maximum gap, use n-1 buckets over [min, max]. The pigeonhole argument says the largest adjacent gap after sorting cannot sit inside a bucket, so you only compare neighbouring non-empty buckets.
  7. Shift negatives by min before indexing. A raw negative key is not a legal array index; subtracting the minimum, or radix on unsigned bits, is what makes the histogram well-defined.

Java implementation

Library sort is correct and simpler. Use it unless R is tiny or they ask for linear.

JavaCountBrute.java
import java.util.Arrays;
    
    public class CountBrute {
        static int[] sort(int[] a) {
            int[] b = a.clone();
            Arrays.sort(b);
            return b;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(sort(new int[] {2, 0, 2, 1, 1, 0})));
        }
        // Input : [2, 0, 2, 1, 1, 0]
        // Output: [0, 0, 1, 1, 2, 2]
    }

Three-way partition and counting sort on a general small range.

JavaDutchFlag.java
import java.util.Arrays;
    
    public class DutchFlag {
        static void sortColors(int[] a) {
            int lo = 0, mid = 0, hi = a.length - 1;
            while (mid <= hi) {
                if (a[mid] == 0) {
                    swap(a, lo++, mid++);
                } else if (a[mid] == 2) {
                    swap(a, mid, hi--);
                } else {
                    mid++;
                }
            }
        }
    
        static int[] countingSort(int[] a, int r) {
            int[] cnt = new int[r];
            for (int v : a) {
                cnt[v]++;
            }
            int[] out = new int[a.length];
            int k = 0;
            for (int v = 0; v < r; v++) {
                for (int c = 0; c < cnt[v]; c++) {
                    out[k++] = v;
                }
            }
            return out;
        }
    
        static void swap(int[] a, int i, int j) {
            int t = a[i];
            a[i] = a[j];
            a[j] = t;
        }
    
        public static void main(String[] args) {
            int[] a = {2, 0, 2, 1, 1, 0};
            sortColors(a);
            System.out.println(Arrays.toString(a));
            System.out.println(Arrays.toString(countingSort(new int[] {2, 0, 2, 1, 1, 0}, 3)));
        }
        // Input : [2, 0, 2, 1, 1, 0]
        // Output: [0, 0, 1, 1, 2, 2]
        //         [0, 0, 1, 1, 2, 2]
    }

Stable LSD radix on non-negative ints, base 256, four passes.

JavaRadixLsd.java
import java.util.Arrays;
    
    public class RadixLsd {
        static void radixSort(int[] a) {
            int n = a.length;
            int[] tmp = new int[n];
            for (int shift = 0; shift < 32; shift += 8) {
                int[] cnt = new int[256];
                for (int v : a) {
                    cnt[(v >>> shift) & 255]++;
                }
                int[] pos = new int[256];
                for (int i = 1; i < 256; i++) {
                    pos[i] = pos[i - 1] + cnt[i - 1];
                }
                for (int v : a) {
                    int d = (v >>> shift) & 255;
                    tmp[pos[d]++] = v;
                }
                int[] swap = a;
                a = tmp;
                tmp = swap;
            }
        }
    
        public static void main(String[] args) {
            int[] a = {170, 45, 75, 90, 802, 24, 2, 66};
            radixSort(a);
            System.out.println(Arrays.toString(a));
        }
        // Input : [170, 45, 75, 90, 802, 24, 2, 66]
        // Output: [2, 24, 45, 66, 75, 90, 170, 802]
    }

Complexity

Time Counting O(n + R); radix O(n · w); DNF O(n) Space O(n + R) for stable counting; O(1) extra for DNF

Counting is one tally pass and one emit or scatter pass over n items plus R buckets: T(n,R) = Θ(n + R). Memory is the same order. At n = 10⁵ and R = n that is about 2×10⁵ writes, versus the 1.7×10⁶ comparisons of a library sort.

LSD radix with digit width w (four bytes, base 256) is T(n) = Θ(w(n + B)) with B = 256, so a 32-bit array is four linear passes — still a small multiple of n. Dutch national flag is one pass, three pointers, and no extra histogram, which is why it is the right answer when the universe is only the three colours.

Edge cases and pitfalls

  • Indexing cnt[a[i]] on a negative key
    A negative key looks like a valid integer, so writing cnt[a[i]]++ either throws ArrayIndexOutOfBoundsException or, after a sloppy shift, allocates a huge unused range.
    Subtract min first so every key lands in 0..R-1, or radix on unsigned bit patterns with >>>.
  • Incrementing mid after swapping a 2
    The value swapped in from hi has not been inspected, so incrementing mid on a 2 skips a 0 that just arrived and leaves a 2 in the middle.
    On a 2, swap with hi and do not increment mid. On a 0, increment both pointers because the swapped-in value came from the already-settled left.
  • Unstable counting inside radix
    Emitting by walking v = 0..R rebuilds each digit's group from scratch and destroys the order the previous digit had already established.
    Scatter via prefix positions, walking the input in a consistent direction, so equal current digits keep their previous-digit order.
  • R = 1e9 with n = 1e5
    new int[1_000_000_000] looks linear in the range, but it is a memory error, not a linear sort: you cannot afford an array of a billion counts.
    Coordinate-compress the n values down to 0..n-1, or just comparison-sort those n numbers and drop counting entirely.
  • Max-gap putting n values into n buckets of width (max-min)/n
    The max adjacent gap in the sorted array can sit inside a bucket if you use n buckets carelessly, or you divide by zero when max equals min and the width formula collapses.
    Use n-1 buckets over the exclusive range, handle max==min as a special case, and scan only adjacent non-empty buckets.

Interview follow-ups

Why does radix need a stable inner sort?

After sorting on digit k, items that share that digit must keep the order they already earned from digits 0..k-1. An unstable inner sort reshuffles those ties, and the next higher-digit pass cannot recover the lost information. Counting-with-scatter is stable; dual-pivot quicksort is not, which is why you never radix with Arrays.sort as the inner step.

Can counting sort be in-place?

The histogram is still extra R memory, so you have not removed the space cost. You can cycle-swap items into the prefix positions, but the code is easy to get wrong and not worth it in an interview. Dutch national flag is the in-place special case that actually gets asked, and it only works because R is 3.

How do you handle 32-bit negatives in radix?

XOR every key with 1 << 31 to flip the sign bit so the negatives, which have that bit set, sort first when you treat the bits as unsigned; sort; then flip the bit back. Alternatively subtract Integer.MIN_VALUE as a long so every pattern lands in the unsigned 32-bit range 0 .. 4294967295.

When is counting slower than Arrays.sort?

When R is millions and n is only thousands: you touch a huge cold array of counts that does not fit in cache, while the library sort only touches the n keys. Rule of thumb: counting wins when R is a small multiple of n and the tally array stays hot. Otherwise just call Arrays.sort.

  • Small integer range → histogram, not comparisons.
  • R=3 → Dutch flag, do not increment mid on a swap with hi.
  • Radix LSD needs a stable inner counting scatter.
  • R ≫ n → compress or comparison-sort; do not allocate R.
  • Max gap is pigeonhole: the big empty space is between buckets.
