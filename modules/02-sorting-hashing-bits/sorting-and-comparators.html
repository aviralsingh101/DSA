Sorting & Comparators

Java's sort is a primitive. The skill is writing a comparator that encodes the order the problem actually wants, then proving that order is a total, transitive key.

Easy 22 min read Prerequisites: Complexity Analysis, Java for DSA sort comparator custom order greedy P0

Why this exists

Almost every greedy proof starts with "sort the input". Intervals by start or by end, tasks by deadline, points by polar angle, strings by a+b vs b+a — the algorithm is often two lines after the sort. If the comparator is wrong, the rest of the code is theatre.

Interviews test comparators because they mix language trivia with algorithmic honesty. Integer.compare versus subtraction (overflow), stability of Arrays.sort on objects versus primitives, and the contract sgn(a,b) == -sgn(b,a) are the three traps that turn a correct idea into a WA or a runtime exception on a single pair of values.

The reformulation is: you are not sorting values, you are sorting keys you invented. Once the key is a number or a pair that is totally ordered, TimSort does the rest in O(n log n). Inventing that key is the problem; calling sort is the punctuation.

Write the comparator so that it answers one question: "if I can only keep one of these two items first, which one must come first for the rest of the algorithm to work?" If that answer is not transitive, the sort is undefined and so is your greedy.

Recognise this pattern

Say yes when you see

  • "Order by X, break ties by Y" — a comparator of two keys
  • A greedy that is obviously correct after the items are in a particular order (intervals, deadlines, Huffman-style merge)
  • "Largest number formed by concatenating", "reorder logs", "rank teams by votes"
  • You need a stable order so equal keys keep their input relative order
  • The bottleneck is deciding the key, not computing it — each key is O(1) or O(|s|)

Not this pattern when

  • You need the k-th element only → quickselect / heap, not a full sort
  • The range is tiny (0..n or 0..10⁴) and you need linear time → counting / radix
  • The sequence is a permutation of 1..n with swaps of misplaced values → cyclic sort
  • Order is defined by a partial order / graph of prerequisites → topological sort, not a comparator

Constraint tell: n ≤ 10⁵ is the signature for one O(n log n) sort. Keys that themselves take O(L) (strings of length L) make the true cost O(n L log n). Subtraction comparators overflow when values reach ±10⁹; use Integer.compare or Long.compare.

Core idea and the invariant

Arrays.sort on int[] is dual-pivot quicksort (not stable). On objects it is TimSort (stable). For a custom order, box to Integer[] or sort an index array. The comparator must be a total order: antisymmetric, transitive, and zero only on equivalents. Violating transitivity ("put a before b because of a local rule that does not extend") is undefined behaviour and shows up as a rare shuffle, not an exception.

The standard Java pattern is (u, v) -> Integer.compare(key(u), key(v)) or Comparator.comparingInt(...).thenComparingInt(...). Never return u - v on arbitrary ints. For concatenation, compare a+b with b+a as strings; do not parse them as integers. After the sort, the greedy scan is usually a single pass that only looks at neighbours.

After Arrays.sort(a, cmp), for every i < j:

cmp(a[i], a[j]) ≤ 0

Interview sentence: "I sort by a key that makes the remaining decision local — each item only needs to look at its sorted neighbour."

Algorithm

  1. Name the key that makes the rest of the algorithm a neighbour scan.
  2. Prove transitivity on paper for two minutes. If A before B and B before C does not imply A before C, the comparator is illegal.
  3. Implement with Integer.compare / Comparator.comparingInt. Never subtract ints.
  4. Stability: need it? Sort Integer[] or indices. Primitive int[] sort is not stable.
  5. Sort once with Arrays.sort(a, cmp) or Arrays.sort(idx, (i, j) -> cmp).
  6. Scan linearly. The greedy decision should now look only at a[i] vs a[i-1].
  7. State O(n log n) plus the cost of the key. String keys of length L cost O(n L log n).

Java implementation

Selection sort: correct, quadratic, the thing you are about to replace.

JavaSortBrute.java
import java.util.Arrays;
    
    public class SortBrute {
        static void selectionSort(int[] a) {
            int n = a.length;
            for (int i = 0; i < n; i++) {
                int best = i;
                for (int j = i + 1; j < n; j++) {
                    if (a[j] < a[best]) {
                        best = j;
                    }
                }
                int t = a[i];
                a[i] = a[best];
                a[best] = t;
            }
        }
    
        public static void main(String[] args) {
            int[] a = {5, 2, 4, 6, 1, 3};
            selectionSort(a);
            System.out.println(Arrays.toString(a));
        }
        // Input : [5, 2, 4, 6, 1, 3]
        // Output: [1, 2, 3, 4, 5, 6]
    }

Library sort plus three comparator patterns: ints, pairs, concatenation.

JavaSortKeys.java
import java.util.Arrays;
    import java.util.Comparator;
    
    public class SortKeys {
        static int[] sortInts(int[] a) {
            int[] b = a.clone();
            Arrays.sort(b);
            return b;
        }
    
        static int[][] sortPairs(int[][] pairs) {
            Arrays.sort(pairs, Comparator
                .comparingInt((int[] p) -> p[0])
                .thenComparingInt(p -> p[1]));
            return pairs;
        }
    
        static String largestNumber(int[] nums) {
            String[] s = new String[nums.length];
            for (int i = 0; i < nums.length; i++) {
                s[i] = String.valueOf(nums[i]);
            }
            Arrays.sort(s, (a, b) -> (b + a).compareTo(a + b));
            if (s[0].equals("0")) {
                return "0";
            }
            StringBuilder sb = new StringBuilder();
            for (String x : s) {
                sb.append(x);
            }
            return sb.toString();
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(sortInts(new int[] {5, 2, 4, 6, 1, 3})));
            System.out.println(largestNumber(new int[] {3, 30, 34, 5, 9}));
        }
        // Input : [5,2,4,6,1,3] then [3,30,34,5,9]
        // Output: [1, 2, 3, 4, 5, 6]
        //         9534330
    }

Sort indices when you must keep the original array, and a stable object sort.

JavaSortIndices.java
import java.util.Arrays;
    import java.util.Comparator;
    
    public class SortIndices {
        static int[] orderByValue(int[] a) {
            Integer[] idx = new Integer[a.length];
            for (int i = 0; i < a.length; i++) {
                idx[i] = i;
            }
            Arrays.sort(idx, Comparator.comparingInt(i -> a[i]));
            int[] out = new int[a.length];
            for (int i = 0; i < a.length; i++) {
                out[i] = idx[i];
            }
            return out;
        }
    
        public static void main(String[] args) {
            int[] a = {5, 2, 4, 6, 1, 3};
            System.out.println(Arrays.toString(orderByValue(a)));
            System.out.println(Arrays.toString(a));
        }
        // Input : values [5, 2, 4, 6, 1, 3]
        // Output: indices [4, 1, 5, 2, 0, 3]
        //         original unchanged [5, 2, 4, 6, 1, 3]
    }

Complexity

Time O(n log n) comparisons, times the cost of the key Space O(n) TimSort scratch; O(1) extra for primitive dual-pivot aside from the call stack

A comparison sort must distinguish n! permutations, so Ω(n log n) comparisons in the worst case. Java's object sort is TimSort, adaptive and stable; primitive sort is dual-pivot quicksort.

If each comparison costs O(L) (string keys of length L), multiply: T(n) = O(n L log n). Concatenation comparators allocate, so they are slower than they look; still the right complexity class for n ≤ 10⁵, L ≤ 20.

Edge cases and pitfalls

  • Subtraction overflow in the comparator
    return a - b with a = Integer.MIN_VALUE and b = 1 wraps and reports the wrong sign.
    Integer.compare(a, b) or Long.compare. Never subtract.
  • Unstable primitive sort
    Sorting int[] of equal keys shuffles their original order, then a tie-breaking scan is wrong.
    Box to Integer[], or sort an index array with a stable object sort.
  • Illegal transitive order
    Comparator says A<B, B<C, C<A. TimSort may throw IllegalArgumentException: Comparison method violates its general contract!
    The key must be a total order. Test a cycle of three items by hand.
  • Parsing concatenated numbers as ints
    LC 179 with numbers that concatenate past 2⁹1. parseInt(a+b) throws.
    Compare strings. Leading-zero answer is the single character "0".
  • Forgetting that sort mutates
    You sort the caller's array and a later assertion on the original order fails.
    Clone first, or sort indices and leave the source untouched.

Interview follow-ups

Why is primitive Arrays.sort not stable?

It is a dual-pivot quicksort tuned for ints. Stability requires extra memory to remember original positions. Objects go through TimSort, which is stable. If you need stability on ints, sort boxed values or indices.

How do you sort by a key that is a long without boxing the array?

Sort indices: Integer[] idx and Comparator.comparingLong(i -> key[i]). The values stay primitive; only the permutation is boxed.

Is a lambda comparator allocated every call?

The lambda is a singleton invokedynamic handle; it is not allocated per comparison. What is allocated is any string you build inside it (concatenation comparators). Cache keys if L is large.

When is n log n not good enough after a sort?

When the true bottleneck is the key, not the sort: string keys with large L, or when you only needed the k-th element. Also when the range is tiny and counting sort is linear.

Recap

  • Invent a totally ordered key, then call the library sort.
  • Integer.compare, never a - b.
  • Primitive sort is not stable; object TimSort is.
  • String concatenation keys compare a+b vs b+a.
  • After the sort the greedy should be a neighbour scan.
