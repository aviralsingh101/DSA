Z-Function

Z[i] is the longest substring starting at i that matches the prefix of s. One linear pass maintains a rightmost Z-box.

Medium 28 min read Prerequisites: KMP & the Prefix Function, Two Pointers Z-function string P1

Why this exists

You are given a string, and at every starting index you want to know how many characters of a prefix of the whole string sit there. Pattern matching is the same question after you glue the pattern in front of the text; so are "shortest period" and a slow-but-honest count of distinct substrings. The obvious answer compares the prefix against the suffix that starts at each i from scratch. On a string of length n that is about n2 / 2 comparisons, and at n = 105 that is five billion steps the judge will not wait for.

The linear algorithm remembers the rightmost stretch it has already proved is a copy of a prefix. That stretch is called a Z-box and is stored as a closed interval [l, r], meaning s[l..r] equals s[0..r-l]. When a new index i lands inside that box, the character at i corresponds to the character at i-l in the prefix, so you already know a lower bound on how far a prefix-match from i can run. You copy that bound, clip it so it does not claim more than the remaining box, and only then walk characters if the copy ran out of known ground.

That reuse is the same two-pointer idea Manacher uses for palindromes: a window that only grows to the right, plus a mirror (here a prefix copy) that fills most cells in constant time. Z and the prefix function determine each other in linear time. Prefer Z when the question is already "how much prefix starts at each index"; prefer π when you are building failure links or an automaton.

In a real statement the signal is n ≤ 106 together with a question about prefix matches, periods, or one pattern in one text. If the statement asks for many different patterns, this page is the wrong tool; if it asks for palindromic radii, go to Manacher; if it asks for suffix order, go to the suffix array.

Inside the rightmost Z-box you already hold a prefix copy, so Z[i] starts at min(Z[i-l], r-i+1) instead of at zero. You only compare fresh characters when that copy hits the box edge or when i sits outside the box, and because r never moves left the extra comparisons stay linear.

Constraint tell: n ≤ 106 is the linear-string window. The extend loop is amortised O(n) because the right edge r only moves right, so each successful comparison is paid for once. If you forget to reuse the box you fall back to the quadratic scan and those limits will time out; if the statement wants many patterns or palindromes, this is the wrong array.

Core idea and the invariant

You need an array Z of length n and two integers l and r. The slot Z[i] will hold the longest length such that s[i..i+Z[i]) equals s[0..Z[i]). Leave Z[0] = 0 and never copy from it: some write-ups store n there, and then a later i-l = 0 copies that n and walks off the string. The pair [l, r] is the rightmost Z-box found so far, meaning s[l..r] is already known to equal s[0..r-l], and both start at 0 so the box is empty.

For each i from 1 to n-1 you first ask whether i sits inside the live box. If i ≤ r, the prefix-copy says that a match of length Z[i-l] starts at the corresponding prefix index, but you must not claim more characters than the box still covers, so you set Z[i] = min(r-i+1, Z[i-l]). If i is past r, you start Z[i] at 0. Then you extend: while the next character past the current length still matches the corresponding prefix character, increment Z[i]. If the new match now ends to the right of r, move the box so l = i and r = i+Z[i]-1. You never shrink r.

The clip is load-bearing. Suppose the copied value Z[i-l] is 5 but only 2 characters of the box remain. Those 2 are known to match; the third character past r has never been compared at this alignment, so claiming 5 would invent a match. Conversely, if the copied value equals the remaining box exactly, the match might continue past r, which is why you always run the extend loop after the copy and do not stop at the clip. The same picture is Manacher's mirror: copy, clip to the window, then try one more character.

Walk ababac. At i = 1 the character b disagrees with s[0] = a, so Z[1] = 0 and the box stays empty. At i = 2 you start from 0 and extend through aba against the prefix aba, stopping before the last c, so Z[2] = 3 and the box becomes [2, 4]. At i = 3 you are inside the box; the corresponding prefix index is 1 and Z[1] = 0, so the copy is 0 and you cannot extend, hence Z[3] = 0. At i = 4 the copy wants Z[2] = 3 but only one character of the box remains, so you start at 1; the next character past the box is c against s[1] = b, they disagree, and Z[4] = 1. At i = 5 you are past the box and c disagrees with a, so Z[5] = 0. To match a pattern, build Z of p + '#' + t; every text index with Z[i] == |p| is a hit starting there.

The interval [l, r] is a prefix of s copied so that it starts at l:

s[l..r] = s[0..r-l], and for i in (l, r] we have Z[i] ≥ min(Z[i-l], r-i+1)

In plain words, everything strictly inside the rightmost prefix-copy is already answered except when that copy runs out of box, and those leftover characters are the only ones the extend loop is allowed to spend. Interview sentence: "I reuse the rightmost Z-box, clip to its edge, then extend; r only moves right, so the pass is linear."

Always extend after the copy

Stopping at min(r-i+1, Z[i-l]) looks complete because both numbers are known matches. When the copy hits the box edge the next character is unknown at this alignment and may still match. Skip the while and you under-report Z-values that reach past r, which then poisons later copies.

Leave Z[0] at 0

Storing n at index 0 is a convention for "the whole string matches itself". The algorithm then needs a special case when i-l is 0, because copying n walks off the array. Leaving Z[0] = 0 makes the copy line safe and you never use that slot as a match start anyway.

Rightmost Z-box

Algorithm

  1. Zero the unused prefix slot. Set Z[0] = 0 so a later copy with i-l = 0 cannot pick up the string length and walk off the array. You will never treat index 0 as a match start.
  2. Start with an empty box. Set l = r = 0, then walk i from 1 to n-1. The pair [l, r] will always be the rightmost prefix-copy discovered so far.
  3. Reuse the box when i sits inside it. If i ≤ r, write Z[i] = min(r-i+1, Z[i-l]). The first number is how much box remains; the second is the known prefix-match at the corresponding prefix index.
  4. Extend with fresh comparisons. While i + Z[i] is in bounds and s[Z[i]] equals s[i + Z[i]], increment. This is the only place new characters are compared, and it is what catches a match that continues past the old r.
  5. Widen the box, never shrink it. If i + Z[i] - 1 > r, set l = i and r = i + Z[i] - 1. Charging every successful extend to a rightward move of r is the linear-time argument.
  6. Match a pattern on the concatenated string. Build Z of p + '#' + t with a sentinel outside both alphabets, then collect every text index where Z[i] == |p|. Those values are start indices, unlike the prefix-function hits which are ends.

Java implementation

Match a prefix from every i. Quadratic.

JavaZBrute.java
import java.util.Arrays;
    public class ZBrute {
        static int[] z(String s) {
            int n = s.length();
            int[] z = new int[n];
            for (int i = 1; i < n; i++) {
                while (i + z[i] < n && s.charAt(z[i]) == s.charAt(i + z[i])) z[i]++;
            }
            return z;
        }
        public static void main(String[] args) {
            System.out.println(Arrays.toString(z("ababac")));
        }
        // Input : ababac
        // Output: [0, 0, 3, 0, 1, 0]
    }

Linear Z-array via the rightmost box.

JavaZFunction.java
import java.util.Arrays;
    public class ZFunction {
        static int[] z(String s) {
            int n = s.length();
            int[] z = new int[n];
            for (int i = 1, l = 0, r = 0; i < n; i++) {
                if (i <= r) z[i] = Math.min(r - i + 1, z[i - l]);
                while (i + z[i] < n && s.charAt(z[i]) == s.charAt(i + z[i])) z[i]++;
                if (i + z[i] - 1 > r) { l = i; r = i + z[i] - 1; }
            }
            return z;
        }
        public static void main(String[] args) {
            System.out.println(Arrays.toString(z("ababac")));
        }
        // Input : ababac
        // Output: [0, 0, 3, 0, 1, 0]
    }

Occurrences of p in t.

JavaZMatch.java
import java.util.*;
    public class ZMatch {
        static int[] z(String s) {
            int n = s.length();
            int[] z = new int[n];
            for (int i = 1, l = 0, r = 0; i < n; i++) {
                if (i <= r) z[i] = Math.min(r - i + 1, z[i - l]);
                while (i + z[i] < n && s.charAt(z[i]) == s.charAt(i + z[i])) z[i]++;
                if (i + z[i] - 1 > r) { l = i; r = i + z[i] - 1; }
            }
            return z;
        }
        static List<Integer> find(String t, String p) {
            int[] z = z(p + "#" + t);
            List<Integer> ans = new ArrayList<>();
            int m = p.length();
            for (int i = 0; i < t.length(); i++) if (z[m + 1 + i] == m) ans.add(i);
            return ans;
        }
        public static void main(String[] args) {
            System.out.println(find("ababa", "aba"));
        }
        // Input : ababa / aba
        // Output: [0, 2]
    }

Complexity

Time O(n) Space O(n)

The outer loop visits each of the n-1 later indices once and the box-copy is a constant amount of arithmetic. The only loop that can run more than once per index is the extend. Every successful extend comparison increases r by at least one, and r never decreases, so successful extends total at most n. A failed extend comparison happens at most once per i after the copied value is installed, which is another n comparisons.

Putting real numbers in: at n = 106 you do a couple of million character reads, which is a few milliseconds. The naive prefix-at-every-i scan is about n2 / 2 comparisons, five billion at n = 105 already, and that is the runtime this box is designed to avoid.

Edge cases and pitfalls

  • Using Z[0]=n in the copy
    Storing the string length at index 0 looks tidy because the whole string is a prefix of itself. The first time i-l is 0 the copy writes n into Z[i] and the extend loop walks off the array or invents a match past the end.
    Leave Z[0] = 0, or special-case the copy when i equals l. Test a string that starts a new box at every other index, such as ababab.
  • Updating [l,r] with a weaker box
    Moving r left, or replacing the box whenever a new i has a positive Z, looks like you are keeping the window current. Shrinking r throws away known prefix-copies, breaks the amortised bound, and can make later Z-values too small if you then skip the extend.
    Only widen when i + Z[i] - 1 > r. The rightmost box is the only one whose remaining characters are still unused information.
  • min(r-i+1, Z[i-l]) without extend
    The clip already looks like the answer, because both arguments are proven matches. When the copied Z-value hits the box edge, the next character past r might still match the prefix and you are supposed to keep going.
    Always run the extend while after the copy. A good test is a string whose Z-box ends in the middle of a longer prefix-match, such as aaaabaaa.
  • Sentinel missing
    Building Z of p+t without a separator looks like the KMP concatenation trick with less punctuation. A Z-value can cross the join and report a hit that is half pattern and half text.
    Insert a character outside both alphabets. Check that no Z-value in the text half exceeds |p| except at real occurrences.
  • Comparing chars with == on substrings
    Writing s.substring(a) == s.substring(b) looks like an equality test and even compiles. In Java that is reference equality of two new String objects, so it is almost always false and the extend loop never runs.
    Compare with charAt in the extend loop, as the listing does. If you ever need a whole-slice check, use equals, not ==.

Interview follow-ups

Why copy min(r-i+1, Z[i-l])?

The live box says s[l..r] equals s[0..r-l], so the character at i is a copy of the character at i-l in the prefix. You cannot claim a longer prefix-match than Z[i-l], because that is already the longest prefix sitting at the corresponding place. You also cannot claim more characters than the remaining box, because past r you have no copy. The minimum of those two numbers is the largest claim that is already proved; the extend loop is what tries to prove more.

Z vs KMP for matching?

Both are linear in |p| + |t|. Z is a little more code for matching and a little less conceptual load when the question is already "prefix at every index". The prefix function composes better with Aho-Corasick, because a failure link is exactly π[q-1]. In an interview, pick the one whose array the rest of the problem already wants.

Can Z handle wildcards?

Not by itself, because a Z-box is a claim that two concrete characters were equal. Split the pattern on each ?, Z-match every concrete chunk against the text, and then check that the gaps between those hits have the right lengths. The other school is FFT string matching, which treats a wildcard as a coefficient that does not contribute to the mismatch count.

Manacher uses the same idea?

Yes. Manacher keeps a rightmost palindrome instead of a rightmost prefix-copy, and the value it reuses is the radius at the mirrored centre rather than Z[i-l]. The rest of the skeleton is identical: clip to the window, extend if the copy hits the edge, and charge every successful extend to a rightward move of r. Once you can write Z, Manacher is the palindrome-flavoured version of the same pass.
