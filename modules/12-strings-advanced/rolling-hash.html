Rolling Hash

Map every substring to a polynomial s[l] b^{len-1} + … + s[r] modulo a prime so equality (and 2D / palindrome checks) become a few multiplies.

Medium 30 min read Prerequisites: Modular Arithmetic, Prefix Sums hashing polynomial hash P1

Why this exists

You are given a string and a pile of questions of the form "is the slice from here to there the same as the slice from over there?" The honest answer compares the two slices character by character. That is correct, and at length n it costs n work per question. With q = 2 × 105 questions on strings of length 105 you are looking at about 2 × 1010 comparisons, and the judge will not wait. KMP and Z solve the special case of one pattern in one text, but they do not give you an arbitrary pair of slices in constant time, and they do not drop a set of slices into a hash set.

The fix is to treat each slice as a number. Pick a base b and a modulus M, and read the characters of a slice as digits of a base-b integer, then reduce modulo M. Two slices that are equal produce the same number; two slices that differ almost always produce different numbers. After one prefix pass you can recover any slice's number with a subtraction and a multiply, the same shape as a prefix-sum difference, except the powers of b have to be aligned before you subtract.

That number is called a polynomial hash or a rolling hash. One comparison against a small prime can collide, which is why contest code uses a random base, two moduli, or the free ring of unsigned 64-bit overflow. The interview sentence is "compare hashes first, and if the modulus is small enough to worry about, verify the characters on a hit". On Codeforces, tests that break a famous base and 109+7 are a known sport.

In a real statement the signal is many substring-equality questions, a binary search on "longest common prefix of these two suffixes", palindrome queries, or "put these slices in a set". If you must be deterministic with one pattern and no collision story, write KMP. If you need the lexicographic order of every suffix, write a suffix array.

A substring hash is a prefix-hash difference scaled by a power of the base — the same identity as a prefix sum, just living in a modular ring. Build H and pow once, then every slice is one multiply and one subtract, and two slices are equal exactly when those numbers agree (or, with a tiny probability, when they collide).

Recognise this pattern

Say yes when you see

  • O(1) substring equality after O(n) preprocess
  • Longest common prefix of two suffixes via binary search + hash
  • Palindrome check: hash(s[l..r]) == reverse-hash of that range
  • 2D grid matching (Rabin-Karp 2D)
  • You need to put substrings in a HashSet

Not this pattern when

  • You must be deterministic with no collision risk and one pattern → KMP
  • Need the suffix order, not equality → suffix array
  • Alphabet is huge and you need frequency maps → different tool
  • Single comparison of two whole strings → equals

Constraint tell: n, q ≤ 2 × 105 substring-equality questions is the signature. Two 64-bit moduli and a base drawn at random from [257, 109) make a collision on that batch a non-event. A single fixed 109+7 with base 31 is the combination Codeforces anti-hash tests are written to break, so do not ship it alone.

Core idea and the invariant

You need two arrays, H and pow, both of length n+1. Fix a base b larger than the alphabet and a modulus M. Set H[0] = 0 and pow[0] = 1. Then for each index i write H[i+1] = (H[i] * b + s[i]) mod M and pow[i+1] = (pow[i] * b) mod M. After that pass, H[i] is the hash of the prefix s[0..i), read as a base-b integer. The half-open slice [l, r) has hash (H[r] - H[l] * pow[r-l]) mod M; if the subtraction went negative, add M back, because Java's remainder operator can return a negative representative.

That difference is doing the same job a prefix-sum difference does. H[r] is the number for the whole prefix up to r. H[l] is the number for the prefix up to l, but its digits sit in higher places, so you multiply by b^{r-l} to shift them into the same places they occupy inside H[r]. Subtract, and the leading digits cancel, leaving only the digits of the slice. Two slices are equal if those leftover numbers agree. They can also agree by accident: with a random base the chance of one unlucky comparison is about n / M, q comparisons cost about q / M, and two independent moduli square that chance down to something you will not see in a contest.

Anti-hash hygiene is part of the algorithm, not an optional extra. A fixed base 31 and modulus 109+7 is famous enough that people generate strings whose polynomials collide on purpose. Draw b from a wide range at startup, or work in unsigned 64-bit overflow (the ring modulo 264, which Java long arithmetic already is) and pair it with one prime if the contest is known to be hostile. Never map a letter to 0: a leading zero makes a and aa the same number, which is a collision you invented yourself.

Walk the toy string aba with a = 1, b = 2, base 3, and no modulus so the arithmetic stays visible. H[0] = 0. After a you have H[1] = 1. After ab you have H[2] = 1 × 3 + 2 = 5. After aba you have H[3] = 5 × 3 + 1 = 16. The slice [1, 3) is ba, and the formula gives 16 - 1 × 32 = 7, which is exactly 2 × 3 + 1. The slice [0, 2) is ab and hashes to 5, so the two middle-overlapping slices are correctly reported different. A palindrome check is the same comparison against a hash built on the reversed string.

The prefix array stores the polynomial of every prefix, and a slice is a scaled difference:

H[i] = ∑j=0i-1 s[j] · bi-1-j (mod M),   hash[l, r) = H[r] − H[l] · br-l (mod M)

In plain words, two slices are the same string exactly when those two polynomials are the same, and with a random base a collision is a rare modular accident rather than a logic bug. Interview sentence: "I prefix-hash like a prefix sum, multiply by pow[len] to line the powers up, and I never ship base 31 with one small prime on Codeforces."

Java % can be negative

(H[r] - H[l] * pow[r-l]) % M is a correct integer in mathematics and a possibly-negative leftover in Java. A HashSet then treats -3 and M-3 as different keys, so two equal slices miss each other. Always fold the representative back into [0, M).

Map letters to 1..26, not 0..25

A leading zero digit makes a and aa the same polynomial when a maps to 0. Using the raw char code is also safe, because it is never 0. The bug is silent: the rest of the code looks right and only one family of slices collides.

Collision chance after q comparisons

Schwartz–Zippel on a degree-n polynomial against a random base says one comparison collides with probability about n / M. After q comparisons that is about q n / M. Two independent 64-bit moduli put the product near q n / 2128, which is not a number you will hit in a contest lifetime.

Algorithm

  1. Pick a base and a modulus you would defend out loud. Draw an odd base larger than the alphabet, and choose one or two moduli from unsigned 264, 261-1, or a pair of 109-ish primes. Do this once at startup, not as a hardcoded 31.
  2. Build the two prefix arrays in one pass. Allocate H and pow of length n+1, set the zeros, and fold each character in with H[i+1] = H[i]*b + s[i]. This is the only O(n) work.
  3. Recover a half-open slice with a scaled difference. For [l, r) compute h = H[r] - H[l]*pow[r-l] and, if you are in a prime modulus, fold a negative leftover back into [0, M). Mixing inclusive r with a pow[r-l] shift is the classic off-by-one.
  4. Compare two slices by those numbers. Equal hashes mean the slices are almost certainly equal; if the modulus is a small single prime, verify the characters on a hit. Different hashes mean the slices are definitely different.
  5. Slide a window when the problem is Rabin-Karp search. The next alignment is window * b - s[i-len]*pow[len] + s[i], which drops the leaving character and appends the incoming one without rebuilding.
  6. Build a reverse hash when you need palindromes. Either prefix-hash the reversed string, or keep a second prefix that grows from the right. A slice is a palindrome when its forward hash equals the reverse hash of the same range.

Java implementation

substring equals. Correct, O(n) per query.

JavaSubEqBrute.java
public class SubEqBrute {
        static boolean eq(String s, int l1, int r1, int l2, int r2) {
            return s.substring(l1, r1).equals(s.substring(l2, r2));
        }
        public static void main(String[] args) {
            String s = "abacaba";
            System.out.println(eq(s, 0, 3, 4, 7));
        }
        // Input : abacaba, [0,3) vs [4,7)
        // Output: true
    }

Single 64-bit unsigned ring via long overflow (mod 2^64). Fast and usually enough with a random base.

JavaRollingHash.java
import java.util.Random;
    public class RollingHash {
        long[] H, p;
        RollingHash(String s, long base) {
            int n = s.length();
            H = new long[n + 1];
            p = new long[n + 1];
            p[0] = 1;
            for (int i = 0; i < n; i++) {
                H[i + 1] = H[i] * base + s.charAt(i);
                p[i + 1] = p[i] * base;
            }
        }
        long hash(int l, int r) { return H[r] - H[l] * p[r - l]; }
        public static void main(String[] args) {
            long base = new Random().nextInt(1_000_000) + 257;
            RollingHash h = new RollingHash("abacaba", base);
            System.out.println(h.hash(0, 3) == h.hash(4, 7));
        }
        // Input : abacaba, [0,3) vs [4,7)  ("aba" vs "aba")
        // Output: true
    }

Two prime moduli. Safer on CF anti-hash.

JavaDoubleHash.java
public class DoubleHash {
        static final long M1 = 1_000_000_007L, M2 = 1_000_000_009L, B = 911382323L;
        long[] h1, h2, p1, p2;
        DoubleHash(String s) {
            int n = s.length();
            h1 = new long[n + 1]; h2 = new long[n + 1];
            p1 = new long[n + 1]; p2 = new long[n + 1];
            p1[0] = p2[0] = 1;
            for (int i = 0; i < n; i++) {
                h1[i + 1] = (h1[i] * B + s.charAt(i)) % M1;
                h2[i + 1] = (h2[i] * B + s.charAt(i)) % M2;
                p1[i + 1] = p1[i] * B % M1;
                p2[i + 1] = p2[i] * B % M2;
            }
        }
        long hash(int l, int r) {
            long x = (h1[r] - h1[l] * p1[r - l] % M1 + M1) % M1;
            long y = (h2[r] - h2[l] * p2[r - l] % M2 + M2) % M2;
            return (x << 32) ^ y;
        }
        public static void main(String[] args) {
            DoubleHash h = new DoubleHash("abacaba");
            System.out.println(h.hash(0, 3) == h.hash(4, 7));
        }
        // Input : same aba vs aba
        // Output: true
    }

Complexity

Time O(n) build, O(1) substring hash Space O(n)

The prefix arrays are one loop of n multiplies. Each substring query is then a constant amount of arithmetic: one multiply by a precomputed power, one subtract, and a possible correction into [0, M). A binary search that asks "do these two suffixes share a prefix of length mid?" spends one hash comparison per probe, so one longest-common-prefix costs O(log n) hashes, about 17 queries at n = 105.

Putting real numbers in: n = q = 2 × 105 is a couple of hundred thousand multiplies to build and the same number of multiplies to answer, which is a few milliseconds. The character-loop alternative is q × n reads, about 4 × 1010 in the same limits, which is the number that forces this page. Double hashing doubles the constants and still fits comfortably.

Edge cases and pitfalls

  • Negative mod in Java
    Writing (H[r] - H[l]*pow) % M looks like the mathematical remainder and compiles cleanly. Java can return a negative leftover, and a HashSet then stores -3 and M-3 as two different keys, so equal slices miss each other.
    After the remainder, if the value is negative add M once. Test it on a slice whose leading prefix hash is larger than the longer prefix hash, which is the usual way the subtraction goes negative.
  • Fixed base 31 and mod 1e9+7 on CF
    The pair is in every blog post and it passes random tests, so it looks finished. Anti-hash generators know that pair and will hand you two different strings with the same polynomial, which is a wrong-answer, not a timeout.
    Draw the base at random each run, use two moduli, or work in unsigned 64-bit overflow plus one prime. On a local stress test, hash a few million random strings into a set and look for unexpected collisions.
  • Mapping letters to 0
    Mapping 'a' to 0 looks like a tidy 0-based alphabet. A leading zero digit makes a and aa the same number, so those two slices collide even though the rest of the hash code is correct.
    Map 'a'..'z' to 1..26, or use the raw char code, which is never zero. Check that hash(0,1) and hash(0,2) differ on a string of all as.
  • pow overflow before mod
    Writing p[i] * B in a long looks safe because you intend to reduce modulo a 1018-ish prime afterwards. The product already overflowed the 64-bit register, so the value you reduce is not the product you wanted.
    Stay in unsigned 264 and accept the overflow as the modulus, or reduce with a mul-mod (or the 261-1 trick) before the product leaves 64 bits.
  • Half-open vs inclusive mix
    Documenting hash(l, r) as inclusive while multiplying by pow[r-l] looks consistent with the array length. The power is one short, every slice of length greater than 1 is wrong, and small palindrome checks still pass by luck.
    Pick half-open [l, r) everywhere, including the dry-run table, and test a length-1 slice next to a length-2 slice so the off-by-one cannot hide.

Interview follow-ups

Why a random base?

For a fixed base an adversary can solve for strings whose polynomials collide, especially against a small well-known modulus. A base drawn at startup, after the tests were generated, makes the polynomial a random one the adversary did not know. The Schwartz–Zippel lemma then bounds the collision chance by the degree over the field size, which is the n / M figure in the derivation.

Is 2^64 overflow OK?

Java long arithmetic is already the ring modulo 264, so you get a 64-bit hash with no remainder instruction. It is a ring, not a field, so it has zero divisors and a few known overflow attacks (Thue–Morse style). Those are rarer than 109+7 collisions. Pair the overflow hash with one prime if the contest is known to be hostile; otherwise a random base in this ring is the usual Codeforces default.

LCP of two suffixes?

Binary search the length. The predicate "the two suffixes share a prefix of length mid" is one hash comparison, so one LCP is O(log n) after the prefix arrays exist. If you need the LCP of every adjacent pair of sorted suffixes, a suffix array plus Kasai is the cleaner linear fill; hashing wins when you only ask about a few pairs.

Hash vs KMP in an interview?

Mention both and then pick. If they want a worst-case linear scan of one pattern and no probability talk, write KMP. If they want many substring queries, a set of slices, or a binary search on string equality, write a rolling hash and say out loud what you will do on a collision (second modulus, or a character verify). Do not pretend a 32-bit String.hashCode is the same tool.
