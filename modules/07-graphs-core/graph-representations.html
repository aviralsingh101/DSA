Graph Representations

Pick the encoding before the algorithm: adjacency list, matrix, or edge list are not interchangeable, and the wrong one turns an O(n + m) walk into an O(n²) timeout.

Easy 24 min read Prerequisites: Complexity Analysis, Java for DSA graphs adjacency list adjacency matrix P0

Why this exists

You are handed a city map as a plain list of 200000 road segments, each one printed as a pair of junction numbers such as 17 4093, and you are asked which junctions a delivery van starting at junction 0 can eventually reach. Before you can search anything you have to decide how those pairs sit in memory, because a bare list of pairs cannot tell you which roads leave junction 17 without reading all 200000 of them. If your search asks that question once for each of the 100000 junctions, you have signed up for roughly 2×10¹⁰ reads, and a judge that gives you two seconds cuts you off after about one percent of the work. The cure is not a cleverer search. It is storing the very same edges so that "the roads leaving 17" is already gathered in one place before the search starts.

Three encodings are in common use, and each makes a different question cheap. An adjacency list keeps, for every vertex u, a small growable array of the vertices you can step to from u, so listing the neighbours of u costs exactly deg(u) reads — deg(u), the degree of u, being the number of edges that touch it. An adjacency matrix is an n × n table of booleans where the cell in row u, column v is true exactly when that edge exists, so "is there a road from 17 to 4093?" is a single array read, but listing the neighbours of 17 means scanning all n cells of row 17 even if only three of them are true. An edge list is the raw pairs kept exactly as they arrived; it supports no lookup at all, and is the right choice only when the whole algorithm is one sorted sweep over every edge.

The input limits usually make the decision for you, so read them first. At n = 10⁵ a matrix wants 10¹⁰ cells, which is ten gigabytes even at one byte per cell, so it cannot be allocated at all; the adjacency list for the same graph stores n + 2m integers, about half a million of them for m = 2×10⁵ undirected edges, which is a few megabytes. At n = 400 the matrix is only 160000 cells and the constant-time edge test becomes worth paying for. The word that names the split is sparse: a graph is sparse when the edge count m grows roughly like n rather than like n², and essentially every graph a contest hands you is sparse.

Two problems come from the statement rather than from the algorithm, and both cause more wrong answers on easy graph tasks than the algorithms do. First, judges usually number vertices from 1 to n while Java arrays start at 0, so either allocate n + 1 slots and leave slot 0 unused, or subtract one from every label as you read it — choose one convention and never mix them, because half-converted input either throws an ArrayIndexOutOfBoundsException at index n or leaves a phantom vertex 0 that no edge ever touches. Second, when the statement says the roads are two-way, the pair u v has to be inserted twice, once into the list of u and once into the list of v; a single insert is the usual reason a perfectly correct search reports that half the map is unreachable.

Store the graph so that the question your algorithm asks most often is the cheap one. Nearly every algorithm in this module walks the neighbours of a vertex, which is why the adjacency list — one array of neighbours per vertex — is the default encoding, and why the matrix only earns its n² cells when n is a few hundred and you keep asking whether one specific pair is joined.

Recognise this pattern

Say yes when you see

  • Input is n and m pairs (u, v), possibly weighted
  • You will iterate every neighbour of a vertex (BFS, DFS, Dijkstra)
  • You need O(1) "is this edge present?" (Floyd, dense DP)
  • The graph is undirected and you must add both directions yourself
  • Nodes arrive 1-indexed from the judge and your arrays are 0-indexed

Not this pattern when

  • The graph is an implicit grid — do not materialise n² adjacency lists
  • You only need to sort the edges once (Kruskal) — keep an edge list
  • The structure is a tree given as parent pointers — that already is the encoding
  • You need range queries on a path — that is a decomposition, not a representation

Constraint tell: n, m ≤ 2×10⁵ is the usual sparse-graph signature and it forces an adjacency list: an n × n matrix would ask for 4×10¹⁰ cells and cannot be allocated. When the statement instead gives n ≤ 400, the matrix fits in a couple of megabytes and the constant-time edge test becomes the reason to pick it. Store vertex ids as int; store path-weight sums as long once a weight can reach 10⁹.

Core idea and the invariant

The default encoding is an adjacency list: an outer list of length n whose slot u holds a growable list of the vertices you can step to from u. You start with n empty inner lists, then for each input pair (u, v) you run g.get(u).add(v). If the statement says the roads are two-way you immediately run g.get(v).add(u) as well, in the same loop body, because a later walk from v has no other way to discover that edge. A weighted edge stores a small pair int[]{v, w} (or a tiny Edge type) instead of a bare integer, so the weight travels with the neighbour and Dijkstra never has to look it up elsewhere.

The other two encodings exist for different questions. An adjacency matrix is an n × n table, boolean[][] for presence or int[][] with a huge sentinel off the edge, and the cell g[u][v] answers "is this pair joined?" in one read. An edge list is just the raw triples kept in an array so you can sort them once, which is what Kruskal needs and what a neighbour-walk does not. Two Java habits sit next to the choice of encoding. If the judge numbers vertices from 1 to n, allocate n + 1 slots and leave slot 0 unused rather than mixing conversions. And never write new ArrayList[n]: loop g.add(new ArrayList<>()) so every slot is a real list before the first insert. A grid stays implicit: from a cell (r, c) you try four deltas and reject any neighbour that walks off the board, without ever allocating RC lists.

Walk the five-node sample that the visual uses. The edges arrive as 0-1, 0-2, 1-2, 1-3, 2-4, all two-way. After the first insert the lists are g[0]=[1] and g[1]=[0]. After 0-2 you have g[0]=[1,2] and g[2]=[0]. The triangle closes with 1-2, then 1-3 hangs a leaf off 1, then 2-4 hangs a leaf off 2. The finished degrees are [2, 3, 3, 1, 1], which is exactly the number of times each vertex appears as an endpoint, and a walk that starts at 0 now sees 1 and 2 in a handful of reads instead of scanning all five input pairs again.

After the build, walking g.get(u) yields each outgoing neighbour exactly once (twice only if the input itself repeated that edge).

undirected (u, v) ⇒ two inserts; 1-based input ⇒ length n+1

In plain words, the list hanging off a vertex is the complete answer to "where can I step from here?", so a later search never has to reread the original pairs, and a missing reverse insert is indistinguishable from a missing road.

Undirected means two writes in the same loop

The pair u v is one road with two ends. If you insert it only into g[u], a perfectly correct BFS that starts at v reports that u is unreachable. Write both directions before you read the next line of input.

Grids never become adjacency lists

A 1000 × 1000 maze has a million cells and about four million possible steps. Generating the four neighbours from (r, c) with a pair of delta arrays costs a few arithmetic operations and no extra heap objects.

Algorithm

  1. Read n and m, then pick the encoding from those two numbers. A list is the default once n is in the tens of thousands, because an n × n table cannot be allocated; a matrix earns its keep only when n is a few hundred and you will ask "is this pair an edge?" many times.
  2. Allocate n empty neighbour lists, or n+1 if the judge numbers from 1. Leaving slot 0 unused is cheaper than mixing conversions later, and every later index into g then matches the printed label.
  3. For each edge (u, v[, w]), write v into g[u], and if the graph is undirected write u into g[v] in the same body. The reverse insert is what makes a walk starting at v able to see u; forgetting it is the usual reason half the map looks unreachable.
  4. Pick one 1-based convention and never mix it. Either allocate length n+1 or subtract one from every label as you read it, because a half-converted vertex either throws at index n or sits in slot 0 as a ghost nobody reaches.
  5. Leave grids implicit: from (r, c) try four or eight deltas and reject anything off the board. Materialising RC lists for a maze spends memory and object headers on neighbours you can compute in a few additions.
  6. If the algorithm only sorts the edges once, keep an int[][] edge list and skip the adjacency structure. Kruskal never asks for the neighbours of a vertex, so building lists is wasted work on that page.

Java implementation

JavaMatrixBuild.java
public class MatrixBuild {
        public static void main(String[] args) {
            int n = 5;
            boolean[][] g = new boolean[n][n];
            int[][] e = {{0,1},{0,2},{1,2},{1,3},{2,4}};
            for (int[] x : e) { g[x[0]][x[1]] = g[x[1]][x[0]] = true; }
            int deg1 = 0;
            for (int v = 0; v < n; v++) if (g[1][v]) deg1++;
            System.out.println(deg1);
        }
        // Input : 5-node sample, undirected
        // Output: 3
    }
JavaAdjList.java
import java.util.ArrayList;
    import java.util.List;
    
    public class AdjList {
        static List<List<Integer>> build(int n, int[][] edges, boolean undirected) {
            List<List<Integer>> g = new ArrayList<>();
            for (int i = 0; i < n; i++) g.add(new ArrayList<>());
            for (int[] e : edges) {
                g.get(e[0]).add(e[1]);
                if (undirected) g.get(e[1]).add(e[0]);
            }
            return g;
        }
        public static void main(String[] args) {
            int[][] e = {{0,1},{0,2},{1,2},{1,3},{2,4}};
            List<List<Integer>> g = build(5, e, true);
            System.out.println(g.get(1));
            System.out.println(g.get(4));
        }
        // Input : undirected edges 0-1,0-2,1-2,1-3,2-4
        // Output: [0, 2, 3]
        //         [2]
    }
JavaWeightedList.java
import java.util.ArrayList;
    import java.util.List;
    
    public class WeightedList {
        static List<List<int[]>> build(int n, int[][] edges) {
            List<List<int[]>> g = new ArrayList<>();
            for (int i = 0; i < n; i++) g.add(new ArrayList<>());
            for (int[] e : edges) {
                g.get(e[0]).add(new int[] {e[1], e[2]});
                g.get(e[1]).add(new int[] {e[0], e[2]});
            }
            return g;
        }
        public static void main(String[] args) {
            int[][] e = {{0,1,4},{1,3,1},{0,2,2},{2,4,7}};
            var g = build(5, e);
            for (int[] x : g.get(0)) System.out.print(x[0] + ":" + x[1] + " ");
            System.out.println();
        }
        // Input : weighted undirected 0-1:4, 1-3:1, 0-2:2, 2-4:7
        // Output: 1:4 2:2
    }

Complexity

Time O(n + m) to build a list; O(n²) a matrix Space O(n + m) list; O(n²) matrix

Building a list writes each directed edge once and each undirected edge twice, so the number of stored integers is n list headers plus a constant times m. Walking every neighbour of every vertex then costs one scan of those stored integers, which is n + 2m reads on an undirected graph.

list: S = n + Θ(m); matrix: S = n² regardless of m

A matrix always occupies n² cells, about 10¹⁰ at n = 10⁵, which is why it is illegal at the usual limits. Listing the neighbours of one vertex on a matrix scans a whole row of n cells even if only three are true, so Dijkstra on a matrix is O(n²) even without a heap. At n = 400 that is 160000 cells and the constant-time edge test is the thing you are buying.

Edge cases and pitfalls

  • Forgetting the reverse edge
    The input says the roads are two-way, but the loop only writes v into g[u]. A later BFS that starts at v never sees u, so a correct search reports that half the map is unreachable.
    In the same loop body write both directions for undirected input, and write once only when the statement says the edges are directed. A two-line print of g.get(u) and g.get(v) after the first edge catches it.
  • 1-based vs 0-based
    The judge prints vertices 1..n and the array has length n, so the largest label throws ArrayIndexOutOfBounds, or you leave a phantom vertex 0 that no edge ever touches.
    Allocate n+1 and ignore slot 0, or subtract one from every label as you read it. Pick one convention and use it in every later index, including the answer you print.
  • new ArrayList[n] generic array
    The generic-array warning is easy to suppress and then forget to fill each slot, so the first g[u].add throws a NullPointerException that looks like a graph bug.
    Build a List of lists and loop g.add(new ArrayList<>()) so every slot is a real list before the first insert. That also avoids the unchecked warning.
  • Materialising a grid graph
    A maze with R rows and C columns is turned into RC vertices and 4RC allocated edges. The object headers alone can cost tens of megabytes and a constant-factor timeout.
    Keep the grid as the grid. From (r, c) add the four deltas, reject anything off the board or blocked, and never build an adjacency list for a maze.
  • Self-loops and multi-edges
    A test that says "m = n-1 so it is a tree" is wrong if the input allowed a self-loop or a repeated pair, because those inflate the edge count without connecting a new vertex.
    Read whether the statement allows loops and parallel edges. Skip u==v when they are noise, and treat a second copy of u-v as a multi-edge if the problem cares about multiplicity.

Interview follow-ups

When is a matrix smaller than a list?

When the graph is dense, meaning m is on the order of n²/2, a boolean matrix is n² bits or bytes and a list of Integer objects is much fatter per stored edge. At n = 400 the matrix is 160000 cells and usually wins. At n = 10⁵ the matrix cannot be allocated at all, so the question does not arise: you use a list because it is the only encoding that fits.

How do you test edge existence on a list quickly?

Membership on a list is O(deg(u)), which is fine when you only ever iterate neighbours. If you truly need a yes/no test, sort each neighbour list and binary search, or keep a HashSet of packed longs ((long)u << 32 | v). BFS and DFS never ask that question: they walk g.get(u) and do not probe arbitrary pairs.

Directed vs undirected in the rest of this module?

Every later page assumes you stored the directions the statement named. BFS, DFS and components walk whatever you inserted, so a missing reverse edge silently splits the graph. Cycle detection and bipartite tests are different algorithms on directed graphs, covered on their own page. In interviews, treat the graph as undirected unless the statement says otherwise.

Why not Map<Integer,List<Integer>>?

When vertices are already numbered 0..n-1, an ArrayList of lists is a direct index and has no hash overhead. A map is the right tool only when labels are sparse or are not integers at all: word-ladder strings, chess squares packed into ints, or a huge id space where only a few nodes appear. Convert those labels to 0..k-1 at the boundary if you can.

Recap

  • List is the default for sparse n,m ~ 1e5.
  • Matrix when n≤400 and you need O(1) edge tests.
  • Undirected means two writes in the same loop.
  • 1-indexed input: allocate n+1.
  • Do not materialise implicit graphs (grids, functional maps).
