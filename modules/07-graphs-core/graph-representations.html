Graph Representations

Pick the encoding before you pick the algorithm — adjacency list, matrix and edge list are not interchangeable, and the wrong one turns an O(n + m) walk into an O(n²) timeout.

Easy 22 min read Prerequisites: Complexity Analysis, Java for DSA graphs adjacency list adjacency matrix P0

Why this exists

Every graph algorithm is written against an encoding, not against a picture. The same four-node drawing becomes a list of neighbour arrays, an n × n boolean matrix, or a flat list of edges, and each of those answers a different question in constant time. Choosing the encoding is therefore the first algorithmic decision, not a bookkeeping detail you sort out after the idea is clear.

Interviews and contests punish the wrong choice immediately. Iterating neighbours of u is O(deg(u)) on a list and O(n) on a matrix. Testing whether (u, v) exists is the opposite. On n = 10⁵, m = 10⁵ a matrix is a memory error before it is a timeout; on n = 400 a matrix is the faster, simpler structure. The constraint line tells you which world you are in.

A second, quieter reason this page exists: off-by-one indexing, forgotten reverse edges, and mixing 0-based code with 1-based input account for more wrong answers on easy graph problems than the algorithms themselves. Get the encoding mechanical, then BFS and DFS are twenty lines.

An adjacency list is the default because most graphs you meet are sparse (m = O(n) or O(n log n)). Reach for a matrix only when n is a few hundred and you need O(1) edge tests or dense all-pairs work.

Recognise this pattern

Say yes when you see

  • The input is n and a list of m pairs (u, v), possibly with a weight
  • You will iterate every neighbour of a vertex many times (BFS, DFS, Dijkstra)
  • You need a constant-time "is this edge present?" test (Floyd-Warshall, some DP)
  • The graph is undirected and you must add both directions yourself
  • Nodes arrive 1-indexed from the judge and your arrays are 0-indexed

Not this pattern when

  • The "graph" is an implicit grid and moves are (dr, dc) — do not materialise n² adjacency lists
  • You only need to sort the edges once (Kruskal) — keep an edge list, skip the adjacency structure
  • The structure is a tree given as parent pointers — that already is the encoding
  • You need range queries on a path — that is a decomposition, not a representation choice

Constraint tell: n, m ≤ 2×10⁵ forces lists (n² memory dies). n ≤ 400 is the matrix signature. Always store vertices as int and weights as int or long if sums of weights can overflow.

Three encodings and when each wins

An adjacency list is an array of lists: g.get(u) holds every neighbour of u. Building it from an edge list is one pass. Walking the whole graph is O(n + m), because each edge is stored a constant number of times. This is the encoding every BFS, DFS, Dijkstra and 0-1 BFS on this module assumes.

An adjacency matrix is an n × n array where mat[u][v] is 1, a weight, or a sentinel. Edge tests and updates are O(1); iterating neighbours is always O(n). Memory is O(n²), which at n = 10⁵ is impossible and at n = 400 is a comfortable 160 000 cells.

An edge list is just the input: an array of (u, v, w). Kruskal and Bellman-Ford iterate edges, not vertices, so they want this form. Converting between the three is always linear in the size of the source.

The interview sentence

Default to an adjacency list of size n (or n + 1 if the input is 1-indexed). For every undirected edge (u, v) push v onto u and u onto v. Then every neighbour scan is for (int v : g.get(u)), and the whole graph costs O(n + m).

1-index the arrays, do not remap the input

If vertices arrive as 1..n, allocate n + 1 lists and ignore index 0. Remapping every edge to 0-based is an extra source of off-by-one bugs and saves nothing. The unused slot is one pointer.

Undirected means two writes

The single most common graph-building bug is adding (u, v) and forgetting (v, u). BFS then reports the graph as disconnected, and the sample that happens to start at the right end still passes. Write both pushes as a single habit, and write a directed-only path as an explicit if (undirected) so the intent is visible.

When the matrix is actually smaller

A list of ArrayList objects plus boxed Integers costs far more than 4 bytes per edge. On a dense graph m ≈ n²/2, a boolean matrix is both smaller and faster. Rule of thumb: if you would store more than about n/4 neighbours per vertex, consider a matrix.

The running example

Degrees and a neighbour walk of vertex 1

The array is the degree of each vertex. Stepping through it is how you verify the list was built correctly: the handshaking lemma says the sum of degrees is 2m.

Algorithm

  1. Read n and m and decide 0-based versus 1-based. If vertices are 1..n, allocate n + 1 slots.
  2. Allocate the structure. List: n empty ArrayLists. Matrix: new int[n][n] filled with 0 or a sentinel.
  3. For each of the m edges read u, v (and w if weighted).
  4. Insert the forward edge: g.get(u).add(v) or mat[u][v] = w.
  5. If undirected, insert the reverse in the same iteration. Never do it in a second pass — you will forget.
  6. Sanity-check: sum of list sizes equals m (directed) or 2m (undirected).
  7. Iterate with for (int v : g.get(u)), never with a nested loop over all n vertices unless you chose a matrix on purpose.

Java implementation

The default encoding. Weighted edges store a pair; unweighted store a bare int. The dry-run graph is built and printed.

JavaGraphList.java
import java.util.ArrayList;
    import java.util.List;
    
    public class GraphList {
    
        static List<List<Integer>> build(int n, int[][] edges, boolean undirected) {
            List<List<Integer>> g = new ArrayList<>();
            for (int i = 0; i < n; i++) {
                g.add(new ArrayList<>());
            }
            for (int[] e : edges) {
                int u = e[0], v = e[1];
                g.get(u).add(v);
                if (undirected) {
                    g.get(v).add(u);
                }
            }
            return g;
        }
    
        static int[] degrees(List<List<Integer>> g) {
            int n = g.size();
            int[] deg = new int[n];
            for (int u = 0; u < n; u++) {
                deg[u] = g.get(u).size();
            }
            return deg;
        }
    
        public static void main(String[] args) {
            int[][] edges = {{0, 1}, {0, 2}, {1, 2}, {1, 3}, {2, 3}};
            List<List<Integer>> g = build(4, edges, true);
            int[] deg = degrees(g);
            for (int u = 0; u < g.size(); u++) {
                System.out.println(u + ": " + g.get(u) + " deg=" + deg[u]);
            }
        }
        // Input : n=4, edges (0-1)(0-2)(1-2)(1-3)(2-3), undirected
        // Output: 0: [1, 2] deg=2
        //         1: [0, 2, 3] deg=3
        //         2: [0, 1, 3] deg=3
        //         3: [1, 2] deg=2
    }

Use this when n is small and you need O(1) edge tests. Sentinel 0 means missing; store a weight if the graph is weighted.

JavaGraphMatrix.java
public class GraphMatrix {
    
        static int[][] build(int n, int[][] edges, boolean undirected) {
            int[][] mat = new int[n][n];
            for (int[] e : edges) {
                int u = e[0], v = e[1];
                int w = e.length > 2 ? e[2] : 1;
                mat[u][v] = w;
                if (undirected) {
                    mat[v][u] = w;
                }
            }
            return mat;
        }
    
        static boolean hasEdge(int[][] mat, int u, int v) {
            return mat[u][v] != 0;
        }
    
        public static void main(String[] args) {
            int[][] edges = {{0, 1}, {0, 2}, {1, 2}, {1, 3}, {2, 3}};
            int[][] mat = build(4, edges, true);
            System.out.println("1-3? " + hasEdge(mat, 1, 3) + "  0-3? " + hasEdge(mat, 0, 3));
            System.out.print("row 1:");
            for (int v = 0; v < 4; v++) {
                System.out.print(" " + mat[1][v]);
            }
            System.out.println();
        }
        // Input : n=4, same five undirected edges
        // Output: 1-3? true  0-3? false
        //         row 1: 1 0 1 1
    }

Weighted list plus an edge-list copy. Copy this into a solution and delete the encoding you do not need.

JavaGraphTemplate.java
import java.util.ArrayList;
    import java.util.List;
    
    public class GraphTemplate {
    
        static final class Edge {
            final int to, w;
            Edge(int to, int w) { this.to = to; this.w = w; }
        }
    
        int n;
        List<List<Edge>> g;
        int[][] raw;                       // edge list kept for Kruskal / Bellman-Ford
    
        GraphTemplate(int n, int[][] edges, boolean undirected) {
            this.n = n;
            this.raw = edges;
            g = new ArrayList<>();
            for (int i = 0; i < n; i++) {
                g.add(new ArrayList<>());
            }
            for (int[] e : edges) {
                int u = e[0], v = e[1], w = e.length > 2 ? e[2] : 1;
                g.get(u).add(new Edge(v, w));
                if (undirected) {
                    g.get(v).add(new Edge(u, w));
                }
            }
        }
    
        public static void main(String[] args) {
            int[][] edges = {{0, 1, 2}, {0, 2, 5}, {1, 2, 1}, {1, 3, 4}, {2, 3, 1}};
            GraphTemplate gt = new GraphTemplate(4, edges, true);
            System.out.println("n=" + gt.n + " edges=" + gt.raw.length
                    + " deg(1)=" + gt.g.get(1).size());
        }
        // Input : n=4, five weighted undirected edges
        // Output: n=4 edges=5 deg(1)=3
    }

Complexity

Time O(n + m) to build a list; O(n²) to allocate a matrix Space O(n + m) list; O(n²) matrix

Each edge is stored a constant number of times in a list (once if directed, twice if undirected), so build and a full walk are both linear in the input size:

Tlist = Θ(n + m)

A matrix pays n² regardless of m. That is the right price only when you will look at a constant fraction of the cells, or when n is small enough that n² fits and O(1) edge tests matter.

Tmatrix neighbour scan = Θ(n) per vertex, Θ(n²) globally

Edge cases and pitfalls

  • Forgetting the reverse edge
    Inserting (u, v) only, on an undirected graph. BFS from one end reaches everyone; BFS from the other end reports a disconnected graph.
    Always write both pushes in the same loop body. Treat "directed" as the explicit special case, not the default.
  • 0-based arrays, 1-based input
    g.get(u) on a vertex labelled n throws, or vertex 0 is a phantom that you later iterate.
    Allocate n + 1 and ignore index 0, or subtract one from every id on the way in. Pick one convention per file and do not mix them.
  • Scanning all n vertices to find neighbours
    for (v = 0; v < n; v++) if (mat[u][v] == 1) inside BFS on a list problem with n = 10⁵. That is O(n²).
    If you built a list, iterate the list. The matrix scan is only legal when you chose a matrix because n is small.
  • Self-loops and multi-edges
    Assuming simple graphs. A self-loop in an undirected cycle check is a cycle of length 1; a multi-edge is a cycle of length 2. Some problems include both.
    Decide up front whether they count. If they do not, skip u == v and deduplicate, or use a matrix which naturally collapses multi-edges.
  • Storing weights as a parallel array of lists
    Two lists to and w that you must keep in lockstep. One missed add desynchronises them permanently.
    Store a small pair / inner class, or pack (to, w) into a long. One structure, one append.
  • Materialising an implicit graph
    Building adjacency lists for every cell of a 1000×1000 grid. That is a million lists and four million edges you can generate with four additions.
    Write a neighbours(r, c) helper that yields the legal moves. BFS never needs the lists to exist.

Interview follow-ups

When is a matrix faster than a list even on a sparse graph?

When the inner loop is an edge test, not a neighbour walk. Floyd-Warshall looks at every triple (k, i, j) and wants mat[i][j] in one array read. A list would turn each test into a scan. Also, when n ≤ 400 the matrix fits in cache and beats pointer-chasing ArrayLists.

How do I represent a graph that changes (edges inserted and deleted)?

Lists support insert in O(1) and delete in O(deg) unless you store iterators or a set. A matrix supports both in O(1). For fully-dynamic connectivity you need a much heavier structure; for "add a few edges then BFS" just append to the lists.

Should I use List<int[]> or a tiny static class for weighted edges?

A static class Edge { int to, w; } is clearer and not slower. int[]{to, w} allocates the same object and loses the names. Do not use ArrayList<Integer> pairs of lists.

What changes for a multigraph or a graph with self-loops?

Lists store them naturally: two entries for a multi-edge, one u in g.get(u) for a loop. A matrix collapses multi-edges unless you store a count. Cycle detection and Euler tours care; shortest paths usually do not (keep the minimum weight).

Hint for LC 547 — do not convert the matrix if you do not need to

The input is an adjacency matrix. DFS from an unvisited city i scans row i for 1s. Converting to a list first is correct and costs O(n²), which you pay anyway. The lesson: walk the encoding you were given unless another algorithm demands a different one.

Hint for CF 500A — a functional graph is already a list of length 1

Each portal i goes only to i + a[i]. You do not need ArrayLists. Walk from cell 1, jumping, until you pass t or the end. Representation insight: when out-degree is 1, an int[] next is the adjacency list.

Recap

  • Adjacency list is the default for sparse graphs and for every algorithm on the rest of this module.
  • Matrix when n is small and you need O(1) edge tests.
  • Undirected means two writes in the same loop body.
  • 1-indexed input: allocate n + 1 and ignore slot 0.
  • Do not materialise implicit graphs (grids, functional graphs, word-ladder vertices).
