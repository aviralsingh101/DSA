TreeMap / TreeSet Patterns

Java's red-black tree in a box: floor, ceiling, first/last and subMap turn "nearest key" and "live set of intervals" into O(log n) per operation.

Medium 26 min read Prerequisites: Heaps & Priority Queue, Java for DSA TreeMap TreeSet floor ceiling intervals P1

Why this exists

You must decide whether each new booking [s, e) overlaps any existing one. The first request [10, 20) is free; [15, 25) collides with it; [20, 30) only touches 20 and is legal on a half-open spec. Scanning every previous booking is correct and costs one pass per request. After n = 10⁵ bookings that is about 5×10⁹ comparisons, and the judge will cut you off. You need the nearest neighbour of s, not a scan.

A HashMap answers "is this exact key present?" and cannot tell you the next key to the left. A heap answers "what is the current min?" and cannot tell you the predecessor of an arbitrary value. A balanced binary search tree answers both: floor (greatest key ≤ x), ceiling (least key ≥ x), higher, lower, first, last, and a view of a key range. Java ships that tree as TreeMap / TreeSet. For calendar, store start → end; the predecessor and successor of the query start are the only two intervals that can conflict.

Sweep-line problems — covered points, skyline, running coverage of the number line — are the same tree with a running counter as the payload: put a +1 at each left endpoint and a -1 at each right, then walk the keys in order. This page is how you write the O(n log n) solution when a deque is too specialised and a heap is too weak. The Java API is the whole skill: floorKey versus lowerKey is closed versus open, and unboxing a null floor is the NPE that only fires on the minimum query.

HashMap is exact match. Heap is the current extreme. TreeMap is the nearest key and an ordered range. Floor, ceiling and subMap are the three methods that justify paying log n instead of hashing.

Recognise this pattern

Say yes when you see

  • "Closest element to x", "contains nearby almost-duplicate", "next interval that starts after t"
  • Booking / calendar: "does [s, e) overlap an existing booking?"
  • A live ordered set of values with insert, erase, and "what is the nearest"
  • Sweep line: events at coordinates, need the current min/max/count of active items
  • Sliding window that needs max and min and you would rather write a TreeMap than two deques

Not this pattern when

  • Exact-key lookup only → HashMap, faster and simpler
  • Only the current min or max, never a predecessor of an arbitrary value → a heap
  • Window maximum of a fixed array range → monotonic deque in O(n)
  • Static range min after build, no updates → sparse table, not a tree

Core idea and the invariant

TreeMap<K,V> is a red-black tree of keys — a self-balancing binary search tree, so every walk from the root to a leaf is O(log n). floorKey(x) is the greatest key ≤ x, or null if none exists. ceilingKey(x) is the least key ≥ x. lowerKey and higherKey are the strict versions. TreeSet is the same tree with dummy values. A null return means "no such key"; writing int f = set.floor(x) unboxes that null into a NullPointerException the first time x is smaller than every key.

Interval bookkeeping stores each booked interval as map.put(start, end) on the half-open range [start, end). To test a new [s, e), look up prev = floorKey(s) and next = ceilingKey(s). They overlap if prev exists and its end is strictly after s, or if next exists and starts strictly before e. Two lookups replace a scan of every booking. subMap is a live view of a key range, not a copy: mutating it mutates the tree.

Trace My Calendar on an empty map. Book [10, 20): both neighbours are null, so store 10 → 20. Book [15, 25): floor of 15 is 10 and that interval ends at 20, which is past 15, so reject. Book [20, 30): floor of 20 is still 10, but the end 20 is not strictly after 20, and there is no ceiling before 30, so the touch is legal and you store 20 → 30. Two probes, never a walk over the bookings you already accepted.

The map's keys are totally ordered. After every put / remove:

floor(x) = max { k in keys | k ≤ x } (or none)

For intervals stored as start → end, the only intervals that can overlap a query [s, e) are the predecessor of s and the successor of s. Checking those two is complete.

In plain words, the tree always knows the nearest key on the left and on the right of any query, and for a calendar those two neighbours are the only bookings that can collide with the new request. If a book ever scans the whole map, or a floor is unboxed without a null check, one half of that claim is already broken.

Algorithm

  1. Name the ordered key first so the tree is not built on the wrong field. Decide whether you are ordering values, start times, or coordinates; everything else is a payload.
  2. Pick TreeSet versus TreeMap from the payload. A set is enough when you only need presence and neighbours; a map is required when each key carries an end time, a count, or a delta.
  3. Choose floor/ceiling versus lower/higher from whether an exact match counts as a neighbour. Assign the result to Integer or Long and null-check before unboxing, because "no such key" is a real answer.
  4. For intervals, store [s, e) as start to end and probe floorKey(s) and ceilingKey(s) only. Those two neighbours are the only bookings that can overlap the new request.
  5. For a window of values, keep a frequency TreeMap: merge +1 on enter, decrement and remove on leave, then lastKey() - firstKey() is max minus min without scanning the window.
  6. For a sweep, put coordinate deltas in the tree first, then iterate entrySet in key order. Building the map and walking it are two separate passes so you never mutate while iterating.
  7. Do not iterate the whole map to find a neighbour. That walk is linear and throws away the reason you paid for a tree. Floor and ceiling are the O(log n) API.

Java implementation

Store intervals in a list and scan them all. Correct, O(n) per book.

JavaCalendarBrute.java
import java.util.ArrayList;
    import java.util.List;
    
    public class CalendarBrute {
        static class Cal {
            final List<int[]> a = new ArrayList<>();
            boolean book(int s, int e) {
                for (int[] iv : a) {
                    if (s < iv[1] && iv[0] < e) return false;
                }
                a.add(new int[] {s, e});
                return true;
            }
        }
    
        public static void main(String[] args) {
            Cal c = new Cal();
            System.out.println(c.book(10, 20));
            System.out.println(c.book(15, 25));
            System.out.println(c.book(20, 30));
        }
        // Input : book [10,20), [15,25), [20,30)
        // Output: true
        //         false
        //         true
    }

Two probes per book. The same skeleton is My Calendar, Exam Room, and most range-conflict questions.

JavaCalendarTree.java
import java.util.TreeMap;
    
    public class CalendarTree {
        static class MyCalendar {
            final TreeMap<Integer, Integer> map = new TreeMap<>();
    
            boolean book(int s, int e) {
                Integer prev = map.floorKey(s);
                if (prev != null && map.get(prev) > s) return false;
                Integer next = map.ceilingKey(s);
                if (next != null && next < e) return false;
                map.put(s, e);
                return true;
            }
        }
    
        public static void main(String[] args) {
            MyCalendar c = new MyCalendar();
            System.out.println(c.book(10, 20));
            System.out.println(c.book(15, 25));
            System.out.println(c.book(20, 30));
            System.out.println(c.book(0, 10));
        }
        // Input : [10,20), [15,25), [20,30), [0,10)
        // Output: true
        //         false
        //         true
        //         true
    }

Floor/ceiling on a TreeSet (contains-nearby-duplicate) and a frequency TreeMap for a window's max-min.

JavaTreeMapTemplates.java
import java.util.TreeMap;
    import java.util.TreeSet;
    
    public class TreeMapTemplates {
        static boolean nearbyAlmostDuplicate(int[] a, int k, int t) {
            TreeSet<Long> set = new TreeSet<>();
            for (int i = 0; i < a.length; i++) {
                long x = a[i];
                Long ceil = set.ceiling(x);
                if (ceil != null && ceil - x <= t) return true;
                Long floor = set.floor(x);
                if (floor != null && x - floor <= t) return true;
                set.add(x);
                if (i >= k) set.remove((long) a[i - k]);
            }
            return false;
        }
    
        static int longestSubarray(int[] a, int limit) {
            TreeMap<Integer, Integer> freq = new TreeMap<>();
            int l = 0, best = 0;
            for (int r = 0; r < a.length; r++) {
                freq.merge(a[r], 1, Integer::sum);
                while (freq.lastKey() - freq.firstKey() > limit) {
                    if (freq.merge(a[l], -1, Integer::sum) == 0) freq.remove(a[l]);
                    l++;
                }
                best = Math.max(best, r - l + 1);
            }
            return best;
        }
    
        public static void main(String[] args) {
            System.out.println(nearbyAlmostDuplicate(new int[] {1, 2, 3, 1}, 3, 0));
            System.out.println(nearbyAlmostDuplicate(new int[] {1, 5, 9, 1, 5, 9}, 2, 3));
            System.out.println(longestSubarray(new int[] {8, 2, 4, 7}, 4));
            System.out.println(longestSubarray(new int[] {10, 1, 2, 4, 7, 2}, 5));
        }
        // Input : nearby ([1,2,3,1], k=3, t=0) and ([1,5,9,1,5,9], k=2, t=3)
        //         longest ([8,2,4,7], 4) and ([10,1,2,4,7,2], 5)
        // Output: true
        //         false
        //         2
        //         4
    }

Complexity

Time O(log n) per insert / floor / ceiling; O(n log n) for n operations Space O(n) keys in the tree

A red-black tree of n keys has height O(log n). Each API call walks a root-to-leaf path:

T(n ops) = n · O(log n) = O(n log n)

At n = 10⁵ that is about 1.7×10⁶ node visits. The brute interval scan is O(n) per book and O(n²) total, around 5×10⁹ comparisons. Two TreeMap probes replace that scan. A window as a TreeMap of frequencies is O(n log n) versus O(n) for two deques, which is why you mention both and write the tree unless they push for linear.

Edge cases and pitfalls

  • Unboxing a null floor/ceiling
    int f = set.floor(x) throws when x is smaller than every key. It looks like a normal lookup, and the NPE often fires only on the minimum query after the sample passed.
    Assign to Integer or Long, null-check, then unbox. The same rule applies to floorKey and ceilingKey.
  • floor vs lower on a closed interval
    Using lowerKey(s) skips an interval that starts exactly at s, so a same-start booking is accepted. Inclusive conflict needs the key that equals s, not the one before it.
    Conflict with an interval that starts at s is a floor (inclusive). Stick to floor plus ceiling on the start.
  • Closed vs half-open overlap test
    Testing prev.end >= s on a half-open spec rejects a legal touch at the shared endpoint. [10, 20) and [20, 30) are allowed to meet at 20.
    LC 729 is [s, e), so overlap is end > s on the predecessor and next < e on the successor.
  • TreeSet.remove of duplicate values in a window
    A set cannot hold two equal values, so nearby-duplicate with t=0 silently drops one of a pair and later reports no duplicate.
    If duplicates of the values themselves matter, store indices or use a TreeMap of counts as a multiset.
  • Mutating a map while iterating entrySet
    Putting a new delta while walking entrySet throws ConcurrentModificationException, or silently skips an entry, because the tree's iterator is fail-fast.
    Build the whole delta map first, then iterate. Or snapshot keySet into an ArrayList before mutating.
  • Comparator inconsistent with equals
    A TreeMap with (a, b) -> a.x - b.x treats two objects with the same x as the same key, so the second silently overwrites the first. Subtraction also overflows.
    If keys can tie on the sort field, add a unique id as a tie-break. Never subtract ints to compare.

Interview follow-ups

floorKey vs lowerKey: which one for interval overlap?

You need the interval that starts at or before s, so floor (inclusive). If an interval starts exactly at s it overlaps [s, e) for any e > s. lowerKey would skip that same-start booking and accept a collision. Stick to floor plus ceiling on the start and ignore lower/higher for this pattern.

When do you prefer two deques over a TreeMap for max-min of a window?

When they want O(n) and the window is on an array you scan once. A TreeMap of frequencies is O(log n) per step and shorter to write. LC 1438 accepts both. Say both out loud, write the TreeMap unless they push for the linear bound, and switch to two monotonic deques if they do.

How does this relate to a policy-based tree on Codeforces?

TreeMap cannot answer "k-th key" in log n without walking, because Java's red-black tree does not store subtree sizes. headMap(x).size() is O(n), not logarithmic. Use a Fenwick tree or segment tree on compressed keys, or accept a linear scan for order statistics. Policy-based trees in C++ are the structure Java is missing here.

Can a TreeMap replace a heap?

Yes, with worse constants: firstKey is min, pollFirstEntry is delete-min, and you also get floor, ceiling, and arbitrary delete in log n. Stay with PriorityQueue when you only ever need the extreme. A TreeMap of counts is still the cleanest multiset Java has, because a heap cannot delete an arbitrary key in log time.

Hint for CF 702C — one ceiling per city

Sort the tower positions (or put them in a TreeSet). For each city at x the nearest tower is min(x - floor(x), ceiling(x) - x), missing neighbour treated as infinity. The answer is the max over cities of that distance. Binary search on a static array is the same algorithm without a tree.

Hint for CF 1000C — coverage by how many segments

Each segment [L, R] contributes +1 at L and -1 at R+1 (closed integer segments). Walk adjacent keys of the TreeMap: between coord and nextCoord there are (next-coord) points with the current coverage. Off-by-one on R vs R+1 is the whole problem.

Recap

  • Floor ≤ x ≤ ceiling; lower < x < higher. Null-check before unboxing.
  • Intervals: TreeMap start → end, two probes, half-open unless the spec says otherwise.
  • Window bag: TreeMap of frequencies; firstKey/lastKey are min and max.
  • Sweep: TreeMap of coordinate deltas, then iterate in key order.
  • Not a heap and not a HashMap: you are here because you need a nearest key or an ordered range.
