Queues & Monotonic Deque

A deque drops candidates from both ends: the front expires by age, the back is dominated by a better newer value — sliding-window maximum in O(n).

Medium 22 min read Prerequisites: Stacks & Monotonic Stack, Sliding Window queue deque sliding window max monotonic deque P0

Why this exists

A queue is FIFO: BFS, moving averages, "first task that arrived". The structure that actually wins interviews is the monotonic deque: indices of candidates for the window maximum (or minimum), increasing in index and decreasing in value. The front is the answer for the current window; the back is where new arrivals land after popping everything they dominate.

Without the deque, window-max is O(nk) or O(n log k) with a heap that cannot cheaply delete the element that just left. The deque deletes expired indices from the front in O(1) and dominated indices from the back in amortised O(1). Same bound as a monotonic stack, plus age.

The same deque solves shortest subarray with sum ≥ k (on prefixes), jump game VI, and constrained subsequence sum. Structural queues (recent calls, circular queue, implement queue with stacks) are a different, easier family.

The front of a decreasing deque is the max of the live window because everything older and smaller has been popped from the back, and everything too old has been popped from the front.

Recognise this pattern

Say yes when you see

  • "Maximum / minimum of every window of size k"
  • "Longest subarray whose max-min ≤ limit" (two deques, or one TreeMap)
  • "Shortest subarray with sum ≥ k" allowing negatives (prefix + increasing deque)
  • Jump game VI / constrained subsequence: dp[i] = a[i] + max of a window of dp
  • BFS, moving average, recent-calls queue (structural FIFO)

Not this pattern when

  • Next greater with no window expiry → monotonic stack (one end only)
  • k-th of a window, not max/min → two heaps or a policy-based tree
  • Need floor/ceiling of arbitrary keys → TreeMap
  • Single running max with no expiry → a variable, not a deque

Core idea and the invariant

Maintain indices with a[dq] strictly decreasing. For each i: pop back while a[dq.peekLast()] ≤ a[i] (i is better and newer); push i; pop front while dq.peekFirst() ≤ i-k (expired). The answer for window ending at i is a[dq.peekFirst()]. Push after cleaning so the new index is live.

For prefix-minima (shortest subarray sum ≥ k): the deque holds increasing prefixes. If P[i] - P[dq.front] ≥ k, the front can be popped as a candidate start (later starts only make the subarray shorter once this one already works). Negatives make sliding-window-on-values illegal; the deque on prefixes is the repair.

The deque is increasing in index and decreasing in value (for window max):

idx0 < idx1 < … and a[idx0] ≥ a[idx1] ≥ … , all idx in (i-k, i]

Interview sentence: "Front is the max of the live window; back pops everyone the new arrival dominates."

Queue vs monotonic deque

Algorithm

  1. Window max: decreasing deque of indices.
  2. For each i: pop back while a[back] ≤ a[i].
  3. Push i. Then pop front while front ≤ i-k.
  4. Record a[peekFirst] once i ≥ k-1.
  5. Prefix variant: increasing deque of P[i]; pop front when P[i]-P[front] ≥ k.
  6. BFS: addLast / pollFirst; never mix with peekLast unless it is a 0-1 BFS.
  7. ArrayDeque, 4-space, long for prefix sums.

Java implementation

Scan each window. O(nk). Fine for teaching, dead at n=1e5, k=n/2.

JavaWindowBrute.java
import java.util.Arrays;
    
    public class WindowBrute {
        static int[] maxSliding(int[] a, int k) {
            int n = a.length;
            int[] ans = new int[n - k + 1];
            for (int i = 0; i + k <= n; i++) {
                int m = a[i];
                for (int j = i + 1; j < i + k; j++) {
                    m = Math.max(m, a[j]);
                }
                ans[i] = m;
            }
            return ans;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(
                maxSliding(new int[] {1, 3, -1, -3, 5, 3, 6, 7}, 3)));
        }
        // Input : [1,3,-1,-3,5,3,6,7], k=3
        // Output: [3, 3, 5, 5, 6, 7]
    }

Sliding-window max in O(n). Front is the answer; back is the insertion end.

JavaMonoDeque.java
import java.util.ArrayDeque;
    import java.util.Arrays;
    
    public class MonoDeque {
        static int[] maxSliding(int[] a, int k) {
            int n = a.length;
            int[] ans = new int[n - k + 1];
            ArrayDeque<Integer> dq = new ArrayDeque<>();
            for (int i = 0; i < n; i++) {
                while (!dq.isEmpty() && a[dq.peekLast()] <= a[i]) {
                    dq.pollLast();
                }
                dq.addLast(i);
                if (dq.peekFirst() <= i - k) {
                    dq.pollFirst();
                }
                if (i >= k - 1) {
                    ans[i - k + 1] = a[dq.peekFirst()];
                }
            }
            return ans;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(
                maxSliding(new int[] {1, 3, -1, -3, 5, 3, 6, 7}, 3)));
        }
        // Input : [1, 3, -1, -3, 5, 3, 6, 7], k=3
        // Output: [3, 3, 5, 5, 6, 7]
    }

LC 862: increasing deque of prefix indices. Negatives make a plain window illegal.

JavaShortestSubarray.java
import java.util.ArrayDeque;
    
    public class ShortestSubarray {
        static int shortest(int[] a, int k) {
            int n = a.length;
            long[] p = new long[n + 1];
            for (int i = 0; i < n; i++) {
                p[i + 1] = p[i] + a[i];
            }
            int best = n + 1;
            ArrayDeque<Integer> dq = new ArrayDeque<>();
            for (int i = 0; i <= n; i++) {
                while (!dq.isEmpty() && p[i] - p[dq.peekFirst()] >= k) {
                    best = Math.min(best, i - dq.pollFirst());
                }
                while (!dq.isEmpty() && p[dq.peekLast()] >= p[i]) {
                    dq.pollLast();
                }
                dq.addLast(i);
            }
            return best <= n ? best : -1;
        }
    
        public static void main(String[] args) {
            System.out.println(shortest(new int[] {1}, 1));
            System.out.println(shortest(new int[] {1, 2}, 4));
            System.out.println(shortest(new int[] {2, -1, 2}, 3));
        }
        // Input : [1] k=1; [1,2] k=4; [2,-1,2] k=3
        // Output: 1
        //         -1
        //         3
    }

Complexity

Time O(n) amortised Space O(k) for a window of size k, O(n) worst case

Each index is pushed at most once and popped at most once from each end:

T(n) = Θ(n)

A heap of size k is O(n log k) and cannot delete the expired max without a lazy deletion map. The deque wins whenever you only need min or max, not k-th.

Edge cases and pitfalls

  • Popping the front with < instead of ≤ i-k
    An index exactly k ago stays and poisons the max.
    while peekFirst ≤ i-k (strictly outside the window of size k ending at i).
  • Using < instead of ≤ when popping the back
    Equal values pile up; the older equal expires later and you keep a stale index.
    Pop back on ≤ so the newest equal sits at the front when the older expires.
  • Recording the max before the window is full
    ans[0] written at i=0 for k=3.
    Only record when i ≥ k-1.
  • Sliding window on values when negatives exist
    Two pointers for sum≥k is wrong if a[i] can be negative.
    Prefix + increasing deque (LC 862), not a shrinkable positive window.
  • LinkedList as a deque
    Pointer chasing, extra objects. Correct but slow in Java.
    ArrayDeque. pollFirst/Last, peekFirst/Last, addFirst/Last.

Interview follow-ups

Why not a max-heap of the window?

You can, with lazy deletion of indices ≤ i-k when they appear at the top. It is O(n log n) and more code. The deque is linear and the intended answer.

Can the deque store values instead of indices?

Only if you also store the index beside the value (a pair). Age tests need the index. A value-only deque cannot tell whether the front has left the window.

Shortest subarray with sum ≥ k and all positives?

Then a two-pointer sliding window on the array itself is enough (prefix is increasing). The deque is what you reach for once negatives appear.

Implement a queue with two stacks?

Inbox stack for push, outbox stack for pop: dump inbox into outbox when outbox is empty. Amortised O(1). ArrayDeque already is a queue; this is the design question.

Hint for LC 862 — two pops, two reasons

Front pop: P[r]-P[front] ≥ k, that left end is used up (later r only makes it longer). Back pop: P[r] ≤ P[back], a later smaller-or-equal prefix is a strictly better left end. After both, push r. Miss either pop and you TLE or return a longer answer.

Hint for LC 1696 — DP with a sliding max

dp[i] = a[i] + max(dp[i-k..i-1]). That inner max is window-maximum on the dp array: decreasing deque of indices, expire i-k. Do not scan k previous states.

Recap

  • Front expires by age, back by domination.
  • Decreasing deque for window max; increasing for min / prefix.
  • Store indices, pop back on ≤ so equals do not stale.
  • Negatives + range sum → prefix deque, not a two-pointer window.
  • ArrayDeque is both the queue and the deque.
