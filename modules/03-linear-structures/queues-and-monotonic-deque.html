Queues & Monotonic Deque

A deque drops candidates from both ends: the front expires by age, the back is dominated by a better newer value — sliding-window maximum in O(n).

Medium 26 min read Prerequisites: Stacks & Monotonic Stack, Sliding Window queue deque sliding window max monotonic deque P0

Why this exists

You are given the array [1, 3, -1, -3, 5, 3, 6, 7] and asked for the maximum of every contiguous window of length 3. The first window [1, 3, -1] answers 3; the next [3, -1, -3] is still 3; then [-1, -3, 5] jumps to 5. The program that writes itself scans each window from scratch. On five or eight numbers that is instant. On n = 10⁵ and a window around n/2 that is about 2.5×10⁹ comparisons, and the judge's one-second budget is gone long before you finish.

A heap of the live window looks smarter because peek is the max, but Java's PriorityQueue cannot delete the element that just slid out of the left edge in logarithmic time. You either scan the heap — back to quadratic — or leave the stale value in and skip it later, which is n log n with extra bookkeeping. The wasted work has a shape: once a newer, larger-or-equal value arrives, every older and smaller neighbour is dominated — permanently useless as a window maximum — and can be thrown away forever.

A deque is a double-ended queue: you may add or remove from either end, unlike a stack (one end only) or a plain FIFO queue (add back, remove front). Keep a deque of indices of still-useful candidates, increasing in index from front to back and decreasing in value. That never-turning-around ordering is what monotonic means here. At any instant the front is the maximum of the current window, because everything older and smaller has already been popped from the back, and everything too old has already been popped from the front. An index is pushed once and popped at most once from each end, so the nested loops are still linear.

In a real statement the signal is n ≤ 10⁵ sitting next to "maximum of every window of size k", or a DP recurrence whose inner max is itself a sliding window. The same deque, flipped so values increase, solves shortest subarray with sum ≥ k on prefix sums, because negatives make a two-pointer shrink illegal. Structural queues — recent calls, circular buffers, implement a queue with two stacks — are a different and easier family: they never compare values, they only remember insertion order.

At any instant the deque holds only live candidates, oldest at the front and newest at the back, values decreasing so the front is the window max. An index leaves the back because a newer arrival dominates it, or the front because it aged out of the window. Each index is pushed once and popped once, so the nested loops stay linear.

Recognise this pattern

Say yes when you see

  • "Maximum / minimum of every window of size k"
  • "Longest subarray whose max-min ≤ limit" (two deques, or one TreeMap)
  • "Shortest subarray with sum ≥ k" allowing negatives (prefix + increasing deque)
  • Jump game VI / constrained subsequence: dp[i] = a[i] + max of a window of dp
  • BFS, moving average, recent-calls queue (structural FIFO)

Not this pattern when

  • Next greater with no window expiry → monotonic stack (one end only)
  • k-th of a window, not max/min → two heaps or a policy-based tree
  • Need floor/ceiling of arbitrary keys → TreeMap
  • Single running max with no expiry → a variable, not a deque

Core idea and the invariant

The container is an ArrayDeque<Integer> called dq, and it holds indices, never values. At any instant during the scan, dq contains exactly the live candidates for the window ending at the current index i: their indices increase from front to back, and the values a[dq] decrease, so the front is the current maximum. An index is popped from the back when a newer arrival is at least as large — it can never be the answer for any later window that also contains the newcomer. An index is popped from the front when it has aged out of the window of size k, because it is no longer a legal candidate even if it is still the biggest number you have seen.

The scan is a single loop over i from 0 to n-1. Before pushing i, pop the back while a[dq.peekLast()] ≤ a[i], because i is both larger-or-equal and newer. Then push i. Then pop the front while dq.peekFirst() ≤ i-k, because that index sits strictly outside the window ending at i. Once i ≥ k-1 the window is full, and the answer is a[dq.peekFirst()]. The inner loops look nested and dangerous; they are not, because each index enters once and leaves at most once from each end — the same amortised argument as the monotonic stack, plus an age test at the front.

Trace [1, 3, -1, -3, 5, 3, 6, 7] with k = 3. At i = 0 the deque is [0]. At i = 1 the value 3 beats 1, so index 0 pops from the back and dq = [1]. At i = 2 the value -1 loses to 3, so it sits at the back: [1, 2], and the first full window answers 3. At i = 3 the value -3 sits down: [1, 2, 3]; front 1 is still inside (1 > 3-3). At i = 4 the value 5 dominates everything still on the deque, so -3, -1 and 3 all pop from the back, and front 1 also expires (1 ≤ 4-3); dq becomes [4] and the answer is 5. The remaining windows answer 5, then 6, then 7.

The deque holds live candidates, increasing in index and decreasing in value (for window max). At the top of every iteration:

idx0 < idx1 < … and a[idx0] ≥ a[idx1] ≥ … , all idx in (i-k, i]

In plain words, the front is the maximum of the current window, the back is where the newest arrival lands after kicking off everyone it dominates, and any index that has left either end is finished: it will never be a candidate again. If a pop ever happens without one of those two reasons, or a push ever leaves a smaller value in front of a larger one, the claim is broken and the output will be wrong.

Interview sentence: "Front is the max of the live window; back pops everyone the new arrival dominates."

Queue vs monotonic deque

Algorithm

  1. Name a decreasing deque of indices for window maximum, because the front must stay the largest live value and the back is the only place a new arrival is allowed to land.
  2. For each index i, pop the back first while a[back] ≤ a[i]. Those older values can never win a later window that also contains i, so keeping them would only waste space and poison the front later.
  3. Push i, then pop the front by age while front ≤ i-k. The new index is now live, and anything that has slid out of the window of size k must leave even if it is still the biggest number you have seen.
  4. Record the front only once the window is full, that is when i ≥ k-1. Writing earlier invents a short prefix window the statement did not ask for.
  5. For shortest subarray with sum ≥ k, flip the deque to increasing prefixes. Pop the front when P[i] - P[front] ≥ k because that start already works and a later start can only make the same end shorter.
  6. Keep structural BFS on a plain FIFO: addLast / pollFirst only. Mixing in peekLast is reserved for 0-1 BFS, not for a monotonic window.
  7. Use ArrayDeque and long prefix sums so the structure is contiguous in memory and a sum of 10⁵ values near 10⁹ does not wrap a Java int before you compare it to k.

Java implementation

Scan each window. O(nk). Fine for teaching, dead at n=1e5, k=n/2.

JavaWindowBrute.java
import java.util.Arrays;
    
    public class WindowBrute {
        static int[] maxSliding(int[] a, int k) {
            int n = a.length;
            int[] ans = new int[n - k + 1];
            for (int i = 0; i + k <= n; i++) {
                int m = a[i];
                for (int j = i + 1; j < i + k; j++) {
                    m = Math.max(m, a[j]);
                }
                ans[i] = m;
            }
            return ans;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(
                maxSliding(new int[] {1, 3, -1, -3, 5, 3, 6, 7}, 3)));
        }
        // Input : [1,3,-1,-3,5,3,6,7], k=3
        // Output: [3, 3, 5, 5, 6, 7]
    }

Sliding-window max in O(n). Front is the answer; back is the insertion end.

JavaMonoDeque.java
import java.util.ArrayDeque;
    import java.util.Arrays;
    
    public class MonoDeque {
        static int[] maxSliding(int[] a, int k) {
            int n = a.length;
            int[] ans = new int[n - k + 1];
            ArrayDeque<Integer> dq = new ArrayDeque<>();
            for (int i = 0; i < n; i++) {
                while (!dq.isEmpty() && a[dq.peekLast()] <= a[i]) {
                    dq.pollLast();
                }
                dq.addLast(i);
                if (dq.peekFirst() <= i - k) {
                    dq.pollFirst();
                }
                if (i >= k - 1) {
                    ans[i - k + 1] = a[dq.peekFirst()];
                }
            }
            return ans;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(
                maxSliding(new int[] {1, 3, -1, -3, 5, 3, 6, 7}, 3)));
        }
        // Input : [1, 3, -1, -3, 5, 3, 6, 7], k=3
        // Output: [3, 3, 5, 5, 6, 7]
    }

LC 862: increasing deque of prefix indices. Negatives make a plain window illegal.

JavaShortestSubarray.java
import java.util.ArrayDeque;
    
    public class ShortestSubarray {
        static int shortest(int[] a, int k) {
            int n = a.length;
            long[] p = new long[n + 1];
            for (int i = 0; i < n; i++) {
                p[i + 1] = p[i] + a[i];
            }
            int best = n + 1;
            ArrayDeque<Integer> dq = new ArrayDeque<>();
            for (int i = 0; i <= n; i++) {
                while (!dq.isEmpty() && p[i] - p[dq.peekFirst()] >= k) {
                    best = Math.min(best, i - dq.pollFirst());
                }
                while (!dq.isEmpty() && p[dq.peekLast()] >= p[i]) {
                    dq.pollLast();
                }
                dq.addLast(i);
            }
            return best <= n ? best : -1;
        }
    
        public static void main(String[] args) {
            System.out.println(shortest(new int[] {1}, 1));
            System.out.println(shortest(new int[] {1, 2}, 4));
            System.out.println(shortest(new int[] {2, -1, 2}, 3));
        }
        // Input : [1] k=1; [1,2] k=4; [2,-1,2] k=3
        // Output: 1
        //         -1
        //         3
    }

Complexity

Time O(n) amortised Space O(k) for a window of size k, O(n) worst case

Each index is pushed at most once and popped at most once from each end:

T(n) = n pushes + P_back + P_front, each P ≤ n, so T(n) = Θ(n)

The nested loops are therefore not a hidden quadratic: one arrival may drain the whole back, but those indices never return. A heap of size k is O(n log k) and cannot delete the expired max without a lazy-deletion map. At n = 10⁵ the deque is about 3×10⁵ operations; the heap is closer to 1.7×10⁶. The deque wins whenever you only need min or max, not the k-th.

Edge cases and pitfalls

  • Popping the front with < instead of ≤ i-k
    An index exactly k ago stays on the front and poisons every later max. It looks correct because the off-by-one is still inside a slightly larger window than the spec asked for.
    Pop while peekFirst ≤ i-k, so anything strictly outside the window of size k ending at i is gone.
  • Using < instead of ≤ when popping the back
    Equal values pile up at the back; the older equal expires later and you keep a stale index as the front after the newer twin has already left.
    Pop the back on ≤ so the newest equal sits at the front when the older one expires.
  • Recording the max before the window is full
    ans[0] is written at i=0 when k=3, inventing a one-element window. The sample of n=k still passes, so the bug hides until a longer array arrives.
    Only record a[peekFirst] once i ≥ k-1, when the window ending at i actually has k elements.
  • Sliding window on values when negatives exist
    Two pointers for sum ≥ k look right from the positive-window lecture, but a negative in the middle means shrinking the left end can make the sum larger, not smaller.
    Build prefix sums and keep an increasing deque of prefix indices (LC 862), not a shrinkable window on the raw values.
  • LinkedList as a deque
    LinkedList works as a deque and the API looks identical, so the code is correct, but every node is a separate object and the judge's time limit is tighter than it looks.
    Use ArrayDeque with pollFirst/Last, peekFirst/Last, addFirst/Last. It is the contiguous Java deque and the one the judge expects.

Interview follow-ups

Why not a max-heap of the window?

You can, with lazy deletion of indices ≤ i-k when they appear at the top. That is correct and O(n log n), but it is more code and a worse bound. The deque is linear because each index is pushed once and popped once, and it is the answer an interviewer wants when the query is only min or max, not the k-th.

Can the deque store values instead of indices?

Only if you also store the index beside the value as a pair. The age test front ≤ i-k needs the position, and a value-only deque cannot tell whether the front has already left the window. Storing indices is the default: the value is one lookup away as a[dq.peekFirst()].

Shortest subarray with sum ≥ k and all positives?

Then a two-pointer sliding window on the array itself is enough, because every prefix is strictly increasing and shrinking the left end can only decrease the sum. The deque on prefixes is what you reach for once negatives appear, since a negative breaks that shrink-makes-smaller assumption.

Implement a queue with two stacks?

Use an inbox stack for push and an outbox stack for pop: dump the whole inbox into the outbox only when the outbox is empty, so each element moves at most twice. That is amortised O(1) per operation. ArrayDeque already is a queue; this trick is the design-question version, not the window-maximum version.

Hint for LC 862 — two pops, two reasons

Front pop: P[r]-P[front] ≥ k, that left end is used up (later r only makes it longer). Back pop: P[r] ≤ P[back], a later smaller-or-equal prefix is a strictly better left end. After both, push r. Miss either pop and you TLE or return a longer answer.

Hint for LC 1696 — DP with a sliding max

dp[i] = a[i] + max(dp[i-k..i-1]). That inner max is window-maximum on the dp array: decreasing deque of indices, expire i-k. Do not scan k previous states.

Recap

  • Front expires by age, back by domination.
  • Decreasing deque for window max; increasing for min / prefix.
  • Store indices, pop back on ≤ so equals do not stale.
  • Negatives + range sum → prefix deque, not a two-pointer window.
  • ArrayDeque is both the queue and the deque.
