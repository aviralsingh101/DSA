Constraints → Complexity

The single highest-leverage page in this course: read the constraint line, and the problem tells you which algorithm it wants before you have understood the question.

Easy 25 min read Prerequisites: Complexity Analysis pattern recognition constraints triage meta

Why this exists

Every problem statement contains a hint that is impossible to hide: the bounds. A setter who wants an O(n log n) solution must set n large enough to kill O(n²) and small enough that O(n log n) passes. That pins the bound into a narrow window. Read the window backwards and you recover the intended complexity, which usually recovers the intended technique.

This is the specific skill that decays when you stop competing. Experienced engineers still know what a segment tree is; what they lose is the reflex that says "n ≤ 20, therefore subsets, therefore bitmask" in under two seconds. Recovering that reflex is worth more than re-reading any single algorithm, because it tells you which page of this course to open before you have even finished the statement.

It also protects you in interviews where no constraints are given. Ask for them. "How large is n?" is not a stalling question — it is the question that determines whether the expected answer is two pointers or a suffix automaton, and asking it signals that you think about cost before you think about code. A setter who answers "up to a hundred thousand" has just told you that a nested pair loop is dead, and you should say that deduction out loud before you pick a data structure.

How to use this page

Cover the right-hand column of the main table below. Read a constraint, say the complexity and the likely technique out loud, then reveal. Do this once a week. It takes four minutes and it is the highest-return four minutes in your preparation.

Recognise this pattern

Say yes when you see

  • There is an explicit bound on n, m, q, ai, or the sum of n over test cases
  • A bound looks oddly specific — n ≤ 22, n ≤ 500, n ≤ 5000 — which is a deliberate signature, not a round number
  • Two different parameters are bounded differently (n ≤ 10⁵ but ai ≤ 100) → the small one is your state space
  • The time limit is unusually generous (3–5 s) → a heavy log factor or √n approach is expected
  • Memory limit is tight (32 MB or 64 MB) → the intended solution has O(n) or O(√n) space, ruling out some DP tables

Not this pattern when

  • No constraints are given at all → ask; do not assume
  • The bound is on the output size rather than the input → the complexity is output-sensitive, and enumeration may be unavoidable
  • The problem is interactive with a query budget → the "complexity" you must respect is the number of queries (often log n or n log n)
  • It is a constructive problem ("output any valid arrangement") → the bound tells you the output size, and the difficulty is the invariant, not the running time

Constraint tell: Java's budget is roughly 10⁸ simple operations per second. Halve it for HashMap-heavy code, quarter it for boxed collections, and add 0.5–1 s of JVM startup on some judges. A bound that sits just under that budget is almost always the intended class, not a coincidence.

Core idea: read the bound backwards

A setter chooses bounds to separate solutions. If O(n²) should fail and O(n log n) should pass, n has to land somewhere around 10⁵. There is no way to write the statement without leaking that. So the procedure is: take the bound, compute which complexity classes fit inside 10⁸ operations, and then ask which techniques deliver those classes.

The second half of that procedure is the part people forget. Knowing "n ≤ 20 means O(2ⁿ)" is only half an answer; the useful reflex is "O(2ⁿ) over n ≤ 20 means the state is a subset, so I am enumerating masks or writing bitmask DP". Complexity classes map to a small number of state shapes, and that mapping is what you are drilling.

Two refinements matter in practice. First, look for a second, smaller bound: when n is huge but ai ≤ 100 or k ≤ 10, the small parameter is almost always the DP dimension. Second, unusual bounds are signatures: n ≤ 40 means meet in the middle, n ≤ 500 means O(n³), and a bound of 10¹⁸ means you will never iterate over the input at all. Walk one line as a check: 1 ≤ n ≤ 2×10⁵ with a request for the longest increasing subsequence forces O(n log n) patience sorting, because the quadratic DP at that size is about 4×10¹⁰ steps.

The reflex to rebuild

Given a bound, complete this sentence without pausing: "n ≤ X, so I have about Y operations to spend, so the intended complexity is Z, so the state is probably W."

For example: "n ≤ 22, so about 4×10⁶ masks, so O(2ⁿ · n), so the state is a subset of items plus a last element — travelling-salesman-shaped bitmask DP."

Powers of two worth knowing cold

2¹⁰ = 1024, 2²⁰ ≈ 10⁶, 2³⁰ ≈ 10⁹, 2⁶⁰ ≈ 10¹⁸. Also 10! ≈ 3.6×10⁶, 13! ≈ 6×10⁹, and log₂(10⁶) ≈ 20. These five facts let you price almost any bound in your head. And note the boundary of int: 2³¹ − 1 ≈ 2.1×10⁹, so a bound of 10⁹ on values plus any summing means long.

The sum-over-test-cases trap

t ≤ 10⁴ with "the sum of n over all test cases does not exceed 2×10⁵" is not permission to be slow, and it is also not a reason to fear O(n log n). It means your per-test work must be proportional to that test's n. The classic failure is clearing an O(maxN) array every test: 10⁴ tests times 2×10⁵ clears is 2×10⁹ operations. Clear only the indices you touched.

Reading the memory limit too

256 MB holds about 6×10⁷ ints or 3×10⁷ longs. So a 2D int DP table of 5000 × 5000 is 100 MB — it fits, barely. 10⁵ × 100 is 40 MB, fine. 10⁵ × 10⁵ is impossible, which is itself a hint that the DP must be rolled down to one or two rows.

Where the one-second wall sits

Each cell is an input size; the value is how many operations an O(n²) solution would perform. Watch exactly where it crosses 10⁸ — that crossing point is what "n ≤ 5000 means quadratic" really encodes.

Triage flow for a fresh problem

Algorithm

  1. Find every bound in the statement: n, m, q, k, value ranges, and the sum-over-tests clause.
  2. Pick the largest one and compute the operation budget: about 10⁸ divided by nothing if you use primitive arrays, by 2–5 if you use collections.
  3. List the complexity classes that fit. Usually only two survive, which is the whole point of the exercise.
  4. Look for a second, smaller bound. If k ≤ 10 or ai ≤ 100, that parameter is almost certainly a DP dimension or a state.
  5. Translate the class into a state shape: subsets, prefix pairs, intervals, sorted order, digits, or all pairs — that mapping is what you are actually drilling.
  6. Check the memory limit against your intended table. If it does not fit, the DP is meant to be rolled to one or two rows.
  7. Sanity-check the output type. Bounds near 10⁹ with any summation or multiplication mean the product no longer fits in a 32-bit int, so use long.
  8. Only now start solving, with the target complexity already fixed so you do not implement a correct idea that the bound has already ruled out.

JavaConstraintTriage.java
public class ConstraintTriage {
    
        private static final double BUDGET = 1e8;   // rough ops/second for Java
    
        static double ops(String cls, double n) {
            switch (cls) {
                case "log n":     return Math.log(n) / Math.log(2);
                case "sqrt n":    return Math.sqrt(n);
                case "n":         return n;
                case "n log n":   return n * Math.log(n) / Math.log(2);
                case "n^2":       return n * n;
                case "n^3":       return n * n * n;
                case "2^n":       return Math.pow(2, n);
                case "n!":        return gamma(n);
                default:          throw new IllegalArgumentException(cls);
            }
        }
    
        private static double gamma(double n) {
            double f = 1;
            for (int i = 2; i <= n && f < 1e300; i++) {
                f *= i;
            }
            return f;
        }
    
        public static void main(String[] args) {
            String[] classes = {"log n", "sqrt n", "n", "n log n", "n^2", "n^3", "2^n", "n!"};
            double[] sizes = {10, 25, 100, 500, 5000, 100000, 1000000};
            System.out.printf("%-8s", "class");
            for (double n : sizes) {
                System.out.printf("%12s", "n=" + (long) n);
            }
            System.out.println();
            for (String c : classes) {
                System.out.printf("%-8s", c);
                for (double n : sizes) {
                    double o = ops(c, n);
                    System.out.printf("%12s", (o <= BUDGET ? "OK " : "-- ")
                            + String.format("%.0e", o));
                }
                System.out.println();
            }
        }
        // Output (abridged): the OK/-- boundary runs diagonally, exactly as in the table above.
    }

JavaMultiTestPattern.java
import java.io.DataInputStream;
    import java.io.IOException;
    
    public class MultiTestPattern {
    
        static final int MAX = 200_001;
        static int[] cnt = new int[MAX];        // allocated once, never per test
    
        /**
         * WRONG: java.util.Arrays.fill(cnt, 0) per test is O(MAX) each, so with
         * t = 1e4 tests that is 2e9 writes even though the total n is only 2e5.
         * RIGHT: undo exactly the indices this test touched.
         */
        static long solveOneTest(int[] a) {
            long distinctPairs = 0;
            for (int v : a) {
                distinctPairs += cnt[v];       // pairs with an earlier equal value
                cnt[v]++;
            }
            for (int v : a) {
                cnt[v] = 0;                    // O(n), not O(MAX)
            }
            return distinctPairs;
        }
    
        public static void main(String[] args) throws IOException {
            FastReader in = new FastReader();
            int t = in.nextInt();
            StringBuilder out = new StringBuilder();
            while (t-- > 0) {
                int n = in.nextInt();
                int[] a = new int[n];
                for (int i = 0; i < n; i++) {
                    a[i] = in.nextInt();
                }
                out.append(solveOneTest(a)).append('\n');
            }
            System.out.print(out);             // one write, not n writes
        }
    
        /** Minimal fast reader; see the Java for DSA page for the full version. */
        static class FastReader {
            private final DataInputStream in = new DataInputStream(System.in);
            int nextInt() throws IOException {
                int ret = 0, b = in.read();
                while (b < '0') {
                    b = in.read();
                }
                while (b >= '0') {
                    ret = ret * 10 + (b - '0');
                    b = in.read();
                }
                return ret;
            }
        }
        // Input : 2 / 3 / 1 1 2 / 2 / 5 5
        // Output: 1
        //         1
    }

Complexity

Time meta-topic Space meta-topic

The whole page rests on inverting one inequality. If the intended complexity is f(n) and the budget is B ≈ 10⁸, the setter must choose n with f(n) ≤ B for the intended solution and g(n) > B for the solution being excluded. Solving f(n) = B gives the boundary:

n² = 10⁸ ⇒ n = 10⁴    n³ = 10⁸ ⇒ n ≈ 464    2ⁿ = 10⁸ ⇒ n ≈ 26    n! = 10⁸ ⇒ n ≈ 11

Those four numbers explain almost every bound you will ever see: n ≤ 5000 (quadratic, with headroom), n ≤ 500 (cubic), n ≤ 20–25 (exponential), n ≤ 10 (factorial). And for the linearithmic case:

n log₂ n = 10⁸ ⇒ n ≈ 4×10⁶

which is why n ≤ 10⁵ or 2×10⁵ is such a comfortable, and therefore common, choice for an O(n log n) problem: it leaves a 20–40× safety margin for slow languages.

Edge cases and pitfalls

  • Reading only the bound on n
    Seeing n ≤ 10⁵ and concluding O(n log n), while missing q ≤ 10⁵ on the next line. O(n log n) per query is 10¹⁰.
    Read every bound and multiply the ones that compose. With n and q both large you need O((n + q) log n) total, which means precomputation, a persistent structure, or going offline.
  • Ignoring the value range as a state space
    Treating ai ≤ 10⁵ as irrelevant metadata. Many problems are O(maxA) or O(maxA log log maxA), and no amount of thinking about n will find that solution.
    When operations are keyed by value ("delete all copies of v", "pairs with gcd g"), index by value. Counting arrays and sieves over maxA are the standard shape.
  • Clearing a global array per test case
    Arrays.fill(cnt, 0) inside the test loop with MAX = 2×10⁵ and t = 10⁴ tests: 2×10⁹ writes, a guaranteed timeout even though your algorithm is linear.
    Undo only the indices you touched, or stamp entries with the test number and treat a stale stamp as zero. See the Multi-test trap tab.
  • Trusting the bound and ignoring the constant
    An O(n log n) solution at n = 2×10⁵ using PriorityQueue<int[]> and Scanner. The class is right and it still times out, because the constant is 20–50×.
    Once the class fits, check the constant: primitive arrays over boxed collections, BufferedReader or DataInputStream over Scanner, and buffered output. See Java for DSA.
  • Missing the long requirement hidden in the bounds
    n ≤ 10⁵ and ai ≤ 10⁹, then summing into an int. The true sum reaches 10¹⁴ and wraps silently to a plausible wrong answer.
    Multiply the two largest bounds in your head. If the product exceeds 2.1×10⁹, use long. This check costs two seconds and prevents a whole class of unexplained wrong answers.
  • Assuming an interview has no constraints
    Jumping straight to a HashMap solution when the interviewer intended n ≤ 100 and wanted to discuss a cleaner quadratic, or intended streaming input that will not fit in memory at all.
    Ask two questions before coding: "how large is the input?" and "does it fit in memory?". These change the answer more than any other clarification, and asking them is itself a positive signal.

Interview follow-ups

The interviewer gives no constraints. What do you ask?

Three questions, in this order. "How large can the input be?" — decides the target complexity. "Does it fit in memory, or is it a stream?" — decides whether you may sort or must keep O(1) state. "What are the value ranges, and can they be negative?" — decides int versus long and whether tricks like counting sort or Dijkstra are available. Each answer eliminates whole families of solutions, which is exactly what you want before you commit.

n ≤ 10⁵ but the answer needs pairs. Is the problem impossible?

No — it means you must count pairs without enumerating them. The standard moves are: sort and use two pointers so each pair is implied rather than visited; use a prefix-sum plus HashMap so that each new index counts all its partners at once; or use a BIT over compressed values to count how many earlier elements satisfy a predicate. "Count pairs" almost never means "visit pairs".

Why is n ≤ 40 such a distinctive bound?

Because it sits precisely in the gap between exponential and polynomial. 2⁴⁰ ≈ 10¹² is too slow, but 2²⁰ ≈ 10⁶ is trivial, and no polynomial algorithm is expected to exist (these are usually subset-sum variants, which are NP-hard). So the setter is telling you to split the input in half, enumerate each half, sort one side and binary search from the other: meet in the middle. Bounds of 30–45 should trigger that thought immediately.

How do I use the memory limit as a hint?

Convert it to a count: 256 MB is about 6×10⁷ ints. Then check your intended table. If the natural DP is dp[n][W] with n = 10⁵ and W = 10⁵, that is 10¹⁰ cells — impossible — so the setter must intend a rolled DP with O(W) memory, or a completely different formulation. A memory limit that is tight relative to the obvious table is a strong hint that the obvious table is not the solution.

Does this reasoning transfer to LeetCode, where limits are looser?

Yes, and LeetCode is arguably more explicit: the constraints block is always present and always tight. 1 ≤ nums.length ≤ 10⁵ means O(n log n); ≤ 10⁴ often tolerates O(n²); ≤ 20 is bitmask; ≤ 12 is permutations. The one difference is that the JavaScript/Python budget is lower, so LeetCode's authors leave more headroom — an O(n²) at n = 10⁴ usually passes in Java.

What if my complexity fits but the problem still feels impossible?

Then you have probably identified the wrong state. Go back to the second bound. A huge n with a tiny k, or a tiny value range, or "at most 10 distinct letters" is the setter handing you the state dimension. The most common form of this is n ≤ 10⁵ with ai ≤ 100: the answer is O(100n) or O(100²), and no amount of cleverness about n alone will find it.

Hint for LC 1782 — when the value range, not n, is the complexity parameter

Both n and ai are bounded by 10⁵, and you need Σ ⌊ai/aj⌋ over all pairs — 10¹⁰ pairs, so pairs are out. Build cnt[v] and its prefix sums, then for each distinct divisor d loop over multiples d, 2d, 3d, … and add k × (count of values in [kd, (k+1)d)). The outer-plus-inner loop is the harmonic series, O(maxA log maxA). Transferable lesson: when both n and the value range are bounded by the same number, try indexing by value — the harmonic series often rescues you.

Hint for LC 847 — recognising a bitmask from the bound alone

n ≤ 12 is far too small to be about n. 2¹² = 4096, and 4096 × 12 = 49152 states — trivial. So the state must be a subset. Here it is (currentNode, maskOfVisited), and because every edge has weight 1 you want plain BFS over those n × 2ⁿ states rather than DP. The reusable move: a bound of 10–22 on a set of items means the item set itself is part of the state.

Recap

  • The bound is the answer key. Compute the budget, list the classes that fit, and translate the class into a state shape before you start solving.
  • Four boundaries explain almost every constraint: n² = 10⁸ at n = 10⁴, n³ at 464, 2ⁿ at 26, n! at 11.
  • Always look for the second, smaller bound. A tiny k or a small value range is the setter handing you the DP dimension.
  • Oddly specific bounds are signatures: 40 means meet in the middle, 500 means O(n³), 22 means bitmask, 10¹⁸ means maths.
  • Multiply the two largest bounds to decide int versus long, and read the memory limit as a hint about whether the obvious DP table is intended.
