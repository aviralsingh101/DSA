Recurrences & Master Theorem

Turn a recursive algorithm into a closed-form complexity by drawing its recursion tree and adding up the levels — then shortcut the whole process with the master theorem.

Medium 20 min read Prerequisites: Complexity Analysis recursion recursion tree master theorem meta

Why this exists

Loop-counting stops working the moment the algorithm calls itself. There is no innermost loop to count, because the work is spread across a tree of calls whose shape depends on how the input is split. Merge sort, quicksort, binary search, divide-and-conquer on the answer, and every tree algorithm you will meet in module 05 need a different tool.

The tool is the recursion tree: draw the calls, compute the total work at each depth, and sum over depths. Almost every recurrence you meet in practice falls into one of three shapes — the root dominates, the leaves dominate, or every level costs the same — and knowing which shape you are in gives the answer immediately.

The master theorem is a lookup table for exactly that classification. It is worth memorising because interviewers ask "why n log n?" and the strong answer is "there are log n levels and each costs Θ(n)", not "because merge sort is n log n". Once you can draw the tree, the lookup table is just a shortcut for a sum you already know how to write by hand. The same three shapes also tell you the space story: a divide-style tree is only log n deep, so it is safe at n = 10⁹, while a peel-one-element recursion is n deep and overflows the Java stack long before the time limit is even the problem. That is why this page sits next to complexity analysis: counting loops prices iterative code, and drawing the recursion tree prices everything that calls itself.

Do not try to unroll the recursion algebraically. Draw the tree, compute the cost of one level, count the levels, and decide which end of the tree dominates. Three questions, and you are done.

Recognise this pattern

Say yes when you see

  • The algorithm calls itself on strictly smaller inputs — sorting, searching, divide and conquer, tree traversal
  • You can describe the work as "split into a pieces of size n/b, plus f(n) to combine" → the master theorem applies directly
  • An interviewer asks "why is that n log n?" or "what is the depth of the recursion?"
  • You need the space complexity of a recursive routine → that is the maximum depth of the tree, not the number of nodes
  • The recursion halves the input and does constant work → Θ(log n), the shape behind every binary search

Not this pattern when

  • The subproblem sizes are unequal and data-dependent (quicksort with a bad pivot) → the master theorem does not apply; analyse expected cost instead
  • The recursion has overlapping subproblems → you are looking at dynamic programming, and the complexity is states × transition cost, not a recurrence
  • The subproblem shrinks by a constant subtraction rather than division (T(n) = T(n-1) + n) → just sum the series; it is Θ(n²)
  • Branching is exponential with no size reduction (T(n) = 2T(n-1) + 1) → Θ(2ⁿ); that is subset enumeration, not divide and conquer

Constraint tell: recursion depth is auxiliary space. T(n) = T(n-1) + … at n = 10⁵ means 10⁵ stack frames and a StackOverflowError in Java at roughly 10⁴–10⁵ frames. Divide-style recursion is safe because log₂(10⁹) < 30.

Core idea: add up the levels

Write the recurrence as T(n) = a · T(n/b) + f(n). Here a is the branching factor, b is how much smaller each subproblem is, and f(n) is the non-recursive work done at this call — the split plus the combine. Merge sort is a = 2, b = 2, f(n) = n.

Now account for the tree. At depth k there are ak nodes, each of size n / bk, so the total work at that depth is ak · f(n / bk). The tree bottoms out when n / bk = 1, that is at depth k = logb n, where there are alogb n = nlogb a leaves.

That last expression, nlogb a, is the total cost of the leaves, and the whole master theorem is just a comparison between it and f(n). If the leaves grow faster, the leaves pay for everything. If f(n) grows faster, the single root call pays for everything. If they tie, every level costs the same and you multiply by the number of levels. Walk merge sort as a check: eight elements split into two fours, then four twos, then eight ones; each of those four depths spends eight units merging, so the total is 8 × 4 = 32 = n(log₂ n + 1). That flat-per-level picture is exactly case 2, and it is the picture you should draw out loud when someone asks why merge sort is n log n.

The master theorem in one comparison

For T(n) = a T(n/b) + f(n) with a ≥ 1, b > 1, let c = logb a. Compare f(n) against nc:

  • Case 1 — leaves win. f(n) = O(nc-ε) ⇒ T(n) = Θ(nc).
  • Case 2 — tie. f(n) = Θ(nc logk n) ⇒ T(n) = Θ(nc logk+1 n).
  • Case 3 — root wins. f(n) = Ω(nc+ε) and a f(n/b) ≤ d f(n) for some d < 1 ⇒ T(n) = Θ(f(n)).

Merge sort: c = log₂ 2 = 1, f(n) = n = n¹, so case 2 with k = 0 gives Θ(n log n).

The three shapes, visually

You can skip the algebra by asking where the mass of the tree is. Top-heavy (costs shrink geometrically going down): the root dominates, answer Θ(f(n)). Bottom-heavy (costs grow going down): the leaves dominate, answer Θ(nc). Flat (every level the same): answer is one level times the number of levels. A geometric series is dominated by its largest term, which is why only the extreme level matters in the first two cases.

Divide is not the same as subtract

T(n) = T(n/2) + 1 has depth log₂ n and is Θ(log n). T(n) = T(n-1) + 1 has depth n and is Θ(n). These look almost identical on the page and differ by an exponential amount. The master theorem covers only the division form; for subtraction, sum the series directly.

Recurrences the master theorem cannot solve

T(n) = 2T(n/2) + n/log n falls in the gap between cases 1 and 2 (no valid ε exists). T(n) = T(n/2) + T(n/3) + n has unequal splits. T(n) = 2T(√n) + 1 is not of the form at all — substitute m = log n to get S(m) = 2S(m/2) + 1, giving Θ(m) = Θ(log n). When the theorem fails, draw the tree; it never fails.

Choosing the right tool for a recurrence

Algorithm

  1. Write the recurrence. Identify a (number of recursive calls), b (size divisor) and f(n) (work outside the calls).
  2. Check divide versus subtract. If the size shrinks by subtraction, skip the master theorem and sum the series.
  3. Compute the leaf exponent c = logb a, which is exactly how many leaves the tree has written as a power of n.
  4. Compare f(n) with nc so you know whether the root, the leaves, or every level is paying for the work.
  5. Case 1 (f smaller): answer Θ(nc) — the leaves pay because the combine work shrinks as you go up.
  6. Case 2 (equal up to log factors): answer Θ(nc logk+1 n) — every level pays equally.
  7. Case 3 (f larger, and regular): answer Θ(f(n)) — the single root call already costs more than everything below it.
  8. Report space separately as Θ(max depth), plus any auxiliary buffers the combine step allocates, because only the live path uses memory.

Java implementation

The canonical 2T(n/2) + Θ(n). Note the single shared buffer: allocating a new array inside merge would still be Θ(n log n) time but would churn O(n log n) allocations.

JavaMergeSort.java
import java.util.Arrays;
    
    public class MergeSort {
    
        /** T(n) = 2T(n/2) + Theta(n)  =>  Theta(n log n), Theta(n) auxiliary space. */
        static void sort(int[] a) {
            sort(a, new int[a.length], 0, a.length - 1);
        }
    
        private static void sort(int[] a, int[] buf, int lo, int hi) {
            if (lo >= hi) {
                return;
            }
            int mid = lo + (hi - lo) / 2;
            sort(a, buf, lo, mid);
            sort(a, buf, mid + 1, hi);
            merge(a, buf, lo, mid, hi);
        }
    
        private static void merge(int[] a, int[] buf, int lo, int mid, int hi) {
            int i = lo, j = mid + 1, k = lo;
            while (i <= mid && j <= hi) {
                buf[k++] = (a[i] <= a[j]) ? a[i++] : a[j++];   // <= keeps the sort stable
            }
            while (i <= mid) {
                buf[k++] = a[i++];
            }
            while (j <= hi) {
                buf[k++] = a[j++];
            }
            System.arraycopy(buf, lo, a, lo, hi - lo + 1);
        }
    
        public static void main(String[] args) {
            int[] a = {5, 2, 9, 1, 5, 6, 3, 8};
            sort(a);
            System.out.println(Arrays.toString(a));
        }
        // Input : [5,2,9,1,5,6,3,8]
        // Output: [1, 2, 3, 5, 5, 6, 8, 9]
    }

Instrument a recurrence and print the cost of each level. This is the fastest way to settle an argument about which case you are in: look at whether the level costs are flat, growing, or shrinking.

JavaRecurrenceProbe.java
import java.util.HashMap;
    import java.util.Map;
    
    public class RecurrenceProbe {
    
        /** Records, per depth, the total value of f(size) across all calls at that depth. */
        static void probe(int n, int a, int b, int fExponent, int depth, Map<Integer, Long> levels) {
            if (n <= 1) {
                levels.merge(depth, 1L, Long::sum);
                return;
            }
            long work = 1;
            for (int e = 0; e < fExponent; e++) {
                work *= n;                       // f(n) = n^fExponent
            }
            levels.merge(depth, work, Long::sum);
            for (int i = 0; i < a; i++) {
                probe(n / b, a, b, fExponent, depth + 1, levels);
            }
        }
    
        static void report(String label, int n, int a, int b, int fExponent) {
            Map<Integer, Long> levels = new HashMap<>();
            probe(n, a, b, fExponent, 0, levels);
            StringBuilder sb = new StringBuilder(label + " -> ");
            long total = 0;
            for (int d = 0; levels.containsKey(d); d++) {
                sb.append(levels.get(d)).append(d + 1 < levels.size() ? ", " : "");
                total += levels.get(d);
            }
            System.out.println(sb + "   total=" + total);
        }
    
        public static void main(String[] args) {
            report("2T(n/2)+n   n=64", 64, 2, 2, 1);   // flat  -> case 2
            report("2T(n/2)+1   n=64", 64, 2, 2, 0);   // grows -> case 1
            report("2T(n/2)+n^2 n=64", 64, 2, 2, 2);   // decays-> case 3
        }
        // Output: 2T(n/2)+n   n=64 -> 64, 64, 64, 64, 64, 64, 64   total=448
        //         2T(n/2)+1   n=64 -> 1, 2, 4, 8, 16, 32, 64   total=127
        //         2T(n/2)+n^2 n=64 -> 4096, 2048, 1024, 512, 256, 128, 64   total=8128
    }

A reference implementation of the classification. Reading it is a good way to check that you can state each case precisely, which is what an interviewer is probing.

JavaMasterTheorem.java
public class MasterTheorem {
    
        /**
         * Classifies T(n) = a T(n/b) + Theta(n^d * log^k n).
         * Returns a human-readable Theta bound.
         */
        static String solve(int a, int b, double d, int k) {
            double c = Math.log(a) / Math.log(b);          // c = log_b(a)
            double eps = 1e-9;
            if (d < c - eps) {
                return "Theta(n^" + trim(c) + ")            [case 1: leaves dominate]";
            }
            if (Math.abs(d - c) <= eps) {
                return "Theta(n^" + trim(c) + " * log^" + (k + 1) + " n)  [case 2: every level ties]";
            }
            return "Theta(n^" + trim(d) + (k > 0 ? " * log^" + k + " n" : "")
                    + ")            [case 3: root dominates]";
        }
    
        private static String trim(double x) {
            return (Math.abs(x - Math.rint(x)) < 1e-9)
                    ? String.valueOf((long) Math.rint(x))
                    : String.format("%.3f", x);
        }
    
        public static void main(String[] args) {
            System.out.println("T=T(n/2)+1      " + solve(1, 2, 0, 0));
            System.out.println("T=2T(n/2)+1     " + solve(2, 2, 0, 0));
            System.out.println("T=2T(n/2)+n     " + solve(2, 2, 1, 0));
            System.out.println("T=2T(n/2)+n^2   " + solve(2, 2, 2, 0));
            System.out.println("T=7T(n/2)+n^2   " + solve(7, 2, 2, 0));
            System.out.println("T=3T(n/2)+n     " + solve(3, 2, 1, 0));
        }
        // Output: T=T(n/2)+1      Theta(n^0 * log^1 n)  [case 2: every level ties]
        //         T=2T(n/2)+1     Theta(n^1)            [case 1: leaves dominate]
        //         T=2T(n/2)+n     Theta(n^1 * log^1 n)  [case 2: every level ties]
        //         T=2T(n/2)+n^2   Theta(n^2)            [case 3: root dominates]
        //         T=7T(n/2)+n^2   Theta(n^2.807)            [case 1: leaves dominate]
        //         T=3T(n/2)+n     Theta(n^1.585)            [case 1: leaves dominate]
    }

Complexity

Time Θ(n log n) for merge sort Space Θ(n) buffer + Θ(log n) stack

Summing the recursion tree for T(n) = a T(n/b) + f(n) gives

T(n) = Σk=0logbn ak f(n / bk)

With f(n) = n, each term is ak · n / bk = n (a/b)k, a geometric series with ratio a/b. Three regimes follow immediately:

  • a < b: ratio below 1, the series is dominated by its first term, total Θ(f(n)) — case 3.
  • a = b: every term equals n, and there are logb n + 1 of them, total Θ(n log n) — case 2.
  • a > b: ratio above 1, the series is dominated by its last term, n(a/b)logbn = nlogba — case 1.

That is the entire master theorem: a geometric series is controlled by whichever end is larger. For merge sort specifically, a = b = 2 puts us in the flat case, and Θ(n log n) is also a lower bound because comparison sorting is Ω(n log n).

Edge cases and pitfalls

  • Assuming recursion implies a logarithm
    "It is recursive, so the depth is log n." For T(n) = T(n-1) + 1 the depth is n, and at n = 10⁵ that is a StackOverflowError.
    Ask whether the size is divided or decremented. Division gives depth logb n; decrement gives depth n. Only the first is safe at large n.
  • Applying the master theorem to overlapping subproblems
    Analysing the naive Fibonacci recursion as T(n) = 2T(n/2) + 1. It is actually T(n) = T(n-1) + T(n-2) + 1, which is Θ(φⁿ), exponential.
    The master theorem needs subproblems of size n/b. If subproblems repeat, the right framing is DP: cost = number of distinct states × cost per transition.
  • Forgetting that case 3 has a regularity condition
    Concluding T(n) = Θ(f(n)) whenever f grows faster than nc, without checking a f(n/b) ≤ d f(n) for some d < 1.
    For every polynomial f the condition holds automatically, so in practice you are safe — but say "and f is polynomial so regularity holds" so the interviewer knows you did not forget it.
  • Counting the buffer allocation as free
    A merge that does int[] tmp = new int[hi-lo+1] on every call. The time class is unchanged, but you have made Θ(n) allocations and the constant factor can be 3–5×.
    Allocate one buffer of length n up front and pass it down, as in the Merge sort tab. Also quote space as Θ(n) for the buffer plus Θ(log n) for the stack.
  • Ignoring the gap between cases
    Forcing T(n) = 2T(n/2) + n/log n into case 1 or case 2. Neither applies: there is no ε > 0 with n/log n = O(n1-ε).
    Sum the tree: each level costs about n / log(n/2k), and the total is Θ(n log log n). When the theorem is silent, the tree still answers.
  • Quoting quicksort as Θ(n log n) worst case
    Quicksort's recurrence with an adversarial pivot is T(n) = T(n-1) + Θ(n) = Θ(n²). On sorted input with a first-element pivot this is not hypothetical.
    Say "Θ(n log n) expected with a random pivot, Θ(n²) worst case". This is also why Java's Arrays.sort(int[]) can be attacked, and why Arrays.sort(Integer[]) (merge sort) cannot.

Interview follow-ups

Derive merge sort's complexity from first principles.

Sorting n elements splits into two halves, each sorted recursively, then merged in one linear pass, so T(n) = 2T(n/2) + Θ(n) with T(1) = Θ(1). At depth k there are 2k calls on inputs of size n/2k, so the level costs 2k · n/2k = n — independent of k. The recursion stops at depth log₂ n, giving n(log₂ n + 1) = Θ(n log n).

Why is the master theorem's answer nlogba in case 1?

That expression is the number of leaves. The tree has depth logb n and branching factor a, so it has alogbn leaves, and by the identity alogbn = nlogba that equals nc. Case 1 says the combine work is so small that the total is just the cost of touching every leaf.

What is the space complexity of a recursive algorithm?

Θ(maximum depth) for the call stack, plus whatever the combine step allocates. Merge sort is Θ(n) total because of the buffer; quicksort is Θ(log n) expected if you always recurse into the smaller side and loop on the larger one. Note that the number of nodes in the recursion tree is irrelevant to space — only the deepest path is live at any moment.

A recursion is 10⁵ deep. How do you avoid a stack overflow in Java?

Three options, in order of preference. Rewrite iteratively with an explicit ArrayDeque or int[] stack — always correct and usually faster. Run on a thread with a bigger stack: new Thread(null, task, "main", 1 << 26).start(), which is a standard competitive-programming trick. Reduce the depth by recursing into the smaller subproblem first. The default JVM stack is around 512 KB, roughly 10⁴–10⁵ frames.

Why does Strassen's algorithm beat the naive matrix multiply?

Block multiplication gives T(n) = 8T(n/2) + Θ(n²), and log₂8 = 3, so case 1 yields Θ(n³) — no better than the triple loop. Strassen replaces 8 multiplications with 7 (at the cost of more additions, which are still Θ(n²)), giving T(n) = 7T(n/2) + Θ(n²) and Θ(nlog₂7) = Θ(n2.807). The general lesson: in case 1, reducing a is the only thing that helps.

When should I not bother with a recurrence at all?

When subproblems overlap. Then the count of distinct subproblems is what matters, and the cost is states × transition. Recursive Fibonacci is Θ(φⁿ); memoised, it is Θ(n), and no recurrence solving is involved — you simply count states. Recognising which of the two situations you are in is more valuable than being fast at the master theorem.

Hint for LC 240 — when a worse recurrence beats a better-looking one

The quadrant recursion discards one of four quadrants, giving T(n) = 3T(n/2) + O(1), i.e. Θ(nlog₂3) = Θ(n1.585) where n is the side length — about Θ(m0.79) in terms of the m = n² cells. That is better than scanning everything, but the staircase walk from the top-right corner is O(m + n) and four lines long. The transferable lesson: a clever recurrence is not automatically the best answer; always compare it against the simplest monotonicity argument.

Hint for LC 1569 — setting up the recurrence

The first element is forced to be the root, which partitions the rest into the elements smaller than it (left subtree, size L) and larger (right subtree, size R). Any interleaving of the two subsequences preserves the BST, so the count is C(L+R, L) × f(left) × f(right). That gives T(n) = T(L) + T(R) + O(n), which is O(n²) worst case and O(n log n) when balanced. You will need nCr under a modulus. General lesson: when a recursive structure is forced by the data, the recurrence writes itself — find the forced choice first.

Recap

  • Draw the tree, not the algebra. Total work is Σk ak f(n/bk), a geometric series, and a geometric series is owned by its larger end.
  • Compare f(n) with nlogba — the cost of the leaves. Smaller means leaves win, equal means multiply by log n, larger means the root wins.
  • Divide versus subtract is the first check. T(n/2) means depth log n; T(n-1) means depth n and a real stack-overflow risk.
  • Overlapping subproblems are not a recurrence problem. Switch to counting states × transitions, which is dynamic programming.
  • Space is the depth of the tree, plus any buffers — never the number of nodes.
