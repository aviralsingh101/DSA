Complexity Analysis

Learn to price an algorithm before you write it, so that the constraints in the problem statement tell you which idea to reach for instead of which idea to abandon.

Easy 22 min read big-o amortised counting meta

Why this exists

You are handed a list of two hundred thousand numbers and asked whether any two of them add up to exactly one million. The first idea anybody has is to try every pair: fix one number, walk over all the numbers after it, and check each sum. That is completely correct, and it is also about 200000 × 200000 / 2 = 2 × 10¹⁰ additions. Java gets through roughly a hundred million simple operations per second, so that loop needs something like three minutes, and the judge that gave you one second stopped watching long ago. The idea was never wrong; the amount of work was.

Notice that nothing about that failure required running the program. The pair loop does a number of steps proportional to n × n, where n is how many numbers you were given, and once you know that shape you know it dies at n = 2 × 10⁵ without touching a keyboard. That prediction is what complexity analysis is: working out how the step count grows as the input grows. The notation for it is Big-O — writing O(n²) says "the work grows like the square of the input size", with constant multipliers such as the one-half above deliberately thrown away because they do not change which sizes are survivable.

This is the skill that rusts fastest once you stop competing, because ordinary engineering almost never punishes getting it wrong. A service that handles fifty records per request can carry a hidden quadratic loop for years without anyone noticing. A judge running the same code on 10⁵ elements notices within one second, and so does an interviewer who asks "and what is the complexity of that?" and watches whether the answer arrives immediately or after you count loops with a finger on the screen.

In a real statement the tell is the constraint line, something like 1 ≤ n ≤ 2 × 10⁵. A setter picks that number so that one family of solutions fits inside the time limit and another family does not, which means the number is a hint you can read backwards to recover the intended approach. The whole discipline reduces to three habits, and the rest of this page is those three habits in detail: count how many times the innermost statement of your code runs, keep only the fastest-growing part of that count, and compare it against a budget of about 10⁸ simple operations per second.

Big-O is a statement about growth, not about seconds on your particular machine. It answers exactly one question: if the input doubles, what happens to the work? Doubling n doubles the work of an O(n) loop and quadruples the work of an O(n²) one. That is the same question the constraint line in a problem statement is silently asking you, which is why the two fit together so neatly.

Recognise this pattern

Say yes when you see

  • You are choosing between two working approaches and need to know which one survives the constraints
  • The problem gives an explicit bound such as n ≤ 10⁵, sum of n over all test cases ≤ 2 × 10⁵, or a time limit of 1 second
  • An interviewer asks "can you do better?" — they are telling you a lower complexity class exists
  • Your solution passes small tests and times out on large ones
  • A data structure operation is cheap on average but occasionally expensive (ArrayList.add, HashMap resize, DSU find) → you need amortised analysis, not worst-case-per-operation

Not this pattern when

  • The bottleneck is I/O rather than computation → fix the reader (fast IO) before optimising the algorithm
  • Two candidates share the same complexity class → the decision is about constants, cache behaviour and code length, which Big-O deliberately hides
  • n is tiny and fixed (say n ≤ 12) → even O(n!) is fine, so pick whatever is easiest to write correctly
  • You need the exact operation count for a proof → that is a recurrence, see Recurrences

Constraint tell: Java gets through roughly 10⁸ simple operations per second, where a simple operation means one array read, one comparison or one addition, and almost every judge allows you between one and two seconds. Divide that budget by 2 to 5 when the inner loop chases object pointers, wraps int values into Integer objects, or touches a HashMap, because each of those costs several machine operations and a likely cache miss rather than one cheap instruction.

Core idea and the counting rules

Find the statement that executes most often. In a loop nest that is the innermost line; in a recursive routine it is the body of the call that happens most frequently. Count how many times it runs, written as a formula in n, the size of the input. Then throw away every constant multiplier and every term except the fastest-growing one, because at the sizes that decide whether you pass, the smaller terms are invisible: 3n² + 500n + 9 at n = 10⁴ is 3 × 10⁸ plus a rounding error. What survives that pruning is the complexity, and everything else on this page is a shortcut for doing the count faster.

Four rules cover almost every case you will meet. Sequence: two blocks that run one after the other cost the larger of the two, not the sum, because O(n) + O(n²) is swamped by the square. Nesting: two independent loops, each running n times, multiply to n². Dependent nesting: when the inner loop's bound depends on the outer index, add up the series rather than multiplying, since the inner loop is short early and long later — though 1 + 2 + … + n = n(n+1)/2 is still Θ(n²), so multiplying happens to land in the right class anyway. Amortisation: when one operation in a long run is occasionally expensive, spread its cost over the cheap operations that made it necessary and quote the average; that average is what amortised means.

Three symbols show up and they are not interchangeable. O(f) is an upper bound and means "grows no faster than f". Ω(f) is a lower bound and means "grows at least as fast as f". Θ(f) claims both at once, which is usually what you actually mean. Everyone says "O" out loud and means "Θ", and that is fine, but the distinction earns its keep the moment you claim a solution cannot be improved: "any correct algorithm has to look at every element, so Ω(n) is a lower bound and my Θ(n) scan is optimal" is a far stronger sentence than "mine is O(n)".

Put the procedure on one concrete snippet. Let a be an array of n numbers, target the value you are hunting for, and hits a counter of matching pairs, and run for (i = 0; i < n; i++) for (j = i + 1; j < n; j++) if (a[i] + a[j] == target) hits++;. The hot statement is the comparison inside. For i = 0 it runs n - 1 times, for i = 1 it runs n - 2 times, and so on down to a single execution, which totals n(n-1)/2. Drop the one-half and the linear term and you are left with Θ(n²). At n = 2 × 10⁵ that is 2 × 10¹⁰ comparisons, which is precisely why the pair loop from the opening scenario cannot be the intended answer.

The one-sentence method

How many times does the innermost statement run, as a function of n? Answer that, drop the constant multipliers and the lower-order terms, and you have the complexity.

In plain words, you are not timing anything and you are not counting lines of source code — you are counting executions of the single line that runs most often, because every other line in the method runs at most as often and therefore cannot change the answer. The one thing that breaks this is a line that hides a loop inside a method call, so substitute the call's own cost before you count: list.contains(x) scans the whole list and costs O(n), while set.contains(x) hashes once and costs O(1). That single substitution is routinely the difference between passing and timing out.

Amortised analysis, concretely

Growing an ArrayList doubles its capacity, which copies every element. Copying looks O(n), so n appends look O(n²). But doubling from 1 to n copies 1 + 2 + 4 + … + n < 2n elements in total, so n appends cost O(n) together, i.e. O(1) amortised each. The geometric series is the whole trick: doubling is amortised O(1), growing by a constant +c is amortised O(n).

Constants are hidden, not absent

O(n log n) with a PriorityQueue<int[]> can lose to O(n²) on n = 2000, because every element is a heap allocation and every comparison is a virtual call. Java's boxing and pointer chasing cost roughly 5–20× a primitive array access. When two solutions are in the same class, prefer flat int[] arrays.

The log factor is nearly free

log₂(10⁶) ≈ 20. Going from O(n) to O(n log n) costs about 20×, while going from O(n log n) to O(n²) at n = 10⁶ costs 50000×. So never contort a solution to shave a log; do contort it to shave a factor of n.

The growth-rate ladder

How to price a loop nest

Algorithm

  1. Identify the hot statement. The innermost line of the deepest loop, or the body of the most frequent recursive call.
  2. Substitute library costs. Replace every call in that line with its own complexity: List.contains → O(n), Set.contains → O(1), TreeMap.get → O(log n), String.substring → O(len).
  3. Count executions. Multiply independent loop bounds; sum the series when an inner bound depends on an outer index.
  4. Add sequential blocks with max, not plus. A sort followed by a linear scan is still O(n log n), because the slower block swallows the faster one.
  5. Amortise the spiky operations. Charge a resize or a path compression to the cheap operations that caused it, then quote the average.
  6. Drop constants and lower-order terms so only the fastest-growing piece survives: 3n² + 500n is the same class as n².
  7. Evaluate against the constraint using 10⁸ operations per second, then divide by 2–5 for boxing and pointer chasing.
  8. State time and space separately, and say whether your bound is tight (Θ) or only an upper bound (O).

Java implementation

Both methods look linear. Both are quadratic. These two shapes account for a large share of unexplained timeouts in Java.

JavaHiddenCost.java
import java.util.ArrayList;
    import java.util.HashSet;
    import java.util.List;
    import java.util.Set;
    
    public class HiddenCost {
    
        /** Looks O(n). Actually O(n^2): List.contains scans the whole list. */
        static int countDistinctSlow(int[] a) {
            List<Integer> seen = new ArrayList<>();
            for (int v : a) {
                if (!seen.contains(v)) {
                    seen.add(v);
                }
            }
            return seen.size();
        }
    
        /** Looks O(n). Actually O(n^2): every += copies the whole string. */
        static String joinSlow(int[] a) {
            String s = "";
            for (int v : a) {
                s += v + ",";
            }
            return s;
        }
    
        /** O(n): hashing makes the membership test O(1) expected. */
        static int countDistinctFast(int[] a) {
            Set<Integer> seen = new HashSet<>();
            for (int v : a) {
                seen.add(v);
            }
            return seen.size();
        }
    
        /** O(n): StringBuilder appends into a doubling buffer, O(1) amortised each. */
        static String joinFast(int[] a) {
            StringBuilder sb = new StringBuilder();
            for (int v : a) {
                sb.append(v).append(',');
            }
            return sb.toString();
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6, 5, 3};
            System.out.println(countDistinctSlow(a) + " " + countDistinctFast(a));
            System.out.println(joinFast(a));
        }
        // Input : [3,1,4,1,5,9,2,6,5,3]
        // Output: 7 7
        //         3,1,4,1,5,9,2,6,5,3,
    }

When you distrust an analysis, count. This prints the exact number of inner-loop executions so you can check it against your closed form.

JavaOperationCounter.java
public class OperationCounter {
    
        /** Dependent nesting: the inner bound depends on i. */
        static long countTriangular(int n) {
            long ops = 0;
            for (int i = 0; i < n; i++) {
                for (int j = i; j < n; j++) {
                    ops++;
                }
            }
            return ops;
        }
    
        /** Multiplicative shrinking: j is halved each step. */
        static long countLinearithmic(int n) {
            long ops = 0;
            for (int i = 0; i < n; i++) {
                for (int j = n; j > 0; j /= 2) {
                    ops++;
                }
            }
            return ops;
        }
    
        public static void main(String[] args) {
            for (int n : new int[] {8, 16, 32}) {
                long tri = countTriangular(n);
                long lin = countLinearithmic(n);
                System.out.println(n + ": triangular=" + tri + " (n(n+1)/2=" + (1L * n * (n + 1) / 2)
                        + "), linearithmic=" + lin + " (n*(log2(n)+1)="
                        + (1L * n * (Integer.numberOfTrailingZeros(n) + 1)) + ")");
            }
        }
        // Output: 8: triangular=36 (n(n+1)/2=36), linearithmic=32 (n*(log2(n)+1)=32)
        //         16: triangular=136 (n(n+1)/2=136), linearithmic=80 (n*(log2(n)+1)=80)
        //         32: triangular=528 (n(n+1)/2=528), linearithmic=192 (n*(log2(n)+1)=192)
    }

A minimal dynamic array that reports total copies, so the < 2n bound is something you have measured rather than something you were told.

JavaAmortisedGrowth.java
public class AmortisedGrowth {
    
        private int[] data = new int[1];
        private int size = 0;
        long copies = 0;
    
        void add(int v) {
            if (size == data.length) {
                int[] bigger = new int[data.length * 2];
                System.arraycopy(data, 0, bigger, 0, size);
                copies += size;                  // the only expensive part
                data = bigger;
            }
            data[size++] = v;
        }
    
        public static void main(String[] args) {
            for (int n : new int[] {1000, 100000, 1000000}) {
                AmortisedGrowth g = new AmortisedGrowth();
                for (int i = 0; i < n; i++) {
                    g.add(i);
                }
                System.out.println("n=" + n + " copies=" + g.copies
                        + " copies/n=" + String.format("%.2f", (double) g.copies / n));
            }
        }
        // Output: n=1000 copies=1023 copies/n=1.02
        //         n=100000 copies=131071 copies/n=1.31
        //         n=1000000 copies=1048575 copies/n=1.05
    }

Complexity

Time meta-topic Space meta-topic

The two series you need by heart. Arithmetic, from dependent nested loops:

1 + 2 + … + n = n(n+1)/2 = Θ(n²)

Geometric, from doubling and from halving:

1 + 2 + 4 + … + 2k = 2k+1 − 1 < 2 · 2k = Θ(2k)

The geometric bound is why capacity doubling is amortised O(1): total copies to reach size n are under 2n, so the average per operation is constant. It is also why halving a search space takes Θ(log n) steps: solving n / 2k = 1 gives k = log₂ n.

One more worth knowing, the harmonic series, which is where sieve-style loops come from:

n/1 + n/2 + n/3 + … + n/n = n · Hn ≈ n ln n = Θ(n log n)

That is exactly the cost of the Sieve of Eratosthenes' inner loops, and it explains why the sieve is O(n log log n) rather than O(n log n) once you restrict the outer loop to primes.

Edge cases and pitfalls

  • Treating a library call as free
    for (int v : a) if (list.contains(v)) … — reported as O(n) because there is one visible loop, but contains on a List is itself O(n), making it O(n²).
    Substitute every call's own cost before counting. Learn the table: ArrayList.contains / indexOf / remove(Object) are O(n); HashSet and HashMap are O(1) expected; TreeMap is O(log n).
  • Adding sequential blocks instead of taking the maximum
    "I sort, then do a linear pass, so it is O(n log n + n)" — then treating that as meaningfully different from O(n log n) and optimising the linear pass.
    O(n log n + n) = O(n log n). Optimise the dominant term only. The corollary is powerful: once you have paid for a sort, extra O(log n) work per element is free.
  • Ignoring the input-dependent factor
    Quoting graph algorithms as O(n²) or O(n log n) when the real parameter is the edge count. Dijkstra is O((V + E) log V), and on a dense graph E = V², so it is O(V² log V).
    Name every parameter: n and m, or V and E, or n and maxValue. A complexity with an unnamed parameter is not an answer.
  • Confusing pseudo-polynomial with polynomial
    Calling 0/1 knapsack "polynomial" because it is O(nW). If W = 10⁹ that is 10¹⁴ operations — W is a value, not an input length.
    Check whether a factor is a count of items or the magnitude of a number. O(nW), O(n · maxA) and O(√x) are pseudo-polynomial: usable only when the value bound is small, and always worth stating.
  • Forgetting recursion's space cost
    "DFS is O(V + E) time and O(1) space" — the call stack holds up to V frames, and on a path graph with V = 10⁵ that is a StackOverflowError, not a slow program.
    Recursion depth is space. Quote O(depth) auxiliary space, and switch to an explicit ArrayDeque stack when depth can reach 10⁵.
  • Assuming HashMap is always O(1)
    Relying on O(1) in a Codeforces solution keyed by Integer. Java's Integer.hashCode() is the value itself, so an adversary can feed keys that collide into one bucket and turn your pass into O(n log n) or worse per operation.
    In competitive settings either sort and use two pointers, or salt your keys: mix each key with a random 64-bit constant, or wrap it with Long.hashCode(x * 0x9E3779B97F4A7C15L) before inserting.
  • Optimising a constant instead of a class
    Spending twenty minutes replacing a % with a bit mask inside an O(n²) loop at n = 10⁵. A 2× win on 10¹⁰ operations is still a timeout.
    First check whether the class fits the constraint. Only micro-optimise when the class is correct and you are within about 5× of the limit.

Interview follow-ups

What is the difference between O, Θ and Ω, and why should I care?

O(f) is an upper bound, Ω(f) a lower bound, Θ(f) both. Every O(n) algorithm is also O(n²), which is why O alone is a weak claim. The reason to care is that Ω lets you argue optimality: "any algorithm must read all n elements, because changing an unread one changes the answer, so Ω(n) is a lower bound and my Θ(n) solution cannot be improved." That sentence ends the "can you do better?" line of questioning.

Why is comparison sorting Ω(n log n)?

A comparison sort's execution is a path down a binary decision tree, one branch per comparison. There are n! possible orderings, so the tree needs at least n! leaves, so its height is at least log₂(n!) = Θ(n log n) by Stirling. Hence no comparison sort beats n log n. The escape hatch is to stop comparing: counting and radix sort read the values themselves and achieve O(n + k).

Your solution is O(n log n) and still times out. What now?

Check, in this order. I/O: Scanner is roughly 10× slower than BufferedReader, and System.out.println in a loop is worse — buffer output in a StringBuilder. Boxing: Integer[], ArrayList<Integer> and PriorityQueue<int[]> allocate per element; switch to int[]. Hash attacks: salt your keys. Hidden factors: a String.substring or Math.pow inside the loop. None of these change the class, and all of them can be a 10× wall-clock difference.

How do I derive the complexity of a recursive function?

Write the recurrence, then solve it. Merge sort splits into two halves and merges linearly, so T(n) = 2T(n/2) + Θ(n), which the master theorem resolves to Θ(n log n). Binary search recurses once on half, so T(n) = T(n/2) + Θ(1) = Θ(log n). The full toolkit is in Recurrences & Master Theorem.

What does the inverse Ackermann function in DSU actually mean?

α(n) is the inverse of the Ackermann function, and it is below 5 for every n that fits in the universe. So amortised O(α(n)) is "constant for all practical purposes", and you may safely quote DSU with path compression plus union by size as effectively O(1) per operation — while noting it is not literally constant.

When is O(n²) the right answer?

Whenever the constraints allow it. If n ≤ 2000, an O(n²) solution you can write correctly in five minutes beats an O(n log n) one you debug for twenty. Interviewers care that you knew it was quadratic and chose it; the failure is not noticing.

Hint for LC 315 — deducing the intended complexity from constraints alone

n ≤ 10⁵ kills O(n²) (10¹⁰). The answer requires a count per index, so you cannot beat Ω(n). That leaves O(n log n), and the phrase "count of smaller elements to the right" is a counting-over-a-prefix problem → merge sort with an inversion count, or a Fenwick tree over compressed values. The transferable move: narrow the complexity from the constraints first, then ask which structure delivers that complexity.

Hint for CF 455A — when the complexity is not in terms of n

The sequence length is up to 10⁵ but the values are also up to 10⁵, and the operation deletes all copies of a value. So the state is the value, not the index: build cnt[v] and run a house-robber DP over v = 1 … 10⁵, giving O(maxA). The lesson: when a problem's operations are keyed by value, your complexity parameter is the value range, and long is required for the answer.

Recap

  • Count how many times the innermost statement runs, substituting the cost of every library call first. That single habit fixes most mis-analyses.
  • Sequential blocks take the max; independent nesting multiplies; dependent nesting sums a series (and still lands in the same class).
  • Budget 10⁸ operations per second, then divide by 2–5 for boxing and pointer chasing. Read the constraint backwards to get the intended complexity.
  • Amortised is not average-case. Doubling gives O(1) amortised because the geometric series of copies is bounded by 2n.
  • State time and space separately, and name every parameter (n, m, W, maxA). An unnamed parameter means the analysis is incomplete.
