Heavy-Light Decomposition

Split every root-path into O(log n) heavy chains so a segment tree on a flattened tree answers path queries in O(log² n).

Hard 32 min read Prerequisites: Binary Lifting & LCA, Segment Tree HLD trees segment tree P2

Why this exists

You are given a tree of people, each holding a number, and you must answer questions like "what is the sum of the numbers on the unique path from person 5 to person 7?". Walking parent pointers from both ends until they meet is correct, and it is also the first thing most people write. The trouble is the cost: a single walk can touch every node on a skinny tree, so one hundred thousand queries on one hundred thousand nodes is on the order of ten billion steps. The judge cuts you off long before that finishes.

A Fenwick tree or segment tree on a depth-first listing of the nodes will answer a subtree in one interval, because a subtree occupies a contiguous block of that listing. A path is not a subtree. On the seven-node tree that hangs 2 and 3 under 1, then 4 and 5 under 2, then 6 and 7 under 3, the path from 5 to 7 visits 5, 2, 1, 3, 7 — five nodes that do not sit next to each other in any standard listing. Heavy-light decomposition is the standard way to cut that path into a handful of contiguous pieces a segment tree can eat.

The cut is structural, and this is where the logarithm comes from. At every node, look at the sizes of the subtrees hanging off its children. The child with the largest subtree is the heavy child, and the edge down into it is a heavy edge; every other child edge is light. A light child v of u cannot own more than half of u's subtree: if it did, it would be strictly larger than everything else under u put together, and it would have been declared heavy. Crossing a light edge toward the root therefore lands you in a subtree at least twice as big as the one you just left.

Start at a leaf, whose subtree has size 1, and walk to the root, whose subtree has size n. Each light edge at least doubles the size you sit in, and a quantity that starts at 1 and doubles can reach n at most log₂ n times — about 17 doublings when n = 10⁵. A heavy chain is a maximal run of heavy edges, so you leave a chain only by taking a light edge. Any root-to-leaf path therefore lives on at most that many chains, plus the chain you started on. Lay each chain down as one contiguous segment of a global array, put a segment tree on that array, and a full path is a handful of range queries.

A light edge at least halves the subtree you leave behind, so a walk toward the root can take only log n light edges before the subtree has grown to the whole tree. Prefer the heavy child in the second DFS so each heavy chain occupies one contiguous interval a segment tree can query.

Recognise this pattern

Say yes when you see

  • Path aggregate or path update on a tree: sum, min, XOR, add-on-path
  • "Sum of node values from u to v" with point updates
  • Subtree queries and path queries on the same tree (HLD DFS order does both)
  • n, q ≤ 10⁵ on a tree, so O(log² n) per query is the intended budget
  • You already have LCA and a segment tree and the missing piece is "the path is not an interval"

Not this pattern when

  • Only subtree queries → Euler tour + Fenwick / segment tree, no HLD
  • Static path-min / path-max → binary lifting or a sparse table on the Euler tour
  • Distance-only queries → precompute depths and LCA, no values to aggregate
  • Centroid / small-to-large problems ("count pairs at distance k") → a different decomposition

Constraint tell: n, q ≤ 2×10⁵ on a tree, with path aggregates or path updates, is the HLD signature. Walking to the LCA would cost about 4×1010 steps and time out. O(log² n) per query is roughly three hundred segment-tree hops times two hundred thousand queries, which Java usually accepts. Drop the extra log with a Fenwick tree when the operation is prefix-friendly (sum, XOR) and you only need point updates.

Core idea and the invariant

You need two depth-first searches and a handful of arrays. The first search fills sz[u] (how many nodes live in the subtree of u, including u itself), par[u] (the parent), depth[u] (distance from the root), and heavy[u] (the child whose subtree is largest, or -1 if u is a leaf). That first pass does not assign positions yet; it only decides, at every node, which single outgoing edge is heavy. Ties can be broken by taking the first child you see.

The second search assigns each node a position pos[u] in a flat array of length n, and records head[u] — the topmost node of the heavy chain that contains u. The rule that makes a chain one interval is this: when you leave u, recurse into heavy[u] first and pass the same head down. Only after that chain is laid out do you visit the light children, each of which starts a brand-new chain with itself as the head. Because a whole subtree is still visited together, the nodes of u's subtree occupy the contiguous half-open interval [pos[u], pos[u]+sz[u]), which is why the same flattening answers subtree queries for free.

A path query from u to v lifts the deeper chain-head up one chain at a time. While head[u] and head[v] differ, compare depth[head[u]] against depth[head[v]] (the heads, not the nodes), query the closed interval from the deeper head down to that pointer, then jump that pointer to par[head[...]], which is one light edge above the chain you just finished. When the two pointers finally share a head they sit on the same chain, and you query the closed interval between their positions once. Always lift the deeper side first so the two pointers meet on the chain that contains their lowest common ancestor.

Walk the seven-node sample. Subtree sizes are 7, 3, 3, 1, 1, 1, 1 at nodes 1 through 7. Node 1 ties between children of size 3, so say 2 is heavy; node 2 then picks 4 as heavy. The heavy-first listing is 1, 2, 4, then light child 5, then light child 3 and its heavy child 6, then light child 7 — four chains. Path 5 to 7 queries chain B (just 5), jumps to 2, queries 1-2 on chain A, jumps to 3, queries 3 on chain C, and finishes with 7 on chain D.

Every root-to-node path crosses at most log₂ n light edges, and therefore lives on O(log n) heavy chains. After a heavy-first DFS, the nodes of the chain from head[u] down to u occupy the contiguous segment-tree interval [pos[head[u]], pos[u]].

# light edges on a root-path ≤ log₂ n

In plain words, you are not hoping the path is short — you are guaranteeing that it changes chains only when the remaining tree at least doubles, which cannot happen more than a logarithm of times. Interview sentence: "I lift the deeper chain-head until both sides share a head, then I query the one leftover in-chain segment."

Why a light edge really halves the tree

Write sz[u] for the number of nodes in u's subtree. If v is a light child and sz[v] > sz[u]/2, then the other children of u together hold fewer than sz[u]/2 nodes, so v is strictly the unique heaviest child — contradicting the label "light". Therefore sz[v] ≤ sz[u]/2. Walking toward the root, each light edge replaces a subtree of size s with one of size at least 2s. From 1 to n that product of doublings is at most log₂ n. Heavy edges do not help the count and do not hurt it: they stay inside one chain.

Subtree queries come free

Heavy-first is still a valid DFS, so the subtree of u is exactly [pos[u], pos[u]+sz[u]). One segment-tree range, no chain walking. That is why statements that mix "sum on the path" with "sum in the subtree" are still HLD.

Algorithm

  1. DFS 1 — measure the tree. Fill sz, par, depth, and heavy[u] (the child of maximum sz) so the second pass already knows which single edge at each node must stay on the current chain.
  2. DFS 2 — flatten heavy-first. Assign pos[u] and head[u], always recursing into heavy[u] with the same head before any light child, so each chain occupies one contiguous block of the array.
  3. Build the range structure. Write every val[u] into a Fenwick or segment tree at index pos[u], because from now on every path or subtree query talks to this flat array, not to the original tree.
  4. pathQuery(u, v) — lift the deeper head. While the heads differ, query [pos[head[u]], pos[u]] on the deeper side and jump u = par[head[u]], which crosses the one light edge that ends that chain.
  5. Same chain — one closed interval. Once both pointers share a head they sit on the LCA's chain, so query the closed interval between pos[u] and pos[v] exactly once and do not add the LCA a second time.
  6. Updates and subtrees use the same addresses. A point update writes the cell at pos[u]; a subtree query is the single interval [pos[u], pos[u]+sz[u]) because the second DFS still visits a whole subtree together.

Java implementation

Walk parent pointers to the LCA. Correct, O(n) per query.

JavaPathSumBrute.java
public class PathSumBrute {
        static int[] par, val, depth;
        static int lca(int u, int v) {
            while (depth[u] > depth[v]) u = par[u];
            while (depth[v] > depth[u]) v = par[v];
            while (u != v) { u = par[u]; v = par[v]; }
            return u;
        }
        static int pathSum(int u, int v) {
            int a = lca(u, v), s = val[a];
            while (u != a) { s += val[u]; u = par[u]; }
            while (v != a) { s += val[v]; v = par[v]; }
            return s;
        }
        public static void main(String[] args) {
            par = new int[] {0, 0, 1, 1, 2, 2, 3, 3};
            val = new int[] {0, 1, 2, 3, 4, 5, 6, 7};
            depth = new int[] {0, 0, 1, 1, 2, 2, 2, 2};
            System.out.println(pathSum(5, 7));
        }
        // Input : tree 1-2-4/5, 1-3-6/7, values = ids
        // Output: 18
    }

Full HLD with a Fenwick tree for path sums and point updates.

JavaHldPathSum.java
import java.util.*;
    public class HldPathSum {
        int n, timer;
        List<Integer>[] g;
        int[] par, depth, sz, heavy, head, pos, val;
        long[] bit;
        HldPathSum(int n) {
            this.n = n;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            par = new int[n]; depth = new int[n]; sz = new int[n];
            heavy = new int[n]; Arrays.fill(heavy, -1);
            head = new int[n]; pos = new int[n]; val = new int[n];
            bit = new long[n + 2];
        }
        void add(int u, int v) { g[u].add(v); g[v].add(u); }
        void dfsSz(int u, int p) {
            par[u] = p; sz[u] = 1;
            int best = 0;
            for (int v : g[u]) if (v != p) {
                depth[v] = depth[u] + 1;
                dfsSz(v, u);
                sz[u] += sz[v];
                if (sz[v] > best) { best = sz[v]; heavy[u] = v; }
            }
        }
        void dfsHld(int u, int h) {
            head[u] = h; pos[u] = timer++;
            if (heavy[u] != -1) dfsHld(heavy[u], h);
            for (int v : g[u]) if (v != par[u] && v != heavy[u]) dfsHld(v, v);
        }
        void bitAdd(int i, long x) { for (i++; i <= n; i += i & -i) bit[i] += x; }
        long bitSum(int i) { long s = 0; for (i++; i > 0; i -= i & -i) s += bit[i]; return s; }
        long bitRange(int l, int r) { return bitSum(r) - bitSum(l - 1); }
        long pathSum(int u, int v) {
            long s = 0;
            while (head[u] != head[v]) {
                if (depth[head[u]] < depth[head[v]]) { int t = u; u = v; v = t; }
                s += bitRange(pos[head[u]], pos[u]);
                u = par[head[u]];
            }
            if (depth[u] > depth[v]) { int t = u; u = v; v = t; }
            s += bitRange(pos[u], pos[v]);
            return s;
        }
        public static void main(String[] args) {
            HldPathSum h = new HldPathSum(7);
            int[][] e = {{0,1},{0,2},{1,3},{1,4},{2,5},{2,6}};
            for (int[] x : e) h.add(x[0], x[1]);
            for (int i = 0; i < 7; i++) h.val[i] = i + 1;
            h.dfsSz(0, -1); h.dfsHld(0, 0);
            for (int i = 0; i < 7; i++) h.bitAdd(h.pos[i], h.val[i]);
            System.out.println(h.pathSum(4, 6));
        }
        // Input : same 7-node tree, values 1..7, query 5 to 7 (0-based 4,6)
        // Output: 18
    }

The query walk, isolated. Plug any range structure in for seg.query.

JavaHldTemplate.java
public class HldTemplate {
        static int[] head, par, depth, pos;
        static long queryRange(int l, int r) { return 0; } // segtree
        static long pathQuery(int u, int v) {
            long ans = 0;
            while (head[u] != head[v]) {
                if (depth[head[u]] < depth[head[v]]) { int t = u; u = v; v = t; }
                ans += queryRange(pos[head[u]], pos[u]);
                u = par[head[u]];
            }
            if (pos[u] > pos[v]) { int t = u; u = v; v = t; }
            ans += queryRange(pos[u], pos[v]);
            return ans;
        }
        public static void main(String[] args) {
            head = new int[] {0, 0, 2, 0, 4, 2, 6};
            par = new int[] {-1, 0, 0, 1, 1, 2, 2};
            depth = new int[] {0, 1, 1, 2, 2, 2, 2};
            pos = new int[] {0, 1, 4, 2, 3, 5, 6};
            System.out.println(pathQuery(4, 6));
        }
        // Input : heads/pos of the 7-node example
        // Output: 0
    }

Complexity

Time O(n) preprocess, O(log^2 n) per query Space O(n)

The logarithm is not a slogan. If v is a light child of u then sz[v] ≤ sz[u]/2, because a larger child would have been the unique heavy child. Walking from any node toward the root, each light edge therefore at least doubles the subtree size you sit in. A size that starts at 1 and doubles can reach n at most log₂ n times, so a node has O(log n) light ancestors and a root-path uses O(log n) chains. A u–v path is two root-paths minus the shared prefix, still O(log n) chains.

Each chain is one contiguous interval, and a segment tree answers that interval in O(log n) hops. The product is the familiar extra log:

Tquery = O(log n) chains × O(log n) = O(log² n)

Putting real numbers in: at n = 2×10⁵ you have about 18 light edges on a worst-case root-path and about 18 hops per segment-tree range, so one query is a few hundred array reads. Two hundred thousand of them stay near 6×107 operations, which Java accepts. The preprocess is two linear DFS passes plus a linear segment-tree build, so it is lost in the noise. A Fenwick tree in place of the segment tree does not remove the chain-count log; it only makes the per-chain constant smaller.

Edge cases and pitfalls

  • DFS does not prefer the heavy child
    Visiting children in input order looks like a normal DFS and still produces a valid Euler-style listing, so the code type-checks and subtree queries even look right. But a "chain" is no longer a contiguous pos interval, and every path query that assumes it is returns garbage.
    In the second DFS, recurse into heavy[u] before any light child, and pass the same head. Test by printing pos along a known heavy path and checking the indices are consecutive.
  • Forgetting to lift the deeper head
    Comparing depth[u] instead of depth[head[u]] looks like the usual LCA lift, and it works on a path that is already a single chain. On two chains of different head-depths it walks off the LCA, double-counts a prefix, or loops.
    Always compare depth[head[u]] against depth[head[v]] and lift the deeper chain. Test on a path whose two sides have different chain lengths.
  • Off-by-one on the in-chain segment
    Half-open [pos[u], pos[v]) is what Fenwick range helpers often want, so dropping the last index looks consistent with the rest of the file. It silently drops the LCA node — or, if both sides add it before they meet, counts it twice.
    After heads meet, query the closed interval between the two positions once. On a one-node path (u == v) the answer must be exactly val[u].
  • 1-index vs 0-index mix
    The root's parent is 0 or -1, Fenwick index 0 is unused, and bitAdd(pos[root], x) looks like it writes the root's cell. If pos is 0-based and the Fenwick is 1-based you write the wrong slot, and every query that includes the root is off by val[root].
    Pick one convention and convert at the boundary. If pos is 0-based, call bitAdd(pos[u] + 1, x). Test a point update on the root and a path query that includes it.
  • Updating values after HLD without writing the tree
    Changing val[u] and then calling pathQuery looks correct because the brute-force walk reads val. After HLD the source of truth is the Fenwick or segment-tree cell at pos[u]; the original array is only the build source.
    Point update is tree.update(pos[u], newValue). Test by updating a leaf and querying a path that contains only that leaf.

Interview follow-ups

Why is the bound O(log n) chains, not O(n)?

A light child owns at most half its parent's subtree — otherwise it would have been the unique heavy child. Crossing a light edge toward the root therefore at least doubles the subtree you sit in. Starting from a leaf of size 1, you can double at most log₂ n times before you reach the whole tree, so a root-path meets at most that many light edges. A chain changes only at a light edge, which is why the chain count, not the path length, is logarithmic.

Can you get O(log n) instead of O(log^2 n)?

The extra log is the segment tree (or Fenwick) on each chain range, not the chain count. Prefix-friendly operations with point updates still pay O(log n) per chain, so the product stays O(log² n). True O(log n) path queries need a heavier structure such as a top tree or a link-cut tree, which almost no contest problem expects you to write.

How do you handle edge weights?

Assign the edge (p, u) to node u, so each node stores the weight of the edge into its parent. When the two pointers sit on the same chain, query the half-open interval (pos[lca], pos[deeper]] so the LCA node — which holds the parent edge, not an edge on this path — is excluded. Point updates then write the child endpoint.

HLD versus centroid for "count pairs at distance k"?

HLD linearises paths so you can aggregate along one path; it does not enumerate pairs. Counting pairs that satisfy a numeric constraint needs a separator so you can join two independent sides, which is centroid decomposition in O(n log n). Use the tool that matches the query shape: path aggregates are HLD, pair counts are centroid.

Recap

  • Heavy child = largest subtree; a light edge halves size.
  • Second DFS prefers the heavy child so a chain is contiguous.
  • Path query = O(log n) chain ranges, always lift the deeper head.
  • Subtree query is a single [pos, pos+sz) interval.
  • Edge weights live on the child; skip the LCA node.
