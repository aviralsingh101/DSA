Small-to-Large Merging

Always merge the smaller sack into the larger. Each node is moved O(log n) times, so subtree-map problems become O(n log n).

Medium 22 min read Prerequisites: DFS & Components, Sorting & Comparators dsu on tree small to large sack P2

Why this exists

A whole family of tree problems wants, for every node, some statistic of its subtree: number of distinct colours, the most frequent colour, a map of values. Building a fresh HashMap per node and inserting every descendant is O(n²).

Small-to-large (also called DSU-on-tree) keeps one map per subtree and always merges the smaller into the larger. When a value moves, the map it lives in at least doubles, so each value moves O(log n) times. Total is O(n log n) map operations.

The implementation is a DFS that identifies the heaviest child, computes it first and keeps its map as the parent's sack, then merges the lighter children in. That is the same heavy-child idea as HLD, used for maps instead of paths.

A value that is copied into a larger map now sits in a container at least twice as big. It can be copied at most log n times before the map is the whole tree.

Recognise this pattern

Say yes when you see

  • For every node, a statistic of the multiset of values in its subtree
  • "Number of distinct colours in the subtree"
  • "Most frequent colour in the subtree" (CF 600E Lomsat gelral)
  • You would write map[u] = merge(map[children]) if that were cheap
  • n ≤ 10⁵ with a subtree-of-values flavour

Not this pattern when

  • Path queries → HLD
  • Pair counts that cross a node → centroid
  • The statistic is a simple sum / min you can compute in one DFS without a map
  • Updates between queries that invalidate sacks → you need a persistent or segment-tree-of-maps structure

Constraint tell: n ≤ 10⁵ with a per-subtree map. HashMap operations make the hidden constant larger than a Fenwick tree; it still passes typical 2-second Java limits.

Core idea and the invariant

DFS computes subtree sizes, then processes the heavy child first without clearing its map. That map becomes the parent's sack. Each light child is computed, merged in, and can then be discarded.

If you need the answer at every node, record it after the light children are merged and before you return. If a caller is a light child of someone else, you will rebuild this sack from scratch next time — that is paid for by the doubling bound.

When a key is inserted into a larger map, the map size at least doubles. Each of the n values is therefore moved O(log n) times, and the whole DFS is O(n log n) map operations.

Structure

Algorithm

  1. DFS sizes so you know the heavy child.
  2. Recurse heavy first and steal its map — do not copy.
  3. Recurse each light child, merge its map into the stolen one, then drop it.
  4. Insert the node's own value.
  5. Record the answer for this node.
  6. If this node is a light child of its parent, the parent will rebuild; that is fine.

Java implementation

Rebuild a set from every descendant. O(n^2).

JavaDistinctBrute.java
import java.util.*;
    public class DistinctBrute {
        static List<Integer>[] g;
        static int[] col, ans;
        static Set<Integer> dfs(int u, int p) {
            Set<Integer> s = new HashSet<>();
            s.add(col[u]);
            for (int v : g[u]) if (v != p) s.addAll(dfs(v, u));
            ans[u] = s.size();
            return s;
        }
        public static void main(String[] args) {
            int n = 7;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1},{0,2},{1,3},{1,4},{2,5},{2,6}};
            for (int[] x : e) { g[x[0]].add(x[1]); g[x[1]].add(x[0]); }
            col = new int[] {1, 2, 2, 3, 1, 3, 2};
            ans = new int[n];
            dfs(0, -1);
            System.out.println(Arrays.toString(ans));
        }
        // Input : colours [1,2,2,3,1,3,2]
        // Output: [3, 3, 2, 1, 1, 1, 1]
    }

Steal the heavy child's map, merge the rest.

JavaSmallToLarge.java
import java.util.*;
    public class SmallToLarge {
        List<Integer>[] g;
        int[] col, sz, heavy, ans;
        List<Map<Integer, Integer>> sack;
        SmallToLarge(int n) {
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            col = new int[n]; sz = new int[n]; heavy = new int[n];
            Arrays.fill(heavy, -1); ans = new int[n];
            sack = new ArrayList<>();
            for (int i = 0; i < n; i++) sack.add(null);
        }
        void add(int u, int v) { g[u].add(v); g[v].add(u); }
        void dfsSz(int u, int p) {
            sz[u] = 1;
            int best = 0;
            for (int v : g[u]) if (v != p) {
                dfsSz(v, u); sz[u] += sz[v];
                if (sz[v] > best) { best = sz[v]; heavy[u] = v; }
            }
        }
        Map<Integer, Integer> merge(Map<Integer, Integer> a, Map<Integer, Integer> b) {
            if (a.size() < b.size()) { Map<Integer, Integer> t = a; a = b; b = t; }
            for (var e : b.entrySet()) a.merge(e.getKey(), e.getValue(), Integer::sum);
            return a;
        }
        void dfs(int u, int p) {
            Map<Integer, Integer> cur = new HashMap<>();
            if (heavy[u] != -1) { dfs(heavy[u], u); cur = sack.get(heavy[u]); }
            for (int v : g[u]) if (v != p && v != heavy[u]) {
                dfs(v, u);
                cur = merge(cur, sack.get(v));
            }
            cur.merge(col[u], 1, Integer::sum);
            ans[u] = cur.size();
            sack.set(u, cur);
        }
        public static void main(String[] args) {
            SmallToLarge t = new SmallToLarge(7);
            int[][] e = {{0,1},{0,2},{1,3},{1,4},{2,5},{2,6}};
            for (int[] x : e) t.add(x[0], x[1]);
            t.col = new int[] {1, 2, 2, 3, 1, 3, 2};
            t.dfsSz(0, -1); t.dfs(0, -1);
            System.out.println(Arrays.toString(t.ans));
        }
        // Input : same tree and colours
        // Output: [3, 3, 2, 1, 1, 1, 1]
    }

The doubling merge, usable on arrays of sets too.

JavaMergeSmallIntoLarge.java
import java.util.*;
    public class MergeSmallIntoLarge {
        static <T> Set<T> merge(Set<T> a, Set<T> b) {
            if (a.size() < b.size()) { Set<T> t = a; a = b; b = t; }
            a.addAll(b);
            return a;
        }
        public static void main(String[] args) {
            Set<Integer> a = new HashSet<>(List.of(1, 2, 3));
            Set<Integer> b = new HashSet<>(List.of(3, 4));
            Set<Integer> c = merge(a, b);
            System.out.println(c.size());
        }
        // Input : {1,2,3} and {3,4}
        // Output: 4
    }

Complexity

Time O(n log n) map operations Space O(n)

Each time a key is copied, it lands in a map at least twice as large. A key starting in a singleton can be copied at most log n times. n keys give O(n log n).

Edge cases and pitfalls

  • Copying the heavy child's map
    new HashMap<>(heavyMap) destroys the bound — you pay linear in the heavy size at every level.
    Steal the reference. The heavy child does not need its map after you have recorded ans[heavy].
  • Merging large into small
    The doubling argument requires the target to be the larger map.
    Swap if a.size() < b.size() before iterating.
  • Recording the answer after discarding the sack
    You merge, return, then try to read a map you already cleared.
    Write ans[u] while the merged map still belongs to u.
  • Using this for path queries
    A sack is the subtree multiset, not the path. Path problems look similar in the statement and are HLD.
    Ask: is the queried set a subtree or a path? Subtree → small-to-large; path → HLD.
  • HashMap on tight limits without reserving
    Rehash storms on Java 8 HashMap can TLE at n = 2e5.
    Size-hint the first map, or use arrays when values are compressed to [1, n].

Interview follow-ups

Why is this also called DSU-on-tree?

You are unioning child sacks into a parent the same way DSU unions components — always small into large. The "DSU" is a metaphor; there is no rollback-free disjoint-set structure unless you add one.

Can you answer path queries this way?

No. A sack is the subtree. For a path you need HLD, or a persistent segment tree on the Euler / DFS order.

What if values are large (1e9)?

HashMap is fine. If you need order statistics, compress coordinates first and use a Fenwick of counts inside the sack.

How do you handle updates to a node's colour?

Small-to-large is a static DFS. Updates need a different structure: HLD + fenwick-of-colours, or a segment tree with sets.

Recap

  • Always merge the smaller map into the larger.
  • Steal the heavy child's map; do not copy it.
  • Each value moves O(log n) times because the host doubles.
  • Record ans[u] before returning the sack.
  • Subtree sacks, not paths — paths are HLD.
