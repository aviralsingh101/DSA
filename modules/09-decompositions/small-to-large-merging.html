Small-to-Large Merging

Always merge the smaller sack into the larger. Each node is moved O(log n) times, so subtree-map problems become O(n log n).

Medium 28 min read Prerequisites: DFS & Components, Sorting & Comparators dsu on tree small to large sack P2

Why this exists

You are given a tree where every node has a colour, and you must report, for every node, how many distinct colours sit in its subtree. The honest code builds a fresh HashSet at each node and inserts every descendant. On a hundred thousand nodes that is about ten billion insertions if the tree is a straight line of parents, and the judge will not wait. The same quadratic wall appears for "most frequent colour in the subtree" and for any other statistic that wants the whole multiset of values under a node.

Small-to-large merging, also called DSU-on-tree, keeps one map per subtree and always pours the smaller map into the larger one. That is the same habit as union-by-size on the disjoint-set page: hang the smaller group under the larger so a group only grows when it absorbs something no bigger than itself. Here the "group" is a sack — the map of values collected from a subtree. When a particular colour is copied out of a sack of L nodes into a sack that already holds at least L nodes, it now lives in a sack of size at least 2L.

A colour that starts in a singleton can therefore be copied at most log₂ n times before its host sack is the whole tree — about 17 moves when n = 10⁵, not n moves. One hundred thousand colours times seventeen copies is a couple of million map operations, which is the intended budget. The implementation is a DFS that identifies the heaviest child, computes it first, and steals its map as the parent's sack, then merges each lighter child in. That is the same heavy-child idea as heavy-light decomposition, used here for maps instead of path intervals.

In a real statement the signal is a per-subtree map sitting next to n ≤ 10⁵. If the queried set is a path rather than a subtree, this page is the wrong tool and you want HLD. If the queried set is pairs that cross a node, you want centroid decomposition. The three techniques share a logarithm; they do not share a query shape.

A value that is copied into a larger sack now sits in a container at least twice as big, so it can be copied at most log n times before that container is the whole tree. Steal the heavy child's map rather than copying it, or you pay linear work at every ancestor and the bound collapses to quadratic.

Recognise this pattern

Constraint tell: n ≤ 10⁵ with a statistic of the multiset of values in every subtree is the small-to-large signature. HashMap constants are larger than a Fenwick tree; a couple of million merges still pass a typical two-second Java limit.

Core idea and the invariant

A first DFS fills sz[u] and heavy[u], exactly as on the HLD page: the heavy child is the one with the largest subtree. The second DFS is the merge. Recurse into heavy[u] first and steal the reference to its map — do not write new HashMap<>(heavyMap). That stolen map is now the sack of u. Then recurse into each light child, merge that child's map into the stolen one (iterating the smaller of the two, which is the light one), and drop the light map. Finally insert u's own colour into the sack.

If you need the answer at every node, write ans[u] after the light children are merged and the node's own value is in, and before you return the sack to the parent. When u itself is a light child of somebody else, that parent will copy every key in this sack into a larger one and then forget this map. Rebuilding it from scratch the next time you need those keys is exactly the work the doubling argument is paying for. When u is a heavy child, the parent steals the map and those keys are not copied at this level at all.

Walk the seven-node sample with colours [1, 2, 2, 3, 1, 3, 2] at nodes 1 through 7. Leaves 4 and 5 hold singleton sacks {3} and {1}. Node 2 keeps 4's sack (the first child, size 1, a tie) and copies 5's colour in, then adds its own 2, ending with three distinct colours. Node 3 does the same with 6 and 7 and ends with two. The root keeps the larger child sack — node 2, three keys — and copies node 3's two keys in. Colour 2 moves from node 3's sack of two nodes into a sack that already holds three, and now lives in a sack of five; that is one doubling, and it will not move again.

When a key is copied from a sack of L tree-nodes into a sack that already holds at least L tree-nodes, the key's new host has size at least 2L. Each of the n values is therefore copied O(log n) times, and the whole DFS is O(n log n) map operations.

host after a copy ≥ 2 × host before it

In plain words, you only ever iterate the smaller sack, so every time a particular colour is touched it graduates to a club at least twice as big, and a club cannot double more than a logarithm of times before it is the whole tree. Interview sentence: "I steal the heavy child's map and I only copy light children, so each value moves log n times."

Why each element moves only log n times

Measure a sack by the number of tree nodes whose values currently live in it, not by the number of distinct keys. The heavy child's sack already holds at least as many nodes as any one light child. When you iterate a light sack of L nodes and pour it into that larger sack, every copied value now lives in a sack of size at least L + L = 2L. A value starts in a sack of 1 (itself) and the host can double at most log₂ n times before it contains the whole tree. Values that sit in a heavy sack are not copied at this node at all — the parent steals the reference — so the only copies that happen are the ones the doubling argument is counting. Copying the heavy map with new HashMap<>(heavy) charges O(sz[heavy]) at every ancestor and the same node is copied O(n) times, which is the quadratic you were trying to avoid.

The DSU metaphor

Union-by-size hangs the smaller component under the larger one so a component only grows when it absorbs something no bigger than itself. Small-to-large does the same thing to subtree maps. There is no parent[] array and no path compression unless you add them; "DSU-on-tree" names the doubling habit, not the data structure.

Structure

Algorithm

  1. DFS sizes first. Fill sz[u] and heavy[u] so the merge pass already knows which one child is allowed to keep its map and which children must be copied.
  2. Recurse into the heavy child and steal its map. Do not write new HashMap<>(heavyMap); take the reference, because copying the heavy keys at every ancestor is exactly the quadratic the doubling argument forbids.
  3. Recurse each light child, then merge small into large. Iterate the light map, pour it into the stolen one, and drop it. If a helper ever sees the target smaller than the source, swap first so the doubling still holds.
  4. Insert the node's own value last. The sack of u is the union of its children plus u itself, so the node's colour has to land in the map before you read any statistic off it.
  5. Record ans[u] while the sack still belongs to u. After you return, a light parent will copy these keys and forget this map, so a later read of the same reference is no longer the subtree of u.
  6. A light child is allowed to be rebuilt. If u is itself a light child, the parent will copy every key; that rebuild is the one doubling this value is charged for, and it is why the total stays O(n log n).

Java implementation

Rebuild a set from every descendant. O(n^2).

JavaDistinctBrute.java
import java.util.*;
    public class DistinctBrute {
        static List<Integer>[] g;
        static int[] col, ans;
        static Set<Integer> dfs(int u, int p) {
            Set<Integer> s = new HashSet<>();
            s.add(col[u]);
            for (int v : g[u]) if (v != p) s.addAll(dfs(v, u));
            ans[u] = s.size();
            return s;
        }
        public static void main(String[] args) {
            int n = 7;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1},{0,2},{1,3},{1,4},{2,5},{2,6}};
            for (int[] x : e) { g[x[0]].add(x[1]); g[x[1]].add(x[0]); }
            col = new int[] {1, 2, 2, 3, 1, 3, 2};
            ans = new int[n];
            dfs(0, -1);
            System.out.println(Arrays.toString(ans));
        }
        // Input : colours [1,2,2,3,1,3,2]
        // Output: [3, 3, 2, 1, 1, 1, 1]
    }

Steal the heavy child's map, merge the rest.

JavaSmallToLarge.java
import java.util.*;
    public class SmallToLarge {
        List<Integer>[] g;
        int[] col, sz, heavy, ans;
        List<Map<Integer, Integer>> sack;
        SmallToLarge(int n) {
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            col = new int[n]; sz = new int[n]; heavy = new int[n];
            Arrays.fill(heavy, -1); ans = new int[n];
            sack = new ArrayList<>();
            for (int i = 0; i < n; i++) sack.add(null);
        }
        void add(int u, int v) { g[u].add(v); g[v].add(u); }
        void dfsSz(int u, int p) {
            sz[u] = 1;
            int best = 0;
            for (int v : g[u]) if (v != p) {
                dfsSz(v, u); sz[u] += sz[v];
                if (sz[v] > best) { best = sz[v]; heavy[u] = v; }
            }
        }
        Map<Integer, Integer> merge(Map<Integer, Integer> a, Map<Integer, Integer> b) {
            if (a.size() < b.size()) { Map<Integer, Integer> t = a; a = b; b = t; }
            for (var e : b.entrySet()) a.merge(e.getKey(), e.getValue(), Integer::sum);
            return a;
        }
        void dfs(int u, int p) {
            Map<Integer, Integer> cur = new HashMap<>();
            if (heavy[u] != -1) { dfs(heavy[u], u); cur = sack.get(heavy[u]); }
            for (int v : g[u]) if (v != p && v != heavy[u]) {
                dfs(v, u);
                cur = merge(cur, sack.get(v));
            }
            cur.merge(col[u], 1, Integer::sum);
            ans[u] = cur.size();
            sack.set(u, cur);
        }
        public static void main(String[] args) {
            SmallToLarge t = new SmallToLarge(7);
            int[][] e = {{0,1},{0,2},{1,3},{1,4},{2,5},{2,6}};
            for (int[] x : e) t.add(x[0], x[1]);
            t.col = new int[] {1, 2, 2, 3, 1, 3, 2};
            t.dfsSz(0, -1); t.dfs(0, -1);
            System.out.println(Arrays.toString(t.ans));
        }
        // Input : same tree and colours
        // Output: [3, 3, 2, 1, 1, 1, 1]
    }

The doubling merge, usable on arrays of sets too.

JavaMergeSmallIntoLarge.java
import java.util.*;
    public class MergeSmallIntoLarge {
        static <T> Set<T> merge(Set<T> a, Set<T> b) {
            if (a.size() < b.size()) { Set<T> t = a; a = b; b = t; }
            a.addAll(b);
            return a;
        }
        public static void main(String[] args) {
            Set<Integer> a = new HashSet<>(List.of(1, 2, 3));
            Set<Integer> b = new HashSet<>(List.of(3, 4));
            Set<Integer> c = merge(a, b);
            System.out.println(c.size());
        }
        // Input : {1,2,3} and {3,4}
        // Output: 4
    }

Complexity

Time O(n log n) map operations Space O(n)

Measure each sack by the number of tree nodes in it. The heavy child's sack is already at least as large as any one light child. Copying a light sack of L nodes into that larger sack places every copied value in a host of size at least 2L. A value starts in a sack of 1 and the host can double at most log₂ n times before it is the whole tree, so each of the n values is copied O(log n) times. Heavy keys are not copied at the current node — the parent steals the reference — so they are charged only when this whole node later sits on the light side of somebody else.

T = n values × O(log n) copies = O(n log n) map operations

Putting real numbers in: at n = 10⁵ you have at most about 17 copies per value, for a couple of million HashMap operations. Java's hash constant is larger than a Fenwick hop, but two million still fits a two-second limit. Copy the heavy map instead and each of the n ancestors of a leaf on a line pays linear work, which is n² / 2 insertions, about five billion, and the solution TLEs. The space is one map entry per live key; stolen references mean you do not keep n full copies at once.

Edge cases and pitfalls

  • Copying the heavy child's map
    new HashMap<>(heavyMap) looks tidy and is correct: the parent really does hold a copy of the heavy keys. It also charges O(sz[heavy]) at every ancestor, so a line of nodes copies the same leaf n times and the doubling bound collapses to quadratic.
    Steal the reference. The heavy child does not need its map after you have recorded ans[heavy]. Test on a path graph: the heavy spine must not allocate a new map at every node.
  • Merging large into small
    Always iterating b into a looks fine when the caller already passed (heavy, light). A helper that does not swap will, on a tie or a swapped call, copy the larger map into the smaller one and a single value can move a linear number of times.
    Swap if a.size() < b.size() before iterating, the same way DSU hangs the smaller root under the larger. Test by merging a singleton into a map of size 100 and then the other way around; both must iterate the singleton.
  • Recording the answer after discarding the sack
    Returning the map and then writing ans[u] = sack.get(u).size() at the parent looks like a clean split of "merge" and "read". By then a light parent may already have copied and dropped this map, so you read an empty or reused object.
    Write ans[u] while the merged map still belongs to u, before the function returns. Test that every ans[u] matches a brute-force set built from the descendants of u.
  • Using this for path queries
    "Distinct values from u to v" looks like the same map problem, and a sack of descendants is sitting right there. A sack is the subtree multiset, not the path; using it for a path counts nodes that are off the path and misses nodes that are on it.
    Ask: is the queried set a subtree or a path? Subtree → small-to-large; path → HLD. Test on a path that is not a subtree: the sack answer and the true path answer must differ.
  • HashMap on tight limits without reserving
    A default-capacity HashMap per sack looks harmless and is correct. Java 8 rehash storms on a stream of n = 2×10⁵ insertions can push a tight limit into TLE even though the asymptotic bound holds.
    Size-hint the first map you allocate, or switch to arrays when values are compressed to [1, n]. Test the worst-case line with distinct colours and a two-second cap.

Interview follow-ups

Why is this also called DSU-on-tree?

You are unioning child sacks into a parent the same way disjoint-set union merges components: always the smaller into the larger, so an element moves only when its host at least doubles. The "DSU" is a metaphor for that doubling habit. There is no parent[] array, no path compression, and no rollback-free disjoint-set structure unless you add one on top for a different part of the problem.

Can you answer path queries this way?

No. A sack is the multiset of values in a subtree, which is a contiguous DFS interval but not a path. For a path you need heavy-light decomposition, or a persistent segment tree on the Euler or DFS order. If you catch yourself merging maps to answer "from u to v", stop and switch tools.

What if values are large (1e9)?

A HashMap keyed on the raw values is fine for distinct-count and mode. If you need order statistics inside the sack (the k-th colour, a range of values), compress coordinates down to [1, n] first and keep a Fenwick tree of counts, still merging small into large. Compression is a preprocess; it does not change the doubling bound.

How do you handle updates to a node's colour?

Small-to-large is a static DFS: the sacks are built once on the way back from the leaves. A colour change invalidates every sack on the path to the root, and there is no cheap way to patch them. Updates need a different structure, typically HLD plus a Fenwick of colours, or a segment tree whose nodes store sets. If the updates are offline, you can sometimes rebuild after each change for tiny n only.

Recap

  • Always merge the smaller map into the larger.
  • Steal the heavy child's map; do not copy it.
  • Each value moves O(log n) times because the host doubles.
  • Record ans[u] before returning the sack.
  • Subtree sacks, not paths — paths are HLD.
