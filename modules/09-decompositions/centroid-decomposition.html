Centroid Decomposition

A centroid splits every remaining component to size at most n/2. Recurse, and every pair of nodes meets at exactly one centroid ancestor.

Hard 30 min read Prerequisites: DFS & Components, Binary Lifting & LCA centroid trees divide and conquer P2

Why this exists

You are given a tree and you must answer questions about pairs of nodes: how many pairs sit at distance k, what is the closest painted node to u, which paths have a given XOR. The honest approach is to start a search from every node, or to list every pair. On a hundred thousand nodes that is about ten billion pair-looks, and the judge will not wait. You need a way to count or optimise pairs without ever writing a nested loop over the whole tree.

The way in is a balanced cut. A centroid of a tree is a node whose removal leaves every remaining piece of size at most half the original. Every tree has at least one (and at most two, adjacent). Once you have a centroid c, every pair of nodes falls into one of two buckets: the path between them goes through c, or both ends live in the same leftover piece. Solve the through-c bucket in linear time in the current piece, mark c dead so it never appears again, and recurse independently on each leftover piece.

The logarithm lives in the recursion depth, not in a heap or a segment tree. After c dies, every remaining component has size at most half of what you just processed. A node that is still alive in the next recursive call therefore sits in a component of size at most s/2. Starting from the whole tree of size n, after k such cuts the component has size at most n / 2k. The component becomes a single node once k reaches log₂ n — about 17 layers when n = 10⁵. Each node is visited in one linear scan per layer it belongs to, so the whole decomposition is O(n log n) work.

The parent pointers of those cuts form the centroid tree: the parent of a later centroid is the centroid that split it off. That tree has height O(log n), which is why the same construction also answers online questions. The answer for a node is an aggregate over its O(log n) centroid ancestors, each of which stores a summary of the layer it decomposed. In a real statement the signal is a pair-count or "paint this node, query the nearest painted" sitting next to n ≤ 10⁵.

Every pair of nodes has a unique deepest centroid that lies on the path between them. Solve the pairs that go through the current centroid, mark it dead, and recurse; the pieces at least halve, so the recursion is only log n layers deep.

Recognise this pattern

Core idea and the invariant

Finding a centroid is a short walk, not a search over every node. First run a size-DFS on the alive component only — dead nodes are invisible, as if they had been deleted — and let s be the number of live nodes you just counted. Then start at any live node and walk toward a child whose live subtree is strictly larger than s/2. The walk has to end: a leaf has no such child, and each step moves to a strictly smaller remaining question. The node where you stop has no child bigger than half, and the leftover parent-side is also at most half (you only arrived here because this side was the one bigger than s/2). That node is a centroid. Do not reuse sizes from an earlier layer; they still count dead nodes and will point at a fake centre.

Once you hold the centroid c, solve the pairs whose path goes through it. Depth-first-search the alive component from c, recording depths (or prefix XORs, weights, whatever the statement cares about) separately for each child. Combine a newly collected child against the children you have already seen, then merge it in. Two nodes from the same child do not go through c — their path stays inside that leftover piece and will be counted when that piece is decomposed. After the through-c work is done, set dead[c] = true and recurse on each remaining alive neighbour, each of which is now the seed of a component of size at most s/2.

Walk the seven-node sample. The full tree has size 7; node 1 has two children of size 3, both ≤ 7/2, so 1 is a centroid. Pairs that cross 1 (one end in {2, 4, 5}, the other in {3, 6, 7}) are counted here. Mark 1 dead. The left piece {2, 4, 5} has sizes 3, 1, 1, so 2 is its centroid; after 2 dies the two leaves are trivial. The right piece {3, 6, 7} is the same story with 3 in the middle. The centroid tree has 2 and 3 under 1, and the four leaves under those two — height 2, which is log₂ 7 rounded up.

In an alive component of size s, the centroid is a node whose removal leaves every remaining piece of size ≤ s/2. Recursion depth is therefore O(log n), and every pair of nodes has a unique deepest centroid that lies on the path between them.

snext ≤ s / 2  →  depth ≤ log₂ n

In plain words, you are allowed to do a linear amount of work on the current piece because you have paid for that work by guaranteeing the piece will never be this large again for any of those nodes. Interview sentence: "I solve through the centroid, mark it dead, and recurse on pieces that are at most half as big."

Why the centroid recursion is only log n deep

Let s be the number of alive nodes in the current component. By definition of a centroid, every remaining piece has size ≤ s/2. A node that survives into a recursive call is therefore inside a component of size at most half. Starting from n, the component containing a given node has size at most n, n/2, n/4, … until it is 1, which is at most log₂ n steps. Finding the centroid is a linear scan of the live component, so if you add up the scans that touch a particular node you get O(log n) visits per node and O(n log n) visits in total. The same halving is why the centroid tree has height O(log n).

Do not combine two nodes from the same child

Their path never touches the centroid. Those pairs belong to a deeper layer. Collect one child, query it against the map of previous children, then merge. Query-after-merge on the same child double-counts pairs a later centroid already owns.

Structure

Algorithm

  1. Find the centroid of the live piece. Size-DFS the alive nodes so you know s, then walk from any of them toward a child whose live size is > s/2 until no such child exists; that stop is a centroid.
  2. Solve the pairs that go through it. Collect depths or prefixes one child at a time, query each new child against the children already seen, then merge, so two nodes from the same child are never paired here.
  3. Mark the centroid dead immediately. Set dead[c] = true after the through-solve and before any recursive call, so the next size-DFS cannot walk back through c into a different leftover.
  4. Recurse on each leftover piece. Each alive neighbour of c seeds a component of size at most s/2, which is why the recursion depth stays logarithmic.
  5. Online queries walk the centroid tree. Store an aggregate at each centroid when you build, then a query at u walks the O(log n) centroid ancestors rather than climbing the original tree.
  6. Distances to those ancestors are precomputed. Use dist(u)+dist(c)-2*dist[lca] or store dist(u, c) while the layer is still live; a naive climb of the original tree makes an online query linear.

Java implementation

DFS from every node. Fine for n <= 2000.

JavaPairsDistKBrute.java
import java.util.*;
    public class PairsDistKBrute {
        static List<Integer>[] g;
        static int dfs(int u, int p, int d, int k) {
            if (d == k) return 1;
            int c = 0;
            for (int v : g[u]) if (v != p) c += dfs(v, u, d + 1, k);
            return c;
        }
        public static void main(String[] args) {
            int n = 5, k = 2;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1},{0,2},{1,3},{1,4}};
            for (int[] x : e) { g[x[0]].add(x[1]); g[x[1]].add(x[0]); }
            int pairs = 0;
            for (int u = 0; u < n; u++) pairs += dfs(u, -1, 0, k);
            System.out.println(pairs / 2);
        }
        // Input : tree 0-1-3/4, 0-2; k = 2
        // Output: 3
    }

Count pairs at distance k via centroid decomposition.

JavaCentroidPairs.java
import java.util.*;
    public class CentroidPairs {
        int n, k, ans;
        List<Integer>[] g;
        boolean[] dead;
        int[] sz;
        CentroidPairs(int n, int k) {
            this.n = n; this.k = k;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            dead = new boolean[n]; sz = new int[n];
        }
        void add(int u, int v) { g[u].add(v); g[v].add(u); }
        int sizeOf(int u, int p) {
            sz[u] = 1;
            for (int v : g[u]) if (v != p && !dead[v]) sz[u] += sizeOf(v, u);
            return sz[u];
        }
        int centroid(int u, int p, int s) {
            for (int v : g[u]) if (v != p && !dead[v] && sz[v] > s / 2) return centroid(v, u, s);
            return u;
        }
        void collect(int u, int p, int d, List<Integer> into) {
            into.add(d);
            for (int v : g[u]) if (v != p && !dead[v]) collect(v, u, d + 1, into);
        }
        void decompose(int src) {
            int s = sizeOf(src, -1);
            int c = centroid(src, -1, s);
            Map<Integer, Integer> all = new HashMap<>();
            all.put(0, 1);
            for (int v : g[c]) if (!dead[v]) {
                List<Integer> got = new ArrayList<>();
                collect(v, c, 1, got);
                for (int d : got) ans += all.getOrDefault(k - d, 0);
                for (int d : got) all.merge(d, 1, Integer::sum);
            }
            dead[c] = true;
            for (int v : g[c]) if (!dead[v]) decompose(v);
        }
        public static void main(String[] args) {
            CentroidPairs t = new CentroidPairs(5, 2);
            int[][] e = {{0,1},{0,2},{1,3},{1,4}};
            for (int[] x : e) t.add(x[0], x[1]);
            t.decompose(0);
            System.out.println(t.ans);
        }
        // Input : same tree, k = 2
        // Output: 3
    }

JavaCentroidFind.java
import java.util.*;
    public class CentroidFind {
        static List<Integer>[] g;
        static boolean[] dead;
        static int[] sz;
        static int sizeOf(int u, int p) {
            sz[u] = 1;
            for (int v : g[u]) if (v != p && !dead[v]) sz[u] += sizeOf(v, u);
            return sz[u];
        }
        static int find(int u, int p, int s) {
            for (int v : g[u]) if (v != p && !dead[v] && sz[v] > s / 2) return find(v, u, s);
            return u;
        }
        static void go(int src) {
            int c = find(src, -1, sizeOf(src, -1));
            // solve through c
            dead[c] = true;
            for (int v : g[c]) if (!dead[v]) go(v);
        }
        public static void main(String[] args) {
            int n = 5;
            g = new List[n]; dead = new boolean[n]; sz = new int[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1},{0,2},{1,3},{1,4}};
            for (int[] x : e) { g[x[0]].add(x[1]); g[x[1]].add(x[0]); }
            go(0);
            System.out.println(Arrays.toString(dead));
        }
        // Input : 5-node tree
        // Output: [true, true, true, true, true]
    }

Complexity

Time O(n log n) Space O(n)

Finding a centroid is a size-DFS plus a walk, both linear in the live component of size s. The through-centroid collect is another linear scan of the same s nodes. After the centroid dies, every leftover piece has size at most s/2, so a given node is still alive in a component that has at least halved. Starting from n, that node can be scanned at most log₂ n times before its component has size 1. Summing over all nodes, the size-DFS and collect work is O(n log n).

T = O(n) per layer × O(log n) layers = O(n log n)

Putting real numbers in: at n = 10⁵ each node is touched about 17 times, for roughly two million node visits, plus whatever the through-centroid combine costs. A hashmap of depths adds a log and lands near 3×107 operations, which Java accepts. Allocating a fresh int[n] frequency array at every centroid would instead cost O(n) per layer-node and blow up to O(n²), about ten billion writes. Reuse one global array and roll it back, or store only the depths you actually saw.

Edge cases and pitfalls

  • Using global subtree sizes
    Reusing sz from the first layer looks free, because those numbers were correct when the whole tree was alive. After a centroid dies they still count dead nodes, so you walk toward a fake centre in a tiny leftover and the halving argument no longer holds.
    Recompute sz on alive nodes only, every time you search for a centroid. Test by asserting that the size you just computed equals the number of nodes you later collect from that piece.
  • Combining two nodes from the same child
    Dumping every depth into one map and then pairing freely looks like "all pairs through c". Two nodes from the same child never go through c, so you double-count pairs that a deeper layer already owns and the sample comes out too large.
    Collect one child, query it against the previous children, then merge. Test on a path that stays inside one subtree of the first centroid: it must not be counted at that layer.
  • Forgetting to mark dead before recursing
    Leaving dead[c] false until after the recursive calls looks harmless because you are "done with c". The next size-DFS walks back through c into other leftovers, sees the whole original tree, and the recursion never shrinks.
    Set dead[c] = true immediately after the through-solve and before any recursive call. Test that a size-DFS started at a neighbour of c reports a size of at most half.
  • O(n) allocation inside the layer
    new int[n] at every centroid looks like a clean frequency array and is correct. It costs linear setup per centroid, and there are n centroids, so the hidden work is O(n²) and the solution TLEs on a line.
    Reuse one global frequency array and roll back the depths you incremented, or use a map of the depths you actually saw. Test that peak extra memory stays linear in n.
  • Distance to a centroid ancestor via naive walk
    Climbing parent pointers in the original tree from u to a centroid ancestor looks like the usual distance formula and is correct. On a line it is O(n) per query, which destroys the O(log n) centroid-tree walk.
    Precompute LCA on the original tree, or store dist(u, c) for every centroid ancestor while the layer is still live. Test an online query on a path graph of length n.

Interview follow-ups

Does every tree have a centroid?

Yes, and the walk finds one. Start at any live node and keep stepping toward a child whose live subtree is bigger than half the component. The walk cannot cycle, and it stops at a node with no such child. The parent-side of that node is also at most half, because you only arrived there by following the unique oversized side. At most two adjacent centroids exist; either one is fine for the decomposition.

Why not use HLD for pair counts?

HLD gives you an aggregate along one already-chosen path; it does not list or count pairs. Counting pairs that satisfy a numeric constraint needs a separator so you can join two independent sides in linear time, which is exactly what a centroid is for. If the statement asks for the sum of values on the path from u to v, that is HLD, not this page.

What if the "tree" has extra edges?

Centroid decomposition is defined on trees, so a cycle breaks the size argument and the walk may never stop. Build the block-cut tree or the bridge-block tree of the original graph first, then decompose that tree. Pair queries that care about the original edges have to be translated onto the block tree before you start.

How do you roll back a frequency array?

While you collect depths from a child, push each depth you increment onto a small list. After the through-centroid combine, walk that list and decrement. Clearing a fresh int[n] at every centroid is O(n) per node and becomes O(n²). The rollback list has length equal to the piece you just scanned, so it is already paid for by the O(n log n) bound.

Recap

  • Centroid: every remaining piece has size at most half.
  • Solve through it, mark dead, recurse — depth log n.
  • Combine across children, never inside one child.
  • Recompute live sizes every search.
  • Online: store an aggregate at each centroid ancestor.
