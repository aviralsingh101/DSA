Centroid Decomposition

A centroid splits every remaining component to size at most n/2. Recurse, and every pair of nodes meets at exactly one centroid ancestor.

Hard 26 min read Prerequisites: DFS & Components, Binary Lifting & LCA centroid trees divide and conquer P2

Why this exists

Many tree problems ask about pairs: how many pairs sit at distance k, what is the closest red node, what is the XOR of a path with a given property. Walking every pair is O(n²). Layering a balanced separator over the tree drops that to O(n log n).

A centroid of a tree is a node whose removal leaves components of size at most n/2. Every tree has one (or two adjacent ones). After you solve "paths that go through this centroid", you mark it dead and recurse on each remaining component.

The recursion depth is O(log n) because every piece halves. The centroid tree (parent = the centroid that decomposed you) is a balanced tree you can also query online: the answer for a node is an aggregate over its O(log n) centroid ancestors.

Every path crosses exactly one centroid at each layer of the decomposition. Solve through the centroid, mark it dead, recurse. Depth is log n because pieces halve.

Recognise this pattern

Say yes when you see

  • "How many pairs of nodes at distance k"
  • Online "paint this node, query nearest painted" on a tree
  • Count / optimise paths with a numeric constraint (XOR, weight sum, length)
  • You can compute a contribution through a fixed node in linear time in the current component
  • n ≤ 10⁵ and a pair-over-tree flavour

Not this pattern when

  • Path aggregates with updates → HLD, not centroid
  • Subtree queries only → Euler tour
  • The graph is not a tree → you need a block-cut / bridge tree first, or a different tool
  • Offline queries that Mo's on trees can handle more simply

Core idea and the invariant

To find a centroid: compute subtree sizes in the alive component, then walk from any node toward a child whose live size is > n/2 until none exists. That node is a centroid. Do not use global sizes — dead nodes are invisible.

Solve: DFS the alive component from the centroid, compute depths (or prefix XOR, etc.), and combine pairs that go through the centroid without combining two nodes from the same child (those paths do not go through the centroid). Then mark the centroid dead and recurse.

In an alive component of size s, the centroid has every remaining piece of size ≤ s/2. Recursion depth is therefore O(log n), and every pair of nodes has a unique deepest centroid that lies on the path between them.

Structure

Algorithm

  1. Find centroid: size-DFS on alive nodes, then walk to a node with no child > s/2.
  2. Solve through it — enumerate depths / prefixes per child, combine across children.
  3. Mark the centroid dead so later size-DFS skips it.
  4. Recurse on each remaining alive component.
  5. Online: store an aggregate at each centroid; a query walks the O(log n) ancestors.
  6. Distance from a node to a centroid ancestor = precomputed dist(u)+dist(c)-2*dist[lca] or a climb with stored depths.

Java implementation

DFS from every node. Fine for n <= 2000.

JavaPairsDistKBrute.java
import java.util.*;
    public class PairsDistKBrute {
        static List<Integer>[] g;
        static int dfs(int u, int p, int d, int k) {
            if (d == k) return 1;
            int c = 0;
            for (int v : g[u]) if (v != p) c += dfs(v, u, d + 1, k);
            return c;
        }
        public static void main(String[] args) {
            int n = 5, k = 2;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1},{0,2},{1,3},{1,4}};
            for (int[] x : e) { g[x[0]].add(x[1]); g[x[1]].add(x[0]); }
            int pairs = 0;
            for (int u = 0; u < n; u++) pairs += dfs(u, -1, 0, k);
            System.out.println(pairs / 2);
        }
        // Input : tree 0-1-3/4, 0-2; k = 2
        // Output: 3
    }

Count pairs at distance k via centroid decomposition.

JavaCentroidPairs.java
import java.util.*;
    public class CentroidPairs {
        int n, k, ans;
        List<Integer>[] g;
        boolean[] dead;
        int[] sz;
        CentroidPairs(int n, int k) {
            this.n = n; this.k = k;
            g = new List[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            dead = new boolean[n]; sz = new int[n];
        }
        void add(int u, int v) { g[u].add(v); g[v].add(u); }
        int sizeOf(int u, int p) {
            sz[u] = 1;
            for (int v : g[u]) if (v != p && !dead[v]) sz[u] += sizeOf(v, u);
            return sz[u];
        }
        int centroid(int u, int p, int s) {
            for (int v : g[u]) if (v != p && !dead[v] && sz[v] > s / 2) return centroid(v, u, s);
            return u;
        }
        void collect(int u, int p, int d, List<Integer> into) {
            into.add(d);
            for (int v : g[u]) if (v != p && !dead[v]) collect(v, u, d + 1, into);
        }
        void decompose(int src) {
            int s = sizeOf(src, -1);
            int c = centroid(src, -1, s);
            Map<Integer, Integer> all = new HashMap<>();
            all.put(0, 1);
            for (int v : g[c]) if (!dead[v]) {
                List<Integer> got = new ArrayList<>();
                collect(v, c, 1, got);
                for (int d : got) ans += all.getOrDefault(k - d, 0);
                for (int d : got) all.merge(d, 1, Integer::sum);
            }
            dead[c] = true;
            for (int v : g[c]) if (!dead[v]) decompose(v);
        }
        public static void main(String[] args) {
            CentroidPairs t = new CentroidPairs(5, 2);
            int[][] e = {{0,1},{0,2},{1,3},{1,4}};
            for (int[] x : e) t.add(x[0], x[1]);
            t.decompose(0);
            System.out.println(t.ans);
        }
        // Input : same tree, k = 2
        // Output: 3
    }

JavaCentroidFind.java
import java.util.*;
    public class CentroidFind {
        static List<Integer>[] g;
        static boolean[] dead;
        static int[] sz;
        static int sizeOf(int u, int p) {
            sz[u] = 1;
            for (int v : g[u]) if (v != p && !dead[v]) sz[u] += sizeOf(v, u);
            return sz[u];
        }
        static int find(int u, int p, int s) {
            for (int v : g[u]) if (v != p && !dead[v] && sz[v] > s / 2) return find(v, u, s);
            return u;
        }
        static void go(int src) {
            int c = find(src, -1, sizeOf(src, -1));
            // solve through c
            dead[c] = true;
            for (int v : g[c]) if (!dead[v]) go(v);
        }
        public static void main(String[] args) {
            int n = 5;
            g = new List[n]; dead = new boolean[n]; sz = new int[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] e = {{0,1},{0,2},{1,3},{1,4}};
            for (int[] x : e) { g[x[0]].add(x[1]); g[x[1]].add(x[0]); }
            go(0);
            System.out.println(Arrays.toString(dead));
        }
        // Input : 5-node tree
        // Output: [true, true, true, true, true]
    }

Complexity

Time O(n log n) Space O(n)

Finding a centroid is linear in the live component. Each node is live in O(log n) layers because every split halves size. Total work is therefore O(n log n), plus whatever the through-centroid combine costs (maps add a log).

ApproachTimeSpaceWhen it is enough
DFS from every nodeO(n^2)O(n)n <= 2000
CentroidO(n log n)O(n)Pair counts, online nearest
HLDO(log^2 n)/queryO(n)Path aggregates, not pairs

Edge cases and pitfalls

  • Using global subtree sizes
    After a centroid dies, sizes still include dead nodes and you pick a fake centroid in a tiny piece.
    Recompute sz on alive nodes only, every time you search.
  • Combining two nodes from the same child
    Their path does not go through the centroid, so you double-count paths that a deeper layer already owns.
    Collect one child, query against the previous children, then merge.
  • Forgetting to mark dead before recursing
    The next size-DFS walks back through the centroid into other components.
    dead[c] = true immediately after the through-solve, before the recursive calls.
  • O(n) allocation inside the layer
    new int[n] freq arrays per centroid blow memory and time to O(n²).
    Reuse a global freq array and roll back, or use a map of the depths you actually saw.
  • Distance to a centroid ancestor via naive walk
    Online queries become O(n) if you climb the original tree.
    Precompute LCA, or store dist(u, centroid) while building the centroid tree.

Interview follow-ups

Does every tree have a centroid?

Yes. Walk from any node toward a child of size > n/2. The walk ends: a node with no such child exists, and that node is a centroid. At most two adjacent centroids exist.

Why not use HLD for pair counts?

HLD gives you path aggregates, not an enumeration of pairs. Counting pairs that satisfy a numeric constraint needs a separator so you can join two independent sides.

What if the "tree" has extra edges?

Build the block-cut or bridge-block tree first, then decompose that. Centroid decomposition is defined on trees.

How do you roll back a frequency array?

Collect the list of depths you incremented and decrement them after the combine. Clearing int[n] each layer is O(n²).

Recap

  • Centroid: every remaining piece has size at most half.
  • Solve through it, mark dead, recurse — depth log n.
  • Combine across children, never inside one child.
  • Recompute live sizes every search.
  • Online: store an aggregate at each centroid ancestor.
