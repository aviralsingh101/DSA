Ternary Search & Convexity

On a unimodal function, two probes shrink the interval by a constant factor — ternary search, or a golden-section / integer-trinary loop.

Medium 28 min read Prerequisites: Binary Search on Answer, Greedy Foundations ternary search unimodal convex P2

Why this exists

You are given a function that goes down and then up — the sum of distances from a point on a line, a convex construction cost, a unimodal bitwise score — and you must find the input that makes it smallest. Binary search will not help, because binary search needs a yes/no predicate that flips once, and here the answers are numbers that first improve and then get worse. Evaluating the function at every integer in a range of size 109 is a billion calls; if each call is a linear scan you are looking at 1014 steps. Ternary search finds the trough with a logarithmic number of probes.

The idea is geometric. If f decreases and then increases, the minimum cannot sit in the third that currently looks worse, so you throw that third away and repeat. Convexity — the second differences of f are non-negative, or the derivative changes sign only once — is a sufficient reason for that shape, which is called unimodal. Convex DP (divide-and-conquer optimisation, Knuth, Li Chao, convex hull trick) is the data-structure upgrade of the same picture: the optimal choice as a function of i is itself unimodal, so you search it or hull it instead of trying every transition.

In a real problem statement the signal is a numeric parameter you get to choose, sitting next to a cost that is obviously "closer is cheaper, then farther is more expensive", and a range too large to scan. On integers, a loop that keeps [lo, hi] and compares f(m1) against f(m2) is safer than floating ternary: stop when the interval is a few units wide and brute the remainder, because a flat bottom can pin the wrong side if you run until lo == hi. On doubles, eighty to a hundred iterations beat an eps of 10-9 on a range of 109.

If f decreases then increases, the minimum cannot lie in the third that currently looks worse, so you throw that third away. Convexity of f is a sufficient condition for that shape; a W-shaped function will send the search into the wrong valley.

Recognise this pattern

Constraint tell: Each evaluation is whatever f costs; the search does O(log X) of them. If f is a linear scan then the total is O(n log X), which at n = 105 and X = 109 is a few tens of millions of steps. On doubles prefer 80–100 fixed iterations over a tiny eps. On integers, loop while hi - lo > 3 and scan the seed.

Core idea and the invariant

On integers keep two bounds lo and hi that are guaranteed to contain the minimiser. While hi - lo is larger than 3, place m1 = lo + (hi - lo) / 3 and m2 = hi - (hi - lo) / 3. Evaluate f at both. If f(m1) is strictly smaller than f(m2), the minimum cannot sit to the right of m2 (a unimodal f would already be climbing), so set hi = m2; otherwise set lo = m1. When the interval is a handful of integers, scan it and return the argmin. The finishing scan is what makes a flat bottom safe.

On reals the same third-and-third split works, or you can use golden-section search, which reuses one probe per step so each iteration costs one new evaluation instead of two. Prove unimodality before you trust either loop. Discrete convexity is the check that second differences are non-negative: f(i) - 2 f(i+1) + f(i+2) ≥ 0 for every i. On a differentiable f, the first derivative should change sign only once. If you can cheaply compare f(m) with f(m+1) on integers, binary search for the first rise is fewer probes than ternary.

Walk f = [9, 7, 4, 2, 3, 8], whose minimum is 2 at index 3. Start with lo = 0, hi = 5. The first thirds land at 1 and 4; f(1) = 7 is worse than f(4) = 3, so the minimum is not left of 1 and lo becomes 1. The next pair is 2 and 4; 4 beats 3, so lo becomes 2. Then 3 and 4: f(3) = 2 beats 3, so hi becomes 4. The remainder 2 .. 4 scans to index 3. A W-shaped array would have let one of those discards throw the true minimum away, which is why the shape has to be proved, not hoped.

If f is unimodal on [lo, hi], the minimiser (or maximiser) still lies in the interval after the worse third is discarded. When hi - lo is a constant, a linear scan of the remainder is exact even if the bottom is flat.

In plain words, you are allowed to throw away the side that is already climbing, and you must stop and look at the last few points instead of trusting one last comparison on a plateau.

Interview sentence: "I discard the worse third of a unimodal f, then brute the last few integers."

A W-shaped f is not unimodal

Two valleys make ternary converge to whichever local minimum the first discard happened to keep. Plot f on a tiny test, or prove second differences, before you ship the loop. Binary search on a monotone predicate is the wrong cousin, not a fallback.

Algorithm

  1. Prove the function is unimodal before you search. Second differences non-negative, a derivative that changes sign once, or a one-sentence convexity argument: without that, a discarded third can contain the true answer.
  2. Choose the domain you will shrink. Array indices, a real coordinate, or a discrete parameter such as a bit-width: the loop is the same, but the stopping rule is not (scan a few integers, or run a fixed number of real iterations).
  3. Place m1 and m2 at one-third and two-thirds, or use golden section. The safe integer spelling is lo + (hi - lo) / 3, which cannot overflow; (2 * lo + hi) / 3 can.
  4. Discard the third whose probe is worse. If f(m1) is smaller then the minimum is not right of m2; otherwise it is not left of m1. A plateau should not be trusted to this comparison alone.
  5. Stop while the interval is still a handful of integers, or after 80 real iterations. Running until lo == hi on a flat bottom can pin the wrong index; a tiny eps on a huge real range under-iterates.
  6. Scan the leftover integers and return the argmin. That finishing pass is exact, cheap, and the reason integer ternary is safer than floating ternary copied onto an array.

Java implementation

Evaluate f everywhere. Correct, uses the unimodal array.

JavaMinScan.java
public class MinScan {
        static int argmin(int[] f) {
            int b = 0;
            for (int i = 1; i < f.length; i++) if (f[i] < f[b]) b = i;
            return b;
        }
        public static void main(String[] args) {
            System.out.println(argmin(new int[] {9, 7, 4, 2, 3, 8}));
        }
        // Input : [9,7,4,2,3,8]
        // Output: 3
    }

Integer ternary plus a finishing scan.

JavaTernaryInt.java
public class TernaryInt {
        static int argmin(int[] f) {
            int lo = 0, hi = f.length - 1;
            while (hi - lo > 3) {
                int m1 = lo + (hi - lo) / 3;
                int m2 = hi - (hi - lo) / 3;
                if (f[m1] < f[m2]) hi = m2;
                else lo = m1;
            }
            int b = lo;
            for (int i = lo + 1; i <= hi; i++) if (f[i] < f[b]) b = i;
            return b;
        }
        public static void main(String[] args) {
            System.out.println(argmin(new int[] {9, 7, 4, 2, 3, 8}));
        }
        // Input : [9,7,4,2,3,8]
        // Output: 3
    }

Minimise a convex f on [L,R] with 80 iterations.

JavaTernaryReal.java
public class TernaryReal {
        static double f(double x) { return (x - 3) * (x - 3) + 1; }
        static double minX(double lo, double hi) {
            for (int it = 0; it < 80; it++) {
                double m1 = lo + (hi - lo) / 3;
                double m2 = hi - (hi - lo) / 3;
                if (f(m1) < f(m2)) hi = m2;
                else lo = m1;
            }
            return (lo + hi) / 2;
        }
        public static void main(String[] args) {
            System.out.printf("%.4f%n", minX(0, 10));
        }
        // Input : (x-3)^2+1 on [0,10]
        // Output: 3.0000
    }

Complexity

Time O(log_{3/2} range) evaluations Space O(1)

Each step replaces an interval of length L by an interval of length at most (2/3) L, because one of the two outer thirds is thrown away. The number of steps until L drops from n to a constant is O(log n) in base 3/2, which is a few dozen iterations even at n = 109. Two evaluations per step (or one, with golden section) multiply that count by a small constant. The finishing scan of a handful of integers is absorbed.

Putting real numbers in: an integer range of size 109 dies in about 60 third-and-third steps, 120 evaluations. If each f is a linear scan of n = 105 items, the total is about 1.2 × 107 operations, which is comfortable. A full scan of the domain would be a billion evaluations. On doubles, 80 to 100 fixed iterations shrink a range of 109 well past 10-9; forty iterations are not enough and are the usual wrong eps loop.

Edge cases and pitfalls

  • Plateaus
    When f(m1) == f(m2) on a flat bottom, either third looks discardable, so dropping one of them can throw away the only index you needed if you then run the loop until the bounds meet.
    Stop while several integers remain and scan them. Treating equality as "shrink both sides a little" also works; the finishing scan is the simpler test.
  • Not unimodal
    A W-shaped cost has two valleys, and the first comparison happily discards the third that held the global minimum, so the loop converges to a local min and the sample with one valley still passes.
    Prove convexity, or plot f on a tiny constructed W. Ternary is the wrong algorithm the moment there are two turns.
  • Floating ternary with too few iters
    An eps of 10-9 on [0, 109] looks like the usual real-search stopping rule, but shrinking by 2/3 each time needs about 90 iterations, and forty leaves an error of metres.
    Run 80 to 100 fixed iterations and ignore eps. The midpoint of the final interval is the answer you print.
  • Integer overflow in m1/m2
    (2 * lo + hi) / 3 looks like a tidy one-third formula, then 2 * lo overflows a 32-bit int when the domain is a billion and the midpoints jump into garbage.
    Write m1 = lo + (hi - lo) / 3 and m2 = hi - (hi - lo) / 3. Those two lines are overflow-safe for non-negative bounds.
  • Ternary when binary on f(m) vs f(m+1) works
    Two probes per step look necessary because the page is about ternary, but on a discrete bitonic array you can test the slope with one neighbour compare, so you spend twice the evaluations and invite plateau bugs.
    On integers with a cheap neighbour test, binary-search the first index where f[i] ≤ f[i+1]. Keep ternary for a heavy f you can only evaluate, not differentiate.

Interview follow-ups

Why not always binary on f(m) vs f(m+1)?

On the reals there is no next integer m+1 to compare against, so a slope test is not even defined. On integers, if a neighbour evaluation is cheap, binary search for the first rise is fewer probes and avoids plateau bugs. Ternary still earns its keep when f is a heavy simulation you can only evaluate at chosen points, not at m and m+1 for free on every candidate.

Is every convex function unimodal?

A strictly convex f has a unique minimum, so it is unimodal and ternary is safe. A weakly convex f can have a flat bottom: every point on the plateau is optimal, but a third-and-third compare that sees two equal values can discard the plateau if you do not scan the remainder. That is why integer ternary stops early and brutes the seed.

Golden section vs 1/3-2/3?

Golden-section search places the probes at the golden-ratio offsets so one of them can be reused after the discard; each iteration then costs one new evaluation. Third-and-third is simpler to type and spends two evaluations per step, still logarithmic. In contests type the 1/3 loop; golden is a constant-factor win on a very expensive f.

Connection to ternary search on trees?

Unrelated name. A 3-ary search tree branches on three children; "ternary search on the answer" shrinks a numeric interval by discarding a third. The phrase on this page always means the interval shrink. If a problem asks you to walk a ternary trie or a 3-child tree, that is a different algorithm and this loop will not help.
