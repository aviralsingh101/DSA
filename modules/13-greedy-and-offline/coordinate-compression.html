Coordinate Compression

Replace huge or sparse values by their ranks 0..k-1 so Fenwick trees, arrays, and DP tables fit in memory — the ranks preserve order.

Medium 26 min read Prerequisites: Fenwick Tree, Sorting & Comparators compression ranking offline P1

Why this exists

You are given n numbers that live anywhere in 1 .. 109, and you must index a Fenwick tree, a segment tree, or a frequency array by those numbers. Allocating an array of size a billion is not an option: that is four billion bytes on a 32-bit cell, and the process is dead before the first update. There are only n numbers, so only n distinct ranks can ever appear. Coordinate compression is the map that sends each value to its rank in 0 .. k-1 while keeping every less-than and every equal intact.

The obvious alternative is a TreeMap or a dynamic segment tree keyed by the raw values. Both work online and both pay heavier constants. Compression is the offline bargain: collect every integer that will ever be used as an index (array values, query bounds, rectangle y-endpoints), sort them, squeeze equal runs into one slot, then replace each original by a binary search into that unique list. A Fenwick of size k then runs in n log k, about two million operations at n = 105, instead of an allocation that cannot exist.

In a real problem statement the signal is values or coordinates up to 109 sitting next to a structure that wants an array index: inversion count, 2D Fenwick, sweep-line y-axes, "next larger value" DP. If the values are already in 1 .. n there is nothing to compress. If new keys arrive after you have built the tree, you cannot pre-assign ranks without leaving gaps, and you want a balanced tree instead. Forgetting to unique the sorted list is the classic wrong version: two equal values then receive different ranks from a raw sort index, and "equal" silently dies.

Order is all the later structure needs. Ranks 0 .. k-1 are a strictly increasing relabelling of the distinct keys, so every comparison that used to say x < y still says rank(x) < rank(y), and equals stay equal.

Constraint tell: The number of distinct keys k is at most n, or about 3n once query bounds and both rectangle y-endpoints are collected. That is the size of the Fenwick, not 109. Java's Arrays.binarySearch on the unique array is the rank, and a missing key returns the insertion point you must treat as a lower bound.

Core idea and the invariant

Collect every integer that will be used as an index into one list: the array values, every query L and R, every rectangle y1 and y2. Sort that list, then compact equal runs so each distinct key appears once; call the compact array unique and let k be its length. The rank of a collected value x is the unique index i with unique[i] = x, found by binary search. Rewrite the working array by replacing each a[i] with rank(a[i]), and size the Fenwick at k (or k+2 if you prefer a 1-based tree with a dummy).

Queries that ask about a value range [L, R], not an index range, need two extra binary searches. lower_bound(L) is the first stored key that is at least L, and that is the first rank you want included. upper_bound(R) is the first stored key strictly greater than R, so the last included rank is one less. Off-by-one on those two calls is the usual wrong answer: including a key just below L, or dropping the key that equals R. Keys that never appeared in the array must still have been collected, or you must use the insertion point as the rank.

Walk a = [100, 3, 100, 50]. The collected sorted list is 3, 50, 100, 100; after unique it is [3, 50, 100] and k = 3. The ranks are 2, 0, 2, 1, so the compressed array is [2, 0, 2, 1]. A Fenwick of size 3 can now count frequencies or inversions: walking left to right, query how many already-seen ranks are larger than the current one. A later query "how many values lie in [40, 100]" becomes ranks [1, 2], because 40 lower-bounds to 50 and 100 upper-bounds just past the last key.

For every pair of keys that appeared in the collected set, rank(x) < rank(y) if and only if x < y, and rank(x) = rank(y) if and only if x = y.

In plain words, the new labels are just a denser spelling of the same order: equals stay glued together, and a smaller original still receives a smaller rank. Lengths and differences still use the original numbers, because ranks throw the gaps away.

Interview sentence: "I collect, sort, unique, then binary-search; ranks preserve order, not distance."

Ranks are indices, not lengths

A rectangle of width 109 still has width 109 after compression. The rank difference between its two x-endpoints may be 1. Multiply original coordinates for area; use ranks only to index the tree.

Algorithm

  1. Collect every integer that will be used as an index. Array values, query bounds, and both y-endpoints of every rectangle belong on the list; a bound you forget cannot be ranked later without guessing an insertion point.
  2. Sort the list and compact equal runs. Unique is not optional: a raw sort index would give two copies of 100 two different ranks, and the later Fenwick would treat equals as ordered.
  3. Define rank(x) as the lower_bound in the unique array. For a key that was collected, binary search returns its exact slot; for a missing bound, the insertion point is the first rank that should be included.
  4. Rewrite the working data and size the tree at k. Replace each a[i] with its rank, allocate the Fenwick at unique.length (plus one if you are 1-based), and never allocate 109.
  5. Translate a value-range [L, R] into ranks. The inclusive rank interval is [lower_bound(L), upper_bound(R) - 1]; off-by-one on either end includes a key you did not ask for or drops one you did.
  6. Keep the original numbers wherever a length is needed. Area, gap, and difference queries still subtract originals. Ranks throw those gaps away on purpose, which is why they fit in memory.

Unique + binarySearch. Ranks of the sample.

JavaCompress.java
import java.util.*;
    public class Compress {
        static int[] unique(int[] a) {
            int[] b = a.clone();
            Arrays.sort(b);
            int k = 0;
            for (int i = 0; i < b.length; i++)
                if (k == 0 || b[i] != b[k - 1]) b[k++] = b[i];
            return Arrays.copyOf(b, k);
        }
        static int rank(int[] u, int x) {
            int r = Arrays.binarySearch(u, x);
            return r < 0 ? -1 : r;
        }
        public static void main(String[] args) {
            int[] a = {100, 3, 100, 50};
            int[] u = unique(a);
            for (int x : a) System.out.print(rank(u, x) + " ");
            System.out.println();
        }
        // Input : [100,3,100,50]
        // Output: 2 0 2 1
    }

Inversions with Fenwick on ranks.

JavaInvCountCompressed.java
import java.util.*;
    public class InvCountCompressed {
        static long inv(int[] a) {
            int[] u = a.clone();
            Arrays.sort(u);
            int k = 0;
            for (int x : u) if (k == 0 || x != u[k - 1]) u[k++] = x;
            int n = a.length;
            long[] bit = new long[k + 2];
            long ans = 0;
            for (int i = n - 1; i >= 0; i--) {
                int r = Arrays.binarySearch(u, 0, k, a[i]) + 1;
                long s = 0;
                for (int j = r - 1; j > 0; j -= j & -j) s += bit[j];
                ans += s;
                for (int j = r; j <= k; j += j & -j) bit[j]++;
            }
            return ans;
        }
        public static void main(String[] args) {
            System.out.println(inv(new int[] {3, 1, 2}));
        }
        // Input : [3,1,2]
        // Output: 2
    }

Complexity

Time O(n log n) Space O(n)

Collecting n (or a few times n) keys and sorting them is n log n comparisons. Compacting equals is a linear pass. Each later rank is one binary search on a list of length k, so rewriting the array is another n log k. The Fenwick or segment tree you build afterwards is O(n log k) updates and queries on a structure of size k.

Putting real numbers in: at n = 105 and k about the same, the sort is roughly 1.7 × 106 comparisons and the tree is a few million bit operations, which is fine. The thing compression avoids is an array of length 109, which is four gigabytes on a 32-bit cell and will not allocate. A TreeMap Fenwick is the same n log n class with slower constants, useful only when keys arrive online.

Edge cases and pitfalls

  • Not uniquing
    Arrays.binarySearch on a sorted array that still holds duplicates returns an arbitrary copy of the key, so two calls on the same value can receive two different ranks and "equal" silently becomes ordered.
    Compact equal runs first, then search only on the unique array. Two copies of 100 must share one rank; that is the test.
  • Forgetting query bounds in the collected set
    A query L that never appeared as an array value has no slot, so binarySearch returns -insertion - 1, and treating that negative number as a rank either crashes or reads the wrong prefix.
    Push every query L and R into the collected list before you unique, or decode the insertion point as a lower bound and never use the raw negative return.
  • Compressing an axis you still measure
    A rectangle whose x-span is a billion looks like width 1 after ranking, so area becomes the rank difference and the sample with tiny coordinates still passes.
    Store original coordinates for every length and area product. Ranks index the tree and nothing else; subtract originals when you need a gap.
  • 1-based Fenwick vs 0-based ranks
    Rank 0 looks like a legal index into bit[], but a Fenwick leaves bit[0] unused, so the smallest key is never updated, or j -= j & -j walks off the array.
    Use rank + 1 as the Fenwick index, or allocate k + 2 and ignore slot 0. Query a single minimum and check that it appears in the tree.
  • long vs int keys
    Coordinates up to 1018 fit the problem statement and look like they belong in an int[], then they overflow on the way into the unique array and two distant keys collide.
    Store the unique list in a long[] (or a Long list) whenever the statement's range exceeds 231. Rank comparisons must use the same type.

Interview follow-ups

lower_bound vs rank of an absent L?

lower_bound(L) is the first stored key that is at least L. That is exactly the first rank that should be included in "values ≥ L", even when L itself never appeared. upper_bound(R) is the first stored key strictly greater than R, so the last included rank is one less. If you collected L up front, both calls are ordinary binary searches on the unique array.

Why not HashMap to dense ids?

A HashMap can pack values into 0 .. n-1, but it assigns ids in insertion order, not value order. A Fenwick prefix then means "the keys I happened to see first", not "every smaller value". Compression exists specifically so that a smaller original still receives a smaller rank; hashing throws that property away.

Can you compress online?

If every key is known before the first update, yes: that is the offline collect-sort-unique pipeline on this page. If a brand-new key can arrive later, you cannot pre-assign a dense rank without leaving gaps or rebuilding. Use a balanced tree, a treap, or a dynamic segment tree keyed by the raw value.

2D compression?

Compress the x-coordinates and the y-coordinates independently, each with its own unique list. A 2D Fenwick is then kx by ky. If that product is too large for memory, sweep one axis (sort by x) and Fenwick only the other (compressed y), which is the offline rectangle-count sweep from the previous page.
