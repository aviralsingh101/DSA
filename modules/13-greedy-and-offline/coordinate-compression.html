Coordinate Compression

Replace huge or sparse values by their ranks 0..k-1 so Fenwick trees, arrays, and DP tables fit in memory — the ranks preserve order.

Medium 20 min read Prerequisites: Fenwick Tree, Sorting & Comparators compression ranking offline P1

Why this exists

Values live in 1..1e9 but there are only n of them. A Fenwick of size 1e9 is impossible; a Fenwick of size n on ranks is O(n). Compression is the map value → rank that keeps < and =.

Offline algorithms collect every coordinate that will ever appear (array values, query bounds, rectangle y's), sort-unique, then replace each by lower_bound. Online structures that must accept new keys use a balanced tree instead.

It shows up in inversion counts, 2D Fenwick, sweep-line y-axes, and DP on "the next larger value". Forgetting to unique duplicates maps two equal values to different ranks if you used a raw sort index.

Order is all you need. Ranks 0..k-1 are a strictly increasing relabelling of the distinct keys.

Recognise this pattern

Say yes when you see

  • Fenwick / segtree on values from 1e9, only n distinct
  • 2D points with large x,y
  • Offline queries whose bounds are in the input
  • Need an array indexed by value
  • Discrete version of a sweep y-axis

Not this pattern when

  • You need the actual numeric gaps (distance 1e9 vs 2) in the index → compression loses gaps
  • Online arbitrary new keys without rebuild → TreeMap / dynamic segtree
  • Values already in 1..n → nothing to do
  • Hashing as identity, not order → HashMap, not ranks

Constraint tell: k distinct ≤ n or 3n (values + query bounds). Java Arrays.binarySearch on the unique array is the rank.

Core idea and the invariant

Copy all relevant numbers into a list, sort, unique. Rank of x is the lowest index with unique[i]==x (binary search). Replace a[i] with rank(a[i]).

Queries with bounds [L,R] on the value axis: rankL = lower_bound(L), rankR = upper_bound(R)-1. Off-by-one here is the usual WA.

rank(x) < rank(y) iff x < y, and rank(x)==rank(y) iff x==y, for every x,y that appeared in the collected set.

Algorithm

  1. Collect every integer that will be an index (values, query L/R, y1/y2).
  2. Sort and unique (compact equal runs).
  3. rank(x) = lower_bound in the unique array.
  4. Rewrite the data. Fenwick size = unique.length (or +2).
  5. Query [L,R] on values: [lower_bound(L), upper_bound(R)-1].
  6. Keep originals if you still need numeric differences.

Unique + binarySearch. Ranks of the sample.

JavaCompress.java
import java.util.*;
    public class Compress {
        static int[] unique(int[] a) {
            int[] b = a.clone();
            Arrays.sort(b);
            int k = 0;
            for (int i = 0; i < b.length; i++)
                if (k == 0 || b[i] != b[k - 1]) b[k++] = b[i];
            return Arrays.copyOf(b, k);
        }
        static int rank(int[] u, int x) {
            int r = Arrays.binarySearch(u, x);
            return r < 0 ? -1 : r;
        }
        public static void main(String[] args) {
            int[] a = {100, 3, 100, 50};
            int[] u = unique(a);
            for (int x : a) System.out.print(rank(u, x) + " ");
            System.out.println();
        }
        // Input : [100,3,100,50]
        // Output: 2 0 2 1
    }

Inversions with Fenwick on ranks.

JavaInvCountCompressed.java
import java.util.*;
    public class InvCountCompressed {
        static long inv(int[] a) {
            int[] u = a.clone();
            Arrays.sort(u);
            int k = 0;
            for (int x : u) if (k == 0 || x != u[k - 1]) u[k++] = x;
            int n = a.length;
            long[] bit = new long[k + 2];
            long ans = 0;
            for (int i = n - 1; i >= 0; i--) {
                int r = Arrays.binarySearch(u, 0, k, a[i]) + 1;
                long s = 0;
                for (int j = r - 1; j > 0; j -= j & -j) s += bit[j];
                ans += s;
                for (int j = r; j <= k; j += j & -j) bit[j]++;
            }
            return ans;
        }
        public static void main(String[] args) {
            System.out.println(inv(new int[] {3, 1, 2}));
        }
        // Input : [3,1,2]
        // Output: 2
    }

Complexity

Time O(n log n) Space O(n)

Sort + unique is O(n log n). Each rank is a binary search. The later Fenwick is O(n log k).

Edge cases and pitfalls

  • Not uniquing
    binarySearch on a sorted array with duplicates returns an arbitrary duplicate index; equal values get different ranks across calls.
    Unique first, then search on the compact array.
  • Forgetting query bounds in the collected set
    A query L that never appeared has no rank; binarySearch returns -insertion-1, which you must treat as lower_bound.
    Insert all L/R into the list before unique, or use the insertion point as rank.
  • Compressing an axis you still measure
    Rectangle width becomes rank difference 1, area is wrong.
    Store original coordinates for lengths; ranks only index the tree.
  • 1-based Fenwick vs 0-based ranks
    rank 0 never updates bit[0] which is unused — you skip all minima, or you AIOOB.
    Use rank+1 as Fenwick index.
  • long vs int keys
    1e18 coordinates in int[] overflow.
    long[] unique.

Interview follow-ups

lower_bound vs rank of an absent L?

lower_bound(L) is the first stored key ≥ L. That is the first rank that should be included in "values ≥ L". upper_bound(R) is the first key > R.

Why not HashMap to dense ids?

HashMap assignment order is insertion, not value order. Fenwick prefix would no longer mean "all smaller values".

Can you compress online?

If all keys are known up front, yes (offline). If not, you cannot pre-assign ranks without leaving gaps. Use a BBST.

2D compression?

Compress x and y independently. A 2D Fenwick is then k_x by k_y. If that product is too big, sweep one axis and Fenwick the other.

Recap

  • Collect, sort, unique, lower_bound.
  • Equal keys → equal ranks. Unique is required.
  • Fenwick size is k, not 1e9.
  • Lengths still use original coordinates.
  • Query bounds must be in the collected set or handled as insertion points.
