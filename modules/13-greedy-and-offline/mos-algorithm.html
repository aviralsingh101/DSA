Mo's Algorithm

Reorder offline range queries into sqrt-blocks so adding/removing one endpoint is amortised O(n sqrt n) instead of O(nq).

Hard 30 min read Prerequisites: Coordinate Compression, Two Pointers Mo offline sqrt P2

Why this exists

You are given an array of length n and q range questions such as "how many distinct values sit in [L, R]", "what is the mode", or "what is the mex". Prefix sums cannot help, because those answers do not have an inverse: knowing the distinct count of [0, R] and of [0, L-1] tells you nothing about [L, R]. Rebuilding a frequency map from scratch for every query costs about n q additions. At n = q = 105 that is ten billion steps, and the judge will cut you off. Mo's algorithm is the offline reorder that makes two pointers crawl the array so cheaply that the same add/remove work finishes in tens of millions of steps instead.

You are allowed to answer the queries in any order, so you sort them before you walk. The sort key is the block of the left endpoint, L / B, and inside a block the right endpoint R. That one decision is what bounds the pointer movement, and the arithmetic is why. The left pointer, inside a single block, lives in a window of only B indices, so it moves at most B steps per query and q B steps in total; when the block changes it may jump across the whole array, at most n steps per block, and there are n / B blocks, which is another n2 / B. The right pointer is sorted inside each block, so it travels across the array at most once per block (or twice if you reset), which is again (n / B) × n = n2 / B. Adding those up gives q B + n2 / B endpoint moves. Setting B ≈ √n (or n / √q when q differs from n) balances the two terms at about n √n.

In a real problem statement the signal is offline [L, R] queries sitting next to n, q ≤ 105 and an answer that is not a prefix difference: distinct, mode, mex, sum of freq2 × value. If you can add or remove one index in constant time (or a log, still often fine), the bound above is the intended budget — about 3 × 107 to 2 × 108 add/remove calls in Java if the inner function stays an array bump, not a HashMap. Hilbert order cuts the constant further and is optional; the block sort is the interview version. Queries that arrive online cannot be reordered, and then you need a real data structure instead.

You pay for moving L and R, not for answering. Sorting by the block of L and then by R is what caps those moves at q B + n2 / B, which becomes about n √n once the block size is √n.

Recognise this pattern

Say yes when you see

  • Offline [L,R] queries, add/remove an index is O(1)/O(log)
  • Distinct values in a range (no updates)
  • Sum of frequencies^2, mode, mex with a frequency of frequencies
  • n,q ≤ 1e5 and you cannot think of a Fenwick identity
  • Tree-path queries via Euler tour (Mo on trees)

Not this pattern when

  • Online queries → you cannot reorder
  • Range sum / XOR → prefix, do not Mo
  • Updates + queries at 1e5 if add is O(n) → too slow even for Mo-with-time
  • n=1e6, q=1e6, add=O(1) → n sqrt n = 1e9, too slow; need a better structure

Core idea and the invariant

Keep a live window [curL, curR] and a frequency structure that matches exactly those indices. Start empty, conventionally curL = 0 and curR = -1, so nothing is in the window and you never double-add index 0. For each query (L, R, id) in the sorted order, expand or shrink with four loops: while curL > L add --curL; while curR < R add ++curR; while curL < L remove curL++; while curR > R remove curR--. Expand before you shrink so the window is never invalid. Then write ans[id]. The functions add(i) and rem(i) must be exact inverses: for distinct count, add does freq[a[i]]++ and increments distinct when the count leaves 0, and rem decrements first and drops distinct when the count returns to 0.

The sort is what makes those four loops cheap, and this is the arithmetic. Pick a block size B, usually ⌊√n⌋. Give every query the key (L / B, R), and for a small extra constant sort R descending in odd-numbered blocks so the right pointer does not reset from n back to 0 at every block boundary. Inside one block the left endpoints all lie in an interval of length B, so curL moves at most B steps per query: that is q B left-moves. At a block change curL may jump up to n indices, and there are n / B blocks, which is n2 / B more left-moves. Because R is monotonic inside a block, curR travels the array at most once per block: another (n / B) × n = n2 / B right-moves. The total is q B + 2 n2 / B add/remove calls. Substitute B = √n and both pieces become n √n when q ≈ n.

Walk a = [1, 2, 1, 3, 2] with queries [0, 2], [1, 4], [0, 4] and B = 2. Block-sorted order is [0, 2], then [0, 4], then [1, 4], because the first two share block 0 and are ordered by R. Start empty. Expanding to [0, 2] adds 1, 2, 1 and distinct becomes 2. Expanding R to 4 adds 3 and 2, distinct becomes 3, and that answers [0, 4]. Moving L from 0 to 1 removes a single 1, the frequency of 1 drops from 2 to 1, and distinct stays 3, which answers [1, 4]. The pointers crawled a handful of steps instead of rebuilding three frequency maps from scratch.

After each query is processed, [curL, curR] equals that query's range and the frequency structure matches it exactly. With block size B = √n, the total number of endpoint moves is O((n + q) √n), because left-moves cost q B + n2 / B and right-moves cost n2 / B.

In plain words, you never rebuild the window: you slide it from the previous query to the next, and the block-then-R order is what stops those slides from adding up to n q.

Interview sentence: "I sort by L-block then R so the two pointers move O(n sqrt n) times, not O(n q)."

Why the block sort bounds the pointers

Left: q B inside blocks plus n × (n / B) at block changes. Right: n of travel per block times n / B blocks. Total q B + n2 / B. Set B = √n (or n / √q) to balance the two terms. Odd-even R does not change the big-O; it roughly halves the right-pointer resets.

add and rem are inverses

If rem is not the exact undo of add, distinct drifts and every later answer is wrong. Start from the empty window [0, -1] and only mutate inside the four while-loops, so you cannot double-add index 0 by accident.

Reorder, then crawl L and R

Algorithm

  1. Compress values so freq[] is a plain array. Keys up to 109 cannot index a frequency table; ranks in 1 .. n make add a single increment, which is the only reason n √n fits the time limit.
  2. Pack each query as (L, R, id) and sort by (L / B, R). The block of the left endpoint is the primary key because that is what caps left-pointer travel; odd blocks should sort R descending so the right pointer does not reset at every boundary.
  3. Write add(i) as the exact increment. For distinct count: bump freq[a[i]] and increment distinct only when the count leaves zero. Any other answer (mode, mex, freq-squared) plugs in here and nowhere else.
  4. Write rem(i) as the exact undo of add. Decrement first, then drop distinct when the count returns to zero. A rem that is not the inverse makes every later answer drift, and the bug is invisible on the first query.
  5. Move with the four while-loops, expand before shrink. Starting from the empty window [0, -1], only these loops mutate the structure, so you cannot double-add index 0 or remove an index that was never in.
  6. Store ans[id] and print in the original order. The sort permutes the queries; the id field is what puts the answers back. Forgetting it prints a correct bag of numbers in the wrong rows.

Java implementation

Rebuild a set per query.

JavaDistinctBrute.java
import java.util.*;
    public class DistinctBrute {
        static int dist(int[] a, int l, int r) {
            Set<Integer> s = new HashSet<>();
            for (int i = l; i <= r; i++) s.add(a[i]);
            return s.size();
        }
        public static void main(String[] args) {
            int[] a = {1, 2, 1, 3, 2};
            System.out.println(dist(a, 0, 2) + " " + dist(a, 1, 4));
        }
        // Input : [1,2,1,3,2], queries [0,2] [1,4]
        // Output: 2 3
    }

Classic Mo for distinct counts.

JavaMoDistinct.java
import java.util.*;
    public class MoDistinct {
        static int[] a, freq, ans;
        static int distinct;
        static void add(int i) { if (freq[a[i]]++ == 0) distinct++; }
        static void rem(int i) { if (--freq[a[i]] == 0) distinct--; }
        public static void main(String[] args) {
            a = new int[] {1, 2, 1, 3, 2};
            int[][] qs = {{0, 2, 0}, {1, 4, 1}};
            int n = a.length, B = (int) Math.sqrt(n);
            Arrays.sort(qs, (p, q) -> {
                int bp = p[0] / B, bq = q[0] / B;
                if (bp != bq) return bp - bq;
                return (bp & 1) == 0 ? p[1] - q[1] : q[1] - p[1];
            });
            freq = new int[4];
            ans = new int[2];
            int cl = 0, cr = -1;
            for (int[] q : qs) {
                while (cl > q[0]) add(--cl);
                while (cr < q[1]) add(++cr);
                while (cl < q[0]) rem(cl++);
                while (cr > q[1]) rem(cr--);
                ans[q[2]] = distinct;
            }
            System.out.println(ans[0] + " " + ans[1]);
        }
        // Input : same two queries
        // Output: 2 3
    }

Complexity

Time O((n + q) sqrt n * T_add) Space O(n + q)

Fix a block size B. Left-pointer travel splits in two. Inside one block every L lies in an interval of length B, so each of the q queries moves curL by at most B, which is q B steps. At a block change curL may jump up to n indices, and there are n / B blocks, which is n2 / B more steps. Right-pointer travel is simpler: because queries inside a block are sorted by R, curR is monotonic and crosses the array at most once per block, another (n / B) × n = n2 / B. The grand total is

T = O(q B + n2 / B)

Set B = √n when q ≈ n, or B = n / √q when they differ, and both terms become O((n + q) √n). Putting real numbers in: at n = q = 105 we have √n ≈ 316, so about 3 × 107 add/remove calls, a few hundred milliseconds in Java if each call is an array bump. Rebuild-per-query on the same input is n q = 1010 steps. Skip the block key and sort only by R, and the left pointer jumps randomly for an O(n q) again.

Edge cases and pitfalls

  • add/rem not inverses
    A rem that decrements after checking freq == 1, or that is called twice on the same index, looks locally symmetric and then freq goes negative, so distinct drifts and every later query is silently wrong.
    Make rem the exact undo of add, and assert freq[x] ≥ 0 after every removal. The first query can still pass while the third is already garbage.
  • HashMap frequencies at 1e5
    A HashMap looks like the natural way to count values up to 109, but each add then costs a hash plus possible resize, and n √n of those is several hundred million map operations that miss the time limit.
    Compress values to 1 .. n and use an int[] freq. The inner function must stay a couple of array writes; that is the whole point of the bound.
  • Starting from [0,0] without adding 0
    Initialising curL = curR = 0 looks like "the window starts at the first index", so you either forget to add a[0] or you add it once at init and again in the first expand, and the first answer is off by one value.
    Start from the empty window [0, -1] and only add or remove inside the four while-loops. Index 0 enters exactly when a query needs it.
  • Sorting by R only
    Sorting queries by the right endpoint alone looks like it should keep curR monotonic, which it does, but then curL jumps anywhere in the array on every query and the left-pointer term becomes O(n q) again.
    The primary key must be the block of L. The right endpoint is only the secondary key, and that is the split the q B + n2 / B bound depends on.
  • Inclusive/exclusive mix
    Queries arrive as inclusive [l, r] and the expand loops look like they should stop at r + 1, so you remove r when you meant to keep it, or you add one past the end and read garbage.
    Pick inclusive endpoints and the four loops on this page, and do not mix in an exclusive r from a Fenwick habit. A one-element query [i, i] is the test.

Interview follow-ups

Why sqrt?

The total movement is q B + n2 / B. The first term grows with B (left pointer wanders more inside a fat block); the second term shrinks with B (fewer blocks, so fewer full-array travels of R and fewer left-pointer resets). Those two pieces balance when B is about √n, or more tightly n / √q when q is far from n. Either choice is O((n + q) √n); the second is a constant-factor win on unbalanced inputs.

Can Mo be online?

No. The bound depends on sorting every query before the pointers move, so you must hold the whole batch. If queries arrive one at a time and must be answered immediately, you cannot reorder them and this page does not apply. Reach for a Fenwick, a segment tree, or a wavelet tree that supports the same question online.

Distinct with updates, online?

Still not Mo, even the 3D variant, because online forbids reordering. A segment tree of Fenwicks, a wavelet tree, or a sqrt-rebuild of the array are the usual answers, and they are heavier code. Mo-with-updates (time as a third coordinate, blocks of size n2/3) is only for an offline mix of updates and queries.

Hilbert order?

A Hilbert curve maps each pair (L, R) to a position on a space-filling curve so queries that are close in the 2D square are close in the 1D sort order. The pointer travel then has a smaller constant than block sort, at the cost of longer code and a 64-bit interleave. Learn the block sort first; add Hilbert only after the add/remove is already tiny and you are still near the time limit.

Recap

  • Offline only. Sort by (L/B, R).
  • Four while-loops move [curL,curR].
  • add/rem inverse, array frequencies after compress.
  • Start empty [0,-1].
  • B ≈ sqrt(n); odd-even R helps.
