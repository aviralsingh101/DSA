Randomised Techniques

Randomised algorithms in contests: hashing bases, Miller-Rabin, treaps, random shuffle + greedy, and Monte-Carlo fingerprints — plus how to bound the failure probability.

Medium 28 min read Prerequisites: Rolling Hash, Modular Arithmetic random hashing treap P2

Why this exists

You are given two strings, or two sets, or a 64-bit integer that might be prime, and a deterministic structure that answers the question is a page of code you do not want to write under a clock. A random fingerprint — a 64-bit hash, a random witness, a random heap priority — turns the same question into a handful of multiplications. Rolling hashes, Zobrist hashes of sets, Miller-Rabin primality, and treaps are the usual forms. The cost of that brevity is a failure probability you must be willing to bound out loud, because a fixed base on Codeforces will be hunted by an anti-hash test and a wrong primality test will declare a composite prime.

There are two error models and they are not interchangeable. A Monte-Carlo algorithm may return the wrong answer, with a probability you choose, and its worst-case runtime is usually deterministic: a hash comparison that collides, a Miller-Rabin witness that lies. A Las Vegas algorithm is always correct and only the runtime is random: randomised quicksort, a treap, a shuffle-then-greedy that retries until a witness works. Shipping a hash without saying "error about q / 264" is claiming Las Vegas for a Monte-Carlo algorithm, which is the interview trap.

In a real problem statement the signal is equality of strings or sets, primality of a 64-bit integer, or a sequence that wants split and merge, sitting next to limits that make the deterministic alternative (KMP build, trial division to √n, a splay tree) either slower to type or slower to run. Codeforces anti-hash tests punish a famous fixed base such as 31 modulo 109+7. Randomise the base from System.nanoTime() at startup, or use two moduli. Never seed new Random(0) in a submission you cannot reproduce the setter's attack against.

If a random 64-bit fingerprint collides with probability about 1 / 264, then q = 105 comparisons still fail with probability about 105 / 264, which is the calculation you recite. Las Vegas algorithms skip that sentence because they are never wrong, only sometimes slow.

Recognise this pattern

Say yes when you see

  • Rolling hash / Zobrist set equality
  • Miller-Rabin primality, Pollard Rho factoring
  • Treap / implicit treap as a randomised BST
  • Shuffle the array then a greedy that is correct in expectation or w.h.p.
  • Randomised incremental: random order of insertion

Not this pattern when

  • The judge is adversarial and you used a fixed hash → still randomise, or go deterministic (KMP, SA)
  • Need a guaranteed worst-case O(n log n) BST → splay / scapegoat / policy_rbtree, not a treap without care
  • Cryptographic randomness → java.security.SecureRandom, not contest RNG
  • Derandomisation required by the statement → method of conditional probabilities, rare

Core idea and the invariant

Zobrist hashing gives each value (or each pair of position and value) a random 64-bit mask, stored in a table you fill once at startup. The hash of a set is the XOR of the masks of its members; adding or removing an element is XOR-ing that mask again, because XOR is its own inverse. Two different sets collide only when their symmetric difference XORs to zero, which for random 64-bit masks happens with probability about 2-64 per comparison. Polynomial rolling hashes are the ordered cousin: a random base and one or two big moduli turn a string into a number, and a substring becomes a pair of prefix hashes. Both are Monte-Carlo: you state the union bound and you move on.

Miller-Rabin tests whether an odd n is prime. Write n - 1 = 2s × d with d odd. For a witness a, compute ad mod n and then square that value s times. If you never see 1 or n - 1 at the moment the theorem demands, n is composite for sure. If every squaring looks legal, n is probably prime; a random witness lies with probability at most 1/4, so a dozen independent witnesses push the error below 2-20. For every 64-bit integer there is a short fixed list of witnesses that jointly catch every composite, which is how the test becomes deterministic on that range. The implementation trap is a * b % m on longs: a billion times a billion overflows, the witness is garbage, and primes are declared composite.

Walk a few integers. For n = 7, n - 1 = 21 × 3; the witness 2 gives 23 = 8 ≡ 1 (mod 7), which is a pass. For n = 15 = 3 × 5, n - 1 = 21 × 7 and 27 = 128 ≡ 8 (mod 15), which is neither 1 nor 14, so 15 is composite after one witness. Zobrist on the side: the sets {1, 2} and {2, 1} XOR the same two masks and compare equal; {1, 2} versus {1, 3} differ unless those three masks are linearly dependent over GF(2), which is the 2-64 event. A shuffle-then-try-first-feasible permutation is Las Vegas: if a constant fraction of permutations work, the expected number of trials is a small constant.

A Monte-Carlo fingerprint is a homomorphism from the object (string, set, integer) into a ring or a bit-vector. Distinct objects collide with probability about 1 / |ring| per comparison when the map is pairwise independent or a random polynomial; a union bound over q comparisons is the failure probability of the whole run.

In plain words, you replaced the object by a random name that almost surely differs from every other object's name, and you must say "almost surely" rather than "always".

Interview sentence: "Hashing is Monte-Carlo with error q over 2 to the 64; a treap is Las Vegas and always correct."

Name the error model

Monte-Carlo: bounded error, usually a deterministic runtime (hash, a single Miller-Rabin round). Las Vegas: always correct, expected runtime (random pivot, treap, retry-until-witness). Do not call a hash "always correct" unless you verify collisions with a deterministic compare.

Name the error model

Algorithm

  1. Name the error model before you pick a tool. A fingerprint (hash, one Miller-Rabin round) is Monte-Carlo; a random tree or a random pivot is Las Vegas. Mixing the two in the analysis is how "always correct" gets attached to a hash.
  2. Seed the RNG from the clock, not from a constant. System.nanoTime() xor-ed with an identity hash is enough for a contest; new Random(0) is a target the setter can reproduce.
  3. Draw a random hash base or a Zobrist table of 64-bit masks. One random base plus two moduli, or XOR of random ids for a set: state the collision probability once in a comment and then treat compares as equalities.
  4. For 64-bit primality, use the known witness list (or k random witnesses). Deterministic bases make Miller-Rabin always correct on that range; random witnesses need the 4-k bound said out loud.
  5. Give every treap node a random long priority and rotate to heap order. The BST order stays on the keys, the heap order on the priorities, and split/merge then run in expected logarithmic time.
  6. Write the failure or expectation bound where a reviewer will see it. Interviews ask for that sentence; a blog without it reads as if the algorithm were deterministic, which is the claim that anti-hash tests exist to punish.

Java implementation

Trial division up to sqrt(n). Fine for n ≤ 1e12 if careful, slow at 1e18.

public class IsPrimeBrute {
        static boolean prime(long n) {
            if (n < 2) return false;
            for (long i = 2; i * i <= n; i++) if (n % i == 0) return false;
            return true;
        }
        public static void main(String[] args) {
            System.out.println(prime(15) + " " + prime(17));
        }
        // Input : 15, 17
        // Output: false true

Deterministic Miller-Rabin for 64-bit (known witness set).

JavaMillerRabin.java
public class MillerRabin {
        static long mul(long a, long b, long m) {
            return (long) ((a * (double) b) % m); // demo only; use BigInteger or int128 mulMod in real contests
        }
        static long pow(long a, long e, long m) {
            long r = 1 % m;
            while (e > 0) {
                if ((e & 1) == 1) r = mul(r, a, m);
                a = mul(a, a, m);
                e >>= 1;
            }
            return r;
        }
        static boolean check(long n, long a) {
            if (n % a == 0) return n == a;
            long d = n - 1, s = 0;
            while ((d & 1) == 0) { d >>= 1; s++; }
            long x = pow(a, d, n);
            if (x == 1 || x == n - 1) return true;
            for (int i = 1; i < s; i++) {
                x = mul(x, x, n);
                if (x == n - 1) return true;
            }
            return false;
        }
        static boolean prime(long n) {
            if (n < 2) return false;
            for (int p : new int[] {2, 3, 5, 7, 11, 13, 17}) if (n == p) return true;
            for (int a : new int[] {2, 3, 5, 7, 11, 13, 17}) if (!check(n, a)) return false;
            return true;
        }
        public static void main(String[] args) {
            System.out.println(prime(15) + " " + prime(17));
        }
        // Input : 15, 17
        // Output: false true
    }

Set hash: XOR of random masks. Toggle membership.

JavaZobrist.java
import java.util.Random;
    public class Zobrist {
        static final long[] MASK = new long[64];
        static {
            Random rng = new Random(1_000_000_007L);
            for (int i = 0; i < MASK.length; i++) MASK[i] = rng.nextLong();
        }
        static long toggle(long h, int x) { return h ^ MASK[x]; }
        public static void main(String[] args) {
            long a = 0, b = 0;
            a = toggle(a, 1); a = toggle(a, 2);
            b = toggle(b, 2); b = toggle(b, 1);
            System.out.println(a == b);
        }
        // Input : {1,2} vs {2,1}
        // Output: true
    }

Complexity

Time MR O(k log n mul); hash O(1); treap O(log n) expected Space O(1) to O(n)

Miller-Rabin on one integer is k modular exponentiations, each a O(log n) sequence of multiplications modulo n. With a 128-bit mulMod those multiplications are constant time; with BigInteger they are O(log n) each, still fine for a few dozen tests. A Zobrist or rolling-hash compare is a handful of XORs or multiplications, treated as O(1). A treap split or merge is expected O(log n) rotations because a random priority heap has logarithmic height.

The failure calculation is a union bound. One 64-bit fingerprint collides with probability about 2-64; q independent compares therefore fail with probability at most q / 264. Putting real numbers in: q = 105 gives about 5 × 10-15, and even a billion compares is still about 5 × 10-11. Miller-Rabin with seven deterministic 64-bit witnesses has error zero on that range. Trial division to √n on a 64-bit composite is up to 232 divisions and is the thing these tests replace.

Edge cases and pitfalls

  • Fixed hash base on CF
    A famous base such as 31 modulo 109+7 looks identical to the textbook rolling-hash, so the sample and the first sixty tests pass, then an anti-hash test constructs a collision and you WA on test 67.
    Draw the base from the clock, or use two independent moduli, or hash modulo 261-1 with unsigned overflow. Re-run against a known anti-hash pair before you submit.
  • mul overflow in MR
    a * b % m on longs looks like the usual modular multiply, but when a and b are near 1018 the product wraps in 64 bits, the witness becomes garbage, and a real prime is reported composite.
    Use BigInteger, a split mulMod, Math.multiplyHigh, or unsigned 128-bit arithmetic. Test on a known 64-bit prime near 264, not on 17.
  • Seeding Random with 0
    A constant seed makes every hash table identical across machines, which is convenient for debugging and is exactly the table a setter can target once they know the seed.
    Seed from System.nanoTime() in the submission. Keep the constant seed only in a local debug build that you will not send to the judge.
  • Treap without unique priorities
    Equal integer priorities look harmless because the BST order is still well defined, but a rotate-on-tie can loop or build a long chain, and the expected-log proof assumes distinct random priorities.
    Draw a random long per node. On the rare remaining tie, break it by node identity and never rotate in a cycle.
  • Calling a Monte-Carlo algorithm Las Vegas in an interview
    "The hash is always correct" sounds like confidence, but a fingerprint can collide, so the claim is false and a follow-up of "what is the error?" has no number attached.
    Say "error about q / 264" for a 64-bit hash, or verify a suspected collision with a deterministic compare (KMP, character-by-character). Treaps and random pivots are the ones that are always correct.

Interview follow-ups

Monte-Carlo vs Las Vegas?

A Monte-Carlo algorithm may be wrong, with a probability you bound, and its worst-case runtime is usually deterministic: a hash compare, a single Miller-Rabin round. A Las Vegas algorithm is never wrong and only the runtime is random: randomised quicksort, a treap, a retry-until-witness loop. Hashing without a deterministic verify is Monte-Carlo. Do not mix the two sentences in an interview.

Why do 7 MR bases suffice for 64-bit?

There is a proven finite set of witnesses that jointly catch every composite below 264. Checking those witnesses, and no others, makes Miller-Rabin deterministic on unsigned 64-bit integers: every composite fails at least one of them, and no prime fails any of them. Random witnesses are for bigger integers, or for when you have not memorised the list.

Zobrist vs polynomial hash for sets?

A polynomial hash cares about order: swapping two characters changes the value. XOR of random ids is commutative and involutive, so it hashes sets (and, with a counter-dependent mask or a 2D table, multisets). Use Zobrist when the object is "these elements, in any order"; use a polynomial when the object is a string or a sequence.

Can you derandomise hashing?

Universal hashing — drawing a function from a 2-universal family at startup — is already the theoretical version of what this page does with a random base. Worst-case deterministic substring equality does not hash at all: it uses KMP, the Z-function, or a suffix array. If the statement forbids randomness, those are the tools, not a fixed "random-looking" base.
