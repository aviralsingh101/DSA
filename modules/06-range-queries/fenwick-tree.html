Fenwick Tree (BIT)

Point update and prefix sum in O(log n) each, using the lowest set bit to jump responsibility ranges — the smallest structure that beats a prefix array once updates appear.

Medium 28 min read Prerequisites: Prefix Sums, Constraints to Complexity Fenwick BIT prefix inversions P1

Why this exists

You are given an array such as [3, 1, 4, 1, 5, 9, 2, 6], and between asking for the sum of a prefix someone keeps changing a single cell. A prefix-sum array answers each range in one subtraction, but the moment you write a[3] += 2 every prefix that includes index 3 is stale, and rewriting those prefixes costs a linear scan. With a hundred thousand updates and a hundred thousand sums you are looking at ten billion writes, and the judge will cut you off. You need the same prefix algebra without the linear repair.

A Fenwick tree, also called a Binary Indexed Tree, keeps each array value inside a handful of buckets instead of one running total. Index i (counting from 1) owns a contiguous range that ends at i and has length equal to the value of i's lowest set bit, written lsb(i) = i & -i. So index 6, whose binary form is 110, owns a range of length 2 ending at 6, which is the pair a[5], a[6]. An update of cell i walks every bucket that contains i; a prefix query walks a disjoint set of buckets that tile [1, i]. Each walk is a handful of array reads, never a scan.

The two walks go in opposite directions because they are answering opposite questions. A prefix query wants buckets that sit inside [1, i] and do not overlap, so it peels the bucket ending at the current index off the prefix and jumps to whatever is left, which is i -= lsb(i). An update wants every bucket that contains index i, including ones that stretch past i to a later end, so it climbs to the next larger owner with i += lsb(i). Same lowest-set-bit quantity, opposite arithmetic.

In a real statement the signal is point updates mixed with prefix or range sums at limits such as n, q ≤ 2×10⁵. That combination rules out a prefix array and is exactly what Fenwick is for. The same twenty lines then cover inversion counting, "how many values to the left are smaller", frequency queries on compressed ranks, and the two-tree trick that turns range-add plus range-sum into four point updates. Reach for a segment tree only when the operation is not a prefix of something invertible.

Index i owns the contiguous sum of length i & -i that ends at i. A prefix query subtracts that length to peel off disjoint buckets; an update adds it to climb to every larger bucket that still contains i. The two walks are opposite because one is covering a prefix and the other is notifying the owners of a single cell.

Recognise this pattern

Say yes when you see

  • Point add / point set mixed with prefix or range sums
  • "Count inversions", "count smaller elements to the left / right"
  • Frequency queries on compressed values (order-statistic tree)
  • The two-BIT trick: range add + range sum
  • n, q ≤ 2×10⁵ with updates, operation is sum or XOR

Not this pattern when

  • No updates, only range sums → prefix array
  • Range minimum (no inverse) → sparse table or segment tree
  • Range add and range min together → lazy segtree
  • Arbitrary associative combine that is not prefix-invertible → segment tree

Constraint tell: n, q ≤ 2×10⁵ with point updates and prefix or range sums is Fenwick's home. Each operation is about twenty array reads, so the whole batch finishes in milliseconds. Values of 10⁹ with n of 10⁵ overflow an int prefix and need long. If the value universe is 10⁹ but you only have n items, compress the coordinates down to ranks 1..n before you index the tree.

Core idea and the invariant

Index the tree from 1, never from 0. The cell bit[i] stores the sum of the closed range a[i - lsb(i) + 1 .. i]: a contiguous bucket that ends at i and has length lsb(i). That length is i & -i because Java integers are two's complement: -i equals ~i + 1, which flips every bit of i and then adds one. Adding one walks through the trailing zeros of i, flips them back to zero, and leaves the lowest 1 of i sitting alone in the conjunction. For i = 12 = 1100 in binary, -i ends with 0100, the conjunction is 4, and so bit[12] owns the four entries that end at 12. The same identity is why you must never call it on 0: 0 & -0 is 0, and adding zero is an infinite loop.

A prefix sum of the first i elements is the sum of the disjoint buckets you land on while repeatedly subtracting the lowest set bit. Each subtraction clears the lowest 1 of the current index, so the walk visits at most one bucket per bit and finishes in at most log2 i steps. An update at i does the opposite: it adds the delta into bit[i] and then into every larger bucket that still contains i, found by repeatedly adding the lowest set bit. Adding the lsb carries into a higher bit and lands on the next index whose owned range is a proper multiple of the current one, which is exactly the next owner that covers i. The two loops share one helper and no recursion.

A range sum [l, r] is two prefixes, prefix(r) - prefix(l - 1), which is legal only because addition has an inverse. The same inverse is why Fenwick cannot do range minimum: there is nothing you can subtract from min(a[1..r]) to recover min(a[l..r]). A range add on a point-query tree is the difference-array trick sitting inside the BIT: add v at l and add -v at r+1. Two Fenwick trees together give range add and range sum, which is the usual contest upgrade before you reach for a lazy segment tree.

Walk the sample [3, 1, 4, 1, 5, 9, 2, 6] after the tree is built. One-based, the buckets are bit[1]=3 (just a[1]), bit[2]=4 (a[1]+a[2]), bit[3]=4 (just a[3]), bit[4]=9 (a[1]..a[4]), bit[5]=5, bit[6]=14 (a[5]+a[6]), bit[7]=2, bit[8]=31 (the whole array). Asking for prefix(7) starts at 7, adds bit[7]=2, drops to 6, adds bit[6]=14, drops to 4, adds bit[4]=9, and lands on 0 with a total of 25, which is 3+1+4+1+5+9+2. An update of +2 at index 3 climbs the other way: 3, then 4, then 8, because those are the three buckets whose owned ranges contain 3. After that write, the same three query nodes would read 27.

With 1-based indexing and lsb(i) = i & -i, each cell owns a contiguous suffix of the prefix that ends at i:

bit[i] = sum(a[i - lsb(i) + 1 .. i])

In plain words, index i does not store "the sum up to i". It stores only the last lsb(i) entries before i, and a prefix is recovered by adding those leftover chunks as you strip one set bit at a time. That is why the query walks down (subtract lsb, peel a finished chunk) and the update walks up (add lsb, notify the next larger owner): one of them is assembling a prefix from pieces that sit inside it, and the other is telling every piece that still covers the cell you just changed.

Interview sentence: "Update adds lsb, query subtracts lsb; both are walking the binary representation of the index."

Why i & -i is the lowest set bit

In two's complement, -i flips every bit of i and adds one, which leaves the lowest 1 of i in place and turns every lower 0 into 0 in the conjunction. Example: i = 12 = 11002, -i = ...01002, conjunction 01002 = 4, and bit[12] covers four entries ending at 12. That numeric value is the length of the range i owns, not a coincidence: the lowest set bit of i is the largest power of two that divides i, and Fenwick assigns i a bucket of exactly that length.

Always 1-based

i & -i on 0 is 0, so i += 0 is an infinite loop. The tree starts at index 1. Translate 0-based array index i to Fenwick index i+1.

Why the two walks go opposite ways

A prefix query asks "which of my own buckets tile [1, i]?" and those buckets end at or before i, so you subtract the lsb and drop to a shorter leftover prefix. An update asks "which buckets in the whole tree still contain i?" and those buckets end at or after i, so you add the lsb and climb to the next larger owner. Same helper, opposite question.

Algorithm

  1. Allocate a 1-based tree. Create long[] bit of length n + 1 and leave index 0 unused, because 0 & -0 is 0 and a loop that adds zero never terminates.
  2. Define lsb as i & -i. That quantity is both the length of i's owned range and the hop you take on every walk, so it is the only helper the two loops share. Never evaluate it at 0.
  3. add(i, v): climb by adding the lsb. Loop for (; i < bit.length; i += i & -i) bit[i] += v. Translate a 0-based array index x to i = x + 1 first, so you notify every bucket whose owned range contains x.
  4. prefix(i): drop by subtracting the lsb. Loop for (; i > 0; i -= i & -i) acc += bit[i]. Each hop peels off the bucket that ends at the current i, and what remains is a strictly shorter prefix.
  5. Range [l, r] is two prefixes. Return prefix(r) - prefix(l - 1) with both ends 1-based and inclusive. prefix(0) is 0 because the loop never runs, which is what makes a query that starts at the first cell safe.
  6. Build by adding each a[i] once, or in linear time. The naive build is n updates. The linear build writes bit[i] = a[i] and then pushes each cell onto its parent i + lsb(i), so each index is written a constant number of times.
  7. Compress coordinates before using the tree as a frequency map. If values go up to 10⁹ you cannot allocate a bucket per value. Sort the unique keys, rank them 1..n, and index the tree by rank so inversion-counting stays O(n log n).

Java implementation

Point update is O(1), range sum is O(n). The Fenwick swaps those to O(log n) each.

JavaBruteRangeSum.java
public class BruteRangeSum {
    
        static int[] a;
    
        static void add(int i, int v) { a[i] += v; }
    
        static long range(int l, int r) {
            long s = 0;
            for (int i = l; i <= r; i++) s += a[i];
            return s;
        }
    
        public static void main(String[] args) {
            a = new int[] {0, 3, 1, 4, 1, 5, 9, 2, 6};   // 1-based
            System.out.println(range(1, 7));
            System.out.println(range(3, 7));
            add(3, 2);
            System.out.println(range(1, 7));
        }
        // Input : [3,1,4,1,5,9,2,6] 1-based, then +2 at index 3
        // Output: 25
        //         21
        //         27
    }

The two loops. Build by adding each element. Same three numbers as the brute tab.

JavaFenwickTree.java
public class FenwickTree {
    
        final long[] bit;
    
        FenwickTree(int n) { bit = new long[n + 1]; }
    
        void add(int i, long v) {
            for (; i < bit.length; i += i & -i) bit[i] += v;
        }
    
        long prefix(int i) {
            long s = 0;
            for (; i > 0; i -= i & -i) s += bit[i];
            return s;
        }
    
        long range(int l, int r) { return prefix(r) - prefix(l - 1); }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
            FenwickTree ft = new FenwickTree(a.length);
            for (int i = 0; i < a.length; i++) ft.add(i + 1, a[i]);
            System.out.println(ft.prefix(7));
            System.out.println(ft.range(3, 7));
            ft.add(3, 2);
            System.out.println(ft.prefix(7));
        }
        // Input : [3,1,4,1,5,9,2,6], then +2 at index 3
        // Output: 25
        //         21
        //         27
    }

Coordinate-compress, scan left to right, query how many already-inserted ranks are strictly larger, then insert. Classic O(n log n) inversion count.

JavaInversionBit.java
import java.util.Arrays;
    import java.util.HashMap;
    import java.util.Map;
    
    public class InversionBit {
    
        static class Fenwick {
            long[] bit;
            Fenwick(int n) { bit = new long[n + 1]; }
            void add(int i, long v) { for (; i < bit.length; i += i & -i) bit[i] += v; }
            long prefix(int i) {
                long s = 0;
                for (; i > 0; i -= i & -i) s += bit[i];
                return s;
            }
            long range(int l, int r) { return prefix(r) - prefix(l - 1); }
        }
    
        static int[] compress(int[] a) {
            int[] b = a.clone();
            Arrays.sort(b);
            Map<Integer, Integer> rk = new HashMap<>();
            int r = 1;
            for (int v : b) if (!rk.containsKey(v)) rk.put(v, r++);
            int[] out = new int[a.length];
            for (int i = 0; i < a.length; i++) out[i] = rk.get(a[i]);
            return out;
        }
    
        static long inversions(int[] a) {
            int[] rk = compress(a);
            Fenwick ft = new Fenwick(a.length);
            long inv = 0;
            for (int i = 0; i < rk.length; i++) {
                inv += ft.range(rk[i] + 1, a.length);   // seen ranks strictly larger
                ft.add(rk[i], 1);
            }
            return inv;
        }
    
        public static void main(String[] args) {
            System.out.println(inversions(new int[] {3, 1, 4, 1, 5, 9, 2, 6}));
            System.out.println(inversions(new int[] {1, 2, 3, 4}));
            System.out.println(inversions(new int[] {4, 3, 2, 1}));
        }
        // Input : [3,1,4,1,5,9,2,6]
        // Output: 8
        //         0
        //         6
    }

Complexity

Time O(log n) per update or prefix query Space O(n)

Each step of either loop changes i by its lowest set bit, which either clears that bit (query) or carries into a higher bit (update). At most log2 n bits exist:

Top(n) = O(log n),   Tbuild = O(n log n) naive / O(n) linear build

A segment tree is the same bound with a larger constant and more memory (4n vs n). Fenwick wins when the query is a prefix of an invertible op. At n = q = 2×10⁵ both pass; Fenwick is shorter to type.

Inversion counting is n updates and n queries on a compressed universe of size n, so O(n log n), matching merge-sort inversions with a reusable structure.

Edge cases and pitfalls

  • 0-based index in a 1-based tree
    add(0, v) does i += 0 forever, or immediately ArrayIndexOutOfBounds. The most common Fenwick crash, and it looks like a harmless 0-based habit.
    Map every 0-based array index i to Fenwick index i+1, and assert i >= 1 at the top of add. A unit test that updates a[0] will catch the translation.
  • int overflow in the buckets
    n = 10⁵, values 10⁹, prefixes 10¹⁴. Wrapping buckets still look vaguely plausible after a subtraction, so the sample can pass and hidden tests fail.
    Allocate long[] bit every time, even when the array itself is int[]. A single prefix of the whole array is the overflow check.
  • range(l, r) with l = 1 calling prefix(0) incorrectly
    Writing prefix(r) - prefix(l) drops a[l], and the remaining sum still looks like a plausible range. Or calling prefix(-1) when someone passed 0-based l = 0.
    prefix(r) - prefix(l - 1) with l, r 1-based. prefix(0) is 0 because the loop never runs.
  • Using a BIT for range minimum
    There is no inverse, so you cannot peel a left prefix off a right prefix. People still try, get a number, and fail hidden tests.
    Segment tree, or a sparse table if static. Fenwick min-trees exist only for very restricted updates (you can update a value downward, not arbitrarily).
  • Forgetting to compress before a frequency BIT
    Values up to 10⁹, allocating new long[1_000_000_001], OOM. Or using the raw value as an index and throwing, which looks like a bounds bug rather than a missing compression.
    Sort unique values, rank them 1..n, BIT of size n. Ties need a stable policy (strictly greater vs greater-or-equal) matching the inversion definition.

Interview follow-ups

How do you build in O(n) instead of O(n log n)?

Set bit[i] = a[i] (1-based), then for i = 1..n push bit[i] onto j = i + lsb(i) if j ≤ n. Each index is written a constant number of times. Useful when n is 10⁷ and the log in the build actually shows up.

Why is a Fenwick unable to do range minimum cleanly?

Querying [l, r] as a difference of prefixes needs an inverse. Min has none. You can store mins of the buckets, but combining an arbitrary [l, r] from those buckets needs the same disjoint-dyadic cover a segment tree already gives you, and the BIT addressing does not produce that cover for an arbitrary inner range. Write a segment tree.

How does inversion count handle duplicates?

For strictly-greater inversions, query ranks > current then insert. Equal values are not inversions. If you insert before querying you count equals as inversions. The order of query-then-insert (or insert-then-query with rank+1) is the whole policy. Coordinate compression must keep duplicates as the same rank.

When do you pick Fenwick over a segment tree in an interview?

When the interviewer asked for range sums with point updates, or inversions. It is twenty lines and the lsb trick is a talking point. If they then say "now make it range min" you have a reason to rewrite as a segment tree, which is the next page.

Hint for LC 315 — scan from the right

"Smaller to the right" means: process a[n-1], then a[n-2], ... At a[i] the BIT already holds the ranks of everything to the right, so prefix(rank(a[i]) - 1) is the answer for i. Then insert rank(a[i]). Compress first. Duplicates: ranks are equal, and prefix(rank-1) correctly ignores equals if you assigned a unique rank per value (not per occurrence).

Hint for LC 493 — reverse pairs with 2*val

A reverse pair is i < j and a[i] > 2*a[j]. Scan from the right: query how many inserted values are > 2*a[i] wait no — when i is current and j's already in (to the right), you want count of inserted values v with a[i] > 2v, i.e. v < a[i]/2. Easier: compress all a[i] and all 2*a[i] together as longs, query the count of ranks strictly above rank(2*a[i]), then insert a[i]. Overflow: 2*a[i] is a long.

  • Update adds lsb, query subtracts lsb. Both O(log n).
  • Range = prefix(r) - prefix(l-1). Use long[].
  • Compress values before a frequency BIT.
  • Not for min. That is a segment tree.
