Module 06 · Range Query Structures

Sparse Table & RMQ

Idempotent range queries on a static array in O(1) after an O(n log n) doubling table — two overlapping blocks, no inverse required.

Medium 26 min read Prerequisites: Prefix Sums, Binary Search Basics sparse table RMQ idempotent P1

Why this exists

You are given an array such as [3, 1, 4, 1, 5, 9, 2, 6] that will never change, and someone keeps asking: what is the smallest value between these two indices? Scanning the range is correct, but a hundred thousand queries each walking a hundred thousand cells is ten billion steps and the judge will cut you off. A prefix-sum array would answer a range sum in one subtraction, because addition has an inverse: if you know the sum up to r and the sum up to l-1, you can peel the left prefix off. Minimum has no inverse of that kind. Knowing min(a[0..r]) and min(a[0..l-1]) tells you nothing about min(a[l..r]), because the overall minimum might sit in the left prefix and hide the answer you actually wanted.

A sparse table exploits a different algebraic property, idempotence — combining a value with itself gives the same value back, so min(x, x) = x. That means two ranges that overlap in the middle can still be combined freely: the overlap is counted twice, and the minimum does not care. The table stores, for every starting index i and every length that is a power of two, the minimum (or gcd, or bitwise AND) of that block. Any query range of length L is then covered by two such blocks of length 2floor(log2 L), one glued to the left end and one glued to the right. Two array lookups and one combine, and you are done in constant time.

The catch is that the array must stay still. Changing one cell invalidates every block that covers it, which in the worst case is about n table entries, so a single point update is as expensive as rebuilding. For mixed updates you want a segment tree. For invertible operations on a static array, a prefix sum is smaller and simpler. This page is the remaining quadrant: the array never changes, and the operation is idempotent.

In a real statement the signal is a static array sitting next to limits such as n, q ≤ 10⁶ and a query that is minimum, maximum, gcd, or bitwise AND / OR. That combination rules out a scan per query, and it is exactly what a sparse table is for. The same doubling then covers the Euler-tour reduction of lowest-common-ancestor, and any other problem that secretly asks for the minimum of a range that never moves.

Idempotent operations can overlap, so any range is the combine of two power-of-two blocks glued to its ends. The overlap is free for min, gcd and AND; it would double-count a sum, which is why this table is not a prefix array.

Recognise this pattern

Say yes when you see

  • Range minimum / maximum / gcd / AND / OR on a static array, many queries
  • The constraints are n, q ≤ 10⁶ and you cannot afford O(log n) per query constants of a segment tree
  • LCA via RMQ on an Euler tour (the min-depth range)
  • "The array does not change" is explicit or implied (build once, query many)
  • You need the index of the minimum, not just the value (store argmin in the table)

Not this pattern when

  • The array is updated between queries → segment tree or Fenwick
  • The operation is sum / XOR (invertible) on a static array → prefix sums
  • Exactly one query → just scan the range
  • You need range add and range min together → lazy segment tree, not a sparse table

Constraint tell: n, q ≤ 10⁶ on a static array with a min / max / gcd / AND query is the textbook sparse-table prompt. The table holds n log n integers — about 80 MB at n = 10⁶ with 32-bit cells — which is acceptable. If n is 10⁷ you cannot afford that memory, and if even one update appears you should switch to a segment tree instead.

Core idea and the invariant

You need a two-dimensional table st[k][i]. The cell st[k][i] holds the combine of the contiguous block a[i .. i + 2k - 1], a stretch of length 2k that starts at index i. Row k = 0 is just a copy of the array, because a block of length 1 is a single element. Every later row is filled from the row below it: st[k][i] = op(st[k-1][i], st[k-1][i + 2k-1]), which glues two already-computed halves of length 2k-1 into one block of length 2k. The outer loop must be k, then i, because each row reads the row you just finished. You only write a cell when the second half still fits inside the array.

A query on the closed interval [L, R] has length len = R - L + 1. Let k = floor(log2 len), the largest power of two that still fits inside the range. The left block [L, L + 2k - 1] starts at L and stays inside the query. The right block [R - 2k + 1, R] ends at R and also stays inside. Together they cover every index in [L, R], and they overlap in the middle whenever len is not itself a power of two. That overlap is harmless precisely because the operation is idempotent. Precompute an array lg[i] so the floor-log is one lookup, not a floating-point call in a hot loop.

Idempotence is load-bearing. Sum is not idempotent: two overlapping blocks would add the middle twice and report a number that looks plausible and is wrong. That is why a sparse table is not a replacement for prefix sums, even though both answer range queries on a static array. The operations that work are minimum, maximum, gcd, lcm (with care around zeros), bitwise AND, bitwise OR, and "the first index at which the minimum occurs" if you store an argmin instead of a value.

Walk the sample [3, 1, 4, 1, 5, 9, 2, 6] through a query on indices [2, 6]. The length is 5, so k = floor(log2 5) = 2 and each block has length 4. The left block is indices 2..5, values 4, 1, 5, 9, minimum 1, which is already stored as st[2][2]. The right block starts at 6 - 4 + 1 = 3, indices 3..6, values 1, 5, 9, 2, minimum 1, stored as st[2][3]. Combining them gives min(1, 1) = 1. The overlap [3, 5] sat in both blocks and did not change the answer. A sum table on the same two blocks would have added 1+5+9 twice and reported 32 instead of 21.

For an idempotent associative operation, any range is the combine of two (possibly overlapping) dyadic blocks:

op(L, R) = op( st[k][L], st[k][R - 2k + 1] ),  k = ⌊log2(R - L + 1)⌋

In plain words, you never have to tile the query with disjoint pieces. You grab the longest power-of-two window that starts at L and the longest power-of-two window that ends at R, and because taking the minimum of a value twice does not change it, the stretch that was in both windows is free. Sum would charge you twice for that stretch, which is why this identity is reserved for min, max, gcd and the bitwise cousins.

Interview sentence: "I overlap two power-of-two windows; min does not mind the overlap, sum would."

Do not sparse-table a sum

It compiles and produces a number. The number is wrong whenever the two blocks overlap, which is every query whose length is not itself a power of two. Use prefix sums.

Precompute lg[]

lg[1] = 0; for (i = 2; i ≤ n; i++) lg[i] = lg[i >> 1] + 1; Integer log in O(1) with no floating point, no numberOfLeadingZeros in a hot loop, and defined at 0-length guards you will not hit.

When a sparse table is the right structure

Algorithm

  1. Allocate the two tables. Create st[LOG][n] and lg[n+1], with LOG = 32 - Integer.numberOfLeadingZeros(n), so you have one row per power of two that can appear as a block length.
  2. Fill the floor-log array first. Set lg[1] = 0 and then lg[i] = lg[i >> 1] + 1 for every later i, because a query must read k in constant time and a floating-point log will round the wrong way at powers of two.
  3. Copy the array into row 0. A block of length 20 = 1 is a single element, so st[0][i] = a[i] is the base case every later row will double from.
  4. Double each row from the one below. For k from 1, for every i whose block of length 1<<k still fits, write st[k][i] = op(st[k-1][i], st[k-1][i + (1<<(k-1))]). The outer loop is k because each row reads the finished row beneath it.
  5. Answer [L, R] with two lookups. Read k = lg[R - L + 1] and return op(st[k][L], st[k][R - (1<<k) + 1]). The + 1 is what makes the right block end exactly at R.
  6. Refuse this structure for sum or XOR. The two blocks overlap on almost every query, so a sum would double-count the middle and XOR would cancel it to zero. Those operations belong on a prefix array.
  7. Rebuild, or switch, if an update arrives. One write invalidates every block that covers that index, which is linear in n. Rare updates can rebuild the whole table; mixed updates want a segment tree.

Java implementation

Each query scans the range. Correct, O(n) per query, dies at n = q = 10⁵.

JavaBruteRmq.java
public class BruteRmq {
    
        static int rangeMin(int[] a, int l, int r) {
            int m = a[l];
            for (int i = l + 1; i <= r; i++) m = Math.min(m, a[i]);
            return m;
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
            System.out.println(rangeMin(a, 2, 6));
            System.out.println(rangeMin(a, 0, 7));
            System.out.println(rangeMin(a, 4, 4));
        }
        // Input : [3, 1, 4, 1, 5, 9, 2, 6]
        // Output: 1
        //         1
        //         5
    }

Min-table with precomputed logs. Queries are two lookups. The dry-run sample.

JavaSparseTable.java
public class SparseTable {
    
        final int[] lg;
        final int[][] st;
    
        SparseTable(int[] a) {
            int n = a.length;
            int LOG = 32 - Integer.numberOfLeadingZeros(n);
            lg = new int[n + 1];
            for (int i = 2; i <= n; i++) lg[i] = lg[i >> 1] + 1;
            st = new int[LOG][n];
            System.arraycopy(a, 0, st[0], 0, n);
            for (int k = 1; k < LOG; k++) {
                for (int i = 0; i + (1 << k) <= n; i++) {
                    st[k][i] = Math.min(st[k - 1][i], st[k - 1][i + (1 << (k - 1))]);
                }
            }
        }
    
        int rangeMin(int l, int r) {
            int k = lg[r - l + 1];
            return Math.min(st[k][l], st[k][r - (1 << k) + 1]);
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
            SparseTable st = new SparseTable(a);
            System.out.println(st.rangeMin(2, 6));
            System.out.println(st.rangeMin(0, 7));
            System.out.println(st.rangeMin(4, 4));
        }
        // Input : [3, 1, 4, 1, 5, 9, 2, 6]
        // Output: 1
        //         1
        //         5
    }

The same doubling with gcd. Range gcd is the other common idempotent query; CF 474F is this plus a count of how many array entries equal the gcd.

JavaSparseTableGcd.java
public class SparseTableGcd {
    
        static int gcd(int a, int b) {
            while (b != 0) { int t = a % b; a = b; b = t; }
            return Math.abs(a);
        }
    
        final int[] lg;
        final int[][] st;
    
        SparseTableGcd(int[] a) {
            int n = a.length;
            int LOG = 32 - Integer.numberOfLeadingZeros(n);
            lg = new int[n + 1];
            for (int i = 2; i <= n; i++) lg[i] = lg[i >> 1] + 1;
            st = new int[LOG][n];
            System.arraycopy(a, 0, st[0], 0, n);
            for (int k = 1; k < LOG; k++) {
                for (int i = 0; i + (1 << k) <= n; i++) {
                    st[k][i] = gcd(st[k - 1][i], st[k - 1][i + (1 << (k - 1))]);
                }
            }
        }
    
        int rangeGcd(int l, int r) {
            int k = lg[r - l + 1];
            return gcd(st[k][l], st[k][r - (1 << k) + 1]);
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
            SparseTableGcd st = new SparseTableGcd(a);
            System.out.println(st.rangeGcd(2, 6));
            System.out.println(st.rangeGcd(4, 7));
            System.out.println(st.rangeGcd(0, 0));
        }
        // Input : [3, 1, 4, 1, 5, 9, 2, 6]
        // Output: 1
        //         1
        //         3
    }

Complexity

Time O(n log n) build, O(1) query Space O(n log n)

Row k has at most n entries, and there are log n rows, each filled with a constant-time combine. At n = 10⁶ that is about 10⁶ × 20 = 2×10⁷ writes, which is a few milliseconds:

Tbuild = Θ(n log n),   Tquery = Θ(1)

A segment tree is O(n) build and O(log n) query, and supports updates. When there are no updates and q is huge, the sparse table wins on query constants (two array reads vs a dozen). At n = 10⁶ the table is the memory you pay for those constants, about 80 MB of 32-bit cells.

Farach-Colton/Bender RMQ is O(n) build and O(1) query after a Cartesian-tree reduction; nobody codes it in a contest. Binary lifting LCA is the usual alternative when the RMQ is on a tree, not an array.

Edge cases and pitfalls

  • Using it for sum / XOR
    The two blocks overlap, the middle is combined twice, and XOR of a value with itself is 0, so you can even "zero out" the overlap. Silently wrong, and it looks fine on any query whose length is itself a power of two.
    Sparse tables are for idempotent ops only. Sum and XOR go to a prefix array; test a query whose length is not a power of two, because that is where the overlap appears.
  • Off-by-one in the right block
    st[k][r - (1< without the + 1, so the right block ends at R-1 and the last element is dropped whenever length is not a power of two.
    Right start is r - (1<. Check a query of length 3: k = 1, blocks of length 2 must cover all three indices.
  • Floating-point log
    (int)(Math.log(len) / Math.log(2)) rounding down incorrectly at powers of two, picking k too large, and reading off the end of a row.
    Build an integer lg[] table, or use 31 - Integer.numberOfLeadingZeros(len). Check a query whose length is exactly 8 or 16, where the float version most often slips.
  • Building with i outer, k inner
    st[k][i] reads st[k-1][...] that has not been filled yet if k is the inner loop. The cell looks initialised because Java zeros the array, so you silently combine zeros instead of real values.
    Keep k as the outermost loop, then i. The dependency is the same as binary-lifting's doubling: each row is defined only in terms of the finished row below it.
  • Inclusive / exclusive bounds mix-up
    The table is built for closed intervals but the query is written as [L, R) from a prefix-sum habit, dropping a[R] or throwing.
    Pick closed [L, R] and document it. The length is R - L + 1.

Interview follow-ups

Can you support updates?

A single point update touches O(n) entries in the worst case (every block that covers that index). Rebuilding the whole table is O(n log n), which is fine if updates are rare. For interleaved updates, use a segment tree: O(log n) per update and query, O(n) memory, and it handles non-idempotent ops too.

How does this become O(1) LCA?

DFS an Euler tour of every visit (length 2n-1) and the depths at those visits. The LCA of u and v is the minimum-depth node between their first occurrences on the tour. That is RMQ on the depth array, which a sparse table answers in O(1). See binary lifting for the version that also gives k-th ancestor.

Why not just use a segment tree always?

You can. A segment tree of mins is O(log n) query, O(n) memory, and survives updates. The sparse table wins when (1) there are no updates, (2) q is large enough that the log n factor and heavier constants show up, and (3) you want the two-line query. In Java the difference is often a factor of 3-5 on query-heavy RMQ.

Does gcd really belong here?

Yes: gcd(a, a) = a, so it is idempotent, and gcd is associative. Range gcd plus "how many entries equal that gcd" is CF 474F: the sparse table gives the gcd, then a binary search on a positions-list of that value counts occurrences in [L, R].

Hint for CF 474F — gcd plus a count

The number of surviving ants in [L, R] is the length minus the number of array entries equal to G = gcd(L, R). Sparse table gives G. The positions of each value are a sorted list; binary search how many sit in [L, R]. If that count is zero, nobody equals G and everyone dies except... wait: ants equal to G survive. Answer is (R-L+1) - count(G in [L,R]).

Hint for CF 475D — how many ranges have gcd g

From a fixed right endpoint, as the left end moves left the gcd jumps down a divisor chain at most log A times. A sparse table plus binary search finds, for each jump, the farthest left where the gcd stays the same. Accumulate counts per gcd value. Queries are then map lookups.
