Module 06 · Range Query Structures

Disjoint Set Union

Maintain a forest of rooted trees, one per component, so that union and find are almost O(1) after path compression and union by rank.

Easy 22 min read Prerequisites: Complexity Analysis, DFS & Connected Components DSU union-find components P0

Why this exists

Picture a room of computers that starts with no cables plugged in at all. Cables get added one at a time, and in between installations somebody keeps asking: can machine 3 currently reach machine 7? You can answer any single question with a depth-first search, following wires from 3 until you either arrive at 7 or run out of cable to follow. That is perfectly correct, but it costs a fresh walk over the whole network every time you are asked. With a hundred thousand cables and a hundred thousand questions you are looking at something like ten billion steps, and the judge will cut you off long before you finish.

The structure on this page removes the repeated walking by never touching the wires again. Every group of machines that can already reach each other elects one member as its representative, and every other member of the group stores a pointer to somebody nearer that representative. Those pointers form a tree for each group, and the whole collection of trees is called a forest — hence the name disjoint-set union, usually shortened to union-find. The question "can 3 reach 7?" now becomes "do 3 and 7 climb to the same representative?", which you answer by following pointers upwards from each of them and comparing where you land.

Left completely alone, that idea can still be slow. If every merge happens to hang a tall tree underneath a short one, the pointers can end up forming a single chain of length n, and climbing that chain is exactly as slow as the search you were trying to avoid. Two small habits prevent it. Union by size always hangs the smaller group underneath the larger one, so a group can only get taller when it merges with something at least as big as itself. Path compression re-points every node you touched on the way up to aim straight at the representative, so the next question about any of them finishes in one hop.

In a real problem statement the signal is the phrase "edges are added" (never removed) sitting next to limits such as n, q ≤ 2×10⁵. That combination rules out re-running a search per query, and it is exactly what union-find is for. The same twenty lines then cover a surprisingly wide spread of problems: rejecting the one cable that closes a loop, merging duplicate user accounts that share an email address, checking a batch of a == b and a != b claims for a contradiction, and Kruskal's minimum spanning tree, which is this structure plus a sort and nothing else.

Two elements belong to the same group exactly when they climb to the same representative, so find answers every question you will be asked and union only ever re-points one representative at another. Keep the trees short by hanging the smaller group underneath, flatten whatever you just walked over, and both operations end up costing about as much as a handful of array reads.

Recognise this pattern

Say yes when you see

  • Edges arrive one by one; after each, ask whether two nodes are connected
  • "Redundant connection", "number of connected components after adding edges"
  • Equality / inequality constraints (union equals, reject conflicting unequals)
  • Merging sets of names / emails / accounts
  • Kruskal's MST: add the next lightest edge if it does not form a cycle

Not this pattern when

  • The graph is given all at once and never changes → DFS / BFS components
  • Edges are deleted, or you need connectivity at many historical times without rollback → link-cut, or offline divide-and-conquer on a DSU with rollback
  • Shortest paths, not just connectivity → Dijkstra / BFS
  • Directed reachability → DSU is undirected; use SCC / topo

If the statement ever deletes an edge, this structure on its own is the wrong tool; and if you drop either of the two accelerations, a deliberately constructed chain pushes a single find back up to O(n).

Core idea and the invariant

You need two arrays. parent[x] holds the element that x currently points at, and it starts out as x itself, which is how you say "every element begins alone in a group that it represents". size[x] is only meaningful when x is a representative, where it counts how many elements that group contains, and it starts at 1. The operation find(x) is the climb: while parent[x] is not equal to x, move up to parent[x]. The element where the loop stops is the one pointing at itself, and that element is the representative of the group containing x.

union(a, b) starts by calling find on both arguments, because you must never re-point an ordinary member — only a representative. If the two roots come back equal, a and b were already in one group, the edge you were handed is redundant, and you report that without changing anything. If the roots differ, compare their sizes and make sure ra is the larger of the two, swapping the two variables if it is not. Then write parent[rb] = ra and add size[rb] into size[ra]. One group has absorbed the other with a single pointer write.

Path compression is the second habit and it costs one extra line. While climbing inside find, once you know the representative r, set the parent of every node you passed to r directly. The usual recursive spelling does this implicitly, because parent[x] = find(parent[x]) assigns the final answer on the way back out of the recursion. The trees therefore get flatter every time you query them, which is why the cost is quoted as α(n), the inverse Ackermann function. You never need that function's definition: it stays below 5 for any n a computer can hold, so treat each operation as constant and say so out loud.

Walk five elements through the whole thing. Everything points at itself, so there are five groups. union(0, 1) finds roots 0 and 1, the sizes tie, so 1 is hung under 0 and size[0] becomes 2. union(2, 3) does the same on the other side. Now union(1, 2) climbs from 1 up to root 0 and from 2 up to root 2, sees sizes 2 and 2, and hangs root 2 underneath root 0, so size[0] is 4. Finally asking find(3) climbs 3 to 2 to 0 and, thanks to compression, leaves both 3 and 2 pointing straight at 0.

Two elements are in the same component exactly when the climb from each one ends at the same place:

connected(x, y) ⇔ find(x) = find(y)

In plain words, the pointer you store is never a claim about the original graph — it is not "my neighbour", it is only "one step towards whoever currently speaks for my group". That is precisely why re-pointing a representative during union, or shortening a path during find, cannot change any answer: both of them shuffle pointers around inside a single group without ever moving an element from one group into another.

Interview sentence: "I hang roots, not arbitrary nodes, and I flatten paths on the way up."

Union the roots, not the original nodes

parent[a] = b without find breaks the tree if a or b is not a root: you can detach a whole subtree from its component. Always a = find(a); b = find(b); parent[a] = b.

Iterative find avoids deep recursion

A pathological chain (union without rank, then find the bottom) is depth n before compression. Recursive find can overflow the Java stack once. Two-pass iterative find (walk to root, walk again to flatten) is stack-safe.

Algorithm

  1. Initialise the two arrays. Set parent[i] = i and rank[i] = 0 (or size[i] = 1) for every element, which declares n separate groups of one member each, every member representing itself. Keep a counter comps = n if the problem asks how many groups survive.
  2. find(x): climb to the representative. Follow parent upwards until you reach the element that points at itself. Every membership question in the problem reduces to this one walk, so this is the operation worth making fast.
  3. Compress the path while you climb. Once the representative r is known, re-point every node you visited so it aims directly at r; the recursive line parent[x] = find(parent[x]) does it for free on the way back out. Future queries on those nodes now take one hop.
  4. union(a, b): resolve both ends first. Compute a = find(a) and b = find(b) before touching anything. If the two are equal then these elements already share a group, the edge closes a cycle, and you return false having changed nothing.
  5. Hang the smaller tree under the larger. If rank[a] < rank[b] swap the two roots so a is the taller one, then write parent[b] = a, and increment rank[a] only when the two ranks were equal. Merging the small side into the big side is what keeps every tree short.
  6. Answer the queries from the roots. connected(a, b) is simply find(a) == find(b), and the number of groups falls by exactly one on every union that returned true, so decrement comps at that point and nowhere else.
  7. Never write parent[a] = b without calling find. Hanging a non-representative under something else detaches whatever was below it, silently splitting a group in half. Every pointer write in this structure targets a root.
  8. Prefer an iterative find when n reaches 10⁵. If you ever skip union by rank, a chain of depth n can appear and a recursive climb overflows the Java stack; walking to the root and then walking the path a second time to flatten it is stack-safe.

Java implementation

Rebuild the graph and DFS after every edge. Correct, O(n) per query.

JavaBruteComponents.java
import java.util.ArrayList;
    import java.util.List;
    
    public class BruteComponents {
    
        static boolean dfs(List<Integer>[] g, boolean[] seen, int u, int t) {
            if (u == t) return true;
            seen[u] = true;
            for (int v : g[u]) if (!seen[v] && dfs(g, seen, v, t)) return true;
            return false;
        }
    
        @SuppressWarnings("unchecked")
        public static void main(String[] args) {
            int n = 5;
            List<Integer>[] g = new ArrayList[n];
            for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
            int[][] edges = {{0, 1}, {1, 2}, {3, 4}, {2, 3}};
            for (int[] e : edges) {
                g[e[0]].add(e[1]);
                g[e[1]].add(e[0]);
            }
            System.out.println(dfs(g, new boolean[n], 1, 4));
            System.out.println(dfs(g, new boolean[n], 0, 3));
        }
        // Input : n=5 edges 0-1, 1-2, 3-4, 2-3
        // Output: true
        //         true
    }

Path compression plus union by rank. The dry-run unions, then a redundant edge.

JavaDisjointSet.java
public class DisjointSet {
    
        final int[] parent, rank;
        int comps;
    
        DisjointSet(int n) {
            parent = new int[n];
            rank = new int[n];
            comps = n;
            for (int i = 0; i < n; i++) parent[i] = i;
        }
    
        int find(int x) {
            if (parent[x] != x) parent[x] = find(parent[x]);
            return parent[x];
        }
    
        boolean union(int a, int b) {
            a = find(a);
            b = find(b);
            if (a == b) return false;
            if (rank[a] < rank[b]) { int t = a; a = b; b = t; }
            parent[b] = a;
            if (rank[a] == rank[b]) rank[a]++;
            comps--;
            return true;
        }
    
        public static void main(String[] args) {
            DisjointSet d = new DisjointSet(5);
            System.out.println(d.union(0, 1));
            System.out.println(d.union(1, 2));
            System.out.println(d.union(3, 4));
            System.out.println(d.union(2, 3));
            System.out.println(d.union(1, 4));
            System.out.println(d.comps);
            System.out.println(d.find(4) == d.find(1));
        }
        // Input : n=5, unions 0-1, 1-2, 3-4, 2-3, then 1-4
        // Output: true
        //         true
        //         true
        //         true
        //         false
        //         1
        //         true
    }

Union by size (also stores component sizes) and a tiny Kruskal on a 4-edge graph. MST weight is the sum of edges that union returned true on.

JavaDsuKruskal.java
import java.util.Arrays;
    
    public class DsuKruskal {
    
        static class Dsu {
            int[] p, sz;
            Dsu(int n) {
                p = new int[n];
                sz = new int[n];
                for (int i = 0; i < n; i++) { p[i] = i; sz[i] = 1; }
            }
            int find(int x) { return p[x] == x ? x : (p[x] = find(p[x])); }
            boolean union(int a, int b) {
                a = find(a);
                b = find(b);
                if (a == b) return false;
                if (sz[a] < sz[b]) { int t = a; a = b; b = t; }
                p[b] = a;
                sz[a] += sz[b];
                return true;
            }
        }
    
        public static void main(String[] args) {
            int n = 4;
            int[][] edges = {{0, 1, 1}, {1, 2, 2}, {0, 2, 4}, {2, 3, 3}};
            Arrays.sort(edges, (x, y) -> Integer.compare(x[2], y[2]));
            Dsu d = new Dsu(n);
            int weight = 0, used = 0;
            for (int[] e : edges) {
                if (d.union(e[0], e[1])) {
                    weight += e[2];
                    used++;
                }
            }
            System.out.println(weight);
            System.out.println(used);
        }
        // Input : 4 nodes, edges (0,1,1), (1,2,2), (0,2,4), (2,3,3)
        // Output: 6
        //         3
    }

Complexity

Time Almost O(1) per find/union (inverse Ackermann) Space O(n)

Take the two accelerations one at a time. Union by rank guarantees that a tree only gets taller when it merges with another tree of the same height, which means a tree of height h must contain at least 2ⁿ elements, and therefore h ≤ log₂ n. That alone caps one find at roughly 20 pointer steps when n = 10⁶. Path compression on its own, without any ranking, is also enough for an amortised O(log n).

Used together the amortised cost per operation drops to α(n), the inverse Ackermann function, which is at most 4 for every n that could physically be stored:

T(q) = Θ(q · α(n)) ≈ Θ(q)

Putting real numbers in: q = 2×10⁵ operations land near 10⁶ array reads, which is a few milliseconds. Skip both accelerations and a chain makes each find cost Θ(n), so the same input becomes Θ(n q), about 4×10⁵⁰ steps. Inside Kruskal the sort at O(m log m) dominates and the O(m α(n)) union-find work is effectively free.

Edge cases and pitfalls

  • Linking the original nodes instead of the roots
    parent[a] = b when a is already a child. The subtree of a is detached from its old root and the structure is no longer a forest of valid components.
    Always resolve both ends first with a = find(a); b = find(b); and only then write a parent. To test it, union a chain of three and check that the element in the middle still reaches the same root.
  • Skipping union by rank and path compression
    A sequence of unions that always hangs the old root under a new singleton builds a linked list. The next find is O(n) and q of them TLE.
    Keep both accelerations every single time: rank or size to decide which root gets hung, plus compression inside find. To test it, union i with i+1 for a hundred thousand values in ascending order and time a find on the last element.
  • Path compression on a DSU you need to roll back
    Compression rewrites parent[] along the whole path, so you cannot undo a union by popping one parent assignment. Offline "delete edge" tricks break.
    Rollback DSU: union by rank only (no compression), push (node, oldParent) on a stack, pop to undo. Finds are O(log n).
  • 1-based nodes in a 0-based array
    n nodes labelled 1..n stored in parent[0..n-1], or parent[n] missing, so node n throws. Mixing both conventions in find vs union.
    Allocate n+1 and ignore index 0, or remap labels to 0..n-1 at the input boundary.
  • Using DSU on a directed graph
    "Can I reach t from s" is not "are they in the same undirected component". Union-find will happily merge both directions of an edge you only had one way.
    Remember that this structure only ever models undirected connectivity. Directed reachability needs a DFS, strongly connected components or 2-SAT instead, so re-read the statement for the word "directed" before reaching for union-find.

Interview follow-ups

Why is the bound inverse Ackermann, not just O(1)?

Path compression without rank is already almost linear; rank without compression is O(log n). The combination is one of the most analysed bounds in algorithms, and it is not quite O(1). In every contest and interview you may treat it as O(1). Do not write α(n) on a whiteboard unless asked; say "effectively constant".

How do you handle weighted edges / MST?

Kruskal: sort edges by weight, then union each if the endpoints have different roots. The unions that return true are the MST edges; their weights sum to the MST cost. If you need the MST as a graph, store those edges. Prim is the heap-based alternative and does not use DSU.

Can DSU do deletions?

Not online with path compression. Offline: time-split the interval an edge is alive and add it in a segment tree of edges, then DFS the segment tree with a rollback DSU (DSU on tree). Online deletions need link-cut trees or Euler-tour trees. Interviews almost never go there; they ask incremental unions.

How does LC 128 (longest consecutive sequence) use DSU?

It does not have to: a HashSet plus a scan of runs is the intended O(n) solution. A DSU version unions each value with value+1 when both exist, then the answer is the maximum component size. Same complexity, more code, a useful way to see "consecutive" as "an edge of weight 1".

Hint for LC 990 — two passes

First union every a == b equation. Then, for every a != b, if find(a) == find(b) the system is unsatisfiable. Doing unequals first, or interleaving, can reject a legal system because the equal- classes are not yet merged. Letters are 26 nodes; the DSU is tiny.

Hint for LC 721 — union on the email, not the name

Names are not unique. Build a map email → first account index that used it. For each later account that repeats an email, union the two account indices. Then group emails by find(account). Sort each group, prefix the name from any account in the component. The DSU lives on accounts, not on email strings.

Recap

  • find returns the root; path compression flattens the walk.
  • union hangs one root under the other by rank or size.
  • union returning false means the edge was redundant (a cycle).
  • Effectively O(1) per op with both accelerations.
  • Undirected and incremental. Deletions need rollback; directed needs a different tool.
