Module 06 · Range Query Structures

Segment Tree

A binary tree over the array: each node is an associative combine of a dyadic segment, so point updates and range queries are O(log n) for any combine, not just sums.

Medium 24 min read Prerequisites: Fenwick Tree, Sparse Table & RMQ segment tree range query associative P1

Why this exists

A Fenwick tree is perfect for prefix sums and a sparse table is perfect for static idempotent queries. Everything else — range minimum with updates, range gcd, range merge of two sorted lists, "number of brackets sequences in a segment" — needs a node that can store an arbitrary associative value. That node layout is a segment tree.

The array is the leaves. Each internal node stores op(left, right) of a contiguous segment whose length is a power of two in the heap layout (or an arbitrary split in the recursive layout). A point update walks the O(log n) ancestors of a leaf. A range query is covered by O(log n) canonical nodes, never more than two per level.

Once you can write build / update / query for a sum, swapping the combine for min, gcd, or a struct (CF 380C's bracket pair) is a one-line change. Lazy propagation, the next page, is what you add when the update is also a range.

Any associative op gets O(log n) point update and range query. The query touches O(log n) canonical nodes that exactly partition the range.

Recognise this pattern

Say yes when you see

  • Point update + range query for min, max, gcd, or a custom struct
  • The operation is associative but not invertible (so Fenwick prefixes do not work)
  • You need both the combine and the ability to update, ruling out a sparse table
  • Merge-sort tree / number of values in [L,R] that are ≤ x (offline or with a Fenwick in each node)
  • n, q ≤ 2×10⁵ and the interviewer said "segment tree"

Not this pattern when

  • Static range min → sparse table is simpler and O(1)
  • Point update + range sum → Fenwick is shorter
  • Range update + range query → lazy propagation
  • No updates, range sum → prefix array

Constraint tell: n, q ≤ 2×10⁵. Allocate 4n nodes for the recursive tree (or 2n for the iterative one). Recursion depth is log n, safe. Combine must be associative; it need not be commutative or invertible.

Core idea and the invariant

Recursive layout: node p covers [l, r]. If l == r it holds a[l]. Otherwise m = l + (r - l) / 2, the left child p<<1 covers [l, m], the right child p<<1|1 covers [m+1, r], and t[p] = op(t[left], t[right]). Build is a postorder fill. A point update at i walks to the leaf and recomputes on the way up.

A query [ql, qr] at node [l, r] has three cases: no overlap (return identity), complete cover (return t[p]), partial overlap (recurse both children and combine). The identity is 0 for sum, +∞ for min, 0 for XOR, 0 for gcd. Completely covered nodes are the canonical partition; there are O(log n) of them.

Iterative layout packs the tree into t[n..2n) as leaves and parents at i>>1. It is faster and has no recursion, but the recursive form is what you want in an interview because the overlap cases are explicit and lazy tags later hang on the same nodes.

Every node stores the combine of its segment. A query returns the combine of O(log n) canonical nodes that partition [ql, qr]:

t[p] = op(a[l], a[l+1], …, a[r])

Interview sentence: "I recurse until a node is either disjoint or fully inside; the fully-inside nodes are the answer."

Identity of the op

The no-overlap return value must be the identity: combining it with anything does nothing. Sum/XOR: 0. Min: Integer.MAX_VALUE. Gcd: 0 (because gcd(x, 0) = x). Getting this wrong poisons every query that does not cover a whole child.

Allocate 4n, not 2n, for the recursive tree

A complete binary tree on n leaves has 2n nodes, but the recursive heap-indexing with uneven splits can index up to about 4n. new long[4 * n] (or n<<2) is the standard allocation. Iterative trees use 2n.

Algorithm

  1. Allocate t[4n] and pick the identity of the op (0 for sum).
  2. Build(p, l, r): leaf copies a[l]; otherwise split at m = l + (r-l)/2, build children, t[p] = t[p<<1] + t[p<<1|1].
  3. Update(p, l, r, i, v): if leaf, store v. Else recurse into the child that contains i, then recompute t[p].
  4. Query(p, l, r, ql, qr): disjoint → identity; fully inside → t[p]; else combine the two recursive calls.
  5. Never add t[p] on a partial overlap. That would include indices outside the query.
  6. Use long for sums. Use m = l + (r - l) / 2, never (l+r)/2 on large indices.
  7. Swap the combine (and the identity) to get min, gcd, XOR, or a struct.

Java implementation

Point set is O(1), range scan is O(n). The tree makes both O(log n).

JavaBrutePointRange.java
public class BrutePointRange {
    
        static int[] a;
    
        static void set(int i, int v) { a[i] = v; }
    
        static long rangeSum(int l, int r) {
            long s = 0;
            for (int i = l; i <= r; i++) s += a[i];
            return s;
        }
    
        public static void main(String[] args) {
            a = new int[] {3, 1, 4, 1, 5, 9, 2, 6};
            System.out.println(rangeSum(2, 6));
            set(3, 3);
            System.out.println(rangeSum(2, 6));
            System.out.println(rangeSum(0, 7));
        }
        // Input : [3,1,4,1,5,9,2,6], then a[3]=3
        // Output: 21
        //         23
        //         33
    }

JavaSegmentTree.java
public class SegmentTree {
    
        final int n;
        final long[] t;
    
        SegmentTree(int[] a) {
            n = a.length;
            t = new long[Math.max(4, n * 4)];
            build(1, 0, n - 1, a);
        }
    
        void build(int p, int l, int r, int[] a) {
            if (l == r) { t[p] = a[l]; return; }
            int m = l + (r - l) / 2;
            build(p << 1, l, m, a);
            build(p << 1 | 1, m + 1, r, a);
            t[p] = t[p << 1] + t[p << 1 | 1];
        }
    
        void set(int p, int l, int r, int i, long v) {
            if (l == r) { t[p] = v; return; }
            int m = l + (r - l) / 2;
            if (i <= m) set(p << 1, l, m, i, v);
            else set(p << 1 | 1, m + 1, r, i, v);
            t[p] = t[p << 1] + t[p << 1 | 1];
        }
    
        long query(int p, int l, int r, int ql, int qr) {
            if (qr < l || r < ql) return 0;              // identity
            if (ql <= l && r <= qr) return t[p];         // canonical node
            int m = l + (r - l) / 2;
            return query(p << 1, l, m, ql, qr)
                 + query(p << 1 | 1, m + 1, r, ql, qr);
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
            SegmentTree st = new SegmentTree(a);
            System.out.println(st.query(1, 0, st.n - 1, 2, 6));
            st.set(1, 0, st.n - 1, 3, 3);
            System.out.println(st.query(1, 0, st.n - 1, 2, 6));
            System.out.println(st.query(1, 0, st.n - 1, 0, 7));
        }
        // Input : [3,1,4,1,5,9,2,6], then a[3]=3
        // Output: 21
        //         23
        //         33
    }

JavaSegmentTreeMin.java
public class SegmentTreeMin {
    
        final int n;
        final int[] t;
    
        SegmentTreeMin(int[] a) {
            n = a.length;
            t = new int[Math.max(4, n * 4)];
            build(1, 0, n - 1, a);
        }
    
        void build(int p, int l, int r, int[] a) {
            if (l == r) { t[p] = a[l]; return; }
            int m = l + (r - l) / 2;
            build(p << 1, l, m, a);
            build(p << 1 | 1, m + 1, r, a);
            t[p] = Math.min(t[p << 1], t[p << 1 | 1]);
        }
    
        void set(int p, int l, int r, int i, int v) {
            if (l == r) { t[p] = v; return; }
            int m = l + (r - l) / 2;
            if (i <= m) set(p << 1, l, m, i, v);
            else set(p << 1 | 1, m + 1, r, i, v);
            t[p] = Math.min(t[p << 1], t[p << 1 | 1]);
        }
    
        int query(int p, int l, int r, int ql, int qr) {
            if (qr < l || r < ql) return Integer.MAX_VALUE;
            if (ql <= l && r <= qr) return t[p];
            int m = l + (r - l) / 2;
            return Math.min(query(p << 1, l, m, ql, qr),
                            query(p << 1 | 1, m + 1, r, ql, qr));
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9, 2, 6};
            SegmentTreeMin st = new SegmentTreeMin(a);
            System.out.println(st.query(1, 0, st.n - 1, 2, 6));
            st.set(1, 0, st.n - 1, 6, 0);
            System.out.println(st.query(1, 0, st.n - 1, 2, 6));
            System.out.println(st.query(1, 0, st.n - 1, 0, 7));
        }
        // Input : [3,1,4,1,5,9,2,6], then a[6]=0
        // Output: 1
        //         0
        //         0
    }

Complexity

Time O(n) build, O(log n) per update or query Space O(n)

Build visits each of the O(n) nodes once. Update and query each descend one path (or two, for a query that splits) of length O(log n), and a query adds O(1) work per visited node:

Tbuild = Θ(n),   Top = O(log n)

At each of the log n levels a query takes at most two canonical nodes, which is why the cover size is O(log n) and not O(n). A Fenwick tree is the same bound with a smaller constant, but only for prefix-invertible ops. A sparse table is O(1) query with no updates.

Edge cases and pitfalls

  • Adding t[p] on a partial overlap
    Missing the complete-cover check and always combining children, or worse, returning t[p] whenever the node overlaps at all. The second includes indices outside [ql, qr].
    Three-way branch: disjoint / complete / partial. Only complete returns t[p].
  • Wrong identity
    Range min returns 0 for a disjoint child. Any query that does not cover both children is then capped at 0, which looks like a plausible minimum.
    Min identity is MAX_VALUE (or a sentinel bigger than any array value). Sum/XOR identity is 0. Gcd identity is 0.
  • Allocating 2n for the recursive heap
    Indices run past 2n on non-power-of-two n (the right spine goes to about 4n). Silent corruption or AIOOB.
    new long[n * 4]. Iterative trees may use 2n.
  • (l + r) / 2 overflow
    On large index ranges (coordinate-compressed to 10⁹ in a dynamic tree) l+r overflows int and the split goes negative.
    int m = l + (r - l) / 2; everywhere, including lazy.
  • Updating t[p] before the recursive call returns
    Recompute from children that still hold the old value. The new leaf is written but ancestors stay stale, and later queries on large ranges miss the update.
    Recurse first, then t[p] = op(t[left], t[right]).

Interview follow-ups

How many canonical nodes does a query use?

At most two per level, so ≤ 2 log n. Proof: once a level has a partial node, the next step either takes a complete child (canonical) or continues into one partial child; you cannot keep two partials on the same path for long. This is why query is O(log n), not O(n).

Can the combine be non-commutative?

Yes, as long as it is associative. Always combine left child then right child in that order. Matrix products on a path, or string concatenation, work. Do not swap children.

What is a merge-sort tree?

Each node stores the sorted list of its segment (merge of the two children). A query [ql, qr] binary-searches "how many values ≤ x" in each canonical node's list, totalling O(log² n). Build is O(n log n) memory and time. Fractional cascading removes one log; a Fenwick of Fenwicks or a wavelet tree are the usual contest substitutes.

When is the iterative form worth it?

When you are tight on time in a contest and the tree is not lazy. In an interview the recursive form is clearer, and it is the one you will extend with lazy tags on the next page. Learn recursive first.

Hint for CF 380C — what a node stores

A segment of brackets is not a single integer. Store three numbers: how many matched pairs sit entirely inside, how many unmatched '(' remain, how many unmatched ')' remain. Merging left and right: new matches = left.matches + right.matches + min(left.open, right.close); leftover opens and closes follow. The answer for a query is 2 * matches of that canonical combine. Associative, not commutative in an interesting way, and a poster-child struct node.

Hint for CF 339D — the op depends on depth

n is a power of two. Leaves are the array. Odd-height parents OR their children, even-height parents XOR (or the other way around, matching the statement). A point update recomputes ancestors, switching the op at each level. The root is the answer after each update. Implementation is a segment tree whose combine is not uniform; pass a boolean down, or key off the node's range length.

Recap

  • Three-way branch: disjoint (identity), complete (return t[p]), partial (recurse).
  • O(log n) canonical nodes partition any query range.
  • Allocate 4n for the recursive heap. Mid is l + (r-l)/2.
  • Any associative op works; pick the identity carefully.
  • Range updates need lazy tags, the next page.
