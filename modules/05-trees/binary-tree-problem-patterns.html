Binary Tree Problem Patterns

Diameter, path sum, LCA of two nodes, serialise, and construct-from-orders are all a postorder combine or a preorder emit with a payload attached to the walk you already own.

Medium 28 min read Prerequisites: Binary Tree Basics & Traversals binary tree diameter path sum P0

Why this exists

You are given a binary tree of 100000 nodes and asked for the longest path anywhere in it, counted in edges. The obvious method picks every pair of leaves, walks up to their meeting point, and keeps the best length. A tree that is a straight chain of 100000 nodes has about 5×10⁹ pairs, and even a bushier tree still makes you pay for a fresh walk per pair. The judge will cut you off long before you finish. The same explosion shows up as "maximum path sum", "lowest common ancestor of two nodes", and "does this path add to k": they all look like a new puzzle and they are all the same walk you already own.

What changes is the payload you carry, not the chase of left and right. A postorder walk — handle both children, then the node — lets each node see a small summary of its two subtrees and decide what to send upward. Diameter needs two heights. Maximum path sum needs two gains, each of which may be dropped if it is negative. Lowest common ancestor, usually shortened to LCA, needs a pair of "did I see p?" / "did I see q?" answers. If you instead collect every root-to-leaf path into a global list and scan it afterwards, you have thrown away the fact that the interesting combination happens at one node.

A few questions emit on the way down instead: serialise writes a node before diving, and constructing a tree from preorder plus inorder consumes the next preorder value as the current root. Those are still the same walk with the recording line moved. In a real statement the tell is a single tree handed as a root pointer, n up to 10⁵, and a question about a path, a diameter, an ancestor, or a rebuild from two orders — not "answer this for every possible root" and not "the tree is a BST".

Name the struct a node returns after both children finish, plus one global best for combinations that go through that node. Almost every hard binary-tree question is that postorder plus a decision about what to send upward.

Constraint tell: n ≤ 10⁵ with a single root pointer is the everyday interview limit, and one postorder that does constant work per node finishes comfortably. Values may be negative, which is why maximum path sum cannot blindly add a child. Recursion depth equals the height; if the statement does not promise a balanced tree, a chain of 100000 nodes will overflow the JVM stack, though interviews rarely demand the iterative rewrite for diameter the way they do for the raw walks.

Core idea and the invariant

Diameter is the longest path anywhere, counted in edges. Write a helper height(u) that returns the height of the subtree in nodes (a null child returns 0, a leaf returns 1). After both recursive calls you have hL and hR. The path that goes through u has hL + hR edges, so update a global ans with that sum. What you return upward is only one side, 1 + max(hL, hR), because a parent can extend just one downward spine. Returning hL + hR as height double-counts and the parent then invents paths that do not exist.

Maximum path sum is the same shape with money instead of edges. A child's gain — the best sum of a downward path starting at that child — is dropped when it is negative, written max(0, gain), because you are allowed to stop. The through-me candidate is val + gainL + gainR and competes for a global best. What you return upward is val + max(gainL, gainR), one downward arm only. LCA uses a different payload: the recursive call returns null if the subtree contains neither target, returns the node itself if it is p or q, and if both sides come back non-null the current node is the answer. Path-sum III is prefix sums on the unique path from the root, with a hashmap of leftover prefixes, the same idea as subarray-sum-k.

Take the sample tree: root 1 with children 2 and 3, and 2 owning 4 and 5. Leaves 4, 5 and 3 each have height 1. At node 2 both heights are 1, so the through-me path 4-2-5 has 2 edges and ans becomes 2; the height returned upward is 2. At the root the heights are 2 and 1, the through-me path 4-2-1-3 has 3 edges, and that is the diameter. LCA of 4 and 3 sees a non-null left and a non-null right at node 1 and stops there. If the values were instead -10 / 9 20 / 15 7, the same walk with gains would keep 15+20+7 = 42 as the global best and drop the -10 arm when sending a number upward.

After both children return, you know every summary of the two subtrees. The only new paths are those that go through the current node, so a global ans is updated with that through-me combination and a one-sided summary is sent to the parent:

ans = max(ans, combine(left, me, right)); return a one-sided summary

In plain words, a child can tell you the best downward spine it owns, but only you can glue the two spines into a path that bends at you, so that glued number lives in ans and never travels upward as if it were a height.

Interview sentence: "I return a summary from postorder and keep through-me in a global."

Algorithm

  1. Name the struct before you type. Decide what a node must return upward — a height, a gain, or a pair of "found p / found q" — because that choice is the whole algorithm.
  2. Walk postorder: children first. Recurse left, recurse right, then combine, so both summaries exist before you invent a through-me candidate or update a global ans.
  3. Diameter stores the bend separately. Write ans = max(ans, hL + hR) and return only 1 + max(hL, hR), with null as 0, so a parent extends one spine rather than a already-bent path.
  4. Maximum path sum drops a losing child. A negative gain cannot help a path that is allowed to stop, so take max(0, gain) both when sending one arm up and when scoring val + gL + gR.
  5. LCA returns the first node that sees both targets. If both recursive calls are non-null this node is the meeting point; otherwise propagate the non-null side, which also covers the case where one target sits under the other.
  6. Construct consumes preorder and splits inorder. The next preorder value is the current root, and a map of inorder indices tells you the left and right ranges in O(1) so the rebuild stays linear.

Java implementation

JavaAllLeafPaths.java
public class AllLeafPaths {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static int diam = 0;
        static int height(Node n) {
            if (n == null) return 0;
            int L = height(n.left), R = height(n.right);
            diam = Math.max(diam, L + R);
            return 1 + Math.max(L, R);
        }
        public static void main(String[] args) {
            Node r = new Node(1);
            r.left = new Node(2); r.right = new Node(3);
            r.left.left = new Node(4); r.left.right = new Node(5);
            diam = 0;
            height(r);
            System.out.println(diam);
        }
        // Input : sample tree
        // Output: 3
    }
JavaDiameterLca.java
public class DiameterLca {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static int ans;
        static int height(Node n) {
            if (n == null) return 0;
            int L = height(n.left), R = height(n.right);
            ans = Math.max(ans, L + R);
            return 1 + Math.max(L, R);
        }
        static Node lca(Node n, Node p, Node q) {
            if (n == null || n == p || n == q) return n;
            Node L = lca(n.left, p, q), R = lca(n.right, p, q);
            if (L != null && R != null) return n;
            return L != null ? L : R;
        }
        public static void main(String[] args) {
            Node r = new Node(1);
            r.left = new Node(2); r.right = new Node(3);
            r.left.left = new Node(4); r.left.right = new Node(5);
            ans = 0;
            height(r);
            System.out.println(ans);
            System.out.println(lca(r, r.left.left, r.right).val);
        }
        // Input : sample, LCA of 4 and 3
        // Output: 3
        //         1
    }
JavaMaxPathSum.java
public class MaxPathSum {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static int best;
        static int gain(Node n) {
            if (n == null) return 0;
            int L = Math.max(0, gain(n.left));
            int R = Math.max(0, gain(n.right));
            best = Math.max(best, n.val + L + R);
            return n.val + Math.max(L, R);
        }
        public static void main(String[] args) {
            Node r = new Node(-10);
            r.left = new Node(9);
            r.right = new Node(20);
            r.right.left = new Node(15);
            r.right.right = new Node(7);
            best = Integer.MIN_VALUE / 4;
            gain(r);
            System.out.println(best);
        }
        // Input : LC 124 sample
        // Output: 42
    }

Complexity

Time O(n) Space O(h)

One postorder visits each of the n nodes once and does a constant amount of arithmetic around the two child calls, so diameter, maximum path sum and LCA are all Θ(n). Building a tree from preorder and inorder is also O(n) if you map values to inorder indices up front; scanning indexOf at every node turns the same idea into O(n²) and dies at n = 10⁵.

T = Θ(n)

Path-sum III with a hashmap is still expected linear time if you increment a prefix count on the way down and decrement it on the way up, so a sibling cannot see a prefix it does not own. At n = 10⁵ the whole family is a couple of milliseconds. The naive all-pairs walk is about 10⁶ path checks and will not finish.

Edge cases and pitfalls

  • Returning the through-me path as height
    Writing return hL + hR looks right because that number is the diameter contribution, and the sample still prints a plausible answer, but the parent then treats a bent path as a single spine and invents edges that do not exist.
    Return 1 + max(hL, hR) and store hL + hR only in the global ans. Check that a parent of a three-node V does not report a path longer than 2.
  • Max path sum without dropping negatives
    Adding a child whose gain is -5 looks consistent with "use both children", yet the parent would have a better path by standing alone, so the global best comes out too small.
    Wrap every child gain in max(0, gain) both upward and through-me. A node with two negative children must be allowed to answer with just its own value.
  • LCA comparing values instead of references
    Comparing n.val == p.val looks fine when every value is unique, then a duplicate or a different instance of the same number makes you return the wrong meeting point.
    Compare node identity, or a unique id, unless the statement promises unique values. Test two nodes that share a value and sit in different subtrees.
  • Construct without a map, O(n^2)
    Calling indexOf on the inorder array at every node looks like the obvious split and works on the tiny sample, then becomes quadratic once both arrays have 100000 entries.
    Build a HashMap from value to inorder index once, and pass shrinking lo/hi bounds. Time a rebuild at a few thousand nodes if you are unsure.
  • Path sum III double-counting with a global map not backtracked
    Leaving a prefix in the map after you leave a subtree looks harmless because the numbers are still "on some path", but a later sibling then counts a prefix it does not share and the answer is too large.
    Increment the prefix count on the way down and decrement it on the way back up. A two-branch tree with the same running sum on both arms is the test.

Interview follow-ups

Diameter in nodes vs edges?

LC 543 asks for edges, so a single node answers 0. If your helper counts height in nodes (a leaf returns 1), the through-me edge count is still hL + hR, because each side's node-count equals the number of edges on that spine. If you prefer edge-height, a null returns -1 and a leaf returns 0, and through-me is hL + hR + 2. Pick one convention, write it in a comment, and match the statement on a one-node tree.

LCA when one node is ancestor of the other?

The first time the walk hits p (or q), it returns that node immediately. The other target sits somewhere below, so the opposite child returns null and you propagate p upward. That is the correct LCA: the first common ancestor is p itself. A sample where 2 is an ancestor of 4 is the check.

Why max(0, gain) in LC 124?

A path is allowed to stop at the current node, and it must contain at least that node. A child whose best downward sum is negative cannot improve any path that is allowed to refuse it, so you replace that gain with 0. The through-me score val + gL + gR can still use both children when both help, and the value you send to the parent uses only the better arm.

Subtree of another tree?

Either serialise both trees with explicit nulls and ask whether B's string sits inside A's, or for each node of A run a simultaneous "same tree" walk against B. The naive version is O(n m). Hashing the serialisations, or comparing hashes of subtrees, brings it back to linear in the two sizes. The simultaneous walk is the one to write in an interview unless they ask for the hash.
