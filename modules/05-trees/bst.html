Binary Search Trees

Left < node < right on every subtree: inorder is sorted, k-th smallest is an inorder walk, and validate is a range (lo, hi) passed down, not a local comparison.

Easy 28 min read Prerequisites: Binary Tree Basics & Traversals, Binary Search Basics BST inorder validate P0

Why this exists

You are handed a binary tree of a few thousand nodes and asked whether it is a binary search tree. The tempting check looks at each node and asks only whether the left child is smaller and the right child is larger. That test accepts a tree whose root is 4, whose left child is 2, and whose right child of 2 is 6: locally 2 < 6, yet 6 sits in the left half of 4 and the whole tree is illegal. Almost every BST bug is that same mistake written a different way: a local compare that is not the real rule.

A binary search tree, usually shortened to BST, is a binary tree plus one range rule: every key in the left subtree is smaller than the node, and every key in the right subtree is larger, not just the two children. Because of that rule, an inorder walk emits keys in sorted order, so "k-th smallest" is "walk inorder and stop at k", and two-sum on a BST is two iterators walking that sorted sequence, not the hash set you needed on an unordered tree. Delete is the one structural edit people fumble: a node with two children is replaced by its inorder successor, the next key to the right.

This page is the interview BST: validate, search, insert, delete, k-th, LCA using the values, and convert a sorted array into a balanced tree. Java's TreeMap is a later, self-balancing structure and is not required here. In a statement the tell is the phrase "binary search tree" next to limits like n ≤ 10⁴ in interviews or n ≤ 10⁵ in contests, and a question that uses the ordered invariant rather than a general path or diameter.

Validate by passing a range down from the ancestors, not by comparing a node to its two children. Inorder of a BST is strictly increasing when keys are unique, and k-th smallest is that same walk stopping early.

Core idea and the invariant

Validate by passing a live range. The helper is ok(node, lo, hi), and the sentinels must be long (or boxed Integer bounds) because Integer.MIN_VALUE is a legal key. Fail as soon as val ≤ lo or val ≥ hi. The left child inherits (lo, val) and the right child inherits (val, hi), which is how a grandchild is still checked against every ancestor. The inorder alternative keeps a prev pointer and fails if the current value is not strictly larger; that is the same rule written as a sorted scan.

Search and insert are binary search on the tree: go left when the key is smaller, right otherwise, and a null slot is where a new node hangs. Delete has three shapes. No children: drop the node. One child: replace it with that child. Two children: copy the value of the inorder successor — the leftmost node of the right subtree, which has no left child — then delete that successor. LCA walks from the root and steps left while both keys are smaller, right while both are larger, and stops at the first node that sits between them.

Walk the sample 4 / 2 5 / 1 3. The root 4 is checked against (-∞, +∞). Node 2 must sit in (-∞, 4), node 1 in (-∞, 2), node 3 in (2, 4), and node 5 in (4, +∞); all pass, and inorder emits 1, 2, 3, 4, 5. Replace 3 with 6 and the local check at 2 still sees 2 < 6, but the range (2, 4) rejects 6 at once. Inserting 0 walks 4 to 2 to 1 and hangs a left child. Deleting 2 copies 3 into 2's slot and then removes the old 3, which had no left child.

For every node, every key in its left subtree is strictly less than node.val and every key in its right subtree is strictly greater (unique keys). That is equivalent to a range inherited from the ancestors:

lo < node.val < hi

In plain words, a node is legal only when it sits inside the open interval its ancestors carved out; checking the two children is not enough, because a grandchild can break an ancestor the parent never looks at.

Interview sentence: "I pass (lo, hi) down; a local left-right check is not the invariant."

Algorithm

  1. Validate with a shrinking range. Recurse as ok(n, lo, hi) and fail unless lo < n.val < hi, then send (lo, val) left and (val, hi) right so every ancestor still constrains the grandchildren.
  2. Or walk inorder and keep the previous key. Fail as soon as n.val ≤ prev, because a legal BST with unique keys must emit a strictly increasing sequence.
  3. Search and insert are binary search. Compare the key to the current node and step left or right; a null child is the hole where a new node belongs, which is why insert is O(h) and not a rebuild.
  4. Delete a two-child node via its successor. The successor is the minimum of the right subtree, it has no left child, so you can copy its value and then delete that easier node instead of splicing two live children.
  5. k-th smallest is inorder that stops. Count visits until you hit k, or store subtree sizes on each node if later queries must stay O(h) after inserts.
  6. LCA walks from the root using values. Step left while both keys are smaller, right while both are larger, and stop at the first node that sits between them, because that is where the two search paths split.

Java implementation

JavaBstLocalCheck.java
public class BstLocalCheck {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static boolean local(Node n) {
            if (n == null) return true;
            if (n.left != null && n.left.val >= n.val) return false;
            if (n.right != null && n.right.val <= n.val) return false;
            return local(n.left) && local(n.right);
        }
        public static void main(String[] args) {
            Node r = new Node(4);
            r.left = new Node(2); r.right = new Node(5);
            r.left.left = new Node(1); r.left.right = new Node(6);
            System.out.println(local(r));
        }
        // Input : invalid BST (6 in left of 4) that local-check misses
        // Output: true
    }
JavaValidateBst.java
public class ValidateBst {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static boolean ok(Node n, long lo, long hi) {
            if (n == null) return true;
            if (n.val <= lo || n.val >= hi) return false;
            return ok(n.left, lo, n.val) && ok(n.right, n.val, hi);
        }
        static int kth(Node n, int[] k) {
            if (n == null) return -1;
            int L = kth(n.left, k);
            if (k[0] == 0) return L;
            if (--k[0] == 0) return n.val;
            return kth(n.right, k);
        }
        public static void main(String[] args) {
            Node r = new Node(4);
            r.left = new Node(2); r.right = new Node(5);
            r.left.left = new Node(1); r.left.right = new Node(3);
            System.out.println(ok(r, Long.MIN_VALUE, Long.MAX_VALUE));
            System.out.println(kth(r, new int[]{3}));
        }
        // Input : BST 4 / 2 5 / 1 3 , k=3
        // Output: true
        //         3
    }
JavaLcaBst.java
public class LcaBst {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static Node lca(Node n, int p, int q) {
            while (n != null) {
                if (p < n.val && q < n.val) n = n.left;
                else if (p > n.val && q > n.val) n = n.right;
                else return n;
            }
            return null;
        }
        public static void main(String[] args) {
            Node r = new Node(6);
            r.left = new Node(2); r.right = new Node(8);
            r.left.left = new Node(0); r.left.right = new Node(4);
            System.out.println(lca(r, 2, 8).val);
            System.out.println(lca(r, 2, 4).val);
        }
        // Input : LC 235 sample
        // Output: 6
        //         2
    }

Complexity

Time O(h) search/insert/delete/LCA; O(n) validate / k-th naive Space O(h)

Search, insert, delete and BST-LCA each walk one root-to-node path, so they cost O(h). On a balanced tree h is about log n, roughly 17 steps at n = 10⁵. On a skew tree the same operations become a linked-list scan of n steps. Validate must look at every node, so it is always Θ(n) no matter how balanced the tree is.

T_search = O(h), T_validate = Θ(n)

Naive k-th smallest is an inorder walk that stops at k, which is O(h + k) and in the worst case O(n). If the follow-up is many k-th queries mixed with inserts, store a subtree size on each node and the same question becomes one more O(h) descent. TreeMap hides a red-black tree and quotes O(log n) for all of this; a hand-rolled BST does not.

Edge cases and pitfalls

  • Local left < me < right only
    A 6 sitting as the right child of 2, under a root of 4, passes every parent-child compare, so the function returns true on an illegal tree and the sample of a valid BST never exposes it.
    Pass (lo, hi) from the ancestors, and use long sentinels so Integer.MIN_VALUE is still a legal key. The 4 / 2 / 6 counterexample is the test.
  • int overflow sentinels
    Starting with lo = Integer.MIN_VALUE looks like "no lower bound", then a root whose value is also MIN_VALUE fails lo < val, or you switch to ≤ and silently accept a duplicate that the statement forbade.
    Use long lo, hi with Long.MIN_VALUE / Long.MAX_VALUE, or pass boxed bounds that can be null. A one-node tree holding Integer.MIN_VALUE is the check.
  • Delete successor incorrectly
    Deleting the successor from the original parent, or treating it as if it might have a left child, looks like a local pointer fix and then either loses the right subtree or leaves a second copy of the key.
    Set successor = min(right), copy s.val into the node, then node.right = delete(node.right, s.val). The successor of a two-child node never has a left child.
  • Duplicates
    Using ≤ on both sides, or a validate that demands a strict < both ways, looks consistent and then either builds a broken tree or rejects a legal policy the statement actually allowed.
    Pick one side for equals, usually the right, and make insert, search and validate all agree. A two-node tree with equal keys is the test.
  • k-th by converting to an array always
    Dumping inorder into a list is correct for one query and looks like the obvious answer, then the follow-up of many k-th questions mixed with inserts rebuilds the list each time and becomes linear per query.
    Store subtree sizes, or keep a persistent inorder iterator. Time a few thousand mixed operations if the follow-up appears.

Interview follow-ups

Why long bounds?

The node stores an int, so both Integer.MIN_VALUE and Integer.MAX_VALUE are legal keys. If you pass those same values as the initial lo and hi with int arithmetic, a root equal to MIN_VALUE fails the lower-bound test. long sentinels sit strictly outside the int range, so every legal key falls inside the first call.

Is every inorder-sorted tree a BST?

For unique keys, yes: the BST range rule is equivalent to inorder being strictly increasing. That does not tell you how to build the tree. An increasing inorder sequence can be laid out as a linked list or as a balanced tree; taking the midpoint of the remaining slice as the root is what gives height about log n.

Delete complexity?

You walk O(h) to find the node, another O(h) to find its successor if it has two children, and O(h) to splice that successor out. All of that is still O(h). Repeated Hibbard deletions slowly unbalance a tree; interviews ignore that and never ask you to rebalance by hand.

LCA in BST vs general tree?

On a BST you walk from the root comparing values, using no extra memory beyond a few pointers, because the split point is decided by the keys. On a general binary tree the keys tell you nothing, so you use the postorder both-sides walk from the previous page, or binary lifting when there are many queries on a static tree.
