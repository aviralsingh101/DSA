Binary Tree Basics & Traversals

A binary tree is a recursive pair of subtrees. Every classic walk — preorder, inorder, postorder, level order — is the same recursion with the visit moved.

Easy 22 min read Prerequisites: Recursion Fundamentals, Complexity Analysis binary tree DFS BFS traversal P0

Why this exists

Imagine a comment thread stored the way a database would store it. Each comment is one record holding its text plus two references: one to the reply displayed above it and one to the reply displayed below it, where a reference of null means there is nothing on that side. You are handed exactly one thing, a reference to the top comment, and asked to print all 100000 comments. There is no array to loop over and no index to increment, so the only way to reach comment number 57000 is to follow references down from the top. Everything on this page is about how to follow them so that every record is reached exactly once and in an order you can reason about.

Now change the task to "how many replies sit underneath each comment". The obvious method answers one comment at a time: stand on it, walk everything reachable below it, count what you saw, then move to the next comment and start again. That is correct and it is also quadratic, because a record sitting 40 levels deep gets counted once for each of its 40 ancestors. If the thread happens to be a straight chain of 100000 comments, the total work is 1 + 2 + ... + 100000, roughly 5×10⁹ reference hops — minutes of computation. One walk that visits each record once and hands its count back up to its parent finishes the same job in 100000 hops.

That single walk is the whole subject, so here is the vocabulary for it. A node is one record; its two references are its left child and right child; a node with no children at all is a leaf; the subtree of a node is that node together with everything reachable below it; the topmost node, the one you were handed, is the root; the depth of a node is how many steps separate it from the root; and the height of the tree is the largest depth in it. The walk has exactly one shape — deal with the left subtree, deal with the right subtree — and the only decision left is when you record the node's own value: before both recursive calls (preorder), between them (inorder), or after them (postorder).

In a problem statement the tell is that the input is described as a root pointer, or as a flat array with null holes, rather than as a list of edges — and that the limit reads something like n ≤ 10⁵ with no promise that the tree is balanced. The missing promise is the part that bites. A binary tree is legally allowed to be a straight chain, and a recursive walk down a chain of 100000 nodes keeps 100000 Java stack frames alive at once, while the default JVM stack runs out after a few thousand. That is why every walk here also gets an iterative spelling that keeps the pending nodes in an ArrayDeque on the heap instead.

There is only one traversal in this entire module and it is "handle the left subtree, handle the right subtree"; preorder, inorder and postorder are that same walk with the single line that records node.val moved before, between, or after the two recursive calls. Level order is the same visiting rule with the recursion's hidden stack swapped for an explicit queue, and that swap is the only thing separating depth-first from breadth-first.

Recognise this pattern

Say yes when you see

  • Return the preorder / inorder / postorder / level-order list of values
  • Height, depth, number of nodes, or is this a leaf / full / complete tree
  • A problem that is "do something at every node, using answers from children"
  • Reconstruct a tree from two of the three DFS orders
  • Iterative traversal is requested, or n is large enough that recursion may overflow

Not this pattern when

  • The input is a general graph with cycles → BFS/DFS on graphs, not a tree walk
  • You need ancestor queries or path aggregates on a static tree → LCA or Euler tour
  • The tree is a BST and the question uses the search-tree invariant → BST page
  • You are counting strings or XOR pairs → trie / XOR trie

Constraint tell: n ≤ 10⁵, with the tree handed to you as a root reference and no sentence promising it is balanced, is the everyday case, and it is comfortable for a walk that touches each node once. The trap here is memory rather than time: a chain-shaped tree of 100000 nodes needs 100000 nested calls, and the default JVM stack holds only a few thousand frames, so what you get is a StackOverflowError rather than a wrong answer. Prefer the iterative form whenever balance is not promised.

Core idea and the invariant

Fix the data first. A Node holds an int val plus two references left and right, either of which may be null to mean "no child on that side". The recursion has exactly one job: given a reference n, deal with the whole subtree rooted at n. Its first line is the base case if (n == null) return;, because an absent child is a subtree containing nothing and there is nothing to do for it. After that it calls itself on n.left, calls itself on n.right, and somewhere around those two calls it appends n.val to the output list out.

Where you put out.add(n.val) is the entire difference between the three depth-first orders. Put it before both calls and a node is recorded the first time you arrive at it, which is preorder. Put it between them and a node is recorded only after its whole left subtree has finished, which is inorder. Put it after both and a node is recorded only once everything below it is done, which is postorder. Quantities that depend on the children have no choice and must be postorder: height(n) returns 1 + Math.max(height(n.left), height(n.right)), and the size of a subtree is 1 + szL + szR. Neither of those two numbers exists until both recursive calls have returned, so the combine has to happen last.

Level order asks a different question — list every node at depth 0, then every node at depth 1, and so on — and recursion cannot answer it directly because recursion dives. Instead keep an explicit ArrayDeque<Node> q of nodes waiting to be handled. Take a node off the front, append its value, and push its non-null children onto the back; because a child always enters behind everything already waiting, the queue stays sorted by depth for free. To see where one depth ends, read int sz = q.size() at the top of each round and poll exactly that many nodes: those sz nodes are precisely the current level, since nothing enqueued during the round can share their depth.

Run the sample tree to see all four at once: root 1 with children 2 and 3, and 2 owning children 4 and 5. Preorder writes 1 on arrival, dives left and writes 2, dives left again and writes 4 whose two calls both return immediately, comes back up to 2 and writes 5, then unwinds to 1 and writes 3: [1,2,4,5,3]. The identical walk with the recording line between the two calls emits [4,2,5,1,3], and after both calls it emits [4,5,2,3,1]. The queue version pulls 1, then 2,3, then 4,5, giving [[1],[2,3],[4,5]].

Every node is entered exactly once and left exactly once, so all four walks do Θ(n) work; the only thing that differs between them is the moment at which node.val is recorded:

pre = visit, L, R  |  in = L, visit, R  |  post = L, R, visit

In plain words, the recursion chases exactly the same references in exactly the same physical order no matter which of the three orders you asked for; the output lists differ only because you chose a different instant to append. You can confirm that yourself on any tree by writing all three add lines into one function and watching a single walk fill three different lists.

Interview sentence: "I walk every node once; the order is just where I put the visit."

Algorithm

  1. Represent the node. Store val, left and right, and treat a missing child as null, because that is the only signal the walk has that a branch has ended.
  2. Write the recursive walk first. Return immediately on null, then place out.add(n.val) before, between, or after the two recursive calls so the same chase of references produces preorder, inorder or postorder.
  3. Iterative preorder uses a stack. Start with the root, pop a node, record it, then push right before left so the left child is handled next, matching the recursive dive.
  4. Iterative inorder walks left first. Push every node while stepping cur = cur.left, then pop, record, and move to that node's right child, because inorder must finish the left subtree before the node itself.
  5. Level order uses a queue and a size snapshot. Read sz = q.size() at the start of each round and poll exactly that many nodes so children enqueued during the round cannot leak into the current depth.
  6. Combine children after both calls return. Height and subtree size do not exist until the two recursive results are known, and if the tree can be a chain of 10⁵ nodes, prefer the iterative spelling so the JVM stack is not the limit.

Java implementation

JavaHeightOnly.java
public class HeightOnly {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static int height(Node n) {
            if (n == null) return 0;
            return 1 + Math.max(height(n.left), height(n.right));
        }
        public static void main(String[] args) {
            Node r = new Node(1);
            r.left = new Node(2); r.right = new Node(3);
            r.left.left = new Node(4); r.left.right = new Node(5);
            System.out.println(height(r));
        }
        // Input : tree 1 / 2 3 / 4 5
        // Output: 3
    }
JavaTreeTraversals.java
import java.util.ArrayList;
    import java.util.List;
    
    public class TreeTraversals {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static void preorder(Node n, List<Integer> out) {
            if (n == null) return;
            out.add(n.val);
            preorder(n.left, out);
            preorder(n.right, out);
        }
        static void inorder(Node n, List<Integer> out) {
            if (n == null) return;
            inorder(n.left, out);
            out.add(n.val);
            inorder(n.right, out);
        }
        static void postorder(Node n, List<Integer> out) {
            if (n == null) return;
            postorder(n.left, out);
            postorder(n.right, out);
            out.add(n.val);
        }
        public static void main(String[] args) {
            Node r = new Node(1);
            r.left = new Node(2); r.right = new Node(3);
            r.left.left = new Node(4); r.left.right = new Node(5);
            List<Integer> pre = new ArrayList<>(), in = new ArrayList<>(), post = new ArrayList<>();
            preorder(r, pre); inorder(r, in); postorder(r, post);
            System.out.println(pre);
            System.out.println(in);
            System.out.println(post);
        }
        // Input : tree 1 / 2 3 / 4 5
        // Output: [1, 2, 4, 5, 3]
        //         [4, 2, 5, 1, 3]
        //         [4, 5, 2, 3, 1]
    }
JavaLevelOrder.java
import java.util.ArrayDeque;
    import java.util.ArrayList;
    import java.util.List;
    
    public class LevelOrder {
        static class Node {
            int val; Node left, right;
            Node(int v) { val = v; }
        }
        static List<List<Integer>> levelOrder(Node root) {
            List<List<Integer>> out = new ArrayList<>();
            if (root == null) return out;
            ArrayDeque<Node> q = new ArrayDeque<>();
            q.add(root);
            while (!q.isEmpty()) {
                int sz = q.size();
                List<Integer> row = new ArrayList<>();
                for (int i = 0; i < sz; i++) {
                    Node u = q.poll();
                    row.add(u.val);
                    if (u.left != null) q.add(u.left);
                    if (u.right != null) q.add(u.right);
                }
                out.add(row);
            }
            return out;
        }
        public static void main(String[] args) {
            Node r = new Node(1);
            r.left = new Node(2); r.right = new Node(3);
            r.left.left = new Node(4); r.left.right = new Node(5);
            System.out.println(levelOrder(r));
        }
        // Input : tree 1 / 2 3 / 4 5
        // Output: [[1], [2, 3], [4, 5]]
    }

Complexity

Time O(n) Space O(h) recursion / stack, O(w) for BFS

Every walk enters each of the n nodes once and leaves it once. The recursive spelling does a constant amount of work around the two child calls, so the recurrence is T(n) = T(n_L) + T(n_R) + Θ(1), which unfolds to Θ(n). The iterative stack and the BFS queue each push and pop a node a constant number of times, so they are the same linear pass written with an explicit collection.

T(n) = T(n_L) + T(n_R) + Θ(1) = Θ(n)

At n = 10⁵ that is 100000 visits, a few milliseconds. Extra memory is the height h for DFS (a right spine uses n frames) or the width w for BFS (a complete last level holds about n/2 nodes). The time is never the problem; the stack is, which is why the iterative forms exist.

Edge cases and pitfalls

  • Using java.util.Stack
    java.util.Stack looks like the named tool for DFS, so it compiles and even produces the right list on the sample, but it is a synchronised Vector with the wrong method names and a real cost per push.
    Use ArrayDeque: push/pop/peek for DFS and add/poll for BFS. Test both walks on a three-node tree.
  • Forgetting the null base case
    Skipping if (n == null) return looks fine on a perfectly full tree where every child exists, then a missing child throws a NullPointerException the first time you read n.val.
    Make the null check the first line, or return the identity of the combine (0 for size, -1 for edge-height). Test a root with only a left child.
  • Height off-by-one (nodes vs edges)
    Returning 1 for a single node matches LC 104 (height in nodes) and is wrong for LC 543, which counts edges, so the same helper silently fails the other problem.
    Write the convention in a comment. For edge-height, a null child returns -1 so a leaf returns 0. Check a one-node tree against the statement.
  • Level-order without snapshotting queue size
    Polling until the queue is empty still lists every node, so a flat walk looks correct, but children of the current depth leak into the same list and grouped levels come out wrong.
    Capture int sz = q.size() and poll exactly that many times. Test that a three-level tree returns three inner lists, not one.
  • Recursive walk on a linked-list-shaped tree
    A right spine of n = 10⁵ is a legal binary tree, so the recursive walk is correct in theory and then dies with StackOverflowError after a few thousand frames.
    Keep an iterative version on the heap whenever the statement does not promise a balanced tree. A chain of a few thousand nodes is the test.

Interview follow-ups

How do you reconstruct from preorder and inorder?

The first preorder value is the root, because preorder records a node on arrival. Find that value in the inorder list: everything to its left belongs to the left subtree and everything to its right belongs to the right. A map from value to inorder index makes each split O(1), so the whole rebuild is O(n). Preorder plus postorder is ambiguous unless every node has zero or two children, because a single-child node can sit on either side.

Why is inorder of a BST sorted?

A BST promises that every key in the left subtree is smaller than the node and every key in the right subtree is larger. Inorder is exactly "whole left, then the node, then whole right", so the values come out in increasing order. That fact is load-bearing on the BST page; here it is just a reason to remember where the visit sits.

O(1) extra space with parent pointers?

From the current node you can walk to its parent and ask whether you arrived from the left child or the right. That is the same three-colour state machine as iterative postorder, stored in the current position instead of on a stack. You still visit every node a constant number of times; you just stopped allocating the deque.

What changes for an n-ary tree?

Depth-first becomes "record the node, then loop its children" instead of two named recursive calls, and there is no unique inorder because there is no unique place between "the left" and "the right". Level order barely changes: enqueue every child instead of two. Height is still one plus the maximum child height.

Recap

  • One DFS, three visit placements give preorder, inorder, postorder.
  • Level order is BFS with sz = q.size().
  • Height and size are postorder combines with a null identity of 0.
  • Iterative forms are required on skew trees.
  • ArrayDeque, never java.util.Stack.
