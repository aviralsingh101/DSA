Trie

A tree of prefixes: each edge is a character, insert/search/startsWith are O(|s|), and the same walk powers word-search II and autocomplete.

Medium 28 min read Prerequisites: Binary Tree Basics & Traversals trie prefix tree P0

Why this exists

You are given 100000 words and asked, after each insertion, whether any stored word starts with a given prefix. A HashSet answers exact equality in time proportional to the query string, which is fine, and then a prefix question forces you to scan every word. A hundred thousand words of length 20 is two million character compares per prefix query; a few thousand of those queries will not finish. You need a structure that shares the common start of app, ape and apple so the prefix ap is one walk, not a scan.

A trie, also called a prefix tree, is that structure. Each edge is one character, and the path from the root to a node spells the prefix that node represents. Words that share a start share the same path, so the whole dictionary occupies memory proportional to the total number of characters, not to the number of prefixes written out as strings. Insert, exact search and starts-with are each one walk of length equal to the query. LC 208 is that API. Word Search II walks the board and the trie in lockstep and prunes when the next cell has no child; autocomplete and replace-words are the same walk with a different payload on a terminal node.

The implementation choice is next[26] versus a HashMap of children. Interviews want the array for lowercase English. A count on each node, how many inserted words pass through it, is what lets you delete without pulling the rug from under a sibling. In a statement the tell is "starts with", "prefix", "dictionary of words", or a board search over many patterns, with total characters around 10⁵. Maximum XOR of numbers is the next page, a 2-child trie on bits, not this 26-way tree.

A trie node is the set of stored strings that share one prefix. The child labelled c is that prefix extended by c, and a terminal flag (or a count) marks the prefix that is itself a complete word.

Constraint tell: Total characters around 10⁵ is the everyday limit, and a next[26] array per node is acceptable memory. Alphabet size multiplies that memory, so a huge alphabet wants a map of children instead. Word Search II is a 4-way board DFS of depth up to 10, pruned by the trie; without the prune it is 4L and will time out on a 12-by-12 board even when the dictionary is tiny.

Core idea and the invariant

A node holds Node[] next = new Node[26], a boolean term, and optionally an integer cnt of words that pass through it. Insert starts at the root and, for each character ch, computes i = ch - 'a'. If next[i] is null it allocates a fresh node, then steps into it and increments cnt. After the last character it sets term = true. Search is the same walk and returns false on a missing child; if the walk finishes it returns term, not true. Starts-with is the same walk and returns true as soon as the walk finishes, whether or not that node is terminal. Mixing those two return values is the classic LC 208 bug.

Word Search II builds a trie of the word list first. The board DFS carries a trie pointer alongside the cell: if the next letter has no child, that branch is dead and you return. Landing on a terminal node emits the word and, to avoid duplicates, you can clear term or delete a now-empty leaf. The cell itself must be marked (commonly with '#') and restored after the four recursive calls, or a word can reuse the same square and invent a loop. Autocomplete is simpler: walk the prefix, then explore the small subtree under that node.

Insert app then ape. The first word creates the path a → p → p and marks the last p terminal. The second reuses a → p and creates a sibling e, also terminal. Search ape walks three edges and finds term true. Search ap lands on the shared p, where term is still false unless you also inserted ap. Starts-with ap does that same walk and returns true because the node exists. Search apple dies when the next letter l has no child. Two words, five nodes, one shared prefix of length 2.

The path from the root to a node spells a prefix of at least one inserted word. term (or an end-count) is true exactly when that prefix is itself a complete word:

search(s) = walk(s) lands on a node with term = true

In plain words, sharing a prefix means sharing a path, and "is this a word" is a flag on the last node, not the mere fact that the path exists.

Interview sentence: "I walk one edge per character; search needs term, startsWith only needs the node."

Algorithm

  1. Give each node a 26-slot array, a term flag, and an optional count. The array is the alphabet; the flag is what distinguishes a finished word from a mere prefix, which is why both fields exist.
  2. Insert by creating a child only when it is missing. Step one character at a time, increment cnt if you will later delete, and set term on the last node so a later exact search has something to read.
  3. Exact search returns the term flag, not the existence of the path. A missing child is false; a finished walk still asks term, or search("ap") after inserting apple comes back true by mistake.
  4. Starts-with is the same walk without the flag. If every edge existed, the prefix is in the dictionary, which is the whole point of sharing paths.
  5. Board search carries a trie pointer next to the cell. A missing child prunes that 4-way branch; a terminal node emits a word; the cell is marked and restored so one word cannot reuse the same square.
  6. Do not store the whole string on every node. Reconstruct it from the walk, or hang one String on terminal nodes only, because copying lists per insert is linear in the dictionary size.

JavaTrie.java
public class Trie {
        static class Node {
            Node[] next = new Node[26];
            boolean term;
        }
        final Node root = new Node();
    
        void insert(String w) {
            Node cur = root;
            for (int i = 0; i < w.length(); i++) {
                int c = w.charAt(i) - 'a';
                if (cur.next[c] == null) cur.next[c] = new Node();
                cur = cur.next[c];
            }
            cur.term = true;
        }
        boolean walk(String w, boolean needTerm) {
            Node cur = root;
            for (int i = 0; i < w.length(); i++) {
                int c = w.charAt(i) - 'a';
                if (cur.next[c] == null) return false;
                cur = cur.next[c];
            }
            return needTerm ? cur.term : true;
        }
        public static void main(String[] args) {
            Trie t = new Trie();
            t.insert("app");
            t.insert("ape");
            System.out.println(t.walk("ape", true));
            System.out.println(t.walk("ap", true) + " " + t.walk("ap", false));
        }
        // Input : insert app, ape; search ape, search ap, startsWith ap
        // Output: true
        //         false true
    }
JavaReplaceWords.java
public class ReplaceWords {
        static class Node {
            Node[] next = new Node[26];
            String word;
        }
        static String replace(String[] dict, String sentence) {
            Node root = new Node();
            for (String w : dict) {
                Node cur = root;
                for (int i = 0; i < w.length(); i++) {
                    int c = w.charAt(i) - 'a';
                    if (cur.next[c] == null) cur.next[c] = new Node();
                    cur = cur.next[c];
                }
                cur.word = w;
            }
            StringBuilder sb = new StringBuilder();
            for (String tok : sentence.split(" ")) {
                Node cur = root;
                String use = tok;
                for (int i = 0; i < tok.length(); i++) {
                    int c = tok.charAt(i) - 'a';
                    if (cur.next[c] == null) break;
                    cur = cur.next[c];
                    if (cur.word != null) { use = cur.word; break; }
                }
                if (sb.length() > 0) sb.append(' ');
                sb.append(use);
            }
            return sb.toString();
        }
        public static void main(String[] args) {
            System.out.println(replace(new String[]{"cat", "bat", "rat"}, "the cattle was rattled by the battery"));
        }
        // Input : LC 648 sample
        // Output: the cat was rat by the bat
    }

Complexity

Time O(L) per insert/search/startsWith Space O(total characters * σ) worst, typically O(total chars)

Each character of each word creates at most one new node, and a shared prefix creates none. Insert, search and starts-with therefore walk exactly |s| edges. Memory is proportional to the total number of characters (times 26 pointers in the array implementation). A dictionary of 100000 words of length 10 is about a million nodes in the worst case, comfortable.

T(insert) = O(|s|), S = O(Σ |s_i|)

A HashSet of the words is also O(|s|) for exact search, but a prefix query scans every word and becomes O(n |s|): two million compares per query at the usual limit. The trie makes that prefix O(|s|). Word Search II is a 4-way DFS whose branches die when the trie has no child, which is what keeps 4L from exploding.

Edge cases and pitfalls

  • Forgetting term vs prefix
    Returning true from search whenever the walk finishes looks like starts-with, so search("ap") after inserting apple is true and LC 208's two methods silently share one implementation.
    Exact search requires term; starts-with does not. Insert only apple and assert both answers, they must differ.
  • Not creating nodes on insert
    Stepping into next[c] without allocating looks fine on a second insert that reuses a prefix, then the first insert of a new letter throws or drops the rest of the word.
    Write if (cur.next[c] == null) cur.next[c] = new Node(); before the step. A first insert of a two-letter word is the test.
  • Word Search II without marking the cell
    Leaving the cell live looks like "the board did not change", then a 4-way DFS re-enters the same square and invents a word that loops through one letter twice.
    Set board[r][c] = '#', recurse, then restore the letter. A 1-by-2 board with word aa is the check.
  • 26 vs 'A'
    Subtracting 'a' from an uppercase letter or from a punctuation mark produces a negative index, so the first non-lowercase input throws and the lowercase sample never saw it.
    Normalise to lowercase, or use a map. Guard that the index sits in 0..25 before you touch next.
  • Storing List<String> on every node
    Copying the list of words that share a prefix into each child looks convenient for autocomplete, then each insert is linear in the dictionary and memory explodes at a few thousand words.
    Keep term plus a reconstruction of the word from the walk, or store one String on terminal nodes only.

Interview follow-ups

Why not a HashMap of all prefixes?

You can: insert every prefix of every word into a HashSet for starts-with, and keep a second set of complete words for search. Memory is worse because every prefix is stored as its own String, and Word Search II still wants a walk that can prune a dead branch in the middle of a word. The trie is the compressed form of that map, with one node per shared character rather than one string per prefix.

Aho-Corasick vs trie DFS on a text?

Aho-Corasick adds failure links so you scan a linear text once and report every pattern that occurs. If the "text" is a 2-D board with 4-way moves, that automaton does not match the shape of the search; board DFS locked to a trie pointer is the right tool (LC 212). If the text really is a string, Aho is linear in the text plus the dictionary plus the number of matches.

Autocomplete top-k?

The subtree under the prefix node holds every candidate. For a small subtree you can DFS it and pick the best k words. If the subtree is large, precompute a small heap of the best words at each node when you insert, so a later query is a read rather than a walk. Either way you start from the node the prefix walk landed on, not from the root.

Unicode?

Use HashMap<Character, Node>, or a byte trie on UTF-8 with 256 slots. Do not allocate next[Character.MAX_VALUE]: that is tens of thousands of unused pointers per node and will exhaust memory on the first handful of words. Interviews stay on lowercase English and the 26-slot array unless the statement names another alphabet.
