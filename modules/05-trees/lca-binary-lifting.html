LCA & Binary Lifting

Precompute the 2^k-th ancestor of every node in O(n log n), then LCA and k-th ancestor queries become O(log n) jumps.

Hard 30 min read Prerequisites: Tree DP & Rerooting, Bit Manipulation LCA binary lifting P1

Why this exists

You are given a static tree of 200000 vertices and 200000 questions of the form "what is the lowest common ancestor of u and v?", or "how far is u from v?", or "what is the k-th node on the path?". The interview LCA on a binary tree is one DFS and dies here: walking parents one step at a time can take 200000 hops per question, and a batch of that size is about 4×10⁶ steps. You need a way to climb many edges in one pointer hop.

That is what the table up[k][v] is for. It holds the ancestor of v that sits exactly 2k steps toward the root: up[0][v] is the parent, up[1][v] is the grandparent, up[2][v] is four steps up, and so on. The reason those particular ancestors are enough is that any climb of d steps has a binary representation, so d is a sum of distinct powers of two. Once every power-of-two ancestor is stored, a climb of d steps is at most twenty pointer hops instead of d of them. You build the table by doubling: the 2k ancestor is the 2k-1 ancestor of the 2k-1 ancestor.

The same jumps answer k-th ancestor and, with a payload stored next to each jump, the max or gcd of the edges you skipped. Euler-tour RMQ is the other LCA and is faster when you only need the meeting node; lifting is the one you reach for when the statement also wants a path aggregate. The tell in a contest is n, q ≤ 2×10⁵ on a static tree, plus distance, k-th, or path-min language.

Any climb of d steps is a sum of distinct powers of two, so up[k][v] stores the ancestor exactly 2k steps up and a query jumps those bits. LCA equalises depth, then lifts both nodes while their 2k parents still differ, then takes the parent.

Constraint tell: n, q ≤ 2×10⁵ is the textbook pair. Take LOG = 18 or 20, because 218 = 262144 already covers the limit. The table is int[LOG][n] (or the swapped layout), about 16 MB of integers at n = 2×10⁵ and 20 rows. The root's parent is -1 or the root itself; whichever you pick, jumping past the root must be defined so up[k][-1] is never read.

Core idea and the invariant

One DFS from the root fills depth[v] and the first row of the table: up[0][v] is the parent of v, the ancestor one step up. That row is the reason the rest of the table exists at all. The doubling loop then sets up[k][v] = up[k-1][up[k-1][v]] for k = 1, 2, …: to jump 2k steps you jump 2k-1 twice. If a midpoint is -1 you keep -1, which is how a short tree stays well-defined. After this preprocess, climbing h steps from a node is a loop over the bits of h: when bit k is set, replace the node by up[k][node].

LCA uses that climb twice. First swap so u is at least as deep as v, then lift u by depth[u] - depth[v] so the two nodes sit at the same depth. If they are now equal, the deeper one was under the shallower and you are done. Otherwise walk k from LOG-1 down to 0 and, whenever up[k][u] still differs from up[k][v], jump both. You must go from the high bit downward: a low-bit jump first can overshoot the meeting point and land on two different ancestors that later cannot resync. When the loop ends the two nodes are the children of the LCA, so the answer is up[0][u]. Distance is then depth[u] + depth[v] - 2×depth[lca].

On the sample tree 0-1-2, 1-3, 0-4 the depths are [0, 1, 2, 2, 1] and up[0] is [-1, 0, 1, 1, 0]. Doubling fills up[1][2] = up[0][1] = 0 and up[1][3] = 0, the grandparents. LCA(2, 3): depths already match and the nodes differ, up[1] of both is 0 so you do not jump 2, up[0] of both is 1 so you do not jump 1 either, and you return that parent 1. LCA(2, 4): lift 2 by one step to 1, 1 is not 4, both parents are 0, return 0. Distance 2 to 4 is 2 + 1 - 0 = 3, the path 2-1-0-4. The 2nd ancestor of 2 is a single jump of bit 1, which lands on 0.

up[k][v] is the ancestor of v sitting exactly 2k steps toward the root (or -1 / the root if the climb runs out). LCA is the deepest node that is an ancestor of both arguments:

lca(u,v) = first common ancestor; dist = d[u]+d[v]-2 d[lca]

In plain words, you never walk one parent at a time: you keep a list of "skip 1, skip 2, skip 4, skip 8, …" pointers so any climb is a handful of those skips, and the meeting node is what is left after the two nodes have been skipped up to just below it.

Interview sentence: "up[k][v] is the 2^k-th parent; I equalise depth, then jump while parents differ."

Algorithm

  1. DFS from the root fills depth and the parent row. Set up[0][v] to the parent (and the root's parent to -1 or itself) because every later jump is defined in terms of that first row.
  2. Double to fill the rest of the table. up[k][v] = up[k-1][up[k-1][v]] with a guard on -1, so a jump of 2k is two jumps of 2k-1 and you never index up[k][-1].
  3. Equalise depth before comparing nodes. Lift the deeper node by the depth gap, using the bits of that gap, so the two arguments sit at the same level and a later joint jump cannot miss the meeting point.
  4. If they coincide after the lift, that node is the LCA. The deeper argument sat inside the shallower one's subtree, and there is nothing left to jump.
  5. Walk bits from high to low and jump while parents differ. A low-bit jump first can overshoot the LCA; the high-to-low order keeps both nodes just below the meeting point.
  6. Return the parent of either node. After the loop they are the two children of the LCA (or the same child twice), so up[0][u] is the answer and distance is the usual depth formula.

Java implementation

JavaLcaWalk.java
import java.util.*;
    public class LcaWalk {
        static int[] p, d;
        static int lca(int u, int v) {
            while (d[u] > d[v]) u = p[u];
            while (d[v] > d[u]) v = p[v];
            while (u != v) { u = p[u]; v = p[v]; }
            return u;
        }
        public static void main(String[] args) {
            p = new int[]{-1, 0, 1, 1, 0};
            d = new int[]{0, 1, 2, 2, 1};
            System.out.println(lca(2, 3) + " " + lca(2, 4));
        }
        // Input : sample parents
        // Output: 1 0
    }
JavaBinaryLifting.java
import java.util.ArrayList;
    import java.util.List;
    
    public class BinaryLifting {
        static final int LOG = 20;
        static int[][] up;
        static int[] depth;
        static List<List<Integer>> g;
    
        static void dfs(int u, int p) {
            up[0][u] = p;
            for (int k = 1; k < LOG; k++) {
                int mid = up[k - 1][u];
                up[k][u] = mid < 0 ? -1 : up[k - 1][mid];
            }
            for (int v : g.get(u)) if (v != p) {
                depth[v] = depth[u] + 1;
                dfs(v, u);
            }
        }
        static int lift(int u, int h) {
            for (int k = 0; k < LOG; k++) if (((h >> k) & 1) == 1) {
                u = up[k][u];
                if (u < 0) return u;
            }
            return u;
        }
        static int lca(int u, int v) {
            if (depth[u] < depth[v]) { int t = u; u = v; v = t; }
            u = lift(u, depth[u] - depth[v]);
            if (u == v) return u;
            for (int k = LOG - 1; k >= 0; k--)
                if (up[k][u] != up[k][v]) { u = up[k][u]; v = up[k][v]; }
            return up[0][u];
        }
        public static void main(String[] args) {
            int n = 5;
            g = new ArrayList<>();
            for (int i = 0; i < n; i++) g.add(new ArrayList<>());
            int[][] e = {{0,1},{1,2},{1,3},{0,4}};
            for (int[] x : e) { g.get(x[0]).add(x[1]); g.get(x[1]).add(x[0]); }
            up = new int[LOG][n];
            depth = new int[n];
            for (int[] row : up) java.util.Arrays.fill(row, -1);
            dfs(0, -1);
            System.out.println(lca(2, 3) + " " + lca(2, 4));
            System.out.println(depth[2] + depth[4] - 2 * depth[lca(2, 4)]);
        }
        // Input : sample tree, queries (2,3) (2,4)
        // Output: 1 0
        //         3
    }

public class KthAncestor {
        static int[][] up;
        static int kth(int u, int k) {
            for (int i = 0; i < 20; i++) if (((k >> i) & 1) == 1) {
                u = up[i][u];
                if (u < 0) return -1;
            }
            return u;
        }
        public static void main(String[] args) {
            up = new int[20][5];
            for (int[] row : up) java.util.Arrays.fill(row, -1);
            up[0][1] = 0; up[0][2] = 1; up[0][3] = 1; up[0][4] = 0;
            for (int k = 1; k < 20; k++)
                for (int v = 0; v < 5; v++)
                    if (up[k - 1][v] >= 0) up[k][v] = up[k - 1][up[k - 1][v]];
            System.out.println(kth(2, 2));
            System.out.println(kth(2, 3));
        }
        // Input : 2's 2nd ancestor and 3rd
        // Output: 0
        //         -1
    }

Complexity

Time O(n log n) build, O(log n) per LCA / k-th ancestor Space O(n log n)

LOG is ceil(log2 n), about 18 at n = 2×10⁵. Filling up[k][v] writes one integer per pair (k, v), so the preprocess is n×LOG assignments, a few million. A query equalises depth with at most LOG jumps and then does at most LOG more, so one LCA is a few dozen pointer reads.

T_build = O(n log n), T_q = O(log n)

A batch of q = 2×10⁵ queries is a few million jumps, comfortable. Walking parents one step at a time on a chain is O(n) per query and about 4×10⁶ steps in the same batch. Euler tour plus a sparse table answers LCA in O(1) after the same n log n preprocess, with heavier constants and no natural hook for a path max; lifting wins when you also need a payload.

Edge cases and pitfalls

  • Lifting past the root without a guard
    Reading up[k][-1], or treating the root's parent as 0 in a 0-based tree, looks like a finished table and then indexes garbage or wraps to a random node on a short climb.
    Store -1 and skip when the midpoint is negative, or set the root's parent to itself so jumps stay put. A query that asks for the 10th ancestor of a depth-2 node is the test.
  • Returning u after the loop instead of up[0][u]
    The high-to-low walk is designed to stop at the children of the LCA, so returning u looks like you finished the loop and then reports a child instead of the meeting node.
    After equalising, if u == v return u; otherwise jump while parents differ and return up[0][u]. LCA(2, 3) on the sample must be 1, not 2.
  • Filling up[k] inside DFS before children set up[k-1]
    A nested k-loop that reads up[k-1][parent] before that parent has been doubled looks like the same recurrence and then writes -1 or a stale parent into later rows.
    Fill every k for the current node after up[0] is set and before recursing to children, or run one global doubling loop after the whole DFS. Either order is safe; mixing them is not.
  • depth not set when lifting
    Skipping the DFS leaves every depth at 0, so the equalise step never lifts and LCA of two distant leaves reports a nonsense meeting point that still type-checks.
    Run one DFS from the statement's true root (often 1, sometimes 0) and set depth[child] = depth[u] + 1. Print the depth array on the sample before any query.
  • 1-based nodes, 0-based table
    Nodes labelled 1..n stored in an array of length n make index n throw, and the same bug looks like an off-by-one only on the last vertex.
    Allocate n+1 and ignore index 0, or remap labels to 0..n-1 at the input boundary and stay consistent in every array.

Interview follow-ups

Why jump from high bits down when equalising is low bits up?

Equalising a known height h uses the bits of h, and any order works because you are jumping an exact distance you already computed. The LCA loop is different: you do not know the remaining distance, you only know whether a trial jump of 2k would land on two different ancestors. A low-bit jump first can overshoot the meeting point and leave the two nodes on different branches that later bits cannot bring back together. High-to-low never steps past the LCA.

Virtual trees?

Sort a subset of important nodes by their DFS enter times, take LCA of each consecutive pair, and stack-build the compressed tree that contains only those nodes and their meeting points. Binary lifting (or Euler+RMQ) supplies those LCAs. The compressed tree has size linear in the subset, which is why DP on a few marked vertices becomes affordable.

Weighted distance?

During the same DFS that fills up[0], store distRoot[v] as the distance from the root to v. Then dist(u, v) = distRoot[u] + distRoot[v] - 2×distRoot[lca]. Sum is invertible, so you do not need a payload on the jumps; max or gcd on the path still does.

LOG = 20 vs 18?

218 = 262144, so n = 2×10⁵ needs 18 rows. 20 is a safe default you can type without thinking. 31 wastes a row per node for no query you will ever make: that is n×31 integers, about 25 MB, for climbs that 20 already cover.
