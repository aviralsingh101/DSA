Binary Search on the Answer

When the answer is a number and the predicate "can I do it with this budget?" is monotone, search the answer itself instead of constructing it.

Medium 24 min read Prerequisites: Binary Search Basics binary search predicate monotonicity P0

Why this exists

A large family of interview problems ask for the minimum maximum or maximum minimum: smallest capacity that can ship all packages in D days, fewest bananas-per-hour so Koko finishes before the guards return, smallest largest sum after splitting an array into k parts. The construction is messy. The check is easy: given a candidate capacity, a single greedy pass tells you whether it works.

If that check is monotone — once a budget is enough, every larger budget is also enough — then the first true budget is the answer, and you already have a firstTrue template for it. The search space is no longer an index range; it is the range of feasible answers, often [1, sum(a)] or [max(a), sum(a)]. At n = 10⁵ and a range of 10⁹, thirty probes of a linear check are about 3×10⁶ operations; scanning every capacity is 10¹⁴ and is dead on arrival.

This is the single highest-leverage binary-search skill after the basic template. Google and Meta ask it constantly because the statement looks like dynamic programming or a greedy construction until you name the predicate. The tell in a real statement is a min-max or max-min sentence sitting next to n ≤ 10⁵ and an answer range up to 10⁹ or 10¹⁴: you cannot try every capacity, but you can afford about thirty linear checks. If you catch yourself designing a DP table whose state is "best split of the first i items into j groups", pause and ask whether a candidate budget has a monotone yes/no check — that one question is usually the whole problem.

Do not search for the construction. Search for the smallest number x such that a greedy/check function feasible(x) returns true. The hard part is proving the check is monotone and writing it correctly; the search is five lines you already know.

Recognise this pattern

Say yes when you see

  • "Minimum possible maximum" / "maximum possible minimum" / "smallest capacity / speed / days"
  • You can check a candidate answer in linear (or n log n) time, but you cannot construct the optimum directly
  • The check is monotone: if x works then x+1 works (or the reverse)
  • Split / allocate / ship / eat / cut with a budget, minimise the budget
  • A real-valued answer with an ε tolerance (square root, min-max distance)

Not this pattern when

  • The check is not monotone → you cannot binary-search the answer; try ternary search, DP, or a heap
  • You need the actual partition, not just the min-max value → still binary-search the value, then reconstruct with the same greedy
  • The search space is an unsorted array of values → that is ordinary binary search or hashing, not this pattern
  • You are counting constructions → DP or combinatorics

Core idea and the invariant

Pick the type of the answer (usually a positive integer). Find a lower bound lo that is always feasible-or-too-small (often max(a) or 0) and an exclusive upper bound hi that is always feasible (often sum(a)+1). Write feasible(x) so that it is false for every x below the optimum and true for every x at or above it. For split-array, that check walks left to right, starts a new part whenever adding the next value would exceed x, and asks whether the number of parts is at most k. The same scan, with hours or days instead of parts, is Koko and the shipping problem.

Then run the half-open firstTrue template you already know: while lo < hi, mid = lo + (hi - lo) / 2, and set hi = mid if feasible(mid) else lo = mid + 1. When the loop ends, lo is the smallest feasible answer. The loop invariant is identical to ordinary binary search: everything below lo is known infeasible, everything at or above hi is known feasible. The only new work is writing and proving the check; the five search lines do not change.

Walk [7, 2, 5, 10, 8] split into two parts. lo starts at max(a) = 10, because one item alone needs at least that much; hi starts at sum + 1 = 33, because one part containing everything always works. feasible(14) needs three parts, so every capacity at or below 14 is discarded. feasible(18) produces the split [7, 2, 5] | [10, 8] and uses exactly two parts, so 18 is feasible and the search collapses onto it. The construction was never built by a clever split; it fell out of the first true capacity.

Say this out loud

"I am binary-searching the answer x. feasible(x) asks whether a budget of x is enough. That predicate is monotone, so the first true x is the optimum. I keep the half-open invariant: [0, lo) infeasible, [hi, ∞) feasible."

In plain words, every value we have rejected is too small, every value we have accepted is big enough, and the answer is the first accepted value.

The only new work is the check

If you cannot write feasible in ten lines, you have not found the right predicate yet. It is almost always a greedy scan: walk left to right, start a new group / day / pile whenever adding the next item would exceed x, and count how many groups you needed.

Bounds must sandwich the answer

If lo starts above the true answer you will never find it. If hi starts below every feasible value the loop returns garbage. Always argue: "the answer is at least max(a) because one item alone needs that much, and at most sum(a) because one group containing everything works."

The decision flowchart

Algorithm

  1. Name the answer type x first — a capacity, a rate, a distance, or a day count — so the search space is a number line, not an array index.
  2. Write feasible(x) as a boolean: true if and only if a budget of x is enough, and prove in one sentence that it is monotone.
  3. Bound the search. lo = smallest conceivable answer (often max(a) or 0). hi = one past a proven-feasible value (often sum(a)+1).
  4. Run firstTrue: while (lo < hi) { mid = lo + (hi-lo)/2; if (feasible(mid)) hi = mid; else lo = mid + 1; }
  5. Return lo. After the loop it is the smallest feasible x, because everything below it failed the check.
  6. If the problem wants the largest feasible x, search the first infeasible and return lo - 1, or invert the predicate.
  7. Reconstruct if asked: walk the same greedy with x = lo and record the cuts, so the partition is recovered in one extra linear pass.

Java implementation

Try every capacity from max(a) to sum(a). Correct, and immediately shows the monotone structure.

JavaSplitArrayBrute.java
public class SplitArrayBrute {
    
        static boolean feasible(int[] a, int k, int cap) {
            int parts = 1, sum = 0;
            for (int v : a) {
                if (v > cap) return false;
                if (sum + v > cap) { parts++; sum = v; }
                else sum += v;
            }
            return parts <= k;
        }
    
        static int splitArray(int[] a, int k) {
            int lo = 0, hi = 1;
            for (int v : a) { lo = Math.max(lo, v); hi += v; }
            for (int cap = lo; cap < hi; cap++) {
                if (feasible(a, k, cap)) return cap;
            }
            return lo;
        }
    
        public static void main(String[] args) {
            System.out.println(splitArray(new int[] {7, 2, 5, 10, 8}, 2));
        }
        // Input : a = [7,2,5,10,8], k = 2
        // Output: 18
    }

            int parts = 1, sum = 0;
            for (int v : a) {

            int lo = 0, hi = 1;                 // hi exclusive
            for (int v : a) { lo = Math.max(lo, v); hi += v; }

                if (feasible(a, k, mid)) hi = mid;
                else lo = mid + 1;
            }
            return lo;
        }

            System.out.println(splitArray(new int[] {7, 2, 5, 10, 8}, 2));
        }
        // Input : a = [7,2,5,10,8], k = 2
        // Output: 18
    }

Parameterise only the predicate and the bounds. Koko, shipping, and split-array are three call sites of this.

JavaBinarySearchAnswer.java
import java.util.function.IntPredicate;
    
    public class BinarySearchAnswer {
    
        /** Smallest x in [lo, hi) such that pred.test(x) is true. pred must be monotone. */
        static int firstTrue(int lo, int hi, IntPredicate pred) {
            while (lo < hi) {
                int mid = lo + (hi - lo) / 2;
                if (pred.test(mid)) hi = mid;
                else lo = mid + 1;
            }
            return lo;
        }
    
        static int koko(int[] piles, int h) {
            int max = 0;
            for (int p : piles) max = Math.max(max, p);
            return firstTrue(1, max + 1, speed -> {
                long hours = 0;
                for (int p : piles) hours += (p + (long) speed - 1) / speed;
                return hours <= h;
            });
        }
    
        public static void main(String[] args) {
            System.out.println(koko(new int[] {3, 6, 7, 11}, 8));
        }
        // Input : piles = [3,6,7,11], h = 8
        // Output: 4
    }

Complexity

Time O(n log RANGE) Space O(1)

Each of the O(log RANGE) probes runs an O(n) scan, so

T = O(n) · log₂(hi − lo) = O(n log RANGE)

RANGE is typically sum(a) ≤ n · max|a[i]|. At n = 10⁵ and max = 10⁹ that is 30 probes, about 3 × 10⁶ additions — fine. The brute linear scan of the answer space is O(n · RANGE) and dies immediately. At n = 10⁵ and RANGE = 10⁹ the binary-search version does about 30 × 10⁵ = 3×10⁶ additions, under ten milliseconds, which is why the constraints are written that way.

Edge cases and pitfalls

  • Off-by-one in the ceiling division
    hours += piles[i] / speed; truncates toward zero, so a pile of 7 at speed 3 is counted as 2 hours instead of the 3 that Koko actually needs.
    hours += (p + (long) speed - 1) / speed;. Cast to long first or p + speed overflows.
  • Starting lo at 0 when 0 is not a legal answer
    Koko with speed = 0 divides by zero, and split-array with cap = 0 is meaningless if items are positive, yet both look like a natural lower bound.
    Lower bound is the tightest necessary value: 1 for a rate, max(a) for a capacity.
  • Using int for the accumulator inside feasible
    int hours on Koko with piles[i] = 1e9 and speed = 1 overflows past 2×10⁹, wraps negative, and the predicate flips from false to true.
    Use long for every running sum or count inside the check, including the hours or parts accumulator.
  • Assuming feasibility is monotone without proving it
    "Minimise the number of groups whose XOR is 0" is not monotone in a useful way. Binary search returns a plausible lie.
    Prove: if x works, x+1 works, in one sentence, before you code. If you cannot, stop.
  • hi not exclusive / not proven feasible
    Initialising hi = sum(a) and using a closed interval, then returning lo after while (lo < hi), can miss the case where sum(a) itself is the answer.
    Half-open: hi = sum + 1, which is always a feasible exclusive bound because a single part equal to the whole array works.
  • Integer vs real search
    Using integer binary search for a real-valued answer (minimise a distance) and stopping when lo == hi — they never meet.
    Loop a fixed 80 times, or while (hi - lo > 1e-7), and return (lo+hi)/2. Never compare doubles with ==.

Interview follow-ups

Prove that feasible is monotone for split-array.

If a split exists with every part ≤ x, the same split has every part ≤ x+1. So the set of feasible capacities is a suffix of the integers, and the first true value is well-defined. That suffix property is exactly the false-then-true shape firstTrue expects, so the search is legal and the smallest true capacity is the min-max sum.

Now return the actual parts, not just the min-max sum.

Run the same greedy with the optimal capacity: start a new part whenever adding the next element would exceed it. Because the capacity is optimal, this uses at most k parts. If you need exactly k, split leftover singleton parts from the right. Either way you reuse the check you already wrote; you do not invent a second construction.

What if k can be as large as n?

Then the answer is max(a): every element is its own part. Your lower bound already handles this; just make sure feasible returns true for cap = max(a) when k ≥ n. At n = 10⁵ this is a single pass to find the max, not a special case in the binary search, and a quick unit test is splitArray(a, n) == max(a).

Can you do it in O(n) expected time?

The decision tree of the search depends on the data, so you cannot skip the log in the comparison model for an arbitrary feasible. In practice the log is 30 and is not worth removing. A heap or a linear-time selection would need a different question, such as "k-th capacity", which this is not.

The answer is a real number and the judge uses 1e-6 absolute error.

Loop 80 times (2^{-80} is far smaller than 1e-6 over any reasonable range) or iterate while hi-lo > 1e-7. Returning (lo+hi)/2 is fine. Do not mix integer mid-rounding with doubles. Eighty iterations cost nothing next to the feasible check, and they remove any worry about the last bit of rounding.

Hint for LC 668 — Kth in the multiplication table

feasible(x) = "at least k entries of the n×m table are ≤ x". For a fixed row i the count is min(m, x/i). Sum over rows in O(n). firstTrue over [1, n*m]. The k-th smallest is the smallest x with count(x) ≥ k.

Hint for CF 1117C — Magic Ship

After t days the wind contributes a known vector W(t) (prefix sums of the weather string, cycling). You can spend t extra moves of length 1. feasible(t) iff manhattan(target - start - W(t)) ≤ t and (t - manhattan) is even. Binary search t.

Recap

  • Search the answer, not the array. The input is only used inside feasible.
  • Monotonicity is the licence to search. If x works, x+1 must work. Prove it.
  • Bounds sandwich the answer: lo is necessary, hi is exclusive and proven feasible.
  • The check is a greedy scan almost every time. If you cannot write it, you have the wrong x.
  • Same four lines as ordinary binary search. Only the predicate changes.
