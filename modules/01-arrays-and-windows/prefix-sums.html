Prefix Sums & Difference Arrays

Trade one linear precomputation for constant-time range queries — the cheapest and most widely applicable optimisation in the whole toolkit.

Easy 24 min read Prerequisites: Complexity Analysis prefix sums difference array 2D hashing P0

Why this exists

You have a year of daily sales in an array and your manager keeps asking questions of one shape: "how much did we sell between day l and day r?" Take a tiny version first, a = [3, 1, 4, 1, 5, 9], and the question "days 2 to 4". The obvious answer is to walk across those three positions adding as you go, 4 + 1 + 5 = 10. That is fine once. Now use realistic sizes: 10⁵ days and 10⁵ questions, each of which may span the whole array. That is up to 10⁵ × 10⁵ = 10¹⁰ additions, ten billion of them, which takes a modern processor well over a minute — and a judge stops you after one or two seconds.

The way out is to answer one harder question in advance instead of many easy ones later. Before any query arrives, build a second array P in which P[i] is the total of the first i entries, so P = [0, 3, 4, 8, 9, 14, 23]. That costs a single addition per element. "Days 2 to 4" is now the total of the first five days minus the total of the first two, P[5] − P[2] = 14 − 4 = 10: one subtraction, and it stays one subtraction even if the range covers a million elements. Such an array is called a prefix sum array, because entry i holds the sum of the prefix of the data that stops just before position i.

In a real problem statement the tell is a line like n, q ≤ 2×10⁵ sitting next to "the array does not change" and a pile of range queries. Those numbers forbid re-adding per query but comfortably allow one linear pass, which is precisely what this technique costs. And it is worth far more than its four lines suggest, because it is a component rather than a solution: prefix sums plus a hash map count the subarrays whose sum equals k; prefix sums plus binary search find the shortest subarray with sum at least k on a non-negative array; prefix XOR plus a trie maximise the XOR of a subarray; and rewriting every zero as -1 turns "equally many zeros and ones" into the far easier "sum is zero".

One sentence carries all of that: a subarray is the difference of two prefixes. Once sum(l, r) = P[r+1] − P[l] is in your head, every question about segments turns into a question about pairs of prefix values — and finding pairs is exactly what hash maps, sorting and binary search are built for. Read the same identity backwards and you get the difference array, which flips the cost model: each range update becomes two writes, and you pay one linear pass at the very end to read all the results out.

A subarray is the difference of two prefixes, so rewrite every subarray condition as a condition on two prefix values. The question stops being "which segment?" and becomes "which pair of prefix indices?" — and locating a pair is what a hash map, a sort or a binary search does in linear or near-linear time.

Recognise this pattern

Say yes when you see

  • Many range-sum, range-count or range-XOR queries on a static array
  • The phrase "subarray sum equals k", "divisible by k", or "equal number of X and Y"
  • Many range updates followed by one final read → difference array, the mirror image of this technique
  • A 2D grid with repeated rectangle-sum queries → 2D prefix sums with inclusion-exclusion
  • Sums appear inside a binary search predicate → precompute prefixes so the predicate is O(1)

Not this pattern when

  • The array changes between queries → use a Fenwick tree or segment tree
  • You need range minimum rather than range sum → min has no inverse, so use a sparse table
  • There is exactly one query → just loop; the precomputation is wasted
  • The operation has no inverse (max, gcd, bitwise AND/OR) → prefix arrays cannot subtract; use a sparse table or a segment tree instead

Constraint tell: n, q ≤ 2×10⁵ with many range-sum queries and no updates in between is the standard signature: re-adding for every query would be about 4×10¹⁰ operations, whereas one build pass plus q subtractions is about 4×10⁵, a hundred thousand times less work. Read the value range as well — 10⁵ elements of size 10⁹ sum to 10¹⁴, which is far beyond the 2.1×10⁹ ceiling of an int, so the prefix array is long[], always.

Core idea and the invariant

Define P[0] = 0 and P[i] = a[0] + a[1] + … + a[i-1]. The leading zero is not decoration: it removes every special case, because with it sum(l, r) = P[r+1] - P[l] holds for all valid l ≤ r including l = 0. Implementations that start at P[0] = a[0] need a branch for l = 0, and that branch is where the bugs live.

The difference array is the same identity read backwards. To add v to a[l..r], write d[l] += v and d[r+1] -= v; after all updates, the prefix sum of d is the array of totals added to each position. So prefix sums turn point updates and range queries into range updates and point queries, at O(1) per update and one O(n) pass at the end.

In two dimensions the same identity needs inclusion-exclusion, because the rectangle above and the rectangle to the left overlap in the corner. With P[i][j] the sum of the submatrix from (0,0) to (i-1, j-1), the build step is P[i][j] = a[i-1][j-1] + P[i-1][j] + P[i][j-1] − P[i-1][j-1], and the query reverses the signs. Take the 2-by-2 grid [[1, 2], [3, 4]]: after the build, P[2][2] = 10 is the whole-grid sum, and the bottom-right cell alone is P[2][2] − P[1][2] − P[2][1] + P[1][1] = 10 − 3 − 4 + 1 = 4. Four reads, and the same four reads would answer any rectangle in a million-by-million grid.

The invariant

P[i] holds the sum of the first i elements, so that for every 0 ≤ l ≤ r < n:

sum(l, r) = P[r+1] − P[l]

Every technique on this page is a restatement of that line. "Subarray with property X" becomes "pair (l, r+1) of prefix indices whose values satisfy X", and counting pairs is what hash maps, sorting and binary search are for.

2D inclusion-exclusion, derived

Let P[i][j] be the sum of all cells strictly above row i and strictly left of column j. The rectangle [r1..r2] × [c1..c2] is the big rectangle minus the strip above minus the strip to the left, but the top-left corner has now been subtracted twice, so add it back:

P[r2+1][c2+1] − P[r1][c2+1] − P[r2+1][c1] + P[r1][c1]

The same alternating-sign pattern generalises to d dimensions with 2d terms, which is why 3D prefix sums have eight.

Seed the map with {0: 1}

When counting subarrays with sum k using a hash map of prefix values, you must insert (0, 1) before the loop. It represents the empty prefix and is what allows a subarray starting at index 0 to be counted. Forgetting it is the single most common bug in this pattern, and it only shows up when the answer includes a prefix of the array — which many sample tests avoid.

Only invertible operations work

Prefix arrays rely on being able to undo the left part. Addition has subtraction and XOR is its own inverse, so both work. Minimum, maximum, gcd, bitwise AND and bitwise OR have no inverse: knowing min(a[0..r]) and min(a[0..l-1]) tells you nothing about min(a[l..r]). Those need a sparse table or a segment tree.

Which prefix variant do you need?

Algorithm

  1. Allocate long[] P of length n + 1 and leave P[0] = 0, so a range that starts at index 0 needs no special case.
  2. Fill it in one pass: P[i] = P[i-1] + a[i-1] for i = 1 … n, which costs exactly one addition per element.
  3. Answer each query as P[r+1] - P[l] using inclusive l and r, so a single-element range sum(i, i) equals a[i].
  4. For 2D, build with a zero border and P[i][j] = a[i-1][j-1] + P[i-1][j] + P[i][j-1] - P[i-1][j-1].
  5. For range updates, use a difference array: d[l] += v, d[r+1] -= v, then prefix-sum d once at the end.
  6. For subarray-property counting, restate the condition as a relation between two prefix values, then use a HashMap from prefix value to count, seeded with {0: 1}.
  7. Choose the accumulator type deliberately. Use long whenever n × max|ai| can exceed 2.1×10⁹, which is the usual contest bound.

Java implementation

The base template. Note the long[] and the n + 1 length with a zero sentinel — both are deliberate and both prevent common failures.

JavaPrefixSum1D.java
import java.util.Arrays;
    
    public class PrefixSum1D {
    
        private final long[] p;
    
        /** O(n) build. P[0] = 0 so that no query needs a special case. */
        PrefixSum1D(int[] a) {
            p = new long[a.length + 1];
            for (int i = 0; i < a.length; i++) {
                p[i + 1] = p[i] + a[i];        // long: n * maxA can exceed int
            }
        }
    
        /** O(1). Inclusive on both ends. */
        long rangeSum(int l, int r) {
            return p[r + 1] - p[l];
        }
    
        /** O(1). Average of a range, as a double. */
        double rangeAvg(int l, int r) {
            return (double) rangeSum(l, r) / (r - l + 1);
        }
    
        public static void main(String[] args) {
            int[] a = {3, 1, 4, 1, 5, 9};
            PrefixSum1D ps = new PrefixSum1D(a);
            System.out.println(Arrays.toString(a));
            System.out.println("sum(2,4) = " + ps.rangeSum(2, 4));
            System.out.println("sum(0,5) = " + ps.rangeSum(0, 5));
            System.out.println("sum(3,3) = " + ps.rangeSum(3, 3));
            System.out.println("avg(0,5) = " + ps.rangeAvg(0, 5));
        }
        // Input : [3, 1, 4, 1, 5, 9]
        // Output: [3, 1, 4, 1, 5, 9]
        //         sum(2,4) = 10
        //         sum(0,5) = 23
        //         sum(3,3) = 1
        //         avg(0,5) = 3.8333333333333335
    }

Inclusion-exclusion in both the build and the query. The zero border removes every boundary check, which is why the code has no if statements at all.

JavaPrefixSum2D.java
public class PrefixSum2D {
    
        private final long[][] p;
    
        /** O(rows * cols) build with a zero border row and column. */
        PrefixSum2D(int[][] a) {
            int n = a.length, m = a[0].length;
            p = new long[n + 1][m + 1];
            for (int i = 1; i <= n; i++) {
                for (int j = 1; j <= m; j++) {
                    p[i][j] = a[i - 1][j - 1]
                            + p[i - 1][j]          // everything above
                            + p[i][j - 1]          // everything to the left
                            - p[i - 1][j - 1];     // the overlap, counted twice
                }
            }
        }
    
        /** O(1). All bounds inclusive. */
        long rectSum(int r1, int c1, int r2, int c2) {
            return p[r2 + 1][c2 + 1]
                 - p[r1][c2 + 1]
                 - p[r2 + 1][c1]
                 + p[r1][c1];
        }
    
        public static void main(String[] args) {
            int[][] a = {
                {1, 2, 3},
                {4, 5, 6},
                {7, 8, 9},
            };
            PrefixSum2D ps = new PrefixSum2D(a);
            System.out.println("whole matrix   = " + ps.rectSum(0, 0, 2, 2));
            System.out.println("bottom-right 2x2 = " + ps.rectSum(1, 1, 2, 2));
            System.out.println("middle row     = " + ps.rectSum(1, 0, 1, 2));
            System.out.println("single cell    = " + ps.rectSum(2, 2, 2, 2));
        }
        // Output: whole matrix   = 45
        //         bottom-right 2x2 = 28
        //         middle row     = 15
        //         single cell    = 9
    }

The mirror image: O(1) range updates and one O(n) pass to materialise the result. This is the right tool whenever all updates come before all reads.

JavaDifferenceArray.java
import java.util.Arrays;
    
    public class DifferenceArray {
    
        private final long[] d;
    
        DifferenceArray(int n) {
            d = new long[n + 1];               // one extra slot so r+1 is always valid
        }
    
        /** O(1). Add v to every index in [l, r], inclusive. */
        void add(int l, int r, long v) {
            d[l] += v;
            d[r + 1] -= v;
        }
    
        /** O(n). Materialise the final array. */
        long[] build() {
            long[] res = new long[d.length - 1];
            long running = 0;
            for (int i = 0; i < res.length; i++) {
                running += d[i];
                res[i] = running;
            }
            return res;
        }
    
        public static void main(String[] args) {
            DifferenceArray da = new DifferenceArray(8);
            da.add(1, 3, 5);                   // +5 on indices 1..3
            da.add(2, 6, 2);                   // +2 on indices 2..6
            da.add(0, 7, 1);                   // +1 everywhere
            System.out.println(Arrays.toString(da.build()));
        }
        // Three range updates in O(1) each, then one O(n) pass.
        // Output: [1, 6, 8, 8, 3, 3, 3, 1]
    }

The three highest-value applications of "a subarray is a difference of prefixes". All three handle negative numbers, which is what distinguishes them from sliding windows.

JavaPrefixHashing.java
import java.util.HashMap;
    import java.util.Map;
    
    public class PrefixHashing {
    
        /** Count subarrays with sum exactly k. Works with negatives. O(n). */
        static int countSumEqualsK(int[] a, int k) {
            Map<Long, Integer> seen = new HashMap<>();
            seen.put(0L, 1);                            // the empty prefix: essential
            long prefix = 0;
            int count = 0;
            for (int v : a) {
                prefix += v;
                count += seen.getOrDefault(prefix - k, 0);
                seen.merge(prefix, 1, Integer::sum);
            }
            return count;
        }
    
        /**
         * Count subarrays whose sum is divisible by k.
         * Two prefixes with the same remainder bound a divisible subarray.
         * O(n) with an int[] of size k instead of a map.
         */
        static long countDivisibleByK(int[] a, int k) {
            int[] cnt = new int[k];
            cnt[0] = 1;
            int rem = 0;
            long total = 0;
            for (int v : a) {
                rem = ((rem + v) % k + k) % k;          // floorMod: Java's % can be negative
                total += cnt[rem];
                cnt[rem]++;
            }
            return total;
        }
    
        /**
         * Longest subarray with equal numbers of 0 and 1.
         * Map 0 to -1: now "equal counts" means "prefix sum returns to a value it had".
         * O(n).
         */
        static int longestEqualZerosOnes(int[] bits) {
            Map<Integer, Integer> firstIndex = new HashMap<>();
            firstIndex.put(0, -1);                      // prefix 0 occurs before index 0
            int prefix = 0, best = 0;
            for (int i = 0; i < bits.length; i++) {
                prefix += (bits[i] == 1) ? 1 : -1;
                Integer first = firstIndex.get(prefix);
                if (first == null) {
                    firstIndex.put(prefix, i);          // keep only the EARLIEST occurrence
                } else {
                    best = Math.max(best, i - first);
                }
            }
            return best;
        }
    
        public static void main(String[] args) {
            System.out.println(countSumEqualsK(new int[] {1, 2, 1, 2, 1}, 3));
            System.out.println(countSumEqualsK(new int[] {1, -1, 0}, 0));
            System.out.println(countDivisibleByK(new int[] {4, 5, 0, -2, -3, 1}, 5));
            System.out.println(longestEqualZerosOnes(new int[] {0, 1, 0, 0, 1, 1, 0}));
        }
        // Output: 4
        //         3
        //         7
        //         6
    }

Complexity

Time O(n) build, O(1) per query Space O(n) extra, or O(nm) in 2D

The build is a single pass performing one addition per element, so it is exactly n additions:

Tbuild(n) = Θ(n),   Tquery = Θ(1),   Ttotal(n, q) = Θ(n + q)

Compare with the naive approach, which is Θ(nq). At n = q = 10⁵ that is 10¹⁰ against 2×10⁵ — five thousand times fewer operations, and the difference between a timeout and a 30 ms run.

The break-even point is worth knowing: precomputation pays off as soon as q > 1 in the amortised sense, since building costs n and a single naive query costs at most n. In 2D the build is Θ(nm) and each rectangle query is four reads, so q queries cost Θ(nm + q) against a naive Θ(q · nm).

For the hash-map variants, each element does O(1) expected map work, giving Θ(n) expected overall. Using an int[] indexed by remainder (as in countDivisibleByK) makes it worst-case Θ(n + k) with no hashing at all, which is both faster and immune to hash attacks.

Edge cases and pitfalls

  • Off-by-one in the query formula
    Writing P[r] - P[l] instead of P[r+1] - P[l], which silently drops a[r] from every answer. With P[0] = a[0] instead of 0, you also need a branch for l == 0.
    Always use the n + 1 array with P[0] = 0 and the formula P[r+1] - P[l]. Verify once on a single-element range: sum(3,3) must equal a[3].
  • int overflow in the accumulator
    int[] p with n = 10⁵ and values up to 10⁹. The true prefix reaches 10¹⁴, wraps, and the differences can still look plausible, which makes it hard to spot.
    Use long[] for the prefix array unconditionally. The memory cost at n = 10⁶ is 8 MB, which is almost always acceptable.
  • Forgetting to seed the map with {0: 1}
    countSumEqualsK([3], 3) returns 0 instead of 1, because the subarray starting at index 0 needs a prefix value of 0 to already be in the map.
    Insert (0, 1) before the loop for counting problems, or (0, -1) for longest-subarray problems where you store first indices.
  • Storing the latest index instead of the earliest
    In "longest subarray with sum k", overwriting the map entry each time a prefix recurs. That yields the shortest such subarray, not the longest.
    Only insert when the key is absent: if (!map.containsKey(p)) map.put(p, i);. For counting problems you do want to accumulate every occurrence — the two problems need opposite handling, which is a frequent source of confusion.
  • Applying prefix sums to a non-invertible operation
    Building a "prefix minimum" array and trying min(l, r) = something(P[r+1], P[l]). There is no such function: minimum cannot be undone.
    Use a sparse table for idempotent operations (min, max, gcd, AND, OR) or a segment tree for the general case. Only sum, XOR, and products in a field support the prefix trick.
  • Difference array without the extra slot
    d[r + 1] -= v throws ArrayIndexOutOfBoundsException when r == n - 1, so people add a guard — and then forget it in the second call site.
    Allocate new long[n + 1] and ignore the last slot when reading. The branch disappears entirely.
  • Java's % returning a negative remainder
    In countDivisibleByK, prefix % k can be negative for negative sums, so cnt[rem] throws or indexes the wrong bucket.
    ((x % k) + k) % k or Math.floorMod(x, k). This applies anywhere you index an array by a remainder.

Interview follow-ups

What changes if the array can be updated between queries?

Prefix sums break, because a single point update invalidates O(n) prefix entries. Switch to a Fenwick tree for point update plus prefix query at O(log n) each, or a segment tree if you also need range updates. The trade is precise: prefix sums are O(1) query and O(n) update; a BIT is O(log n) for both. If updates are rare, rebuilding the prefix array is sometimes still the right call.

Why does the sliding-window approach fail for "subarray sum equals k" with negatives?

A sliding window relies on monotonicity: extending the window must move the sum in a predictable direction so that you know whether to grow or shrink. With negative values, extending can decrease the sum, so "sum too large, shrink from the left" is no longer valid reasoning. The prefix-plus-hash-map approach makes no monotonicity assumption at all — it just counts pairs — which is why it is the general answer. Reserve sliding windows for non-negative arrays.

How do you find the longest subarray with sum exactly k?

Same prefix map, but store the first index at which each prefix value occurred and never overwrite it. At index i with prefix p, look up p - k; if present at index j, the candidate length is i - j. Because j is the earliest occurrence, that candidate is the longest one ending at i. Counting problems, by contrast, need every occurrence, so they accumulate counts instead. Getting these two backwards is a classic interview slip.

Can you do range minimum with prefix arrays?

No — minimum has no inverse, so there is no way to remove the contribution of the left part. Use a sparse table, which exploits the fact that min is idempotent: overlapping ranges may be combined freely, so two lookups of the largest power-of-two blocks suffice. That gives O(n log n) build and O(1) query on a static array. The general rule: invertible → prefix sums; idempotent → sparse table; neither → segment tree.

How would you handle 10⁵ range-add updates and 10⁵ range-sum queries interleaved?

Neither prefix sums nor a plain difference array works, because the two operation types are interleaved. Use a lazy segment tree, or the two-BIT trick: maintain Fenwick trees B1 and B2 so that the prefix sum up to i equals sum(B1, i) × i - sum(B2, i). Both are O(log n) per operation; the two-BIT version has a much smaller constant and is about twenty lines.

What is the 3D version?

The same alternating-sign inclusion-exclusion with 2³ = 8 terms: add the corners with an even number of "low" coordinates and subtract those with an odd number. Build is O(nmk) and each box query is 8 reads. In general d dimensions need 2d terms, which is why nobody goes beyond three — and it is a good illustration of why inclusion-exclusion is worth knowing as a general principle.

Hint for LC 525 — the reformulation that makes it a prefix problem

"Equal numbers of 0 and 1" is not obviously a sum condition. Replace every 0 with -1: now a balanced subarray is exactly one whose sum is 0, which means the prefix sum at both ends is the same value. So store the first index at which each prefix value appears and take the largest i - firstIndex[p]. Seed with {0: -1} so a balanced prefix starting at index 0 is measured correctly. Transferable lesson: when a condition compares two counts, subtract them into a single running quantity — "equal counts" becomes "difference is zero", which prefix sums handle directly.

Hint for LC 974 — why counting pairs works and how to avoid the HashMap

sum(l, r) ≡ 0 (mod k) is equivalent to P[r+1] ≡ P[l] (mod k), so you need the number of pairs of prefix indices sharing a remainder. If remainder x occurs cx times, it contributes C(cx, 2) pairs, or equivalently you can accumulate cnt[rem]++ as you go. Use int[k] rather than a HashMap: remainders are bounded by k, so array indexing is both faster and hash-attack-proof. Watch Math.floorMod for negative values. General lesson: whenever the key space is a small bounded integer range, replace the hash map with a plain array.

Recap

  • P[0] = 0 and sum(l, r) = P[r+1] - P[l]. The sentinel removes every boundary case; use long[] always.
  • A subarray is a difference of two prefixes. Rewrite subarray conditions as conditions on pairs of prefix values, then hash, sort, or binary search the pairs.
  • Difference arrays are the mirror image: O(1) range updates, one O(n) pass at the end. Allocate n + 1 slots.
  • 2D needs inclusion-exclusion in both build and query, with a zero border to remove all boundary checks.
  • Only invertible operations qualify. Sum and XOR yes; min, max, gcd, AND and OR need a sparse table or segment tree.
