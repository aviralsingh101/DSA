Sliding Window

Maintain a contiguous segment and a small amount of state about it, so that moving either edge costs O(1) instead of rescanning — the answer to nearly every "longest / shortest / count of substrings such that…" question.

Medium 26 min read Prerequisites: Two Pointers, Prefix Sums sliding window two pointers strings counting P0

Why this exists

"Longest substring without repeating characters", "minimum window substring", "subarrays with at most K distinct", "count nice subarrays" — these are among the most frequently asked interview questions in existence, and they are all the same algorithm. A right pointer extends the segment, a left pointer repairs it when it becomes invalid, and a small amount of incrementally maintained state (a count array, a distinct counter, a running sum) tells you which case you are in.

The reason it works is monotonicity of validity: for a fixed right endpoint, there is a threshold left endpoint such that every window starting at or after it is valid and every window starting before it is invalid. That threshold never moves backwards as the right endpoint advances, so the left pointer only ever goes forward and the whole scan is O(n). On n = 10⁵ that is at most two pointer movements per element, about 2×10⁵ updates, versus a nested scan of every pair of endpoints, which is about 5×10⁹ windows and a timeout.

Two things separate people who solve these reliably. First, knowing the three templates (fixed size, longest-valid, shortest-valid) and which one a question maps to. Second, knowing the exactly-K trick: "exactly K" is not directly window-able, but atMost(K) - atMost(K-1) is, and that single identity unlocks an entire family of counting problems that otherwise look intractable.

Ask: for a fixed right end, is validity monotone in the left end? If yes, the left pointer never retreats and the scan is linear. If no — typically because values can be negative — you need prefix sums with a deque or a hash map instead.

Recognise this pattern

Say yes when you see

  • "Longest / shortest / count of contiguous subarrays or substrings such that …"
  • A constraint on the window such as "at most K distinct", "no repeats", "sum ≤ target", "contains all characters of T"
  • All values are non-negative, so extending the window never decreases the sum
  • Fixed window size k is given explicitly ("maximum sum of any k consecutive elements")
  • "Exactly K" phrasing on a countable property → use atMost(K) - atMost(K-1)

Not this pattern when

  • The array contains negative numbers and the condition is about sums → validity is not monotone; use prefix sums with a hash map or a monotonic deque
  • The subsequence need not be contiguous → that is a DP problem, not a window
  • You need the maximum or minimum inside the window → the window is right but you need a monotonic deque to maintain the extreme
  • The window must satisfy a condition that can be repaired by moving either edge → monotonicity fails; think again about the formulation

Core idea and the three templates

All three templates share a skeleton: for (r = 0; r < n; r++) { add a[r]; … ; }. What differs is what happens in the middle. Fixed size: once r - l + 1 > k, remove a[l] and increment l exactly once — the window size is constant, so it is an if, not a while. Longest valid: while (invalid) { remove a[l]; l++; } then record r - l + 1. Shortest valid: while (valid) { record r - l + 1; remove a[l]; l++; }.

The order of operations matters and is the source of most bugs. In the longest-valid template you record the answer after the repair loop, because only then is the window guaranteed valid. In the shortest-valid template you record inside the shrink loop, because you want the smallest window that still satisfies the condition, and the last valid one before it breaks is the one you want.

The state is whatever makes the validity check O(1). For "no repeats" it is a count array plus the knowledge that a repeat exists iff some count exceeds 1 — cheaply tracked by checking only the incoming character. For "at most K distinct" it is a count map plus a distinct counter, incremented when a count goes from 0 to 1 and decremented when it returns to 0. For "contains all of T" it is a count map plus a satisfied counter of how many required characters have met their quota. Designing that O(1)-updatable state is the real work.

The invariant

At the top of each iteration of the outer loop, the window [l, r] satisfies the problem's validity predicate, and l is the smallest left endpoint for which that holds given the current r. The state variables (counts, sums, distinct counters) exactly describe [l, r] and nothing else.

The left pointer never retreats, because if [l, r] is valid then [l, r+1] can only become invalid by needing a larger l, never a smaller one.

The exactly-K trick

"Exactly K distinct" is not monotone: shrinking a window can take you from K to K-1, so there is no single threshold left endpoint. But "at most K" is monotone, and

exactly(K) = atMost(K) − atMost(K − 1)

so you run the same linear window twice and subtract. This converts a whole family of hard-looking counting problems into two applications of a template you already have. It works for any property where "at most" is monotone: distinct characters, odd numbers, zeros, and so on.

Counting subarrays, not just measuring them

When "at most K" holds for the window [l, r], every subarray ending at r and starting at l, l+1, …, r is also valid, because shrinking preserves "at most". That is r - l + 1 subarrays, so the counting version of the template just accumulates count += r - l + 1 at each step instead of taking a maximum. Recognising that one line converts "find the longest" into "count them all" is worth a lot.

Negative numbers break everything

"Shortest subarray with sum at least k" is a clean window problem when all values are non-negative, because the sum is monotone in the window size. Add one negative value and it collapses: a longer window can have a smaller sum, so "shrink while valid" no longer finds the shortest. The correct tool becomes prefix sums plus a monotonic deque (LeetCode 862). Always check the sign constraint before committing to a window.

Choosing the template

Algorithm

  1. Confirm the window is legal: the answer must be a contiguous segment, and values must be non-negative if the condition involves sums.
  2. Pick the template from the flowchart: fixed size, longest valid, shortest valid, or a counting variant, before writing any loop.
  3. Design the O(1)-updatable state. Usually a count array plus one scalar summary (distinct, satisfied, sum).
  4. Write the add step for a[r] first, updating both the count array and the scalar summary in one place.
  5. Write the remove step for a[l] as the exact mirror image. Asymmetry here is the most common bug.
  6. Place the answer update correctly: after the repair loop for longest-valid, and inside the shrink loop for shortest-valid.
  7. For counting, accumulate r - l + 1 at each right endpoint instead of taking a running maximum.
  8. For "exactly K", call the at-most helper twice and subtract, because exactly-K is not itself a monotone window.

Java implementation

Memorise these three shapes. Almost every window problem is one of them with a different state variable, and the position of the answer update is the part to get right.

JavaWindowTemplates.java
import java.util.HashMap;
    import java.util.Map;
    
    public class WindowTemplates {
    
        /**
         * TEMPLATE 1 - fixed size k.
         * The size is constant, so the shrink is an if, not a while.
         */
        static long maxSumFixed(int[] a, int k) {
            long sum = 0, best = Long.MIN_VALUE;
            for (int r = 0; r < a.length; r++) {
                sum += a[r];                            // add the incoming element
                if (r >= k) {
                    sum -= a[r - k];                    // remove the outgoing element
                }
                if (r >= k - 1) {
                    best = Math.max(best, sum);         // only once the window is full
                }
            }
            return best;
        }
    
        /**
         * TEMPLATE 2 - longest valid window.
         * Grow, repair while invalid, THEN record.
         */
        static int longestAtMostKDistinct(int[] a, int k) {
            Map<Integer, Integer> cnt = new HashMap<>();
            int l = 0, best = 0;
            for (int r = 0; r < a.length; r++) {
                cnt.merge(a[r], 1, Integer::sum);
                while (cnt.size() > k) {                // invalid: too many distinct
                    int out = a[l++];
                    if (cnt.merge(out, -1, Integer::sum) == 0) {
                        cnt.remove(out);                // must remove, or size() lies
                    }
                }
                best = Math.max(best, r - l + 1);       // window is valid here
            }
            return best;
        }
    
        /**
         * TEMPLATE 3 - shortest valid window.
         * Grow, then record INSIDE the shrink loop while it stays valid.
         * Requires non-negative values.
         */
        static int shortestSumAtLeast(int[] a, int target) {
            int l = 0, best = Integer.MAX_VALUE;
            long sum = 0;
            for (int r = 0; r < a.length; r++) {
                sum += a[r];
                while (sum >= target) {                 // valid: try to make it smaller
                    best = Math.min(best, r - l + 1);
                    sum -= a[l++];
                }
            }
            return best == Integer.MAX_VALUE ? 0 : best;
        }
    
        public static void main(String[] args) {
            System.out.println(maxSumFixed(new int[] {2, 1, 5, 1, 3, 2}, 3));
            System.out.println(longestAtMostKDistinct(new int[] {1, 2, 1, 2, 3}, 2));
            System.out.println(shortestSumAtLeast(new int[] {2, 3, 1, 2, 4, 3}, 7));
        }
        // Output: 9
        //         4
        //         2
    }

The two most-asked string window problems. Both use an int[128] rather than a HashMap, which is roughly ten times faster and removes all boxing.

JavaStringWindows.java
public class StringWindows {
    
        /**
         * Longest substring with no repeated characters. O(n).
         * lastSeen[c] lets l jump directly instead of stepping one at a time.
         */
        static int longestUnique(String s) {
            int[] lastSeen = new int[128];
            java.util.Arrays.fill(lastSeen, -1);
            int l = 0, best = 0;
            for (int r = 0; r < s.length(); r++) {
                char c = s.charAt(r);
                if (lastSeen[c] >= l) {
                    l = lastSeen[c] + 1;              // jump past the previous occurrence
                }
                lastSeen[c] = r;
                best = Math.max(best, r - l + 1);
            }
            return best;
        }
    
        /**
         * Minimum window in s containing every character of t with multiplicity.
         * O(|s| + |t|). 'need' counts how many distinct required chars are still short.
         */
        static String minWindow(String s, String t) {
            if (s.length() < t.length()) {
                return "";
            }
            int[] want = new int[128];
            int need = 0;
            for (char c : t.toCharArray()) {
                if (want[c]++ == 0) {
                    need++;                            // a new distinct requirement
                }
            }
            int[] have = new int[128];
            int satisfied = 0, l = 0, bestLen = Integer.MAX_VALUE, bestL = 0;
            for (int r = 0; r < s.length(); r++) {
                char c = s.charAt(r);
                if (++have[c] == want[c]) {
                    satisfied++;                       // this char's quota is now met
                }
                while (satisfied == need) {            // valid: shrink as far as possible
                    if (r - l + 1 < bestLen) {
                        bestLen = r - l + 1;
                        bestL = l;
                    }
                    char out = s.charAt(l++);
                    if (have[out]-- == want[out]) {
                        satisfied--;                   // quota broken; stop shrinking
                    }
                }
            }
            return bestLen == Integer.MAX_VALUE ? "" : s.substring(bestL, bestL + bestLen);
        }
    
        /** All start indices of anagrams of p in s. Fixed-size window over 26 counts. */
        static java.util.List<Integer> findAnagrams(String s, String p) {
            java.util.List<Integer> out = new java.util.ArrayList<>();
            if (s.length() < p.length()) {
                return out;
            }
            int[] want = new int[26], have = new int[26];
            for (char c : p.toCharArray()) {
                want[c - 'a']++;
            }
            for (int r = 0; r < s.length(); r++) {
                have[s.charAt(r) - 'a']++;
                if (r >= p.length()) {
                    have[s.charAt(r - p.length()) - 'a']--;
                }
                if (r >= p.length() - 1 && java.util.Arrays.equals(have, want)) {
                    out.add(r - p.length() + 1);       // 26 comparisons = O(1)
                }
            }
            return out;
        }
    
        public static void main(String[] args) {
            System.out.println(longestUnique("abcabcbb"));
            System.out.println(longestUnique("bbbbb"));
            System.out.println(minWindow("ADOBECODEBANC", "ABC"));
            System.out.println(findAnagrams("cbaebabacd", "abc"));
        }
        // Output: 3
        //         1
        //         BANC
        //         [0, 6]
    }

The identity exactly(K) = atMost(K) - atMost(K-1) applied to two different predicates. Once you see the pattern, a whole class of "count subarrays with exactly…" problems becomes mechanical.

JavaExactlyK.java
import java.util.HashMap;
    import java.util.Map;
    
    public class ExactlyK {
    
        /** Number of subarrays with exactly k distinct integers. O(n). */
        static int subarraysWithKDistinct(int[] a, int k) {
            return atMostDistinct(a, k) - atMostDistinct(a, k - 1);
        }
    
        /** Subarrays with at most k distinct. Counting line: count += r - l + 1. */
        private static int atMostDistinct(int[] a, int k) {
            if (k < 0) {
                return 0;
            }
            Map<Integer, Integer> cnt = new HashMap<>();
            int l = 0, total = 0;
            for (int r = 0; r < a.length; r++) {
                cnt.merge(a[r], 1, Integer::sum);
                while (cnt.size() > k) {
                    int out = a[l++];
                    if (cnt.merge(out, -1, Integer::sum) == 0) {
                        cnt.remove(out);
                    }
                }
                total += r - l + 1;      // every subarray ending at r and starting in
                                         // [l, r] is valid, because shrinking preserves
                                         // "at most k distinct"
            }
            return total;
        }
    
        /** Number of subarrays containing exactly k odd numbers ("nice subarrays"). */
        static int numberOfNiceSubarrays(int[] a, int k) {
            return atMostOdd(a, k) - atMostOdd(a, k - 1);
        }
    
        private static int atMostOdd(int[] a, int k) {
            if (k < 0) {
                return 0;
            }
            int l = 0, odds = 0, total = 0;
            for (int r = 0; r < a.length; r++) {
                odds += a[r] & 1;
                while (odds > k) {
                    odds -= a[l++] & 1;
                }
                total += r - l + 1;
            }
            return total;
        }
    
        public static void main(String[] args) {
            System.out.println(subarraysWithKDistinct(new int[] {1, 2, 1, 2, 3}, 2));
            System.out.println(subarraysWithKDistinct(new int[] {1, 2, 1, 3, 4}, 3));
            System.out.println(numberOfNiceSubarrays(new int[] {1, 1, 2, 1, 1}, 3));
            System.out.println(numberOfNiceSubarrays(new int[] {2, 2, 2, 1, 2, 2, 1, 2, 2, 2}, 2));
        }
        // Output: 7
        //         3
        //         2
        //         16
    }

Complexity

Time O(n) for the scan; O(n · A) if you compare full count arrays Space O(A) where A is the alphabet or distinct-value count

Both pointers move only forward and each is bounded by n, so the total number of pointer movements is at most 2n:

T(n) = Θ(n) × O(cost of one add/remove) = Θ(n) when the state update is O(1)

The nested while does not make it quadratic, for the same amortised reason as two pointers: l never decreases. Each element enters the window exactly once and leaves at most once.

The constant hides in the state update. With an int[26] and a scalar summary, add and remove are single array operations. With a HashMap they are O(1) expected but roughly 20–50 times slower per operation. And the anagram template that calls Arrays.equals(have, want) per position is Θ(n · 26) — still linear in n, but you can reduce it to Θ(n) by maintaining a matched counter instead.

The exactly-K trick runs the same linear scan twice, so it is Θ(2n) = Θ(n) — the constant is 2, and that is the entire price of converting a non-monotone problem into a monotone one.

Edge cases and pitfalls

  • Using a window when values can be negative
    "Shortest subarray with sum at least k" on an array containing negatives. Shrinking from the left can increase the sum, so the shrink loop terminates early and misses the answer.
    Check the sign constraint first. With negatives, use prefix sums plus a monotonic deque (the deque keeps prefix indices in increasing order of prefix value).
  • Recording the answer in the wrong place
    In the longest-valid template, updating best before the repair loop records an invalid window. In the shortest-valid template, updating after the shrink loop records a window that has already been broken.
    Longest: record after repairing. Shortest: record inside the shrink loop, before removing. Write the template from memory a few times until the placement is automatic.
  • Asymmetric add and remove
    Incrementing distinct when a count goes from 0 to 1, but forgetting to decrement it when a count returns to 0. The state then describes a window that does not exist.
    Write remove as the literal mirror of add, and check the transition condition on both sides. With a HashMap, actually remove the key at zero — otherwise map.size() counts stale entries.
  • map.size() counting zero-valued keys
    Using cnt.size() > k as the validity test while leaving entries whose value has dropped to 0 in the map. The window looks invalid forever and l runs past r.
    if (cnt.merge(key, -1, Integer::sum) == 0) cnt.remove(key);, or maintain an explicit distinct counter and never call size().
  • Fixed-size window using a while
    while (r - l + 1 > k) { … } in the fixed-size template is harmless but signals confusion; the real bug is starting to record before the window is full, which yields answers from undersized windows.
    Guard the answer update with if (r ≥ k - 1), and use a single if for the removal since the size grows by exactly one each step.
  • Trying to window "exactly K" directly
    Writing while (distinct > k) and then recording only when distinct == k. This undercounts, because for a given r there is a range of valid left endpoints and the window only sees one of them.
    atMost(K) - atMost(K-1). Two passes of a template you already trust, and no special-case reasoning.
  • Character index out of range
    int[26] indexed by c - 'a' when the input contains uppercase letters, digits or spaces. Throws ArrayIndexOutOfBoundsException, or silently corrupts memory-adjacent counts with a negative index.
    Read the constraints on the alphabet. Use int[128] indexed by the raw char for ASCII, or a HashMap for Unicode. The extra 100 ints cost nothing.

Interview follow-ups

Why does the left pointer never need to move backwards?

Because validity is monotone in the left endpoint for a fixed right endpoint. If [l, r] is invalid, then [l', r] for any l' < l is also invalid, since it contains strictly more elements and the constraints are all of the "at most" form. So once l has advanced past a position, that position can never become a valid left endpoint again for any larger r. That is exactly the property that fails for "exactly K", which is why the direct window does not work there.

Prove the atMost(K) - atMost(K-1) identity.

Let D(S) be the number of distinct values in subarray S. atMost(K) counts all subarrays with D(S) ≤ K, and atMost(K-1) counts those with D(S) ≤ K-1. Every subarray counted by the first but not the second has D(S) ≤ K and D(S) > K-1, i.e. D(S) = K exactly. The sets are nested, so the subtraction is exact with no double counting. The same argument works for any integer-valued monotone statistic of the window.

How do you find the maximum in every window of size k?

A monotonic deque of indices, kept in decreasing order of value. When r advances, pop from the back while the back's value is at most a[r] — those can never be the maximum again, since a[r] is both larger and stays in the window longer. Then pop from the front if its index has left the window. The front is always the maximum. Each index is pushed and popped once, so the whole scan is O(n). Storing indices rather than values is essential, because the expiry test needs the position.

When is a window wrong for a sum problem?

Whenever any value can be negative or zero-with-a-twist. The window technique needs "extending increases the sum" so that shrinking is the correct repair. With negatives, the correct tool depends on the question: for "count subarrays with sum exactly k" use prefix sums plus a hash map; for "shortest subarray with sum at least k" use prefix sums plus a monotonic deque. Both are O(n), so you lose nothing but the simplicity.

What is the complexity of the anagram-finding template?

As written with Arrays.equals(have, want) at each position it is O(n · 26), which is linear in n but with a constant of 26. You can make it a true O(n) with a small constant by maintaining a matched counter: increment it when a character's count becomes exactly equal to its requirement and decrement it when it stops being equal, then test matched == 26 in O(1). Both pass comfortably, but the second version is the one to mention.

How do you handle a window on a circular array?

Either concatenate the array with itself and cap the window length at n, or index with i % n and run r from 0 to 2n - 1. The cap is essential: without it the window can wrap all the way around and count an element twice. For "maximum circular subarray sum" specifically there is a neater trick — the answer is max(kadaneMax, totalSum - kadaneMin), with a special case when all values are negative.

Hint for LC 424 — why you never need to shrink maxCount

The window is valid when (r - l + 1) - maxCount ≤ k, where maxCount is the frequency of the most common character inside it. The surprising part is that you can let maxCount go stale — never recompute it downward when the window shrinks — and the answer is still correct. The reason: the final answer only ever comes from a window whose maxCount is genuinely achieved, and a stale (too large) maxCount only prevents the window from shrinking, never lets it grow beyond a truly achievable size. Transferable lesson: when you only care about the maximum window size ever reached, monotone-but-stale state is often safe, and checking that is cheaper than maintaining exact state.

Hint for LC 862 — the deque over prefix sums

Compute prefix sums P. You want the smallest r - l with P[r] - P[l] ≥ k. Maintain a deque of indices with increasing P values. Two rules: pop from the front while P[r] - P[front] ≥ k, recording the length — that front index can never give a shorter answer later. Pop from the back while P[r] ≤ P[back] — a later index with a smaller prefix dominates an earlier index with a larger one, for every future r. Both pops are permanent, so the scan is O(n). General lesson: when a window fails because of non-monotonicity, look for a monotonic structure over the prefix array instead — the deque enforces the monotonicity the data lacks.

Recap

  • Three templates: fixed size (if shrink), longest valid (while repair then record), shortest valid (record inside the shrink loop).
  • Design O(1) state: a count array plus one scalar summary such as distinct, satisfied, or sum. Add and remove must be exact mirrors.
  • Counting adds one line: count += r - l + 1, because every suffix of a valid "at most" window is also valid.
  • Exactly K is atMost(K) - atMost(K-1) — two linear passes, no special reasoning.
  • Negatives kill the window. Switch to prefix sums with a hash map (exact sums) or a monotonic deque (shortest sum at least k).
