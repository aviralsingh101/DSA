Two Pointers

Two indices moving under a monotonicity guarantee turn a quadratic double loop into a single linear pass — provided you can prove that neither pointer ever needs to go back.

Easy 24 min read Prerequisites: Complexity Analysis, Prefix Sums two pointers sorted linear P0

Why this exists

An enormous number of array problems have an obvious O(n²) solution built from two nested loops over indices i < j. Two pointers is the observation that, when the data has the right monotonic structure, you never need to revisit a position: each pointer advances only forward, so the total work is O(n) rather than O(n²). On a sorted array of n = 10⁵, the nested loops check about 5×10⁹ pairs and time out; two pointers examine each index once, about 10⁵ additions after the sort.

The technique comes in three distinct shapes that people often conflate. Opposite ends: l starts at 0, r at n-1, and they converge — used for pair sums on sorted arrays, container with most water, and palindromes. Same direction: both start at 0 and r outruns l — that is the sliding window, plus in-place partitioning and merging. Fast and slow: one pointer moves twice as fast — cycle detection and finding the middle of a list.

What makes it an interview favourite is that the correctness argument is short but not trivial. "Why is it safe to move l here?" has a real answer — usually an exchange argument showing that every pair you skip is dominated by one you keep — and being able to give that answer separates people who memorised the pattern from people who understand it.

The pattern is valid only when moving a pointer provably discards no candidate answer. Before writing the loop, state which pointer moves and why every solution containing the discarded element is dominated by one that remains.

Recognise this pattern

Say yes when you see

  • The array is sorted, or sorting it does not destroy the question
  • "Find a pair / triplet with sum equal to (or closest to) a target"
  • "Longest or shortest contiguous segment satisfying …" with non-negative values → the same-direction form
  • In-place rearrangement: remove duplicates, move zeroes, partition by a predicate, reverse
  • Merging two sorted sequences, or intersecting two sorted sets
  • A linked list question about cycles, the middle node, or the k-th from the end

Not this pattern when

  • The array is unsorted and order matters → hashing or prefix sums instead
  • You need arbitrary index pairs with no monotonic relationship → there is nothing to exploit; consider sorting by a different key first
  • Values can be negative in a "longest subarray with sum ≥ k" question → monotonicity is lost, so use a monotonic deque over prefix sums
  • You need to count subarrays with an exact sum including negatives → prefix + HashMap

Constraint tell: n ≤ 10⁵ with a pair or triplet question is the signature: O(n²) is dead, sorting is affordable, so the intended solution is sort plus two pointers at O(n log n) (or O(n²) for triplets with n ≤ 3000).

Core idea and the exchange argument

Take the canonical case: a sorted array and a target sum. Put l at 0 and r at n - 1. If a[l] + a[r] < target, then a[l] paired with anything at or below r is also too small — because a[r] is the largest remaining partner. So no valid pair uses a[l] at all, and l++ discards nothing. The symmetric argument justifies r--. Each step removes one index permanently, so the loop runs at most n times.

That is the shape of every correctness proof in this family: the pointer you move is the one whose current element cannot participate in any better answer. For container with most water, the area is min(h[l], h[r]) × (r - l); moving the taller wall inward keeps the same limiting height while strictly reducing the width, so it can never improve — therefore move the shorter wall. State that sentence out loud in an interview and the problem is finished.

The same-direction form has a different justification. There, r extends the window and l repairs it. The invariant is "the window [l, r] is valid", and because l only ever increases, the total number of pointer movements across the whole run is at most 2n even though the inner while loop looks nested. That is an amortised argument, not a per-iteration one, and being able to say so is the standard follow-up answer.

The invariant

Opposite ends: every pair (i, j) with i < l or j > r has already been considered or provably cannot be optimal. The answer, if it exists, lies within [l, r].

Same direction: the segment [l, r] satisfies the problem's validity predicate at the top of every iteration, and l is the smallest left endpoint for which that is true given the current r.

The amortisation argument, stated properly

Same-direction two pointers have a while inside a for, which looks quadratic. It is not: l only increases and is bounded by n, so the inner loop executes at most n times in total across the whole run. Combined with n outer iterations that is at most 2n pointer movements, hence O(n). Say "amortised" when asked; it is exactly the same accounting as dynamic array growth.

Sorting destroys indices

If the problem asks for the positions of the two numbers (LeetCode 1 Two Sum) rather than the values, sorting loses them. Either pair each value with its original index before sorting, or abandon two pointers and use a HashMap, which is O(n) and needs no sort. Check what the problem wants returned before you reach for the sort.

Three pointers and beyond

k-sum generalises: sort once, fix k - 2 indices with nested loops, and two-pointer the innermost pair. That gives O(nk-1) — O(n²) for 3-sum and O(n³) for 4-sum. Beyond k = 4, meet in the middle becomes better. The duplicate-skipping logic is the same at every level and is where almost all the bugs are.

Which of the three forms do you need?

Algorithm

  1. Identify the shape first: opposite ends, same direction, or fast/slow, because each shape has a different correctness argument.
  2. Sort if needed, and first check whether the problem wants original indices — if it does, sorting is wrong.
  3. Initialise: l = 0, r = n - 1 for opposite ends; l = r = 0 for same direction.
  4. Write down the exchange argument for which pointer moves. If you cannot state it in one sentence, the technique may not apply.
  5. Loop while l < r for opposite ends, or while r < n for the same-direction form, so every index is examined once.
  6. Update the answer before moving either pointer, so the pair or window you are about to leave is not skipped.
  7. Handle duplicates explicitly in k-sum problems: after recording a hit, advance past all equal values on both sides.
  8. Verify the termination condition: every iteration must move at least one pointer, or the loop hangs and the judge reports a timeout.

Java implementation

Three classics that share one skeleton. In each case the comment above the pointer move is the exchange argument — that sentence is what an interviewer is listening for.

JavaOppositeEnds.java
import java.util.Arrays;
    
    public class OppositeEnds {
    
        /** Pair summing to target in a SORTED array. Returns indices, or null. O(n). */
        static int[] pairSum(int[] a, int target) {
            int l = 0, r = a.length - 1;
            while (l < r) {
                int sum = a[l] + a[r];
                if (sum == target) {
                    return new int[] {l, r};
                }
                if (sum < target) {
                    l++;      // a[r] is the largest partner left; if a[l]+a[r] is still
                              // too small, a[l] can pair with nothing. Discard it.
                } else {
                    r--;      // symmetric: a[l] is the smallest partner left.
                }
            }
            return null;
        }
    
        /** Maximum water container. O(n). */
        static int maxArea(int[] h) {
            int l = 0, r = h.length - 1, best = 0;
            while (l < r) {
                best = Math.max(best, Math.min(h[l], h[r]) * (r - l));
                if (h[l] < h[r]) {
                    l++;      // moving the TALLER wall keeps min() the same at best and
                              // strictly shrinks the width, so it can never improve.
                } else {
                    r--;
                }
            }
            return best;
        }
    
        /** Palindrome check ignoring non-alphanumerics. O(n). */
        static boolean isPalindrome(String s) {
            int l = 0, r = s.length() - 1;
            while (l < r) {
                while (l < r && !Character.isLetterOrDigit(s.charAt(l))) {
                    l++;
                }
                while (l < r && !Character.isLetterOrDigit(s.charAt(r))) {
                    r--;
                }
                if (Character.toLowerCase(s.charAt(l)) != Character.toLowerCase(s.charAt(r))) {
                    return false;
                }
                l++;
                r--;
            }
            return true;
        }
    
        public static void main(String[] args) {
            System.out.println(Arrays.toString(pairSum(new int[] {1, 3, 4, 6, 8, 11}, 14)));
            System.out.println(maxArea(new int[] {1, 8, 6, 2, 5, 4, 8, 3, 7}));
            System.out.println(isPalindrome("A man, a plan, a canal: Panama"));
            System.out.println(isPalindrome("race a car"));
        }
        // Output: [1, 5]
        //         49
        //         true
        //         false
    }

The duplicate handling is the entire difficulty. There are three separate guards and each one is needed; removing any of them produces repeated triplets.

JavaThreeSum.java
import java.util.ArrayList;
    import java.util.Arrays;
    import java.util.List;
    
    public class ThreeSum {
    
        /** All unique triplets summing to zero. O(n^2) after an O(n log n) sort. */
        static List<List<Integer>> threeSum(int[] a) {
            Arrays.sort(a);
            List<List<Integer>> out = new ArrayList<>();
            int n = a.length;
            for (int i = 0; i < n - 2; i++) {
                if (a[i] > 0) {
                    break;                          // sorted: no way to reach 0 from here
                }
                if (i > 0 && a[i] == a[i - 1]) {
                    continue;                       // guard 1: skip duplicate anchors
                }
                int l = i + 1, r = n - 1;
                while (l < r) {
                    int sum = a[i] + a[l] + a[r];
                    if (sum == 0) {
                        out.add(Arrays.asList(a[i], a[l], a[r]));
                        int vl = a[l], vr = a[r];
                        while (l < r && a[l] == vl) {
                            l++;                    // guard 2: skip duplicate left values
                        }
                        while (l < r && a[r] == vr) {
                            r--;                    // guard 3: skip duplicate right values
                        }
                    } else if (sum < 0) {
                        l++;
                    } else {
                        r--;
                    }
                }
            }
            return out;
        }
    
        public static void main(String[] args) {
            System.out.println(threeSum(new int[] {-1, 0, 1, 2, -1, -4}));
            System.out.println(threeSum(new int[] {0, 0, 0, 0}));
            System.out.println(threeSum(new int[] {1, 2, 3}));
        }
        // Output: [[-1, -1, 2], [-1, 0, 1]]
        //         [[0, 0, 0]]
        //         []
    }

A read pointer scans and a write pointer compacts. This shape is the answer to every "do it in place with O(1) extra space" instruction.

JavaSameDirection.java
import java.util.Arrays;
    
    public class SameDirection {
    
        /** Remove duplicates from a sorted array in place. Returns the new length. O(n). */
        static int dedupeSorted(int[] a) {
            if (a.length == 0) {
                return 0;
            }
            int write = 1;                          // a[0..write-1] is the deduped prefix
            for (int read = 1; read < a.length; read++) {
                if (a[read] != a[write - 1]) {
                    a[write++] = a[read];
                }
            }
            return write;
        }
    
        /** Move all zeroes to the end, preserving the order of non-zeroes. O(n). */
        static void moveZeroes(int[] a) {
            int write = 0;
            for (int read = 0; read < a.length; read++) {
                if (a[read] != 0) {
                    int t = a[write];
                    a[write++] = a[read];
                    a[read] = t;
                }
            }
        }
    
        /** Merge two sorted arrays into a new one. O(n + m). */
        static int[] merge(int[] a, int[] b) {
            int[] out = new int[a.length + b.length];
            int i = 0, j = 0, k = 0;
            while (i < a.length && j < b.length) {
                out[k++] = (a[i] <= b[j]) ? a[i++] : b[j++];
            }
            while (i < a.length) {
                out[k++] = a[i++];
            }
            while (j < b.length) {
                out[k++] = b[j++];
            }
            return out;
        }
    
        /** Dutch national flag: partition into <p, ==p, >p in one pass. O(n). */
        static void threeWayPartition(int[] a, int pivot) {
            int lt = 0, i = 0, gt = a.length - 1;
            while (i <= gt) {
                if (a[i] < pivot) {
                    swap(a, lt++, i++);
                } else if (a[i] > pivot) {
                    swap(a, i, gt--);               // do NOT advance i: the swapped-in
                                                    // value has not been examined yet
                } else {
                    i++;
                }
            }
        }
    
        private static void swap(int[] a, int i, int j) {
            int t = a[i]; a[i] = a[j]; a[j] = t;
        }
    
        public static void main(String[] args) {
            int[] d = {1, 1, 2, 2, 2, 3, 4, 4};
            System.out.println(dedupeSorted(d) + " " + Arrays.toString(Arrays.copyOf(d, 4)));
    
            int[] z = {0, 1, 0, 3, 12};
            moveZeroes(z);
            System.out.println(Arrays.toString(z));
    
            System.out.println(Arrays.toString(merge(new int[] {1, 4, 7}, new int[] {2, 3, 9})));
    
            int[] p = {3, 1, 4, 1, 5, 9, 2, 6, 5};
            threeWayPartition(p, 4);
            System.out.println(Arrays.toString(p));
        }
        // Output: 4 [1, 2, 3, 4]
        //         [1, 3, 12, 0, 0]
        //         [1, 2, 3, 4, 7, 9]
        //         [3, 1, 1, 2, 4, 9, 5, 6, 5]
    }

Floyd's cycle detection plus the two list utilities it shares a skeleton with. The second phase of Floyd's algorithm is the part worth being able to justify.

JavaFastSlow.java
public class FastSlow {
    
        static class Node {
            int val;
            Node next;
            Node(int v) { val = v; }
        }
    
        /** Middle node (the second one when the length is even). O(n), O(1) space. */
        static Node middle(Node head) {
            Node slow = head, fast = head;
            while (fast != null && fast.next != null) {
                slow = slow.next;
                fast = fast.next.next;
            }
            return slow;
        }
    
        /**
         * Floyd's cycle detection. Returns the node where the cycle starts, or null.
         * Phase 2 works because if the tail before the cycle has length m and the
         * meeting point is k steps into a cycle of length L, then m == (L - k) mod L,
         * so walking m steps from the head and m steps from the meeting point collide
         * exactly at the cycle entry.
         */
        static Node cycleStart(Node head) {
            Node slow = head, fast = head;
            while (fast != null && fast.next != null) {
                slow = slow.next;
                fast = fast.next.next;
                if (slow == fast) {                 // phase 1: they meet inside the cycle
                    Node p = head;
                    while (p != slow) {             // phase 2: walk both at the same speed
                        p = p.next;
                        slow = slow.next;
                    }
                    return p;
                }
            }
            return null;
        }
    
        /** k-th node from the end. One pass, O(1) space. */
        static Node kthFromEnd(Node head, int k) {
            Node lead = head;
            for (int i = 0; i < k; i++) {
                if (lead == null) {
                    return null;
                }
                lead = lead.next;
            }
            Node trail = head;
            while (lead != null) {
                lead = lead.next;
                trail = trail.next;
            }
            return trail;
        }
    
        public static void main(String[] args) {
            Node a = new Node(1), b = new Node(2), c = new Node(3), d = new Node(4), e = new Node(5);
            a.next = b; b.next = c; c.next = d; d.next = e;
            System.out.println("middle = " + middle(a).val);
            System.out.println("2nd from end = " + kthFromEnd(a, 2).val);
            System.out.println("cycle = " + cycleStart(a));
            e.next = c;                              // create a cycle back to node 3
            System.out.println("cycle starts at " + cycleStart(a).val);
        }
        // Output: middle = 3
        //         2nd from end = 4
        //         cycle = null
        //         cycle starts at 3
    }

Complexity

Time O(n) after sorting; O(n log n) total Space O(1) auxiliary

For opposite ends, each iteration strictly decreases r - l by at least one, and the loop stops when l ≥ r, so there are at most n iterations of O(1) work:

T(n) = Θ(n) after sorting, so Θ(n log n) overall when a sort is needed

For same direction the argument is amortised. The outer pointer r advances n times. The inner pointer l also advances at most n times in total, because it never decreases and is bounded by n. Hence the total number of pointer movements is at most 2n, giving Θ(n) despite the nested loops:

Σr (movements of l during step r) ≤ n  ⇒  T(n) = Θ(n)

For k-sum, fixing k - 2 indices with nested loops and two-pointering the last pair gives Θ(nk-1). Space is Θ(1) auxiliary in every case, except that sorting an Integer[] costs Θ(n) and recursion in a quicksort costs Θ(log n) stack.

Edge cases and pitfalls

  • Using two pointers on an unsorted array
    Applying the converge-from-both-ends pair search without sorting. The monotonicity argument is simply false, so the algorithm silently returns wrong answers on some inputs and correct ones on others.
    Sort first, or use a HashMap. Before writing the loop, say the exchange argument out loud — if it does not hold, you have caught the bug before writing it.
  • Sorting when the problem wants original indices
    LeetCode 1 asks for the indices of the two numbers. Sorting destroys them, so the returned indices refer to the sorted array.
    Either use a HashMap<value, index> in one pass (O(n), and simpler), or sort an array of {value, originalIndex} pairs.
  • Incomplete duplicate handling in k-sum
    Skipping duplicates for the anchor i but not after a successful hit looks finished, yet [0,0,0,0] then produces [[0,0,0],[0,0,0]].
    Three guards: skip i when a[i] == a[i-1], and after recording a triplet advance l past all equal values and retreat r past all equal values.
  • Advancing the index after a swap in Dutch-flag partitioning
    In three-way partitioning, doing swap(a, i, gt--); i++;. The value just swapped in from the right has never been examined, so it can be misplaced.
    Advance i only in the < and == branches. When swapping with gt, leave i where it is.
  • An iteration that moves neither pointer
    A branch structure where some condition leads to continue without changing l or r. The loop hangs, and on a judge that shows as a timeout rather than an obvious infinite loop.
    Audit every path through the loop body and confirm at least one pointer changes. Making the pointer updates the last statements of each branch makes this easy to verify.
  • Reading past the end in fast/slow traversal
    while (fast.next != null && fast.next.next != null) versus while (fast != null && fast.next != null). The wrong one throws NullPointerException on an empty or single-node list, or returns the wrong middle for even lengths.
    Use while (fast != null && fast.next != null), which is safe for all lengths and returns the second middle for even lists. Test on lists of length 0, 1 and 2.
  • Applying a sliding window when values can be negative
    "Shortest subarray with sum at least k" with negative values. Shrinking from the left can increase the sum, so the window logic is unsound.
    Use prefix sums plus a monotonic deque, which is O(n) and makes no monotonicity assumption about the values.

Interview follow-ups

Prove that two pointers on a sorted array finds the pair if one exists.

Suppose a valid pair (i*, j*) with i* < j* exists. The pointers start outside it (l ≤ i* and r ≥ j*) and each step moves exactly one inward. Consider the first moment a pointer would move past one of them — say l = i* and we are about to do l++. That only happens when a[i*] + a[r] < target with r ≥ j*, so a[r] ≥ a[j*], so a[i*] + a[j*] ≤ a[i*] + a[r] < target — contradicting that (i*, j*) is valid. The symmetric argument covers r--. Hence the pointers must meet at the pair.

Why is the same-direction form O(n) when it has nested loops?

Because the inner pointer never moves backwards. Across the entire execution, l advances at most n times in total, no matter how the advancement is distributed among outer iterations. So the total work is bounded by n outer steps plus n inner steps, giving O(n) amortised. This is the same accounting used for dynamic array growth: the worst single iteration is O(n), but the sum over all iterations is O(n).

When should you use a HashMap instead of two pointers?

Three situations. When the problem needs original indices, since sorting destroys them. When the array is unsorted and sorting would be too slow or would break a required ordering. And when the condition involves exact equality on an unsorted quantity, such as counting subarrays with a given sum in the presence of negatives — there is no monotonicity to exploit. Roughly: two pointers buy O(1) space at the cost of needing order; hashing buys order-independence at the cost of O(n) space.

How does Floyd's cycle detection find the start of the cycle?

Let the tail before the cycle have length m and the cycle have length L. When slow has taken m + k steps, fast has taken 2(m + k), and they meet, so the difference m + k is a multiple of L. That means walking a further m steps from the meeting point lands exactly on the cycle entry, because m + k + m ≡ m (mod L) positions into the cycle. So reset one pointer to the head, advance both one step at a time, and they collide at the entry. Total O(n) time and O(1) space, against O(n) space for the HashSet approach.

How would you extend this to 4Sum without O(n⁴)?

Sort, then two nested loops fix i and j, and two pointers handle the remaining pair — O(n³). An alternative is to enumerate all O(n²) pairs, group them by sum in a hash map, and look for two complementary pairs; that is O(n²) time and O(n²) space, but deduplicating overlapping index sets is fiddly. For large k with small n, meet in the middle is the right generalisation.

What if the array is sorted but rotated?

Two pointers from the ends no longer works, because a[l] + a[r] is not monotone across the rotation point. Either find the pivot with binary search in O(log n) and then run two pointers with modular index arithmetic, or fall back to a HashSet. The general principle: two pointers need a total order along the traversal direction, and a rotation breaks exactly that.

Hint for LC 42 — why two pointers beats the prefix-max arrays

Water above index i is min(maxLeft[i], maxRight[i]) - h[i], which suggests two O(n) arrays. The O(1)-space version keeps only leftMax and rightMax as scalars and always advances the side with the smaller maximum. The reason that is safe: if leftMax < rightMax, then for the left pointer the true limiting height is leftMax regardless of what lies between, because some wall of at least rightMax > leftMax is guaranteed to exist on the right. Transferable lesson: when a formula takes a min of two running extremes, you can often process whichever side is currently smaller and never need the other side's exact value.

Hint for LC 287 — turning an array into a linked list

With n + 1 values all in [1, n], define the successor function i → a[i]. Starting from index 0, this walk must eventually repeat a node, and since two different indices map to the same value, the repeated node is the duplicate — it is the entry point of the cycle. So run Floyd's algorithm with slow = a[slow] and fast = a[a[fast]], then the phase-2 walk from index 0. That gives O(n) time, O(1) space, and no modification of the input, which is exactly what the constraints demand. General lesson: an array of indices is a functional graph, and every cycle technique applies to it.

Recap

  • Three shapes: opposite ends (converge on sorted data), same direction (window or read/write compaction), and fast/slow (cycles and midpoints).
  • State the exchange argument before coding. "Moving this pointer discards only pairs that are dominated by ones we keep" is the correctness proof and the interview answer.
  • Same-direction is O(n) amortised, not quadratic, because the inner pointer never moves backwards.
  • Duplicates need explicit guards in k-sum: one on the anchor and one on each pointer after a hit.
  • Two pointers need order. Unsorted with required indices, or subarray sums with negatives, both call for hashing or prefix sums instead.
