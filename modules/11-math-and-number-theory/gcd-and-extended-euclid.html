GCD & Extended Euclid

Euclid's algorithm is O(log min(a,b)). Extended Euclid also returns x,y with ax+by=gcd, which is the inverse of a mod m when gcd=1.

Medium 28 min read Prerequisites: Modular Arithmetic, Recursion Fundamentals gcd exgcd Bezout P1

Why this exists

You are given two jug sizes, 30 and 18, and you must decide whether you can measure exactly 6 litres by filling, emptying, and pouring. The amounts you can actually measure are exactly the multiples of the greatest common divisor of 30 and 18, written gcd(30, 18) — the largest positive integer that divides both. Here that gcd is 6, so 6 is possible and 5 is not. The same number appears when you reduce a fraction, count lattice points on a segment, or jump by two step sizes on a circle.

Bézout's identity says there exist integers x and y such that a*x + b*y equals gcd(a, b) — that linear combination is the smallest positive amount those two step sizes can build. Extended Euclid is Euclid's remainder loop plus a back-substitution that finds those x and y. When gcd(a, m) = 1, the coefficient x is the modular inverse of a modulo m: the number that acts like division even when m is not prime and Fermat does not apply.

A subtractive loop that replaces the larger number by the difference of the two can take a linear number of steps on a Fibonacci pair. Replacing the larger by the leftover after division — gcd(a, b) = gcd(b, a % b) — is already logarithmic even in that worst case, under 100 remainders for 64-bit inputs. Always use %, never a subtract-in-a-loop.

In a real statement the signal is “can you make amount z with steps a and b”, or “inverse of a modulo m” when m is not promised prime, or a, b ≤ 1018 next to a gcd or lcm query. That combination rules out trial-dividing down from min(a, b), and it is exactly what this page is for.

The leftover of a after dividing by b is built from a and b, so they share the same gcd: gcd(a, b) = gcd(b, a % b). Unrolling those remainders and substituting backwards produces the pair x, y with a*x + b*y = gcd — that back-substitution is extended Euclid, and it is the inverse when the gcd is 1.

Constraint tell: Inputs a and b go up to 1018, so store them in long; a 64-bit remainder is one hardware instruction. Fibonacci pairs are the worst case for Euclid and still finish in under 100 remainders. Trial-dividing down from min(a, b) at that size is about 1018 steps and will not return.

Core idea and the invariant

Plain Euclid is a leftover loop. While b is not 0, replace the pair (a, b) by (b, a % b) — that leftover is what remains after dividing a by b, and any common divisor of a and b also divides it. When b hits 0 the current a is the gcd; take the absolute value so a negative input cannot poison later arithmetic. The least common multiple is then a / gcd * b, computed in long with the divide first so the product does not overflow.

Extended Euclid also returns the Bézout pair. If b is 0, the combination is a*1 + b*0 = a, so you return (a, 1, 0). Otherwise recurse on (b, a % b) and get (g, x1, y1) meaning b*x1 + (a % b)*y1 = g. Substitute a % b = a - (a/b)*b and rearrange: a*y1 + b*(x1 - (a/b)*y1) = g. That is why the update is x = y1 and y = x1 - (a/b)*y1 — those two numbers compute a combination that still equals the gcd. The inverse of a modulo m is that x, normalised into 0..m-1, but only when the gcd is 1.

Walk 30 and 18. Remainders: 30 = 1*18 + 12, then 18 = 1*12 + 6, then 12 = 2*6 + 0, so the gcd is 6. Substituting backwards: 6 equals 18 - 1*12, and 12 equals 30 - 1*18, so 6 equals 2*18 - 1*30. The inverse of 18 modulo 30 does not exist because that gcd is 6, not 1. The inverse of 7 modulo 30 does: extended Euclid finds 7*(-17) + 30*4 = 1, and leftover of -17 after adding 30 is 13, the number that acts like one-over-7 in that ring.

At every remainder step the current pair still has the same gcd as the original pair, and the coefficients the algorithm returns satisfy a*x + b*y = g for that current pair.

In plain words, you never invent new common divisors: each leftover is built from the previous two numbers, so the largest shared divisor cannot change, and the back-substitution only rewrites that same gcd as a combination of the original a and b.

Interview sentence: “Remainders preserve the gcd; unrolling them gives the inverse when that gcd is 1.”

No inverse when gcd is not 1

Returning x without checking g == 1 looks like the same helper you used on a prime modulus. Multiply back: a*x will not have leftover 1, and later modular division is silently wrong. Fail (or report no solution) when the gcd does not divide the target.

Divide before you multiply for lcm

a * b / gcd overflows a long when a and b are both near 1018. Write a / gcd * b after you know gcd divides a exactly.

Algorithm

  1. Compute the gcd by remainders. While b is not 0, replace (a, b) by (b, a % b) and finally return the absolute value of a. The leftover loop is what keeps the worst case logarithmic.
  2. Track coefficients for extended Euclid. Recurse as above, or iterate with x, y = 1, 0 and x1, y1 = 0, 1, updating them the same way the remainders update, so you finish with a*x + b*y = g.
  3. Read the inverse from x when gcd is 1. Call (g, x, y) = exgcd(a, m); if g != 1 there is no inverse. Otherwise return leftover of x in 0..m-1, the number that acts like one-over-a.
  4. Solve ax + by = c by scaling. If c is not a multiple of g there is no integer solution. Otherwise multiply x and y by c/g, then step x by b/g and y by -a/g to list every solution.
  5. Form the lcm without overflowing. Write a / g * b in long after confirming g divides a. Multiplying first can wrap even when the true lcm fits.
  6. More than two integers. Fold gcd(gcd(a, b), c) and so on. A full lattice basis for many variables is rare in contests and is a different tool.

Java implementation

Subtract. Worst-case linear in a+b.

JavaGcdSub.java
public class GcdSub {
        static int gcd(int a, int b) {
            while (a != b) { if (a > b) a -= b; else b -= a; }
            return a;
        }
        public static void main(String[] args) {
            System.out.println(gcd(30, 18));
        }
        // Input : 30,18
        // Output: 6
    }

Iterative extended Euclid and modular inverse.

JavaExGcd.java
public class ExGcd {
        static long gcd(long a, long b) { return b == 0 ? a : gcd(b, a % b); }
        static long[] exgcd(long a, long b) {
            long x = 1, y = 0, x1 = 0, y1 = 1;
            while (b != 0) {
                long q = a / b;
                long nb = a % b; a = b; b = nb;
                long nx = x - q * x1; x = x1; x1 = nx;
                long ny = y - q * y1; y = y1; y1 = ny;
            }
            return new long[] {a, x, y};
        }
        static long inv(long a, long m) {
            long[] g = exgcd(a, m);
            if (g[0] != 1) return -1;
            long x = g[1] % m;
            return x < 0 ? x + m : x;
        }
        public static void main(String[] args) {
            System.out.println(gcd(30, 18));
            System.out.println(inv(7, 30));
        }
        // Input : gcd 30,18 and inv 7 mod 30
        // Output: 6
        //         13
    }

One particular solution of ax+by=c, or null.

JavaDiophantine.java
public class Diophantine {
        static long[] exgcd(long a, long b) {
            if (b == 0) return new long[] {a, 1, 0};
            long[] r = exgcd(b, a % b);
            return new long[] {r[0], r[2], r[1] - (a / b) * r[2]};
        }
        static long[] solve(long a, long b, long c) {
            long[] t = exgcd(a, b);
            if (c % t[0] != 0) return null;
            long k = c / t[0];
            return new long[] {t[1] * k, t[2] * k};
        }
        public static void main(String[] args) {
            long[] s = solve(30, 18, 12);
            System.out.println(s[0] + " " + s[1]);
        }
        // Input : 30x+18y=12
        // Output: -2 4
    }

Complexity

Time O(log min(a,b)) Space O(1) iterative / O(log) recursive

Lamé's theorem says each leftover is at most two-thirds of the previous pair's larger number, so the number of remainders is O(log min(a, b)). The worst inputs are consecutive Fibonacci numbers, where each leftover is the previous Fibonacci, and even then a 64-bit pair finishes in under 100 steps. A subtractive loop on the same pair is linear in the values and dies at 1018.

Putting real numbers in: gcd(F90, F89) for 64-bit Fibonacci numbers is about ninety remainders, a few hundred nanoseconds. Extended Euclid does the same number of updates plus a handful of multiplies for the coefficients. Fermat's inverse on a prime M ≈ 109 is about sixty modular multiplies; extended Euclid is comparable and also works when M is composite.

Edge cases and pitfalls

  • lcm overflow
    a * b / gcd looks like the textbook formula and compiles, but the product wraps a long before the divide when both inputs are near 1018.
    Write a / gcd * b in long after computing the gcd first. Test lcm(1018/2, 1018/4) if you want a loud failure.
  • Negative a,b
    Java % follows the sign of the left operand, so a negative input can make the returned gcd negative and later comparisons or inverses look randomly wrong.
    Take absolute values on the way in, or normalise the sign of the gcd at the end. Unit-test gcd(-30, 18) and expect 6.
  • Ignoring g!=1 for inverse
    You still return x, and leftover of a*x is 0 or some other junk, which looks like a legal inverse until a later multiply fails a self-check.
    If g != 1 there is no inverse. For a*x ≡ b (mod m) you also need g to divide b. Always test mul(a, inv(a)) is leftover 1.
  • Recursive exgcd on Fibonacci 1e18
    Depth is about 90 on a 64-bit Fibonacci pair, which happens to fit the Java stack, so the recursive version looks fine until someone ports it to a tighter limit.
    Prefer the iterative update of x, y. It is stack-safe and the coefficient writes are easier to read on a whiteboard.
  • General solution forgetting t step b/g
    Stepping x by b instead of b/g skips legal solutions and the first few you print look plausible, so the off-by-factor hides.
    Write x += (b/g)*t and y -= (a/g)*t. Check that two consecutive solutions differ by that reduced step.

Interview follow-ups

Why does Euclid terminate?

Each leftover is a non-negative integer strictly smaller than the previous b, so the pair cannot descend forever. The gcd is preserved because any common divisor of a and b also divides a % b, and conversely any common divisor of b and that leftover divides a. When the leftover hits 0 you are done, and the current a is the shared divisor.

Binary GCD?

Stein's algorithm divides out factors of 2 with shifts, then subtracts odd numbers. It is a win on huge bit-integers where a remainder is expensive. For ordinary 64-bit long values in Java, hardware % is faster and the code is shorter, so stick to Euclid unless the inputs are big-integers.

Frobenius coin problem?

If a and b are coprime, the largest amount you cannot make with non-negative combinations is a*b - a - b. If the gcd is greater than 1 you can only ever make multiples of that gcd, so “every large enough integer” is false — only every large enough multiple of the gcd is reachable. Water-jug problems are this lemma plus the capacity cap a+b.

n-dimensional ax=c?

The gcd of all the coefficients must divide c, or there is no integer solution. One particular solution is built by folding extended Euclid across the coefficients; the remaining freedom is a lattice of rank n-1. Contests almost always stay at two variables, where that lattice is the single parameter t on this page.
