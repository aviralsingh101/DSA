Primes & Sieves

The linear sieve builds every prime ≤ n in O(n) and the smallest-prime-factor table factors any k ≤ n in O(log k).

Medium 28 min read Prerequisites: Modular Arithmetic, Complexity Analysis sieve SPF primes P1

Why this exists

You are given every integer from 2 to n and you must mark which of them are prime, or factor a long list of them. Trial division tests one candidate in about sqrt n divisions, so asking the question a million times at n = 106 is already about a billion steps and the judge will cut you off. A sieve pays that cost once, up front, and then primality of any k ≤ n is a single array read.

The extra prize is the smallest-prime-factor table, usually shortened to SPF: spf[k] stores the smallest prime that divides k. Once you have it, factoring any k ≤ n is a loop that peels off spf[k] until you hit 1, at most about log k divisions. That is why you sieve even when the statement never asked you to list primes — it asked you to factor many numbers in a range.

In Java a boolean or integer sieve is comfortable up to about n = 107 (tens of megabytes and a few hundred milliseconds). A limit of 1012 cannot allocate an array of that length, so you either sieve a short window (a segmented sieve) or test one huge integer with Miller-Rabin. The constraint that names this page is “all primes up to n” or “factor many k ≤ n” with n in the 106 to 107 band.

The same linear pass that writes SPF also fills multiplicative functions — functions determined by their values at prime powers, such as Euler's phi (count of leftovers coprime to n), Möbius mu, and the divisor-count tau. One sieve, several arrays, and every later query is an array read.

Every composite k ≤ n has a smallest prime factor p. The linear sieve writes k = p * m exactly once, when p does not exceed spf[m], so each composite is marked by its true smallest prime and the whole table costs a constant amount of work per integer.

Core idea and the invariant

Eratosthenes is the simpler sieve. Allocate a boolean array prime[0..n], set everything true, then force prime[0] and prime[1] false. For each i from 2 up to sqrt n, if i is still marked prime, walk j = i*i, i*i+i, i*i+2i, ... and mark those slots composite. Starting at i*i is safe because every smaller multiple of i already had a smaller prime factor and was marked earlier. After the loops, prime[k] is true exactly when k is prime.

The linear sieve, also called Euler's sieve, builds SPF instead of a boolean. Allocate spf[0..n] of zeros and an empty list of primes. For each x from 2 to n: if spf[x] is still 0 then x is prime, so write spf[x] = x and append x to the prime list. Then, for every prime p in the list so far, if p exceeds spf[x] or p*x exceeds n, stop; otherwise write spf[p*x] = p. The break when p > spf[x] is the whole algorithm: it guarantees each composite is written exactly once, by its smallest prime.

Walk the table up to 10. At x = 2 the slot is unmarked, so 2 is prime and you write spf[4] = spf[6] = spf[8] = spf[10] = 2. At x = 3 you append 3; 6 already has SPF 2, so you do not overwrite it. At x = 4 the slot is already 2, and the only prime you try is 2. At x = 5 you append 5 and later 9 = 3*3 receives SPF 3. Factoring 84 on a larger table peels 2, 2, 3, 7 by repeating n /= spf[n]. Euler's phi[10] is 4 because 10 has prime factors 2 and 5, and the leftover count is 10 * (1-1/2) * (1-1/5).

After the linear sieve, spf[x] is the smallest prime dividing x, and spf[p] = p for every prime. Factorisation peels spf[k] until k becomes 1, in at most about log k steps because each peel shrinks k by a factor of at least 2.

In plain words, you do not test each integer against every prime; you let each composite be claimed once by the smallest prime that divides it, and that claim is the factor you will peel first later.

Interview sentence: “Each composite is written once, by its smallest prime; the break on p > spf[x] is the algorithm.”

The break is load-bearing

If you forget if (p > spf[x]) break, a number such as 12 is written by both 2 and 3. Then spf[12] is no longer the smallest prime, factorisation is wrong, and the pass is no longer linear.

Eratosthenes when you only need prime[]

A boolean sieve has better cache behaviour if you will never factor. Reach for the linear sieve when you also want SPF, phi, or mu in the same pass.

Algorithm

  1. Allocate the SPF table. Create int[] spf = new int[n+1] filled with zeros; a zero slot still means “not yet claimed”, so you can tell a prime from a composite as you walk.
  2. Discover primes as you walk x. For each x from 2 to n, if spf[x] is still 0 then x is prime: write spf[x] = x and append x to the prime list.
  3. Claim multiples by their smallest prime. For each prime p, stop if p exceeds spf[x] or p*x exceeds n; otherwise write spf[p*x] = p. That break is what keeps each composite written once.
  4. Factor by peeling SPF. While k > 1, push spf[k] and divide k by it. Each peel shrinks k, so the loop finishes in at most about log k steps.
  5. Fill phi in the same pass. When you write p*x, set phi[p*x] = phi[x]*p if p already divides x, else phi[x]*(p-1), which is the leftover-count recurrence for a multiplicative function.
  6. Segment a huge window. Sieve primes up to sqrt(R), then mark a boolean array of length R-L+1. Never allocate an array of length 1012.

Java implementation

O(sqrt n) per test.

JavaTrialPrime.java
public class TrialPrime {
        static boolean isPrime(int n) {
            if (n < 2) return false;
            for (int i = 2; i * i <= n; i++) if (n % i == 0) return false;
            return true;
        }
        public static void main(String[] args) {
            int c = 0;
            for (int i = 2; i <= 10; i++) if (isPrime(i)) c++;
            System.out.println(c);
        }
        // Input : count primes ≤ 10
        // Output: 4
    }

JavaLinearSieve.java
import java.util.*;
    public class LinearSieve {
        static int[] spf;
        static List<Integer> primes = new ArrayList<>();
        static void sieve(int n) {
            spf = new int[n + 1];
            for (int x = 2; x <= n; x++) {
                if (spf[x] == 0) { spf[x] = x; primes.add(x); }
                for (int p : primes) {
                    if (p > spf[x] || (long) p * x > n) break;
                    spf[p * x] = p;
                }
            }
        }
        static List<Integer> factor(int n) {
            List<Integer> f = new ArrayList<>();
            while (n > 1) { f.add(spf[n]); n /= spf[n]; }
            return f;
        }
        public static void main(String[] args) {
            sieve(100);
            System.out.println(primes.subList(0, 4));
            System.out.println(factor(84));
        }
        // Input : n=100, factor 84
        // Output: [2, 3, 5, 7]
        //         [2, 2, 3, 7]
    }

The simpler sieve if you only need a boolean prime[].

JavaEratosthenes.java
import java.util.Arrays;
    public class Eratosthenes {
        static boolean[] sieve(int n) {
            boolean[] p = new boolean[n + 1];
            Arrays.fill(p, true);
            p[0] = p[1] = false;
            for (int i = 2; i * i <= n; i++) if (p[i])
                for (int j = i * i; j <= n; j += i) p[j] = false;
            return p;
        }
        public static void main(String[] args) {
            boolean[] p = sieve(10);
            System.out.println(p[7] + " " + p[9]);
        }
        // Input : n=10
        // Output: true false
    }

Complexity

Time O(n) linear / O(n log log n) Eratosthenes Space O(n)

The linear sieve writes each composite exactly once and appends each prime once, so the whole table is a constant amount of work per integer from 2 to n — that is why it is quoted as O(n). Eratosthenes marks every multiple of every prime, and the number of those marks is the harmonic sum of n/p over primes, which is about n log log n. Starting the inner loop at i*i does not change the class, but it cuts a large constant.

Putting real numbers in: at n = 107 the linear pass is ten million writes, a few hundred milliseconds in Java, and the integer table is about 40 MB. Trial-dividing every integer up to that n would be on the order of n sqrt n ≈ 3 × 1010 steps. A segmented window of length 106 inside [1, 1012] sieves primes to 106 once, then marks the window, which fits in time and memory; allocating 1012 slots does not.

Edge cases and pitfalls

  • Inner loop from 2i instead of i*i
    Starting at 2i is still correct, so it looks fine, but you re-mark numbers that a smaller prime already claimed, and i*i computed in int overflows once i reaches 46341.
    Cast (long) i * i and start the inner loop there. Time a sieve to 107 both ways if you want to feel the constant.
  • Linear sieve not breaking on p>spf[x]
    Without the break, 12 is written by both 2 and 3. The table still looks populated, but SPF is no longer the smallest prime and the pass becomes O(n log n).
    The break if (p > spf[x]) break is the algorithm. After sieving, check that spf[12] is 2, not 3.
  • spf[1] and factor(1)
    spf[1] stays 0, so while (n > 1) on input 1 never divides and the loop runs forever, which looks like a hang rather than a factorisation bug.
    Special-case 1 as an empty factor list before you enter the peel loop. Unit tests should include factor(1).
  • n=1e8 boolean in Java
    A boolean array of length 108 is tight on both memory and startup, and a slow marking loop times out even when the idea is right.
    Stay at n = 107, use a bitset, or switch to the linear sieve. Measure init time, not just the query loop.
  • Segmented sieve off-by-one on L=1
    Index 0 of the window maps to L. If L is 1 you leave 1 marked prime, and later counts are off by one in a way that looks like a fence-post error.
    Force 0 and 1 composite whenever the window covers them. Print primes in [1, 10] and confirm you get four, not five.

Interview follow-ups

Why is the linear sieve linear?

Every composite m has exactly one writing m = p * x where p is the smallest prime dividing m and p does not exceed spf[x]. The inner loop emits that pair and then stops, so each composite is produced once and each prime is appended once. That is a constant amount of work per integer, which is why the pass is O(n) rather than O(n log log n).

Eratosthenes vs linear in practice?

Eratosthenes walks contiguous multiples and hits cache better if you only need a boolean prime[]. The linear sieve wins when you also want SPF, phi, or mu, because those arrays fill in the same pass. For a one-off prime list up to 107 either is fine; reach for linear the moment a later query asks you to factor.

How do you list primes in [1e12, 1e12+1e6]?

Sieve ordinary primes up to a little past 106 (that is sqrt of the right end), then allocate a boolean window of length 106+1 and mark multiples of those primes inside it. Do not allocate an array of length 1012. After marking, any unmarked slot whose value is at least 2 is prime.

Goldbach / twin primes?

Both are scans over a prime list you already built. Goldbach asks whether n - p is prime for some prime p ≤ n/2; twins ask whether p and p+2 are both in the list. The sieve is the preprocess; the scan is linear in the number of primes, not a second sieve.
